# Работа над GigaCode Workbench

Это личный инструмент пользователя, не производственная система. Продвигайся небольшими работающими срезами; проверяй реальный результат и предлагай улучшения, не меняя молча цель задачи. Не переноси облегчённые правила этого репозитория на производственные проекты пользователя.

## Начало работы

Если агент запущен на рабочем Windows для первичного переноса, начни с `WORK-COMPUTER-BOOTSTRAP.md` и сохрани продолжение до перезапуска GigaCode.

1. Прочитай `README.md` и `docs/IMPLEMENTATION_STATUS.md`. Они отделяют реально работающий `app/` от более полного замысла в `workbench/`.
2. Для продолжения разработки прочитай `workbench/START-GIGACODE-UI.md`, затем только документы текущего этапа. Не загружай весь пакет в контекст.
3. На рабочем Windows сначала проверь сборку и установленный GigaCode 26.9.75 по `docs/MANUAL_ACP_PROBE.md`. Начни с бесплатных initialize/new/config проверок. Не считай совместимость Qwen доказательством совместимости форка.
4. Если требуется собственный CLI внутри дистрибутива, следуй `docs/BUNDLED_CLI.md`. Не копируй настройки авторизации и историю вместе с runtime. Не меняй исходники чужого CLI.
5. После проверки окружения предложи конкретный следующий срез из `docs/IMPLEMENTATION_STATUS.md`, с ожидаемым результатом для пользователя. Если пользователь уже поручил этот срез, выполняй его без повторного согласования.

## Правила реализации

- Иерархия: проект → задача → разговоры/роли/исполнители. Не создавай второй несвязанный workflow-контроллер рядом с текущим состоянием.
- Основной UX — чат, компактные инструменты, настоящие материалы, перестраиваемый план и перетаскиваемые панели. Вопросы показываются поверх рабочей области. Скрытая координация не превращается в ленту уведомлений.
- Источники истины: реальные ответы CLI и его capabilities/config, файлы, наблюдаемый UI, тесты. Неподдерживаемую возможность обозначай явно. Не подменяй настоящий backend демонстрационными данными.
- Новый system prompt поверх чужого CLI нельзя считать заменой его внутреннего system prompt без подтверждённого механизма. Текущий native host передаёт роли как контекст.
- Не повторяй весь prompt после неизвестного исхода: сначала сверка внешних эффектов, затем восстановление. Встроенные повторы провайдера и host retries — разные уровни.
- Храни короткий checkpoint, ссылки на факты и результаты проверок. Для длинного контекста используй адресное чтение истории/документов. Память — проверяемые сведения, не источник разрешений.
- Уважай чужие несохранённые изменения. Не перезаписывай файлы после конфликта сохранения. Не отключай TLS-проверку для корпоративных сертификатов.
- До завершения проверь импорт/сборку, подходящие тесты и затронутый живой сценарий. Текст модели «всё работает» не считается проверкой. Различай unit, protocol fixture, live CLI, live Electron и Windows installer.

## Команды и выдача результата

Из `app/`: `npm ci --include=optional`, `npm test`, `npm run build`, `npm start`. Из корня: `node tools/check-bundle.mjs`. Windows CI дополнительно запускает прежние PowerShell-тесты под Windows PowerShell 5.1 и собирает NSIS/portable.

Не запускай платные live prompts по умолчанию. Их отдельная команда и явный переключатель описаны в manual probe. Не выводи ключи или полный environment. `app/runtime/package`, локальные данные, трассы и `node_modules` не публикуются в Git.

Для каждого среза выдай работающий результат, короткий список наблюдений, способ повторить проверку и оставшиеся ограничения. Обнови статус документации только по фактам. Полную языковую IDE делай на поздних этапах; панели, браузер и устойчивость основного цикла — текущий приоритет.
