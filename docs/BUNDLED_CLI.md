# Собственный GigaCode CLI внутри локальной сборки

Приложение может использовать подготовленный вами комплект GigaCode CLI без изменений его исходников или бинарников. Импорт — необязательный шаг сборки; отсутствие `app/runtime/runtime.json` не означает, что GigaCode установлен. Выбор CLI и запасной путь запуска определяет приложение, а не помощник импорта.

В этом репозитории поставляется [помощник импорта](../app/tools/bundle-cli.mjs), но не сам дистрибутив GigaCode, его авторизация или рабочие сессии. Здесь проверена механика импорта на временных данных; совместимость вашей версии GigaCode с ACP проверяется на целевой машине после сборки.

## 1. Подготовить самостоятельный комплект

1. Найдите CLI entrypoint в разрешённом для чтения дистрибутиве GigaCode Desktop либо в отдельно полученном CLI-комплекте. Используйте фактические файлы и документацию установленной версии; не угадывайте путь по аналогии с Qwen.
2. Подготовьте отдельную папку, содержащую entrypoint **и все его runtime-зависимости**. JavaScript-файл с зависимостями, оставшимися уровнем выше в чужом `node_modules`, не является самостоятельным комплектом. Помощник не извлекает зависимости из Desktop, ASAR или package manager и не восстанавливает hoisted dependencies.
3. Для Windows возьмите Windows-совместимые executable/native dependencies нужной архитектуры. Успешное копирование на macOS не подтверждает запуск Windows-бинарника или native addon.
4. Исключите пользовательские данные: профиль `.gigacode`/`.qwen`, `.env`, токены, cookies, OAuth-файлы, SSH/облачные ключи, историю разговоров и сессии. Не копируйте весь пользовательский каталог Desktop. Авторизация создаётся/используется отдельно штатным способом CLI на рабочей машине.
5. Сохраните требуемые лицензии и notices точной версии CLI и включённых зависимостей. Доступность установленного Desktop сама по себе не устанавливает право публиковать его содержимое. Публичный репозиторий не должен содержать импортированный локальный комплект; условия передачи готового приложения с CLI проверяются для его фактического дистрибутива.

Папка-источник должна быть вне `app/runtime`, не совпадать с ним и не быть его предком или потомком. Не выбирайте корень репозитория, весь `app` или текущий установленный `runtime/package` как источник замены. Исходный комплект во время импорта должен оставаться неизменным.

## 2. Выполнить импорт

Запустите из каталога `app` на машине, где доступен Node.js для сборки:

```text
node tools/bundle-cli.mjs --source "C:\BuildInputs\GigaCode-runtime" --entry "bin\gigacode.js"
```

`--source` — абсолютный путь к подготовленной папке. `--entry` — путь внутри неё, с точным именем файла; разрешены `.js`, `.mjs`, `.cjs`, `.exe`. Разделители `/` и `\` принимаются. Абсолютный entrypoint, `..`, `.` и Windows drive/ADS-компоненты запрещены.

Чтобы **явно заменить** ранее импортированный комплект:

```text
node tools/bundle-cli.mjs --source "C:\BuildInputs\GigaCode-runtime-next" --entry "bin\gigacode.js" --replace
```

Без `--replace` существующие `runtime.json` или `package/` останавливают импорт. Ошибка возвращает ненулевой код завершения; это не приглашение молча собрать приложение с другим CLI. Помощник не выполняет entrypoint, не запускает установку пакетов, не получает токены и не меняет настройки проектов.

## 3. Что создаётся и проверяется

```json
{
  "entry": "package/bin/gigacode.js",
  "label": "GigaCode CLI",
  "sha256": "64 hexadecimal characters calculated from the entrypoint bytes"
}
```

Это форма манифеста, а не готовый файл: настоящий SHA-256 рассчитывает помощник. Хеш относится к **байтам entrypoint**, а не ко всем зависимостям, подписи поставщика или доказательству совместимости.

| Проверка | Поведение |
|---|---|
| Source/entry scope | Отказ при выходе за источник, пересечении источника и целевого runtime, отсутствующем/неподходящем entrypoint |
| Symlinks/junctions/special files | Отказ; ссылки не разыменовываются для включения чужих файлов |
| Объём | Не более 1 GiB обычных файлов суммарно и 100 000 элементов дерева; учитывается фактически прочитанный объём |
| Известные секретные файлы | Отказ на `.env` и варианты, auth/credentials/OAuth/session data, пользовательские профили и ключи; файлы не пропускаются молча |
| Файлы кода | Обычный модуль `auth.js` не считается автоматически пользовательским токеном |
| Существующий runtime | Только явная замена; неизвестное содержимое в целевой папке не удаляется |
| Одновременный импорт | Один writer через `.bundle-cli.lock`; второй импорт получает отказ |
| Источник во время чтения | Контроль типа, размера и метаданных открытого файла; замеченное изменение прерывает импорт |
| Копирование | Байты entrypoint и остальных файлов не переписываются; исполняемые permission bits обычных файлов сохраняются без setuid/setgid |

Проверка имён намеренно консервативна: даже `.env.example` останавливает импорт. Подготовьте чистую отдельную папку, не изменяя установленный Desktop. Это **не** антивирус, DLP-проверка всех форматов или доказательство отсутствия секретов внутри executable/архива. Комплект должен происходить из доверенного источника.

Файлы сначала копируются во временную соседнюю папку. После проверки прежний runtime переименовывается в backup, подготовленный каталог занимает его место; обычный сбой переключения вызывает попытку возврата backup. Это транзакционная замена с откатом при ошибках процесса, а не обещание одной атомарной файловой операции для всей пары каталогов на любой ОС.

Не запускайте сборку одновременно с импортом. При аварийном выключении между переименованиями могут остаться `.runtime-stage-*`, `.runtime-backup-*` или `.bundle-cli.lock`. Сначала убедитесь, что процесс импорта завершён, сохраните/проверьте оставшийся комплект и восстановите целый runtime из backup при необходимости. Не удаляйте backup, пока не определили фактическое состояние. Обычные успешные и отклонённые импорты очищают свои временные данные.

## 4. Контракт загрузчика приложения

Загрузчик, принадлежащий main process, должен:

- Читать только локальный `runtime.json` из ожидаемого runtime-каталога сборки, валидировать обязательные строки и форму SHA-256.
- Разрешать `entry` внутри runtime: после `realpath` он остаётся в разрешённой области и является обычным файлом. Проверять хеш фактических байтов entrypoint перед выбором этой поставки.
- Сохранять в диагностике название выбранной поставки и источник выбора. Не сообщать «встроенный GigaCode», если манифест отсутствует, повреждён или не принят.
- Для JS entrypoint использовать поддерживаемый приложением Node runtime/режим, для `.exe` — непосредственный запуск с массивом аргументов, без shell-конкатенации. Фактические ACP-аргументы берутся из установленной версии GigaCode; импорт не добавляет придуманных флагов.
- Сохранять пользовательскую возможность выбрать внешний CLI. Изменение поставки применяется в безопасной точке следующего запуска процесса, без подмены текущей выполняющейся сессии.
- Держать пользовательскую авторизацию/профиль вне упакованного runtime. Не записывать секреты и полное окружение в диагностический вывод.

Конкретный приоритет внешнего выбора и встроенных вариантов реализуется main process и настройками приложения. Этот документ не объявляет установленными отсутствующие пакеты и не требует патча GigaCode CLI.

## 5. Проверить именно собранное приложение

После импорта и обычной сборки на целевой Windows-машине:

1. Убедиться в показанном выбранном CLI и пути/версии из доступного readback; сравнить с подготовленным комплектом.
2. Выполнить штатную авторизацию CLI без включения её файлов в сборку; проверить реальный запуск и `initialize/session` обмен через уже существующий adapter.
3. Отправить короткий безопасный запрос в тестовом проекте, дождаться настоящего terminal response; проверить stderr/ошибки, не превращая сам факт запуска в «ACP работает».
4. Открыть две отдельные сессии и проверить адресацию ответов/остановки; доступные модели и reasoning должны происходить из фактического CLI.
5. Перезапустить приложение, убедиться в сохранности истории и корректном повторном выборе поставки. Проверить диагностируемый отказ на неверный entrypoint/хеш в отдельной тестовой копии сборки.

Если запуску не хватает зависимостей, вернуться к подготовке самостоятельного комплекта. Не подменять результат тихим скачиванием другой версии, автоматическим патчем CLI или повтором уже отправленного запроса.
