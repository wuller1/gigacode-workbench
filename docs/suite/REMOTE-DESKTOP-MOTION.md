# Анимации в ВАРМ и удалённой рабочей среде

Статус 13.10.2026: контракт прототипа и последующей реализации. Этот документ не подтверждает работу Electron-сборки в конкретной ВАРМ. Изменения `app/` выполнять после согласования полного макета. Прямая настройка пользователя: анимации самого Workbench должны оставаться включёнными, даже если система сообщает сокращение анимаций.

## Что именно исправляем

Системное `prefers-reduced-motion: reduce` — сигнал предпочтения, который интерфейс учитывает своими стилями и JavaScript. Это не запрет браузерного движка рисовать движение. Для Workbench явный выбор пользователя `always` имеет приоритет над этим сигналом; системные настройки Windows не изменяются. [MDN: prefers-reduced-motion](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion).

Нужно различать четыре причины неподвижного индикатора:

| Слой | Наблюдение | Решение в приложении |
| --- | --- | --- |
| Правила UI | `animation: none`, duration около нуля или reduced-motion ветка JS | Единая политика анимаций; явное исключение `always` из системного сокращения |
| Планировщик renderer | `requestAnimationFrame`/timers не получают время; ошибочно скрытое окно | Диагностика visibility и оконного lifecycle; адресная настройка Electron, если причина доказана |
| Состояние приложения | Индикатор не получает новые данные, хотя процесс работает | Исправить subscriptions/reconciliation, не маскировать дефект постоянным spinner |
| Доставка изображения ВАРМ | Renderer рисует, но клиент получает кадры редко или не получает | Измерение и отчёт; приложение не может гарантировать политику и частоту кадров чужого удалённого канала |

RDP отдельно кодирует и доставляет изображение; выбор кодека и качество зависят от ресурсов и канала. Поэтому успешная проверка кадров внутри Electron ещё не доказывает плавность на клиенте ВАРМ. Нужны оба уровня наблюдения. [Microsoft: graphics encoding over RDP](https://learn.microsoft.com/en-us/azure/virtual-desktop/graphics-encoding).

## Пользовательская настройка

Один пункт в настройках внешнего вида: **Анимации**.

- **Всегда · для ВАРМ** (`always`) — значение по умолчанию для этой поставки; сохранять движение независимо от системного reduced-motion.
- **Как в системе** (`system`) — применять текущее `matchMedia('(prefers-reduced-motion: reduce)')`, включая его изменение без перезапуска.
- **Без анимации** (`reduced`) — явный выбор внутри приложения; короткие мгновенные переходы, статичные обозначения работы и обычные текстовые статусы.

Настройка общая для приложения, не для проекта или роли. Она синхронизируется между окнами, сохраняется до следующего запуска и применяется до первого отображения интерфейса. Переключение не перезагружает приложение, не теряет черновики, не завершает CLI и не останавливает задачи. Ошибка записи настроек видна пользователю; нельзя показывать сохранение, если оно не произошло.

Контракт для будущего runtime:

```ts
type MotionPreference = 'always' | 'system' | 'reduced';
type MotionPolicy = {
  preference: MotionPreference;
  systemReduced: boolean;
  effective: 'full' | 'reduced';
};
```

`effective = preference === 'always' ? 'full' : preference === 'reduced' || systemReduced ? 'reduced' : 'full'`. Ни одна библиотека анимаций не должна отдельно переопределять эту формулу. UI kit принимает effective policy из одного provider.

В текущем прототипе настройка находится в общих настройках: три режима, движущийся preview, видимый фактический системный signal и диагностический переключатель имитации отключённых CSS-анимаций. В `always` статусные glyphs используют общий совместимый scheduler с частотой 12 кадров/с; курсор агента — явный `moveTo` tween. Другие собственные CSS-переходы разрешены независимо от системного signal. Диагностическая имитация действует только на макет, не меняет ОС и не является доказательством работы удалённого канала.

## CSS и программное движение

В корне документа хранить выбранный режим и effective policy; например, `data-motion="always"` и `data-motion-effective="full"`. Глобальное правило `@media(prefers-reduced-motion:reduce){*{animation:none}}` без исключения больше недопустимо. Правило сокращения должно выбирать только root с соответствующим effective policy. Проверить обычные элементы, `::before`, `::after`, SVG, portal/dialog surfaces, дочерние приложения UI kit и новые панели.

`always` восстанавливает авторские duration, iteration count и easing. Не задавать всем узлам одну длительность и `animation: initial !important`: это удалит имена keyframes, незаметно отключит движение или ускорит разные эффекты до одинаковой скорости. Сокращённый режим не должен менять бизнес-состояние, готовность кнопок или завершение операции.

Критические индикаторы состояния (работа агента/субагента, текущий шаг, запрос браузера, сборка/загрузка) поддерживают совместимый способ отрисовки. В согласованном `always` он используется непосредственно для статусных glyphs, поэтому они не зависят от CSS animation. Для возможного автоматического fallback в других режимах сначала доказать, что CSS-анимация действительно не продвигается в видимом окне:

1. Проверить policy, наличие активной операции и видимость узла; для автоматического detection дополнительно проверить computed animation/сдвиг времени, исключив ещё не начавшуюся animation delay. В `reduced` не запускать принудительное движение.
2. Использовать один управляемый scheduler на окно для зарегистрированных индикаторов. Отрисовывать простую фазу через отдельный внутренний wrapper/SVG, не перезаписывая transform внешней layout-обёртки.
3. Изменять фазу по прошедшему времени; не считать, что каждый callback равен 16 миллисекундам. Ограничивать частоту совместимого режима примерно 12–20 кадров/с, проверять фактическую плавность в ВАРМ.
4. Убирать renderer registrations при завершении, скрытии панели, удалении DOM или закрытии окна. Не создавать независимые вечные интервалы для каждой строки.
5. При возобновлении вычислять текущую фазу, не проигрывать накопившиеся кадры. Состояние «готово/ошибка» немедленно останавливает индикатор.

Это наша стратегия устойчивого UI, а не обещание обхода произвольной системной блокировки. Если весь renderer/композитор остановлен, резервный таймер также не сможет показать кадр. `requestAnimationFrame` во многих браузерах приостанавливается в скрытых документах; elapsed time нужно брать из времени callback или монотонных часов. [MDN: requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame).

Не восстанавливать все эффекты перерисовкой DOM на каждом кадре. Использовать локальные изменения opacity/transform в штатном пути; не добавлять незаметное full-window video, busy loop или искусственный repaint всего экрана. Акцентные цвета, статусы и текст «Выполняется» остаются читаемыми на статичном снимке. Кольцо контекста показывает заполнение, поэтому не превращается в spinner.

## Electron после согласования макета

Вначале сверить установленную версию Electron и старую доработку пользователя. Если прежний механизм надёжнее или лучше проверен в ВАРМ, представить сравнение и спросить, какой вариант сохранить; не заменять его молча. Скопировать необходимое из существующего решения без второго контроллера окон и без сброса настроек.

`webContents.setBackgroundThrottling(false)` и `webPreferences.backgroundThrottling: false` — официальные настройки анимаций и timers в фоне. Они также меняют поведение Page Visibility; начиная с Electron 28 отключение для одного contents влияет на кадры всей host BrowserWindow. Использовать адресно для окон оболочки при подтверждённом дефекте background classification, записывать значение в диагностику. Не выдавать переключатель за override reduced-motion или за устранение RDP frame suppression. [Electron: background throttling](https://www.electronjs.org/docs/latest/api/web-contents#contentssetbackgroundthrottlingallowed).

Отдельный API `setImageAnimationPolicy('animate')` применим только к политике анимированных изображений, не к CSS или оконной анимации. Если такие собственные assets появятся, проверить наличие API и вызвать до загрузки изображений; смена политики не меняет уже загруженные изображения автоматически. [Electron: image animation policy](https://www.electronjs.org/docs/latest/api/web-contents#contentssetimageanimationpolicypolicy).

Границы применения:

- Окно может быть видно, но не иметь focus: не останавливать его индикаторы по одному событию blur. Это требуется при нескольких открытых окнах.
- Скрытый/минимизированный shell не обязан тратить ресурсы на невидимый ornament. IPC, получение событий и управление задачами продолжаются независимо от анимационного scheduler.
- Источником truth для минимизации/показа считать оконный lifecycle main process. Не полагаться только на `document.visibilityState` после отключения throttling.
- Внешние страницы Browser Lab не получают молчаливую замену accessibility preferences. Проверяемый сайт должен сохранять настоящее поведение; его media emulation — отдельная тестовая настройка вкладки, видимая пользователю.
- Не ставить глобально экспериментальные Chromium switches, не отключать GPU наугад и не править реестр/GPO Windows. Если требуется проверка graphics backend, это отдельный диагностический эксперимент с исходным и изменённым результатом, затем осознанное решение.
- CLI, retries, очередь, таймауты команд и сохранение данных не должны зависеть от CSS animationend/transitionend либо renderer frame loop. Fallback окончания visual transition нужен и при исчезновении элемента.

## Диагностика

По требованию «Проверить анимации» собрать короткий bounded sample: выбранный/effective режим, системный media signal, версия Electron/Chromium, window ID, visible/minimized/focused, backgroundThrottling, тип индикатора, число callbacks и интервал p50/p95, наличие долгих провалов, запуск CSS/совместимого пути. Не писать каждый кадр в постоянный журнал.

Состояние graphics backend можно получить через официальные `app.getGPUFeatureStatus()`/`app.getGPUInfo()` с обработкой ошибки и ограничением данных. Это диагностические сведения, не команда менять настройки устройства. [Electron: app API](https://www.electronjs.org/docs/latest/api/app#appgetgpufeaturestatus).

При сбое различать «приложение не рисует новые кадры» и «передача изображения не проверена». Успешный rAF-counter сам по себе не равен успешной paint-проверке. Отчёт содержит наблюдения, но не содержимое страниц, запросов пользователя, пароли или credentials ВАРМ.

## Приёмка

1. `always` + обычная система: текущий шаг, spinner, курсор агента и переходы движутся; завершённые/отменённые операции статичны.
2. `always` + эмуляция `prefers-reduced-motion: reduce`: движения продолжаются, computed duration не становится 0/0.01ms. Повторить в dark/light, popup/dialog, после добавления новой панели.
3. `system` + смена системного media signal: режим меняется без reload; `reduced` остаётся сокращённым независимо от системы. Названия и сохранение соответствуют результату.
4. В test harness отключить CSS animation для критического индикатора; проверить совместимую отрисовку нескольких фаз, возврат после переключения режима и cleanup. Эмуляция CSS не подменяет живой тест ВАРМ.
5. Reload и второе окно: настройка сохраняется/синхронизируется, нет начальной вспышки неправильного режима; черновики и задачи остаются на месте.
6. Два видимых окна, переключение focus между ними: оба отображают реальные актуальные статусы. Minimize/restore и disconnect/reconnect ВАРМ: UI восстанавливает состояние без клика и перезагрузки страницы.
7. Десятки одновременно работающих строк не порождают десятки timers. После закрытия всех соответствующих панелей нет оставшихся animation subscriptions. Замерить CPU/frame gaps относительно исходного состояния на той же машине.
8. Freeze/stall renderer в отдельном fault test: журнал не утверждает, что доставленные кадры проверены; controller задач сохраняет события, UI догоняет состояние после восстановления.
9. На рабочем Windows провести именно удалённую проверку: отсутствие ввода минимум 30 секунд при активной операции, перемещение/resize, несколько окон, reconnect. Записать наблюдаемое движение на клиенте и данные renderer раздельно.

Chrome DevTools позволяет эмулировать reduced-motion через Rendering; это подходит для пункта 2, но не воспроизводит GPO, аппаратный backend или удалённый transport. [Chrome: emulate CSS media features](https://developer.chrome.com/docs/devtools/rendering/emulate-css).

Пункты 1–5 могут иметь prototype evidence. Пункты 6–9 для Electron/Windows/ВАРМ нельзя закрывать на основании HTML-макета в локальном браузере. Итоговый отчёт должен явно разделять эти уровни проверки.
