# Личный браузер и браузер агента

Статус 13.10.2026: целевой контракт и сценарии макета; расширение `app/` не реализовано этим документом. Сначала согласование полного прототипа. Контракт уточняет [BROWSER.md](BROWSER.md), [управление браузером](../../workbench/docs/BROWSER_WORKSPACE_CONTROLS.md) и [корпоративную identity](../../workbench/docs/AGENT_BROWSER_AND_IDENTITY.md).

## 1. Что видит пользователь

В Browser Lab есть два пространства: **«Мой браузер»** и **«Браузер агента»**. У каждого свой набор вкладок, выбранная вкладка, история и размеры просмотра. Агент работает в своём пространстве по умолчанию. Его переходы, новые вкладки, клики и ввод не меняют личную вкладку, адресную строку или фокус пользователя.

Пользователь в любой момент открывает браузер агента. При нескольких исполнителях компактный выбор показывает задачу, имя исполнителя и фактическое состояние: работает, ждёт, управление у пользователя, завершён, ошибка. Переключение просмотра не переключает цель выполняемой команды и не останавливает других исполнителей. Просмотр завершённого браузера доступен, пока ресурс не закрыт явно.

Оба пространства можно открыть рядом или в разных панелях/окнах. Открытие одного не закрывает другое. Сворачивание, закрытие панели и уход в IDE скрывают представление; вкладки и выполнение остаются живыми. «Закрыть вкладку» — отдельное действие над конкретной вкладкой, «Остановить работу» — над выполнением.

## 2. Как агент показывает результат

`present` по умолчанию раскрывает браузер агента рядом с результатом: пользователь прямо попросил позволить агенту показывать нужную страницу. Повторные сообщения одной операции обновляют одно представление; навигация и каждый скриншот сами по себе не создают уведомлений.

Настройка **«Агент может открывать свой браузер рядом»** включена по умолчанию; её можно отключить. Раскрытие сохраняет текущую личную вкладку, раскладку остальных панелей и фокус. Оно не выводит приложение поверх других программ, не активирует другое окно ОС и не переключает проект. При вводе, открытом диалоге, перетаскивании, развёрнутой другой панели или недостатке места `Layout.reveal` откладывает раскрытие. В разговоре появляется компактная карточка с причиной, адресом и кнопкой **«Показать»**; это приглашение к просмотру, а не окно разрешения. При отключённом автопоказе используется та же карточка.

Если результат относится к фоновому проекту/задаче, сначала показывается адресное уведомление в соответствующем разговоре; активная задача не меняется. Кнопка открытия явно ведёт к исходной задаче или открывает её представление рядом. Закрытую пользователем панель агент не открывает снова для той же причины; новое существенное событие допускает новое приглашение.

Пользователь уже разрешил агенту показывать браузер, когда это нужно. Не вводить подтверждение на каждый `present`, просмотр, разрешённый переход или клик. Выбор режима автопоказа — постоянная настройка поведения, отдельная от прав выполнения действий.

## 3. Ресурсы и идентичность

BrowserService в host остаётся единственным владельцем настоящих вкладок; PanelRegistry управляет только их представлениями. Размонтирование компонента не уничтожает ресурс. Не создавать параллельный браузерный backend ради двух переключателей.

Предлагаемые внутренние DTO, а не новые поля ACP:

```ts
type BrowserWorkspace = {
  id: string; projectId: string; kind: "user" | "agent";
  taskId?: string; sessionId?: string; executorId?: string;
  profileId: string; orderedTabIds: string[]; activeTabId?: string;
  revision: number; lifecycle: "live" | "restorable" | "closed";
};
type BrowserPresentation = {
  id: string; workspaceId: string; windowId: string; panelId: string;
  selectedTabId?: string; mode: "observe" | "control"; visible: boolean;
};
type BrowserControl = {
  workspaceId: string; controller: "user" | "agent";
  controlRevision: number; executionId?: string;
  state: "running" | "pausing" | "paused" | "stopped" | "unknown";
};
```

`workspaceId` стабилен. Пользовательское пространство привязано к проекту; агентское — к `projectId + taskId + sessionId + executorId`. Субагенты получают отдельные пространства, а не конкурируют за одну выбранную вкладку. Повторная доставка create/reopen не плодит ресурсы: host использует idempotency key и реестр.

`tabId`, navigation/document/viewport revisions из общего browser-контракта сохраняются. Команда всегда адресует конкретные workspace/tab/execution и ожидаемые revisions. Нельзя подставлять «текущую вкладку UI» вместо захваченного target после переключения пользователя. Имя проекта, задачи или вкладки не является ключом идентичности.

`BrowserPresentation.selectedTabId` — выбор наблюдателя; `BrowserWorkspace.activeTabId` — последняя активная вкладка владельца пространства. Режим **«Следить за агентом»** обновляет только агентское представление; ручной выбор другой вкладки отключает слежение в этом представлении. Агентская цель от этого не меняется. Личный браузер не подписывается на агентскую активную вкладку.

Один живой интерактивный surface имеет одного host-владельца отображения. Для показа того же tab в другом окне либо атомарно переносить surface, сохраняя ресурс, либо использовать обозначенное наблюдение через снимки/поток. Не клонировать вкладку с повторной навигацией и не выдавать снимок за интерактивную страницу.

## 4. Вход, сертификаты и фоновая работа

По умолчанию агентский browser profile отделён от личного: собственные cookies/storage/cache/downloads. Разделение вкладок и разделение авторизации — разные настройки. Общая авторизация возможна через явную привязку обоих пространств к разрешённому профилю; UI обозначает **«Общий вход»**. Не переносить автоматически cookies, пароли или хранилища другого браузера.

Агенту доступны скачивание, просмотр и редактирование полученных файлов по [BROWSER-FILES.md](BROWSER-FILES.md). Загрузка сохраняет project/task/session/executor/profile/workspace/tab и operation ID; переключение наблюдаемой вкладки не меняет владельца. Готовый файл открывается без создания лишней browser tab, поддерживаемый текст — в общем IDE buffer как рабочая копия с diff и защитой от конфликтов. Закрытие агентской панели не отменяет передачу, а общий вход не объединяет права чтения файлов разных проектов. Разрешённые download/read/edit не требуют popup на каждом шаге; пользователь видит прогресс и может забрать редактирование.

Корпоративные proxy, trust и разрешённые сертификаты используют существующий контракт identity. Разные partitions не обещают разные личности Windows или изоляцию системных ключей. Не извлекать private keys и не отключать проверку TLS. При обязательном PIN/MFA агент сообщает о необходимости ручного входа в своём браузере; такие поля не отправляются модели.

Скрытый браузер продолжает необходимую навигацию/automation по подтверждённым возможностям adapter. При реализации измерить поведение конкретной версии Electron/Chromium при скрытии, сворачивании и ВАРМ. Отдельно проверить screenshot, обновления DOM, таймеры сайта и DevTools; видимость панели не считать гарантией активности renderer. При недоступности честно показывать paused/unavailable, не возвращать старый кадр как свежий.

Фоновое выполнение не управляет системной мышью/клавиатурой пользователя. Использовать адресный browser adapter. Если внешний connector умеет только активировать пользовательскую вкладку, обозначить ограничение и не включать для него режим независимого фонового браузера. Agent cursor рисуется только в его surface и не двигает реальный курсор ОС.

## 5. Управление и отказоустойчивость

Просмотр по умолчанию не отправляет клики странице. **«Забрать управление»** останавливает новые agent dispatch, сверяет in-flight действие, увеличивает `controlRevision` и включает ручной ввод. Переход между задачами не возвращает управление автоматически. **«Вернуть агенту»** получает свежий snapshot и продолжает с текущей страницы, а не повторяет прежний клик.

**«Пауза»** останавливает следующие шаги этого браузерного выполнения; не отменяет другие задачи. **«Продолжить»** сверяет target/revisions. **«Остановить»** прекращает выполнение и оставляет браузер для проверки; не заявляет отмену уже отправленной формы. Закрытие управляемой вкладки отменяет/сверяет её очередь и сообщает конкретному исполнителю, не выбирая вместо неё личную вкладку.

После потери ответа сначала читать фактическое состояние и журнал operation receipts. Не повторять submit, download/upload или действие с неизвестным эффектом только ради retry. После перезапуска восстанавливать метаданные и вкладки с пометкой восстановления; живое выполнение не считать продолженным до reconciliation.

## 6. Обязательные операции adapter

Ниже точные **предлагаемые** имена внутренних host-операций. При реализации сопоставить существующие IPC/MCP или зарегистрировать реальные narrow tools; их наличие у установленного CLI не предполагается.

| Операция | Вход и результат |
|---|---|
| `browser.workspace.ensure` | trusted project/task/session/executor binding, kind, profileRef, requestId → workspaceId и revision; повтор возвращает тот же ресурс |
| `browser.workspace.list` | trusted scope → доступные пространства с фактическим состоянием; без секретов/чужих targets |
| `browser.workspace.observe` | workspaceId, afterRevision → snapshot/delta с tabs, execution и receipts; UI subscribe не даёт право управления |
| `browser.presentation.open` | workspaceId, tabId?, panel/window target, follow, focusPolicy → presentationId; `preserve` обязателен для автопоказа |
| `browser.presentation.hide` | presentationId → скрыто; не cancel/close ресурса |
| `browser.presentation.selectTab` | presentationId, tabId, expectedRevision → выбор наблюдателя; не automation target |
| `browser.present` | workspaceId, tabId, reason, dedupeKey, executionId → invitation/revealed/deferred; без implicit project switch |
| `browser.control.change` | workspaceId, expectedControlRevision, take/return/pause/resume/stop → confirmed/pending/unknown и новая revision |
| `browser.tab.command` | operationId, captured target/revisions, action, arguments, authorizationRef → actual observation/receipt; общий путь для разрешённых ручных и агентских операций |

Host получает actor/ownership из доверенного вызова, а не верит произвольному `actor` от модели. Разрешение на агентский browser не даёт доступ к личному. Доступ к общей identity и внешние эффекты следуют уже настроенной политике, без нового окна на каждый MCP-вызов.

## 7. Этапы и приёмка

Зависимости — существующий [план](../../suite/implementation-plan.json): `S2-00` isolation → **`S2-04` отдельный браузер агента** → `S2-01` profiles → `S2-02` automation/diagnostics. Новая карточка `S2-04` имеет статус `planned` и зависит от `S2-00` и `S1-03`; `S2-01` также зависит от `S2-04`. Прежний статус `S2-00` — `implemented_pending_live` — не означает реализации разделения личного и агентского браузеров.

1. В макете: два пространства, независимые tabs/selection, наблюдение, показ результата, takeover, закрытие панели. Все события обозначены демонстрацией.
2. После согласования: сначала host ownership/idempotency и persistence; затем UI projections/present; затем automation/takeover и live Windows проверки.
3. Только после базовой изоляции — параллельные исполнители, несколько окон и корпоративный external connector. Не откладывать изоляцию до этих расширений.

Обязательные сценарии приёмки:

- Пользователь вводит текст в своём браузере; агент открывает, переключает и закрывает свои вкладки. Текст, selection и focus пользователя не меняются.
- Два исполнителя и два проекта работают параллельно; переключение/скрытие/перетаскивание панелей не перенаправляет команды и не создаёт лишних вкладок.
- Пользователь открывает агентский браузер, выбирает другую вкладку и возвращает «Следить». Automation продолжает исходную цель; личный браузер неизменён.
- Агент показывает результат: default auto-reveal открывает рядом без focus steal; при вводе/диалоге/перетаскивании/развёрнутой другой панели или отключённой настройке появляется одна карточка «Показать»; фоновый проект не становится активным; закрытие панели не вызывает цикл reopen.
- Takeover во время in-flight fill/submit: новые шаги заблокированы, исход сверяется; resume не повторяет внешний эффект; устаревшая control revision отклоняется.
- Закрытие панели не отменяет выполнение; остановка не закрывает результат; закрытие tab не подменяет его соседней/личной вкладкой.
- Изолированные profiles не обмениваются cookies; общий профиль включается явно; вход/MFA проходит без захвата секретов моделью.
- Потерянный create response, out-of-order snapshots, restart и перенос между окнами сохраняют identity и честный статус. Недоступный hidden capture не возвращает фиктивный успех.
- Клавиатурный доступ, узкая панель, две темы и ВАРМ: одинаково доступен ручной просмотр, нет неожиданных переключений и перекрытия набираемого текста.

Отчёт различает prototype fixture, unit/contract, live Electron и live Windows/ВАРМ. Этот документ задаёт проверку, но не свидетельствует о её выполнении.
