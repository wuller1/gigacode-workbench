# Рабочий Data workspace: перенос и продолжение

Срез 14.10.2026, приложение 0.3.0-preview.1. Это рабочий код PostgreSQL workspace, а не сертификат полного соответствия DataGrip. IDE остаётся на Theia; собственные Data-сервисы общие для UI и агента. На рабочем компьютере сначала сравнить существующие реализации и сохранить более удачные по правилам `SUITE-UPGRADE-AGENT.md`. Не заменять рабочий LLM-router пользователя локальным keyword fallback этого репозитория.

## Что уже работает

- Настройки → Подключения БД: несколько общих подключений, произвольные названия окружений, привязка одного подключения к нескольким проектам. Секрет хранится отдельно через Electron safeStorage; открытый fallback запрещён. Смена адреса/параметров сервера инвалидирует прежнюю target-привязку документа; его SQL и сохранённые результаты остаются доступны. Для нового сервера создать новую консоль/копию SQL.
- Встроенный отдельный stdio MCP-процесс с `pg` и отдельной физической сессией на консоль. Корпоративные stdio/HTTPS MCP подключаются через фактический inventory и `bindings`, без догадок об именах tools.
- PostgreSQL SQL editor: CodeMirror, Monokai в тёмной теме и самостоятельная светлая палитра, форматирование, Ctrl+Enter, statement/script/selection, несколько результатов, реальные позиции ошибок. Сохранение SQL проверяет revision; конфликт между окнами сохраняет отдельный recovery draft.
- Auto/manual transactions, Begin/Commit/Rollback, savepoint/rollback-to; состояние приходит от PostgreSQL ReadyForQuery. `COMMIT`, на который сервер ответил `ROLLBACK`, не выдаётся за подтверждение записи.
- Catalog: сохранённый выбор нескольких схем, системные схемы по запросу, поиск/постраничная выдача на сервере, таблицы/представления, materialized views, sequences, functions/procedures; описание columns/constraints/indexes/triggers/dependencies. Дерево скрывается и меняет размер; таблица открывается самостоятельным документом.
- Серверные фильтры/сортировка/постраничное чтение таблиц. Inline cell edits, NULL/DEFAULT, новые и удалённые строки, staged changeset. Сверка `tableoid/ctid/xmin` откатывает весь changeset при конфликте. Generated и identity ALWAYS не редактируются; произвольные SELECT/join/views не притворяются автоматически изменяемыми.
- Редактирование functions/procedures через отдельный Apply DDL: проверка исходного SHA-256, одна CREATE OR REPLACE, savepoint/transaction, чтение фактически применённого объекта до Commit. Смена сигнатуры/имени не выдаётся за обновление исходного OID. Конкурентное внешнее DDL не блокируется универсальным CAS: нужна повторная сверка.
- EXPLAIN JSON tree; оценки стоимости и фактическое ANALYZE-время различаются. ANALYZE действительно выполняет SQL и требует подходящего окружения/транзакции.
- Sessions/locks/roles/extensions, cancel/terminate по реальным PostgreSQL permissions.
- Streaming CSV → COPY FROM STDIN; XLSX → bounded OpenXML parser → COPY; SQL → incremental PostgreSQL lexer → statements в одной transaction/savepoint. Ошибка, изменение исходного файла или отмена дают rollback, если соединение позволяет подтвердить исход. Неизвестный исход остаётся unknown.
- Экспорт CSV/SQL/XLSX из полученного результата либо полный поток таблицы. Полный экспорт таблицы явно отличается от текущей страницы и не наследует её фильтр. Произвольный SQL не выполняется повторно ради экспорта. Существующий файл назначения не перезаписывается.
- BIGINT/NUMERIC/date/time/JSON/bytea сохраняются текстом без JavaScript rounding; NULL и пустая строка различаются. В XLSX значения пока экспортируются строковыми cells для сохранения точности.
- SQLite spool, журнал операций и исходный SQL/параметры/target с SHA-256; page и history читаются порциями. История и локальные результаты доступны без новой PostgreSQL-сессии. Агентский preview ограничен; усечённые cells не используются как полное значение для записи.
- Реальный потерянный ответ COMMIT (autocommit changeset и ручной Commit): write-ahead intent сохраняется host до RPC; unknown changeset блокирует повтор, изменение подключения и удаление консоли до сверки. Перезапуск не снимает блокировку. Агентская сверка требует завершённых проверок на том же подключении после исходной операции, note и evidence job IDs. Наличие job само по себе не доказывает смысл сверки: агент обязан проверить ключи/значения/эффекты, а не писать «всё работает».

## Дополнение: desktop UX, связи и защита DDL

Таблица теперь открывается сразу с grid; SQL раскрывается кнопкой. Метаданные представлены компактными вкладками columns/keys/indexes/triggers с поиском, реальными определениями, inline read-only SQL и точным ограниченным копированием. `DatabaseStructure.tsx` и отдельный CSS не используют чужие компоненты DataGrip.

`DatabaseRelations.tsx` и `electron/database/relations.ts` показывают настоящие прямые входящие/исходящие FK: composite/cross-schema/self references, ordered pairs, PK/type и ON UPDATE/DELETE/validation/deferrable. Карточки перетаскиваются, масштабируются и открывают общий документ таблицы. Лимит — 30 таблиц, 50 FK, 8 колонок на таблицу; shown/total/truncation явные. Это прямое окружение выбранной таблицы, а не полный ERD/modeling engine. Один SQL-запрос читает согласованный каталог для этого ответа; сохранённого schema snapshot после него нет. Отображаются реальные FK каталога, а не предполагаемые связи по именам столбцов. Выбор схем в дереве не обрезает cross-schema окружение FK. У представлений остаются обычные зависимости каталога. Агентский `database_relations` читает тот же graph DTO; отдельных MCP-команд перемещения/масштабирования карточек, сохранения layout и редактирования схемы пока нет.

Grid: F2/Enter начинает редактирование; Tab/Shift+Tab фиксирует ячейку в changeset и переводит фокус по столбцам, Enter — вниз, Escape — отменяет текущую ячейку. До Apply серверные записи не меняются. Ячейка привязана к console/result/page/optimistic row key; смена страницы, размера, результата, refresh и применение фильтра блокируются до завершения/отмены изменений. Ключи React имеют отдельные пространства имён для SQL/structure/relations: metadata refresh не оставляет дубликатов редактора.

Исходный SHA-256 процедуры принадлежит host и хранится между запусками. Metadata read и caller hash не принимают новую версию. Повторные manual edits используют hash физической сессии; известный Commit подтверждает его атомарно, полный Rollback очищает hash незакоммиченного DDL и оставляет исходную baseline. Текст черновика при Rollback не заменяется. После перезапуска hash прежней manual-сессии не становится committed baseline; сохранённый SQL остаётся черновиком для проверки и дальнейшей работы. Apply ждёт terminal job; потеря подтверждения остаётся pending/unknown и блокирует повтор. Явная «Загрузить DDL из БД» работает по revision CAS и сохраняет прежний текст в recovery. Для неё нужны живое подключение к прежнему target, idle-транзакция и отсутствие любого pending effect. UI сначала сохраняет текущий SQL. Если сохранение конфликтует либо recovery-хранилище заполнено, текст не перезаписывается: сначала сохранить копию/разобрать конфликт. Старые документы без baseline требуют этой загрузки. После rollback-to-savepoint дальнейший Apply консервативно блокируется до полного Rollback либо завершения транзакции и явной загрузки DDL. Это по-прежнему не универсальный атомарный CAS против чужого параллельного DDL.

Закрытие вкладки сначала сохраняет SQL; ошибка оставляет вкладку открытой. Активная manual-транзакция при закрытии вкладки требует выбора отката. Незавершённый/конфликтующий draft и очередь удерживаются вне размонтированного редактора в пределах живого renderer. Native close и повторный Quit ждут renderer save barrier, замораживают ввод и не обходят сохранение вторым нажатием. Перед завершением всего приложения host проверяет свежие состояния БД, включая закрытые консоли. Открытая/ошибочная транзакция, выполняющаяся операция либо невозможность подтвердить состояние отменяют выход; пользователь выполняет Commit/Rollback или отмену явно. Status существующих подключений проверяется параллельно с SDK timeout 5 секунд на запрос; таймаут отменяет запрос проверки, а не PostgreSQL-транзакцию. Неуспешный status не считается доказательством завершения active/failed-транзакции. Если физическая сессия всё ещё числится, но её состояние недоступно, восстановить связь либо после сверки явно выполнить Disconnect. Уже сохранённый unknown intent сам по себе не требует повтора/автоматического разрешения для выхода. Новые окна и выполняющие операции БД в период закрытия не запускаются; чтение истории, отмена и сохранение SQL для barrier остаются доступны. Реализация: `DatabaseConsoleEditor.tsx`, `window-close.ts`, `App.tsx`, `main.ts`, `DatabaseService.assertShutdownReady()`. Форсированный reload/crash/завершение процесса ОС и последние ещё не подтверждённые символы остаются отдельной crash-recovery задачей. Принудительное завершение процесса может откатить manual-транзакцию; сохранённый SQL не означает Commit данных.

Изменённый target помечается «Прежний сервер»; документ не переиспользуется по одному OID на новом сервере. Потерянная сессия не получает зелёный connected state. После неизвестного Apply/Commit сверить фактическое определение/данные в независимой консоли. `effect.resolve` записывает результат сверки и снимает блокировку, но не проверяет смысл note вместо пользователя/агента. Для routine Apply и Commit с незакоммиченным routine hash исходная версия после сверки становится непроверенной: дальнейший Apply требует явной загрузки DDL. Это относится к обоим исходам сверки, `applied` и `notApplied`. Агентский `database_routine_reload` требует `adoptServerVersion: true` и явного запроса пользователя принять серверную версию; boolean не заменяет это поручение. Автоматическое подавление конфликта запрещено. «Загрузить сохранённый SQL» в конфликте редактора читает локальную host-консоль; это другая операция, которая не принимает новую серверную DDL-baseline.

| `app/electron/mcp.ts`, `main.ts` | Общий UI/agent dispatch, адресные project scopes и выбор файлов |

Операционный журнал сохраняет исходный payload query/routine Apply/changes/Commit/file операции до dispatch, scoped console ID, hash и receipt. Запрос, записанный как accepted/done, отдельно сверяется с terminal jobStatus; потерянный ответ не становится успехом. Журнал читается порциями из UI и MCP даже после сверки unknown. Хранятся исходные intents и последняя запись `lastResolution`; отдельная полная история решений по сверке пока не реализована. Schema selection ограничивает metadata/introspection и не меняет серверный search_path или целевую БД SQL. Референс принципа — [DataGrip metadata/introspection](https://www.jetbrains.com/help/datagrip/introspection.html); UI/код собственные.

Data — обычная панель общего docking tree, доступная рядом с IDE/чатом/браузером. Не создавать второй владелец подключения или отдельную «агентскую БД», которую пользователь не видит. MCP вызовы привязаны к console ID/project, а не к текущему фокусу окна.

## Настройка на Windows

1. Сначала `WORK-COMPUTER-BOOTSTRAP.md`, затем `IDE-RUNTIME-HANDOFF.md` и этот документ. Требуется Node 22.19+ (рекомендуется закреплённый runtime), Git и доступ к пакетам; IDE setup описан отдельно. Для работы Data клиенту не нужен локальный PostgreSQL server.
2. В `app/` выполнить `npm ci --include=optional`, `npm run build`, `npm start`. Сборка создаёт `dist-electron/database-provider.cjs`; в Windows package он входит вместе с основным кодом. CLI/GigaCode не модифицируются.
3. Создать подключение в UI. Для встроенного MCP указать host/port/database/user, пароль отдельным полем, SSL и при необходимости PEM CA. Для HTTPS указать URL без credentials, отдельный token, реальное имя credential header и prefix. Для stdio — executable и JSON-массив args, отдельное имя token environment variable. Не писать секреты в args/bindings/prompt/Git.
4. Сохранить → Проверить подключение/inventory. Встроенный probe действительно открывает и закрывает PostgreSQL-сессию; remote probe проверяет доступный MCP inventory. Сам факт listTools не доказывает выполнение операций БД.
5. Для корпоративного MCP сопоставить `operation → exact tool name`. Адаптер должен принимать поля Data DTO и возвращать `{value: ...}` либо совместимое structuredContent. Если существующий server имеет другую схему, написать тонкий адаптер и проверить его на собственном тестовом ресурсе. Не выдавать наличие произвольного SQL tool за готовую поддержку session, transactions, cancel, COPY и локальных file paths.
6. Привязать profile к нужным проектам. Открыть Базы данных, создать SQL-консоль, подключиться, выполнить адресную проверку. Новая консоль имеет отдельную физическую сессию; переключение вкладки не переносит транзакцию.

TLS проверяется всегда. Node default/system roots плюс явно заданный CA используются без `rejectUnauthorized:false`. Hardware client cert/mTLS, proxy, корпоративный SSO и чужой JDBC driver не считаются поддержанными без отдельного адаптера/пробы.

## MCP surface

Host tools: `database_snapshot`, `database_console_create/open/read/update`, `database_history_load`, `database_job_read`, `database_operation_list/read`, `database_execute`, `database_page`, `database_catalog`, `database_describe`, `database_relations`, `database_table`, `database_changes`, `database_routine_apply/reload`, `database_transaction`, `database_import/export`, `database_admin`, `database_cancel`, `database_disconnect`, `database_effect_read/resolve`, `database_reveal`.

Query/table jobs, routine Apply, staged changes, Commit и import/export используют operationId/receipt. Для этих операций ID не меняется из-за retry; новый payload получает новый ID только после установленного исхода предыдущего. Provider receipt записывается до dispatch и не разрешает replay pending. Это защита повторения конкретной операции, а не универсальная SQL exactly-once транзакция. Console CRUD, явный DDL reload, mode/Begin/Rollback/savepoint и cancel/admin не имеют такой же гарантии receipt по operationId; их исход проверяется отдельно. SQL/reload консоли защищены revision CAS. `database_effect_*` обслуживает staged table changes, ручной Commit и routine Apply; unknown arbitrary SQL/import остаются jobs со статусом unknown и требуют отдельной сверки без автоматического повтора. Снятие блокировки неизвестного routine Apply не обновляет исходный DDL автоматически.

Для первого открытия routine-документа агент читает каталог и полный исходный `ddl` через `database_describe` на том же подключении, затем создаёт `database_console_create` с `object: {oid, kind: "function" | "procedure"}` и этим неизменённым SQL. `database_console_open` сравнивает hash первоначального текста с реальным определением; затем `database_console_update` сохраняет правки по revision. Применение выполняется только через `database_routine_apply` с тем же OID и новым operationId. Обычный `database_execute` и import в routine-документ запрещены; произвольный SQL выполняется в отдельной SQL-консоли. Если полный исходник недоступен либо уже изменился, не достраивать его по памяти и не подставлять новый caller hash: проверить конфликт/адаптер или по поручению пользователя загрузить серверную версию.

После `database_routine_apply` проверить terminal `status`, `routine.previousHash/appliedHash/committed` и состояние транзакции. В manual-режиме завершённый Apply ещё не означает Commit; пользователь видит изменения своей сессии, независимая сессия — прежнюю committed-версию. При таймауте внешнего MCP-вызова сначала прочитать `database_snapshot`, `database_effect_read`, job/operation history. Ответ accepted, отмена запроса клиента или сброс соединения не разрешают повтор DDL. Для явного reload использовать текущую revision из `database_console_read`, завершить транзакцию, разобрать pending effect и только затем принять серверный исходник; recovery ограничено 40 сохранёнными черновиками и при заполнении операция откажет, сохранив текущий текст.

На рабочем MCP отсутствие отдельной операции — конкретный unsupported. UI/агент должны объяснить недостающий adapter, а не показывать фиктивный успех. File import/export через host agent разрешён внутри project root; пользовательский native file chooser может выбрать другой файл. Remote MCP не видит автоматически файловую систему клиента: upload/streaming adapter проектируется отдельно.

## Проверки и ограничения объёма

Из `app/`:

```text
npm test
npm run build
node tools/test-database-live.mjs
node tools/test-database-live.mjs --ui
node tools/test-database-live.mjs --ui --packaged
```

Harness требует PostgreSQL binaries (`WORKBENCH_PG_BIN`, `PGBIN` либо обнаруженный путь). Он создаёт собственный временный cluster с random credentials и loopback port, не подключается к рабочей БД/службе и удаляет свой cluster после теста. Последняя команда требует готовый `release/win-unpacked`.

На macOS/Node 22.23.3 прошли 43 live engine/file/MCP/service сценария, включая 100k result rows, 72.9 MB CSV/300k COPY rows, ~128 MiB export, rollback, TLS/schema validation, bounded composite/cross-schema/self FK graph, потерю COMMIT, restart/offline/target, сохранённую версию процедур и отказ/тайм-аут проверки состояния перед выходом. Отдельный настоящий stdio worker обработал/экспортировал ~128 MiB при old-space cap 64 MiB / semi-space 4 MiB. Это стресс-проверка worker, не обещание такой же RAM всего desktop/IDE.

25 живых Electron сценариев проверяют UI/IPC/stdio MCP/реальный PostgreSQL, клавиатуру grid, отсутствие дубликатов редактора, настоящий DDL, два окна, сохранение при закрытии, запрет нового окна во время Quit и сохранность открытой ручной транзакции. Повтор после проверки идентичности страницы прошёл одновременно с PostgreSQL-нагрузкой. Отрицательный контроль проверяет, что async predicate со значением false не считается успехом. В установленном Playwright `waitForFunction` проверял немедленную truthiness Promise; harness теперь дожидается async результата на Node-стороне. Прежние исторические отчёты не превращать в более сильную проверку задним числом.

Windows run [38500965402](https://github.com/wuller1/gigacode-workbench/actions/runs/38500965402) на `396be5b` успешен: 35 PostgreSQL + 15 source desktop + 15 packaged desktop, IDE/languages и упаковка. Это версия до нынешних ER/metadata/routine/close исправлений; исходные отчёты с hashes сохранены в `evidence/database-windows-396be5b/`. Новая Windows-проверка текущего кода требуется отдельно. Точные версии, measured heap, names и SHA-256 находятся в `evidence/database-runtime-*.json`.

Пределы встроенного provider: 4 jobs и 32 физических sessions на подключение, 2 GiB spool, 8 MiB входящий PostgreSQL message, 3 MiB UI page, SQL/params до 2 MiB, до 1000 staged rows; context preview значительно меньше. Большое значение ограничивается до буферизации драйвером; потерянная session получает unknown. Remote MCP должен отдельно подтвердить свои limits и совместимость DTO; локальная конфигурация не навязывает ему этот набор PostgreSQL-возможностей. Это не проверка файлов 10 GB и не замена chunked LOB editor. Очистка результатов доступна адресно, а автоматическая retention/архивная политика ещё нужна.
