# Полный макет перед реализацией

После критики компактные группы инструментов отображаются вкладками, сохраняя исходное разбиение и состояние. Дополнительные нижние панели раскрываются по необходимости. Объект передаётся агенту как снимаемое вложение с просмотром снимка данных; очередь фиксирует его версию. [Причины и проверки](UX-AUDIT-2026-10-13.md).

Ревизия: **full-flow-r2**, 13 октября 2026. Статус: **design_in_progress**, согласование не получено.

Прямое указание пользователя: до полного макета и его согласования не реализовывать приложение. Изменения относятся к `design/`, дизайн-источникам и инструкциям. Предыдущие изменения `app/` не откатываются, но новые runtime-возможности на этом этапе не добавляются. Положительная оценка отдельного экрана не является разрешением на реализацию всего suite.

## Что именно считается полным макетом

Полнота оценивается по сценариям, а не количеству кнопок. У каждой функции должны быть вход из обычного экрана, контекст проекта/задачи/разговора, основные действия, результат, отмена/выход, ошибки и восстановление. Нативный системный диалог, внешний API, CLI, JDBC и инструменты ОС допустимо моделировать, но только с явной пометкой. Успех fixture не доказывает реальную интеграцию.

Макет должен показать все основные пользовательские потоки по согласованным функциям; это не обещание точной копии всех плагинов IntelliJ, DataGrip, Jira или OpenShift. Обнаруженная функция без продуманного сценария остаётся незакрытым пунктом, а не исчезает из scope.

## Канонический порядок интерфейса

- Проект → задача → разговоры и управляемые исполнители. Роль определяет агент, ручного выбора текущей роли нет.
- Спокойная тёплая тёмная/светлая тема; собственные векторные иконки, без копирования фирменной графики конкурентов.
- Компактная полоса инструментов слева. Видимый чат можно скрыть верхней кнопкой; скрытый чат возвращается через тонкую полосу слева от рабочей области, которая становится заметнее при наведении и фокусе. Отдельной кнопки чата среди инструментов нет.
- **Проводник файлов только внутри IDE, слева и открыт по умолчанию.** Может скрываться; выбранный файл, раскрытие дерева и буферы сохраняются.
- **IDE — приоритетный текущий срез.** Java со Spring/Maven, Python и frontend описаны в [IDE-LANGUAGE-WORKFLOWS](IDE-LANGUAGE-WORKFLOWS.md). Плотный проводник, массовое переименование, перенос и extension ecosystem — в [IDE-EXTENSIONS-AND-EXPLORER](IDE-EXTENSIONS-AND-EXPLORER.md). Расширения планируются через Open VSX/корпоративный каталог; совместимость Windows подтверждается в S4-00 до выбора движка и выполнения следующих IDE-карточек. «В плане установки» не означает установленное расширение.
- Разделитель панелей меняет размеры; перетаскивание меняет расположение; фокус, активная вкладка, draft и выполнение не зависят от видимости.
- Левая панель инструментов открывает все рабочие области одновременно без ограничения «чат + один инструмент». Скрытый чат возвращается тонкой полосой слева, заметной при наведении/фокусе; заголовки панелей перетаскиваются мышью. Актуальные правила — [WORKSPACE-PANEL-LAYOUT.md](WORKSPACE-PANEL-LAYOUT.md).
- В нижней строке composer: ветка слева, автоматически выбранная роль перед моделью, объединённое значение «модель + reasoning» справа. Reasoning меняется внутри выбора модели. Контекст — цветное кольцо вокруг Send, точные данные по запросу.
- Вопросы по одному поверх интерфейса, свободный ответ доступен сразу. Отдельной постоянной панели вопросов и межагентских сообщений нет.

## Состояния каждого значимого workflow

Рабочее состояние; пустое пространство; загрузка/частичная загрузка; отсутствие результатов поиска; ошибка параметров; отказ в доступе; неподдерживаемый MCP метод; потеря сети; устаревшие данные; внешнее изменение/конфликт; активная операция при закрытии/смене проекта; отмена до и после начала; неизвестный исход; восстановление; длинные названия и большие наборы данных.

Общие образцы состояний доступны через «Обзор макета». Они задают язык интерфейса, но не закрывают автоматически специфические сценарии каждой системы. Например, конфликт строки БД, конфликт PR и conflict страницы Knowledge требуют разных экранов.

## Приоритет проверки UX

1. Понятен ли текущий проект, задача, объект, connection и scope операции?
2. Находится ли основное действие без чтения инструкции? Есть ли безопасный выход из каждой формы?
3. Сохраняются ли draft, активный ресурс и результат при переключении? Нет ли смешения между проектами и задачами?
4. Не создаются ли лишние вкладки и дубликаты запуска? Не выдаётся ли очередь за выполняющуюся работу?
5. Нет ли горизонтального переполнения оболочки, сжатых текстов и обрезанного Send? Таблицы/код могут иметь собственный scroll.
6. Контраст, клавиатура, фокус после закрытия, labels, размер цели, reduced motion, светлая/тёмная темы.
7. Не засоряет ли основной экран диагностика? Подробности доступны по запросу без потери контекста.

## Файлы макета

Точка входа: `design/suite-workspace-prototype.html`. Модули подключены локально, внешние JS/CDN не нужны:

- `suite-prototype-shell.js` — общий lifecycle, settings, agent plan/control/context, review map;
- `suite-prototype-data-ide.js` — Data и IDE;
- `suite-prototype-ide-languages.js`, `suite-prototype-ide-explorer.js`, `suite-prototype-ide-extensions.js` — сценарии Java/Spring/Maven, Python, frontend, плотный проводник и план установки расширений поверх общего IDE-state;
- `suite-prototype-tasks-ops.js/.css` — Tracker, SCM, Operations и Knowledge;
- `suite-prototype-browser-design.js/.css` — Browser и Design/Artifacts/UI Kit;
- `suite-prototype-panels.js` — перенос терминала к четырём краям, изменение размеров и адаптация к узкому окну.

Состояние преимущественно в памяти страницы. Настоящая долговечная многопроцессная синхронизация — будущая реализация, не свойство этого HTML. Открытие второго окна показывает самостоятельный макет, не общий host. Кнопки системного окна отключены с объяснением до Electron. Демонстрационные SQL, shell, Jenkins и cluster операции не выполняются.

## Процесс согласования

Вначале закрываются найденные дефекты макета и отдельным файлом фиксируется проверка. Затем пользователь проходит итоговую ревизию и указывает, что согласовано и что исправить. До явного согласования данной ревизии `blocksRuntimeImplementation=true`. После согласования план разработки использует точные экраны, действия, переходы, контракты и критерии; повторное придумывание UX слабой моделью не требуется.

### Анимации в удалённой среде

В общих настройках режим «Всегда · для ВАРМ» включён по умолчанию. Режим «Как в системе» и явное «Без анимации» доступны отдельно. Критические индикаторы и курсор имеют резервную отрисовку при отключённых CSS animations; диагностическая имитация не изменяет настройки ОС. См. [REMOTE-DESKTOP-MOTION](REMOTE-DESKTOP-MOTION.md).
