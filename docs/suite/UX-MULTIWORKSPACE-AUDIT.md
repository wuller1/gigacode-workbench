# Аудит UX: несколько проектов, общие подключения и панели

Дата: 2026-10-13. Статус: прототип, требуется согласование пользователя до реализации UI в app/.
Это критический разбор текущего макета и обязательные условия реализации, не заявление о готовности backend.

## Вердикт

Макет стал визуально спокойнее, но пока не готов служить доказательством бесшовной работы. Самые серьёзные недостатки — демонстрационное состояние вместо изолированных проектов, несогласованные индикаторы и слишком много функций без полноценных состояний ошибки/восстановления. Нельзя считать успехом только отсутствие исключений JavaScript.

## Переиспользование подключений

Connection: стабильный ID, тип, MCP transport/address, ссылка на секрет в vault, trust/certificate profile, capabilities, health, revision. На весь Workbench один реестр. Секреты не копировать в проект, Git, макет или экспорт.
ProjectBinding: projectId, connectionId, alias, environment, resource scope (cluster/namespace, database/schema, Jenkins folder, forge workspace/repo, knowledge space), defaults, revision. Связь многие-ко-многим для всех интеграций, включая Sprut.
ExecutionContext: projectId/taskId/sessionId/connectionId/bindingRevision/resource target. Фиксировать при постановке действия в очередь. Переключение текущего проекта или изменение default не перенаправляет уже поставленные команды.

Пользовательский путь: Настройки → Подключения → существующее подключение → «Использовать в проекте» → выбрать scope. Создание второго проекта предлагает совместимые существующие подключения. Изменение общего адреса/учётной записи показывает затрагиваемые проекты. Удаление привязки не удаляет само подключение. Disconnect не отменяет чужую транзакцию. Удаление используемого подключения показывает конкретные активные операции и предлагает сначала отвязать/дождаться; не делать скрытую отмену.

DB: общий credential pool допустим, но SQL-console/transaction/session settings изолированы. OpenShift/k8s: namespace/context передавать явно в каждом действии, не менять глобальный kube context. Jenkins/forge: folder/workspace/repository указывать в запросе, исключить fallback к первому доступному.
МCP без параллельной работы/с изменяемым состоянием получает отдельный клиент на execution scope или сериализацию с явно восстановленным контекстом. Проверить реальные capabilities адаптера.

## Панели и окна

Основной режим: чат слева, выбранный инструмент справа. Дополнительные пресеты: чат + diff; чат + SQL/результат; браузер + код; диагностика (чат, приложение, логи); обзор фоновых задач. Не открывать всё сразу. Инструмент открывается в последней подходящей группе, не создаёт дубликат ресурса. Заголовки перетаскиваются, зоны drop видны только во время drag. Разделитель меняет размеры; двойной клик возвращает разумный баланс. Сохранять layout по проекту и окну, предлагать сброс.

На узком окне использовать вертикальное размещение; не сжимать элементы управления до нечитаемых размеров. Если обе панели ниже минимального размера, предложить вкладки/отдельное окно. Фокус-режим одной панели обратим и не закрывает остальные.

Отдельные окна: windowId и независимый selectedProject/task/resource. Общий host владеет CLI, MCP, terminal processes и DB operations. Подписки с sequence/revision и snapshot+delta после разрыва; идемпотентные команды. Один resourceId открывается в нескольких представлениях без нового запуска. Browser WebContentsView нельзя одновременно прикрепить к двум окнам: переносить владельца с явной заглушкой в старом месте или открывать отдельную вкладку по выбору, не притворяться зеркалом. Не менять partition авторизации при переносе. После отключения монитора возвращать окна в доступную область. Unsaved drafts сохраняются; конфликты редактирования не теряются.

## Курсор агента

Источник — события настоящего tool runner: sessionId, agentId, actionId, surfaceId, windowId/tabId, sequence, viewport revision, phase, target bounds/coordinates, result. Нужны pending/acting/succeeded/failed; подсветка клика не означает успех. API/MCP-действия без экранной цели показывать компактным статусом ресурса, не придумывать курсор.

Позиции в CSS-pixels целевой поверхности; учитывать scroll, zoom, DPI, responsive viewport, iframe offsets и перенос окна. Устаревшую геометрию не использовать. Overlay pointer-events:none, вне DOM страницы там, где возможно. Для Electron native view обычный renderer overlay может оказаться под WebContentsView: проверить реальный compositor и выбрать отдельный доверенный overlay/поддержанный механизм без перехвата ввода. Не вводить привилегированный preload в сторонние страницы ради курсора.

Курсор с именем агента, короткая подсветка цели/клика; без вечного движения. Reduced motion отключает перемещение/пульс, оставляет статичный маркер. В inactive tab/window не красть фокус; показывать индикатор фоновой работы и переход к месту действия. Одновременно один агент управляет конкретной поверхностью (lease), остальные ждут или получают другую. Ручное взаимодействие пользователя приостанавливает автоматический ввод в этой поверхности; понятные «Продолжить»/«Остановить». Не логировать пароли/введённые секреты; чистые screenshot artifacts по умолчанию без маркера, replay/debug может включать его.

## Этапы, без переписывания лучшего существующего решения

1. До UI runtime: согласовать парные панели и bindings в прототипе. Сравнить существующий рабочий код пользователя с контрактами, показать аргументы и спросить при конкурирующих подходах.
2. Общий connection registry + project bindings и immutable execution context. Миграция существующих настроек с резервной копией, dry-run diff и проверкой scopes.
3. Единый host lifecycle и подписки нескольких окон, сохранение draft/layout/active resource. Затем dock/split/detach без повторного запуска процессов.
4. События действий, курсор агента и контроль владения поверхностью; сначала Browser, затем IDE/Data/Operations по реальным capabilities.
5. Live regression: два проекта + два окна + два агента; никаких перекрёстных данных, самопроизвольного focus или повторных операций.

## Приёмка

- Два проекта используют одно подключение OpenShift, разные namespace: команды приходят в правильный namespace после 20 переключений проекта во время исполнения.
- Две SQL-консоли с общей учётной записью: транзакция/rollback одной не затрагивает другую; результаты маркированы project/target.
- Отмена диалога bindings не сохраняет изменения; изменение общего подключения показывает всех потребителей; binding removal не удаляет connection.
- Чат + браузер при 1440×900 и 1024×768; divider мышью и клавиатурой, drag заголовка; 200% масштаб, светлая/тёмная темы, reduced motion; отсутствие недоступных кнопок/горизонтального overflow страницы.
- Второе окно, закрытие первого, restart renderer, временная потеря IPC и unplug monitor: run не дублируется/не исчезает, выбранная вкладка и черновик восстановлены.
- Курсор совпадает с target при zoom 80/125/200%, DPI 100/150/200%, iframe, scroll и resize; out-of-order events игнорируются; никаких кликов от самой визуализации.
- Вся проверка Windows/Electron с реальными MCP остаётся обязательной: localhost HTML этого не доказывает.

## Проверено в этой итерации

В localhost-прототипе проверены: открытие парного режима, изменение divider с клавиатуры (45 → 50), перестановка сторон через меню, сохранение OpenShift binding для второго проекта, отмена несохранённого изменения. Первый визуальный проход выявил неверное направление flex в неактивной browser view; исправлено, повторно просмотрено. JS синтаксис и git diff --check проходят. Drag, отдельные окна, малый viewport/масштаб и Windows/Electron пока не подтверждены этой проверкой; критерии выше остаются открытыми.
