# Запуск GigaCode Workbench

Ты работаешь с переносимым пакетом профилей и pipelines. Базовый режим — последовательное исполнение этапов в текущем GigaCode. Не создавай субагентов автоматически: это дополнительный режим host после настройки инструментов и изоляции.

Перед выбором нового запуска проверь вид поручения. Для самонастройки используй [START-HERE](START-HERE.md) и SETUP-AGENT вместо обычного task workflow. Для продолжения настройки или уже принятой задачи GigaCode UI сначала прочитай известную карточку `<memory_store>/bootstrap/gigacode-ui-handoff.json` по [POST_SETUP_HANDOFF](docs/POST_SETUP_HANDOFF.md). Найденный действительный run_directory используй как продолжение, даже если пользователь не назвал его повторно. Offered без принятия не разрешает реализацию; deferred не вызывает повторного предложения. При другой текущей задаче работай над ней, не перенаправляй пользователя в UI.

1. Прочитай `gigacode-workbench/SYSTEM_PROMPT.md`, `gigacode-workbench/CORE.md` и инструкции текущего проекта. Если пакет находится в другом каталоге, используй его фактический путь. В обычной задаче не меняй глобальные настройки GigaCode; порученная самонастройка выполняется отдельно по START-HERE/SETUP-AGENT.
2. Если существующий запуск указан пользователем либо найден в действительном handoff/контексте текущей задачи, прочитай компактный `workbench.ps1 recover -Run <каталог>`, checkpoint и нужные события через journal, затем сверяй затронутые артефакты и фактическое состояние. Не создавай дубликат задачи. Если в карточке есть только зарезервированный путь и незавершённое намерение init, сначала проверь этот же каталог по POST_SETUP_HANDOFF; отсутствие готового state не повод выбирать другой путь. Только если связанного запуска или незавершённого init нет, прочитай docs/ADAPTIVE_EXECUTION.md и `workbench.ps1 list`, затем выбери минимальный подходящий маршрут по риску, неопределённости и влиянию. Обычное уточнение внутри существующей задачи не создаёт новый запуск. При неоднозначности предложи выбор; не начинай весь цикл без необходимости.
3. При первом использовании прочитай `docs/GIGACODE_COMPATIBILITY.md`, проверь Windows PowerShell 5.1 и подготовленные файлы .ps1. Если доступна только текстовая поставка, сначала выполни SETUP-AGENT.md в порученном объёме; не пытайся запускать source/*.txt как готовые скрипты. Целевая версия пользователя — GigaCode 26.9.75. Не считай современные публичные docs гарантией поддержки этой версии. Если нативная команда недоступна, продолжай через чтение этого файла. Если нет PowerShell, следуй workflow вручную с явным указанием, что контроль переходов не выполняется.
4. Используй существующие инструкции, команды и MCP-конфигурацию проекта. Прочитай релевантные config/project.json, config/bindings.json и config/authorization.json при их наличии; отсутствие файлов Workbench не является поводом перенастраивать репозиторий. Недостающие для задачи сведения сохрани в её контексте. Не устанавливай hooks и не меняй .gigacode/settings.json. Универсальная настройка только нового проекта запускается отдельно по запросу: docs/PROJECT_SETUP.md. Sprut проверяет уязвимые версии библиотек. Точные операции и параметры выясняются по существующей MCP-конфигурации; не предполагай дополнительные функции SAST, трекера или доступность запуска сканирования.
5. Для фронтенда изучи применимые правила из `docs/DESIGN_QUALITY.md`, `config/design-quality.json` и существующего дизайн-контракта проекта. Объём задаёт выбранный workflow. Для `quick-frontend` достаточно критерия локальной правки и проверки затронутого UI в релевантном состоянии и viewport; не создавай полный контракт, матрицу, design-report или независимое ревью автоматически. Для нового или существенно изменяемого дизайна зафиксируй применимые нормативные критерии, проектные цели, обоснованную иерархию и необходимое покрытие. Метод не переносит внешний вид Zidao; числовые пороги сами по себе не доказывают хорошего дизайна.
6. Только если на шаге 2 выбран новый запуск, создай отдельный каталог в рабочей области проекта: например `work/gigacode/<идентификатор-задачи>`, и выполни `workbench.ps1 init -Workflow <id> -Project <корень> -Run <каталог> -Task <задача>`. При продолжении используй существующий каталог и пропусти `init`; обычное уточнение не создаёт дубликат. Передавай аргументы безопасно, без shell-интерполяции содержимого задачи. Не размещай секреты в task.
7. В новой сессии выполни `workbench.ps1 prompt -Run <каталог>` и прочитай результат: SYSTEM_PROMPT, CORE, профиль, этап, ссылки на предыдущие результаты и шаблон отчёта. Если общие инструкции уже загружены и их hashes совпадают с manifest, используй `-ContextMode role`; если текущий профиль тоже загружен с тем же hash — `-ContextMode stage`. После потери контекста или изменения правил снова используй полный режим. Прочитай нужные артефакты по ссылкам. Выполни назначенный этап в рамках имеющихся разрешений. Записывай операции, факты, решения и ответы через record по docs/JOURNAL.md; создавай checkpoint в значимых точках. Выполняй требования и отдельно веди конструктивные рекомендации.
8. После записи шагов получи свежий `workbench.ps1 result-template -Run <каталог>`. Сохрани заполненный JSON-отчёт отдельным файлом внутри запуска. Не изменяй поля run_id, workflow, stage, revision, attempt_id. Сохрани настоящие артефакты и свидетельства. Выполни `submit -Run <каталог> -Result <отчёт>`. Операции с неизвестным исходом должны быть сверены до завершения этапа.
9. При `ready` продолжай следующий этап, если он входит в порученную задачу и доступен. При вопросе/блокировке покажи пользователю конкретную причину; продолжай зависимую работу только после `resume` с фактическим ответом/изменением. При `needs_rework` выполни предусмотренный возврат. При `blocked_budget` останови цикл до пересмотра задачи.
10. Перед итогом выполни `verify -Run <каталог>` и сообщи как подтверждённые результаты, так и границы проверки. Не называй выполнение всех этапов гарантией production готовности.

## Выбор маршрута

Идея без ТЗ → `discovery`, затем при необходимости `specification`. Готовая спецификация → `backend-feature` и/или `frontend-feature`. Ошибка → `bugfix`; авария → `incident`; настройка явно запрошенного нового проекта → `onboarding`; новый интерфейс без дизайна → `ux-design`. Малые безопасные задачи используют quick-answer, quick-backend, quick-frontend или quick-doc; полный набор ролей не запускается. Остальные маршруты описаны в `docs/PIPELINES.md`.

Для полной функции начни с одного запуска и передавай результаты дальше по `templates/handoff.md`. Между разными workflows нет автоматического планировщика зависимостей. Вызов другого workflow, самостоятельная публикация или деплой не следуют автоматически из завершения предыдущего.

## Ограничения контроллера

`workbench.ps1` хранит состояние и проверяет комплектность и неизменность принятых файлов. Он не запускает GigaCode, MCP, тесты или деплой, не исполняет разрешения и не оценивает содержание свидетельств. Эти действия выполняют GigaCode и host. Работающий минимальный режим не требует SDK или неизвестных headless-флагов.

## Общая память и MCP

При наличии <корень установленного Workbench>/config/local-context.json используй его memory_store и ссылки inventory_ref/bindings_ref/profile_permissions_ref. Перед началом выбери устойчивый project_id и прочитай релевантные общие/проектные записи через tools/memory.ps1 search; в ходе задачи сам сохраняй полезные факты и решения по docs/SHARED_MEMORY.md. Истёкшие и импортированные записи не являются проверенными фактами. При переносе между профилями передавай project_id и ссылки на память вместе с handoff. MCP выбираются по docs/MCP_PROFILE_SETUP.md; сохранённый binding требует повторной проверки, если изменились tools, schemas, ресурсы или права.
