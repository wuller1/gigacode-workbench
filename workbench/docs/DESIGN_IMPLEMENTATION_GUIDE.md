# Дизайн GigaCode UI: инструкция для реализации небольшими шагами

Это самостоятельная визуальная спецификация для существующего личного Electron-приложения: тёплая нейтральная светлая тема, угольная тёмная, компактная навигация и центральный разговор как рабочий редактор. Режим — `personal_fast`. Здесь предложены собственные цвета, размеры и поведение; это не копия Codex, Claude, Linear или Zidao. [UI_REFERENCES.md](UI_REFERENCES.md) объясняет отдельные приёмы; внешние картинки не нужны для применения этой инструкции.

Приведённые значения — **проектная стартовая спецификация**, пока не сверенная с настоящим приложением пользователя. Это не готовая реализация и не утверждение, что дизайн уже принят или проверен. Используй существующие компоненты и состояние; сначала перенеси один согласованный экран. Отличие от работающего приложения фиксируй как осмысленную delta, а не повод переписывать весь UI. CLI остаётся неизменным; возможности интерфейса ограничены реально подтверждёнными API.

## Происхождение материалов и права

Личный режим не отменяет требования пользователя соблюдать права. Токены и композиция этого руководства заданы самостоятельно: из референсов извлекаются общие приёмы организации работы. Знакомая схема sidebar + рабочая область + нижний ввод проектируется своими средствами под собственные задачи. Не переносить в приложение чужие screenshots, иллюстрации, логотипы, фирменные иконки, тексты и узнаваемую композицию целиком; не выдавать приложение за продукт другого автора. Внешний screenshot остаётся ссылкой для анализа, а не фоном, asset или материалом для обводки. Подробный порядок — [ASSET_RIGHTS.md](ASSET_RIGHTS.md).

Перед **первым добавлением** стороннего компонента, набора иконок, иллюстрации или шрифта сохрани в существующей записи зависимостей/материалов: конкретный источник и автора; package/version или commit и hash взятых файлов; точное название/версию лицензии либо текст предоставленного разрешения и ссылку/путь к нему; разрешённое применение; обязательные attribution, copyright/NOTICE и место их сохранения. Если одна лицензия явно покрывает весь неизменённый набор, достаточно одной записи на набор, без карточки на каждую иконку. Выполни условия до включения материала. Атрибуция сама по себе не заменяет разрешение.

Проверь охват лицензии: вложенные fonts, photos, demo assets, screenshots, trademarks и заимствованные иконки могут иметь отдельные условия. Публичный репозиторий или корневой LICENSE не доказывает права на каждый его материал; прочитай соответствующие notices/лицензии выбранных файлов и включаемых зависимостей. Отсутствие подтверждённых прав означает «не включать этот материал»: выбери собственный простой элемент или проверенный разрешённый набор и продолжай задачу. [GitHub: лицензирование репозитория](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)

В приведённом font stack используется **имя установленного системного шрифта**, без включения font binary в приложение. Не извлекай и не упаковывай файлы шрифтов из ОС или другого приложения; наличие на диске не подтверждает право распространения. Для bundling/webfont нужна отдельная проверка условий именно выбранных файлов. Microsoft отдельно различает указание имени Windows-шрифта в CSS и распространение его файла. [Microsoft: Font redistribution FAQ](https://learn.microsoft.com/en-us/typography/fonts/font-faq)

Проверку прав переиспользуй для тех же dependency/version/hash, лицензии и способа применения. Повторять её нужно при их изменении или новой информации о происхождении, а не после каждой CSS-правки. В task packet передавай ссылку на уже проверенную запись, не все тексты лицензий. Этот документ не сертифицирует права на ещё не выбранные материалы.

## 1. Какой экран строим первым

Первый результат: пользователь выбирает задачу в левой навигации, читает обсуждение, пишет следующий запрос и открывает план, изменения, проверки или связанный материал, не теряя место чтения и черновик. Актуальное размещение определено в [CHAT_FIRST_DESIGN.md](CHAT_FIRST_DESIGN.md): sidebar → один компактный header → conversation → composer с ролью и моделью. Постоянной полосы task tabs нет. Справа узкий rail инструментов: план задачи, browser, terminal, материалы, проверки и исполнители. Несколько вкладок и drag-and-drop входят в M3. [TASK_WORKSPACE.md](TASK_WORKSPACE.md) задаёт связь представлений с задачей. Не добавляй dashboard и пустые вкладки будущих функций.

Иерархия: **содержимое задачи → действие пользователя → состояние работы → служебные детали**. Заголовок задачи и результат заметнее имени модели. Центральная область похожа на редактор: общая ось текста, свободные промежутки, один читаемый поток без рамки вокруг каждого ответа. Tool-вызовы по умолчанию свёрнуты в строки. Статусы читаются словами; цветная заливка нужна для требующего внимания события, а не для каждой metadata. Самостоятельные блоки оставь для composer, permission и материала; никаких рядов одинаковых badges и dashboard-плиток. Собственные иконки заданы в [ICON_LIBRARY.md](ICON_LIBRARY.md), состояния и движение — в [GRAPHICS_AND_MOTION.md](GRAPHICS_AND_MOTION.md); чужие наборы не подключать вместо них.

До правки открой настоящий экран, запиши build/revision, CSS viewport, тему и выбранный сценарий. Сохрани один baseline screenshot и наблюдаемые проблемы. Если приложения нет, можно подготовить спецификацию/прототип, но нельзя завершить приёмку live UI. Подробный порядок — в [GIGACODE_UI_DEVELOPMENT_PLAN.md](GIGACODE_UI_DEVELOPMENT_PLAN.md).

## 3. Контраст: рассчитанная часть и границы доказательства

Отношения ниже **рассчитаны для JSON-пар** по sRGB luminance; это не измерение приложения. Для каждой роли взят худший из шести общих фонов canvas/surface/subtle/raised/hover/selected; для статусов — только именованная пара. Округление здесь для чтения, сравнение с порогом выполнялось до округления. Все 22 значения таблицы дополнительно совпали с независимым расчётом десятичной арифметикой с точностью 50 знаков; отдельно проверена пара onAccent/accentHover.

| Пара / худшая общая поверхность | Light | Dark |
|---|---:|---:|
| text / общие поверхности | 12.31:1 | 9.64:1 |
| textSecondary / общие поверхности | 6.16:1 | 7.06:1 |
| textMuted / общие поверхности | 4.55:1 | 5.32:1 |
| accent / общие поверхности | 9.70:1 | 7.20:1 |
| borderControl / общие поверхности | 3.12:1 | 3.50:1 |
| focus / общие поверхности | 6.19:1 | 6.36:1 |
| onAccent / accent | 11.29:1 | 10.08:1 |
| successText / successBg | 6.85:1 | 6.70:1 |
| warningText / warningBg | 6.31:1 | 6.92:1 |
| errorText / errorBg | 6.18:1 | 6.62:1 |
| infoText / infoBg | 6.27:1 | 7.13:1 |

Дополнительная hover-пара `onAccent / accentHover`: light **13.97:1**, dark **12.15:1**. Минимальный light textMuted имеет небольшой запас над 4.5: не ослаблять его opacity и не переносить на непроверенный фон.

Для воспроизведения: нормализуй канал `c = byte/255`; linear = `c/12.92` при `c ≤ 0.04045`, иначе `((c+0.055)/1.055)^2.4`; `L = 0.2126R + 0.7152G + 0.0722B`; ratio = `(max(L1,L2)+0.05)/(min(L1,L2)+0.05)`. Используй имеющийся `DesignMetrics.contrastRgb`, описанный в [DESIGN_QUALITY.md](DESIGN_QUALITY.md); не оценивай контраст на глаз или по тексту скриншота.

Обычный текст требует 4.5:1, необходимая графика/признаки компонентов — применимого 3:1; условия и исключения собраны в DESIGN_QUALITY. Например, 4.499 не проходит 4.5. Наши 13–18 px проверяются как обычный текст. Предложенные размеры 13–15 px не являются WCAG-нормой. [WCAG: контраст текста](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

Focus recipe: непрозрачное кольцо `focus` толщиной 2 с offset 2 на общей поверхности; не обрезать overflow контейнера. Это проектный рецепт, не доказательство полной доступности. На accent-кнопке зазор показывает окружающую поверхность; на statusBg, картинке, overlay или ином фоне пару пересчитать. Ссылки в тексте подчёркивать: одного accent недостаточно для различения. Hover/disabled не делать общей opacity, которая незаметно снижает контраст всех надписей; disabled обозначать недоступностью и объяснением.

## 4. Геометрия окна и переключение областей

Опирайся на **измеренный CSS viewport**, а не разрешение монитора. Предлагаемые размеры окна для baseline: 1440×900 и 1280×800; компактный проход — 960×720. Это размеры проверки, не запрет на меньший viewport. Собственные window controls и drag/no-drag зоны согласуй с [DESKTOP_STATE_AND_CHROME.md](DESKTOP_STATE_AND_CHROME.md): интерактивные элементы не попадают в область перетаскивания окна, стандартный menu bar не возвращается ради layout.

| Доступная ширина W | Sidebar | Центр | Inspector |
|---|---|---|---|
| W ≥ 1080 | 224; изменение пользователем 208–296 | Остаток; conversation max-width 800, по центру | 340 по умолчанию; 320–520 с учётом оставшегося места |
| 760 < W < 1080 | 224; допускается сворачивание пользователем | Основная область | Сбоку только если помещаются minima; иначе снизу или временный полноширинный просмотр |
| W ≤ 760 | По кнопке слева, drawer до min(280, 85% W) | Вся доступная ширина; padding 16, при W < 480 — 12 | Снизу либо переключаемый вид с явным возвратом; draft и scroll сохраняются |

При wide-режиме `center = W − sidebar − inspector − right rail − фактические divider/gaps`; минимум центра 360–480 в зависимости от контента. При нехватке места инструмент показывается снизу/временным видом без перезаписи сохранённого desired layout. Не сохраняй три колонки ценой нечитаемого чата. Resizer ограничен допустимым диапазоном; закрытый inspector не резервирует место. Browser и terminal должны уметь оставаться видимыми одновременно; левый список задач никогда не становится правым inspector.

Rail справа: предлагаемая ширина 40 CSS px, собственная иконка 18–20 в кнопке 32×32, один тонкий divider, без подписей-плашек у каждой кнопки. Browser, Terminal, Materials, Checks и нужные реализованные инструменты имеют доступное имя, tooltip при hover/focus и явный focus/active indicator. Это общий tool-window приём, знакомый по IntelliJ IDEA, с нашей графикой/композицией — без заимствования её assets/брендинга. Кнопка возвращает последний dock/group/active tab данного типа; не создаёт дубликат ресурса. При нехватке высоты инструменты доступны через прокрутку/overflow menu. На узком окне rail не исчезает за краем; инструмент открывается переключаемым видом/группой, а не новой обязательной колонкой.

Header — компактное название задачи 14/20 weight 600, открытие изменений и меню самой задачи. Текущая композиция и размеры уточнены в CHAT_FIRST_DESIGN. Под ним сразу разговор: без постоянной полосы представлений и отдельной строки роли. План раскрывается в ленте и отдельной панели «План задачи»; изменения, материалы и проверки открываются в сохранённой context group. Ссылка из ленты и rail открывают тот же объект и revision, а не копию. Роль и модель размещены у composer. Кнопка проектов/задач всегда слева в chrome.

Это представления одной задачи, а не новые чаты или режимы CLI: переключение на «План» само по себе не запускает workflow и не меняет model mode. «План» — читаемый список с текущим шагом; «Изменения» — существующий diff с выбором файла; «Проверки» — строки результата/сценария/evidence. У каждого вида свои loading/empty/error и сохранённое место чтения; незавершённая реализация вида не маскируется декоративной вкладкой. Источники данных и правила сохранности — в TASK_WORKSPACE.

Conversation — единственная основная вертикальная прокрутка центра. Composer стоит снизу в layout, не перекрывает сообщения fixed-слоем; input растёт от 80 до min(240, 35% высоты viewport), затем прокручивается внутри. Область сообщения и composer имеют одну ось/максимальную ширину. При смене вида draft и фокус возврата сохраняются; видимость composer определяется сценарием workspace, а не уничтожением его состояния. Inspector/context pane прокручивается отдельно; горизонтальная прокрутка допустима внутри кода/diff/таблицы, не для всего окна.

Панели browser/terminal/tools/материала сразу поддерживают добавление, скрытие, drag-and-drop, resize, группы вкладок и сохранённую раскладку. Перемещение начинается за header/tab handle; drag из текста, кода, textarea или browser content не запускает docking. Только во время drag показывать допустимые drop zones справа/слева/снизу группы для split и в центре для tab; после drop/Escape overlays и пустые placeholders исчезают. **Постоянных кнопок «Справа»/«Снизу» нет.** При недостаточной ширине split не предлагать. Разговор и composer перемещаются как одна панель; это настройка вида, не остановка задачи.

В меню панели нужны «Скрыть» и «Переместить…» с выбором области/группы с клавиатуры; это рабочая альтернатива drag, а не подсказка «используйте мышь». «Добавить панель» открывает список реализованных типов. Скрыть/переместить ≠ остановить CLI, terminal или browser: процессы, draft, история, выбранный материал и места чтения сохраняются в своей области. Восстановление layout использует стабильные ID панелей и ограничивает размеры текущим окном. «Сбросить раскладку» выполняется только по явному действию пользователя и меняет расположение, не удаляет содержимое или задачи. Конкретная модель панелей — [PANELS_AND_IDE.md](PANELS_AND_IDE.md); специализированные IDE-функции Java/Python/React — последующий этап, не условие полезной настройки панелей сейчас.

Terminal имеет несколько вкладок со своими PTY/process IDs и Project/Task binding, «+» и выбор обнаруженной оболочки. Windows PowerShell 5.1 известен из сообщения пользователя: проверить executable/версию, не требовать pwsh 7. cmd и другие shells доступны только после probe; выбор shell profile (absolute exe, argv, cwd, env policy) создаёт новую вкладку, не меняет живую PTY. Browser допускает несколько panels/tab groups и страниц со stable tab/resource IDs; это не несколько Chrome engines или обещание импорта профилей других браузеров. «+» создаёт ресурс; switch/drag/hide/reopen только меняет представление. Общая browser partition допустима при явном разрешённом выборе profile, не как скрытое смешение разных Tasks. Input/agent action всегда адресован captured resource/Task.

Если проекту нужен min window, стартовое предложение — 760×560 в logical/DIP единицах Electron; сначала сверить текущие ограничения, не повысить минимум без необходимости. Это не освобождает от адаптации: zoom/scale может уменьшить доступный CSS viewport. Проверить используемые области до 320 CSS px с переключаемыми панелями, переносом toolbar и без потери действий; для действительно двумерного содержимого учитывать исключения из DESIGN_QUALITY.

Windows scaling 100/150/200% и zoom приложения — разные параметры. На доступной Windows-машине запиши оба, CSS viewport и devicePixelRatio; переключи scale с реальным окном, затем верни. Отдельно проверь увеличение текста/zoom до 200% без потери ввода и функций. Не объявляй Windows scaling проверенным по одному viewport эмулятора. Недоступная среда остаётся `not_run`, не требует остановки независимой разработки. [WCAG: увеличение текста](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)

## 6. Как выдать работу Flash-модели

Один проход меняет **один экран/компонент и его затронутые состояния**. Host сначала находит актуальные файлы/primitives, затем передаёт исполнителю короткий packet и только нужные строки этого руководства. Название модели не доказывает умение видеть экран; vision проверяется локально по [FLASH_MODEL_EXECUTION.md](FLASH_MODEL_EXECUTION.md). Новую библиотеку компонентов не подключать ради одного поля, если подходящий primitive уже есть.

```text
Задача: [один видимый результат], режим personal_fast, CLI не менять.
Область: [экран/компонент, разрешённые файлы], текущий build/revision: [факт].
Сохранить: [draft, выбранный чат, работающие действия и существующие контракты].
Дизайн: [только нужные token/geometry/component строки]; ссылка на исходный раздел.
Входы: [baseline screenshot + viewport/theme, текущие компоненты, state/API факты].
Материалы: [ссылки на проверенные источник/version/hash/лицензию]; новых чужих assets не брать без проверки.
Сценарии: [2–4 применимых случая], плохой случай: [конкретное нарушение].
1. Прочитай перечисленные источники; неизвестные APIs не придумывай.
2. Дай план максимум 4 действий; проверь, не добавляешь ли лишние элементы.
3. Выполни минимальную правку существующей реализации. Не меняй посторонние экраны.
4. Открой этот build. Пройди назначенные сценарии, сними геометрию и реальные screenshots.
5. Верни: изменение; measured; visual-review; unknown/not_run; evidence и версию.
Запрещено: «дизайн хороший» по score, готовность по одному mock/test или выдуманные замеры.
Без доступа к приложению: только implementation/prototype готовность, live-приёмка incomplete.
```

Порядок первых небольших заданий: (1) токены + существующая оболочка; (2) sidebar/header и контекстные представления; (3) conversation/composer и сохранность ввода; (4) реальные tool/waiting/error/approval; (5) правый rail и одна connected context group; (6) drag/tab groups, несколько browser/PTY вкладок, shell chooser и keyboard/resize. Всё это ближайший M3, без зависимости от IDE. Каждый пункт — отдельный завершённый кусок; уже рабочую часть пропустить. После максимум двух неудачных попыток сузить причину или подключить подходящего исполнителя; не запускать бесконечный круг «сделай красивее».

Короткий prompt визуального ревью: «Сравни реальные before/after при одинаковых условиях с целью [X]. Найди максимум 5 конкретных препятствий: место → наблюдение → последствие → исправление. Проверь иерархию, ритм, читаемость и следующий шаг. Отличай наблюдаемое от предположения. Числа бери из measurements; поведение — из live-сценария. Не ставь общий балл и не объявляй сценарий пройденным по screenshot». Независимый проход нужен для существенного нового экрана; локальная подпись не требует отдельного агента.

## 7. Приёмка одного изменённого экрана

До запуска выбери 2–4 содержательных случая; при большем изменении добавь обоснованно необходимые, без полного произведения всех тем/размеров/статусов. Пример для composer: (C1) отправка; (C2) длинный русский draft → переключение A/B → возврат; (C3) busy/error без потери ввода; (C4) узкое окно/keyboard. Для чистой смены цвета достаточно затронутых пар и реального состояния; не повторять параллельные сессии после каждой подписи.

Фикстуры для layout: название «Проверка параллельных сессий и восстановление после отключения»; кнопка «Прекратить ожидание повторной попытки»; длинный путь с пробелами и кириллицей; абзац ответа, code block и многострочный draft. Никакой из этих текстов не должен превращать важное действие в недоступные многоточия. На 320 CSS px кнопки могут переноситься вертикально. Эталон — сохранность смысла и действий, не идентичный перенос строк между платформами.

Для новой panel system обязательно пройти две terminal tabs и две browser tabs: drag right/left/bottom/tab group → hide → reopen через rail → возврат focus/scroll/draft; process/resource IDs прежние, wrong-Task input/actions не происходят. Отдельно keyboard/context-menu fallback, исчезновение drop zones после Escape, rail/overflow на узком окне и восстановление last dock/active tab. Restart сохраняет refs/layout, а умерший PTY не объявляется живым. Это набор checks конкретного M3 изменения, не обязательный повтор после каждой опечатки.

| Проверка | Достаточное evidence для назначенной области |
|---|---|
| Геометрия | CSS viewport + bounding boxes; нет непреднамеренного горизонтального overflow, перекрытого composer/action и обрезанного важного текста; min/max ширины соблюдены либо объяснена адаптация |
| Типографика/цвет | Computed font/size/line-height, реальные непрозрачные пары и ratio; для сложного фона unknown до корректного замера. Body 15, control 14, meta 13 — проектные роли, а не единый универсальный порог |
| Действия/фокус | Реальные шаги → наблюдаемый результат; send/close/selection, Tab/Shift+Tab, открытие/закрытие меню, достижимость и видимость focus; draft/scroll сохранены там, где обещаны |
| Состояние и версия | Screenshot/короткая запись нужного перехода + build/revision + фактический выбранный чат/материал. Fixture label виден; mock-успех не подменяет реальную CLI/Live Electron интеграцию |
| Визуальная оценка | Конкретные accepted/rework/unknown для иерархии, читаемости, ритма и ясного следующего действия, с местом/наблюдением. Никакого «9/10» и автоматического aesthetic pass |

Для плотного desktop-контракта сборщику из DESIGN_QUALITY можно задать `productFontSizePx: 13` как общую нижнюю цель и отдельно проверить роли body≥15/control≥14/meta≥13; `primaryTargetPx` — 40 для pointer или 44 для принятого touch-сценария. Это явная проектная адаптация, не способ скрыть мелкий текст и не пересмотр WCAG. Сборщик даёт кандидатов, не итоговую оценку: clipping, labels/hit areas, zoom, focus и фактическую задачу проверять отдельно.

Сохрани краткий результат в существующем [design-report](../templates/design-report.md): выбранных N, выполненных K, pass/fail/unknown, условия и evidence. `0`/всё skipped не pass. Снимки только реальной проверенной версии; логи подтверждают события, но не видимость UI. Baseline обновляется после разбора отличий, не автоматически ради зелёного diff. Новый/изменённый detector проверь на clean/bad/empty fixture; неизменившийся измеритель не требует полного повторного цикла на каждой задаче.
