# Рабочий интерфейс с центральным разговором

Принятое направление: привычная по Claude и Codex организация рабочего инструмента — постоянная левая навигация, спокойная центральная колонка разговора и инструменты по запросу. Внешность, токены и иконки собственные. Это инструкция для реализации в существующем GigaCode UI, а не готовый Electron-клиент. Она уточняет размещение из [DESIGN_IMPLEMENTATION_GUIDE](DESIGN_IMPLEMENTATION_GUIDE.md); смысл сущностей определяет [TASK_WORKSPACE](TASK_WORKSPACE.md).

## 1. Композиция и неизменные места

| Область | Что находится | Чего здесь не должно быть |
|---|---|---|
| Верх слева, над навигацией | Название приложения, кнопка свернуть/открыть левую навигацию | Кнопка задач справа от заголовка текущей задачи |
| Левая колонка | Новая задача, поиск, проекты с вложенными задачами, настройки внизу | Отдельный глобальный список ролей, конкурирующий со списком задач |
| Заголовок рабочей области | Название выбранной задачи, открыть изменения, меню действий задачи | Постоянные строки роли, состояния, вкладок, повторяющие друг друга |
| Центр | Разговор, компактные tool rows, раскрываемый план, рекомендации, ссылки на результаты; текущий вопрос поверх разговора | Dashboard, ряд KPI, процент готовности без измерения, постоянная панель вопросов |
| Нижняя часть центра | Composer, роль и модель данного хода, отправка/очередь/остановка, сведения о reasoning и контексте | Глобальные настройки роли, случайно меняющие все задачи |
| Правый узкий rail | Browser, terminal, материалы, проверки, исполнители, добавить панель | Проекты, навигация между задачами и отдельная иконка Questions |
| Открытые панели | Настоящие связанные материалы, diff, checks, browser, terminal, managed workers | Декоративные «работающие» инструменты или выдуманные результаты тестов |

На старте инструментальные панели закрыты, пустого зарезервированного места нет. Вся навигация между задачами живёт слева. Кнопка раскрытия остаётся на той же стороне при любом размере окна. В узком окне открывается левый drawer поверх содержимого с доступным закрытием/Escape и возвратом фокуса; заголовок и список задач не перестраиваются в горизонтальную вторую страницу. В реальном приложении drawer получает корректное управление фокусом и делает недоступными перекрытые элементы; снимок макета этого сам по себе не доказывает.

Начальное широкое окно: sidebar 224 CSS px (208–296 регулируется), rail 38–40, conversation max-width 800, внутренний padding 24–32. Header задачи около 52–56, custom chrome около 40–42. Title 14/20 semibold, основной текст 15/24, metadata 12–13/18. Разговор и composer стоят на одной оси. Primary action — круглая нейтральная кнопка 32–40; внешняя область клика расширяется для touch. Эти числа — выбранные параметры продукта, не утверждение о размерах Claude/Codex. Контраст и функциональные минимумы остаются из DESIGN_QUALITY.

## 2. Проект и задачи

Проект раскрывается, название и папка доступны с клавиатуры. Создание задачи из проекта автоматически заполняет projectId; глобальная «Новая задача» использует выбранный проект и позволяет выбрать другой. Не спрашивать заново путь уже известного проекта. Роль не создаёт вложенную пользовательскую задачу: Project → Task → RoleAssignments, AgentTasks и Runs. Развилка обсуждения по явному действию пользователя создаёт отдельную Task с parentTaskId и выбранной границей истории; работа текущей роли этого не делает.

Задачи показывать компактными строками. Второй строкой — только полезное состояние: требуется ответ, 429, ошибка, активная работа, непрочитанный результат. Не повторять «Готова/Локальная/Личный режим» на каждой строке. Состояние задания не равно состоянию видимого окна. Переключение и закрытие навигации не останавливают выполнение, не создают сессию, не меняют текущий адрес инструмента.

Сохранять отдельно на Task: draft и attachments, место чтения, открытый материал/его версия, выбранная роль/модель и ожидающие изменения, очередь ввода, связанные panel/resource IDs. Глобально сохранять размеры/порядок панелей отдельно от этих данных. Строка задачи не должна менять сортировку на каждом streaming token: перенос вверх после смыслового события/по настройке, сохраняя цель клика.

## 3. Разговор как основное рабочее место

Ответы на открытой поверхности; сообщение пользователя — спокойный блок без аватара, рамки и ряда badges. Автор и роль могут быть одной краткой строкой. Текст результата важнее служебной хронологии. Tool calls свернуть в осмысленные строки «Прочитал 3 файла», «Проверяет отмену»; агрегировать только реально подтверждённые события и оставлять раскрытие к исходным данным. Не превращать скрытые chain-of-thought в лог; журналировать действия, аргументы в безопасном виде, результаты, решения и доказательства.

План раскрывается непосредственно в ленте и доступен через меню задачи. Изменения, проверки и документы открываются в контекстной панели, сохраняя разговор и ввод. Постоянная полоса «Обсуждение / План / Изменения / Проверки» не нужна. У этих объектов единые IDs и источники состояния: ссылка в сообщении и панель показывают один и тот же artifact/check, а не независимые копии Markdown.

На узком окне допустим временный полноширинный просмотр с явным возвратом в чат; draft/selection/scroll не уничтожаются. Условие перехода определяется доступными ширинами, а не маркой монитора. В расширенном режиме инструменты могут располагаться сбоку и снизу одновременно. Скрытие inspector не сбрасывает место чтения обсуждения.

Ассистент рекомендует улучшение рядом с затронутым решением: причина, польза, риск, способ проверки, входит ли в разрешённую задачу. Неблокирующая рекомендация не должна превращаться в обязательный вопрос и задерживать работу. Вопрос текущей Task открывается **overlay поверх разговора**, с вариантами и всегда доступным свободным ответом. Никакой отдельной панели/иконки вопросов в rail. В ленте остаются короткий anchor и unresolved count для повторного открытия по [ARTIFACTS_AND_QUESTIONS](ARTIFACTS_AND_QUESTIONS.md).

Одновременно показан один текущий вопрос; остальные — в очереди Task, без стека окон. Свернуть/Escape сохраняют draft и выбор, не отвечают за пользователя; явное открытие и закрытие корректно переводят/возвращают focus. При Task switch вопрос прежней Task сворачивается и сохраняет адресата, новая показывает только свои вопросы. Blocking статус остаётся видимым даже у свёрнутой формы; независимая работа продолжается. Настоящий tool permission имеет отдельный тип/адресный callback: generic свободный ответ не разрешает операцию. После принятого изменения требований отметить зависимые evidence как stale, не заново прогонять всё без причины.

## 4. Composer и роль

В нижней строке composer: добавить material/attachment, model, **reasoning рядом с моделью**, context, автоматически выбранную role и Git branch/worktree, затем основную кнопку Send/Stop. Context раскрывает состав и сжатие. Role — read-only chip с reason/confidence и selected/captured/actual, не selector. При узкой ширине вторичные детали уходят в popover, Send/Stop и status warnings остаются доступными. Выбор reasoning уже работает в приложении пользователя: сохранить его service/adapter и допустимые значения по [MODEL_AND_REASONING_CONTROLS](MODEL_AND_REASONING_CONTROLS.md). Подпись «нет данных» у контекста сохраняется до доказанного измерения. Не рисовать 256k/процент как факт только из пользовательского названия модели. Сжатие и восстановление — по [CONTEXT_CONTROL_AND_ERROR_RECOVERY](CONTEXT_CONTROL_AND_ERROR_RECOVERY.md).

Роль выбирает AI router из запроса, Project/Task/stage, выбранного workspace resource и ожидаемого результата. Нажатие на chip показывает основание, confidence, фактический способ применения prompt и «Посмотреть инструкции»; ручного списка ролей нет. Во время активного хода новый route остаётся pending до безопасной границы. Простая смена label не доказывает замену system prompt. Модель, reasoning, auto-role, native mode и permission policy — отдельные поля. Полный алгоритм — [ROLE_PROMPT_BINDING](ROLE_PROMPT_BINDING.md).

Idle: отправка; busy: новое сообщение можно поставить в очередь с редактированием/удалением до dispatch. Steer — только отдельное поддержанное действие с подтверждённой семантикой протокола. Stop отменяет конкретный активный turn; queue pause запрещает новые dispatch и не утверждает паузу внутри рассуждения. Неподтверждённая отмена остаётся видимой. Очередь/переход роли не отправляются вторым конкурентным prompt в ту же ACP session.

Первый Enter в composition/IME не отправляет сообщение. Shift+Enter — новая строка, shortcut выбран в настройках. Permission не получает Enter из composer. При send failure текст, attachments и идентификатор submission сохраняются; кнопка «Повторить» не создаёт дубликат, пока не определён исход предыдущей отправки.

## 5. Панели как рабочие инструменты

Browser и terminal могут быть видимы одновременно. Пример default после открытия: browser справа, terminal снизу, chat остаётся по центру. Новый terminal/browser tab создаёт ресурс; переключение существующего — только view. Вкладки можно переносить между группами, группу — за заголовок. Drag из редактора/страницы/терминального текста не перестраивает окно. Drop previews показывают результат, Escape отменяет перенос. Подробный lifecycle и работа WebContentsView — [PANELS_AND_IDE](PANELS_AND_IDE.md).

Расположение ограничивать вычисляемой шириной: sidebar + rail + side panel + chat minimum. Стартовые minima: chat 360–480 в зависимости от содержимого, side 320–360; если не помещается, показать инструмент снизу/временным видом без изменения сохранённого desired layout. Возврат к широкому окну восстанавливает намерение. Не схлопывать чат до 100 px и не переносить левую навигацию вправо ради панели.

В rail повторное открытие возвращает последнюю panel/group/tab, не новый экземпляр. Скрыть сохраняет расположение, размеры и resource IDs. Меню содержит доступную клавиатурную команду «Переместить…»; постоянных кнопок сторон нет. Tab move переносит одну вкладку, header move — группу. Прототип может показывать часть этих взаимодействий; приёмка продукта требует реальных независимых browser/PTY ресурсов и проверки каждого варианта.

Исполнители — панель текущей задачи, с parent/worker, назначением, ролью, состоянием, лимитами, уточнением поручения от пользователя, отменой, очередью и результатом. Служебный обмен между сессиями работает автоматически и не выводится в разговор или отдельную панель; технические записи доступны диагностике. Глобальный монитор по всем задачам может быть отдельным поздним видом. Он не заменяет дерево Project → Tasks. Работа managed workers определена в [MANAGED_SUBAGENTS](MANAGED_SUBAGENTS.md).

## 6. Конкретные этапы реализации и проверки

| Итерация | Малый результат | Обязательное наблюдение |
|---|---|---|
| UI1 | Левая навигация, один header и чат/composer | При 1280/960/320 CSS px нет горизонтального overflow; кнопка навигации слева; меню не уходит за экран |
| UI2 | Контекстные plan/checks/materials, одна модель данных | Открытие из чата и rail показывает тот же объект и revision; возврат не теряет draft/scroll |
| UI3 | Composer role/model/reasoning/context + очередь | Существующий reasoning перенесён; A/B имеют разные значения; busy switch показывает pending; новые неподтверждённые значения не подставлены |
| UI4 | Browser справа и terminal снизу, несколько вкладок | Оба видимы; разные resource IDs; hide/reopen/drag не дают новых процессов и не стирают ввод |
| UI5 | Пусто/работа/429/permission/неизвестный исход/ошибка; Task question overlay | Для каждого состояния есть понятный следующий шаг; вопрос сворачивается/открывается без потери ответа, queue без modal storm, A→B не меняет адресата; permission не подменён вопросом, stop не выдаёт false completed |
| UI6 | Клавиатура, темы, длинные названия и масштабы | Focus виден; overlay закрывается с возвратом фокуса; контраст измерен; Windows scale проверен на Windows |

UI1–UI6 — детализация M3/D2–D3, не второй независимый roadmap и не требование отложить D2 до полного feature set. После каждой итерации показать пользователю работающий результат и ограниченный список нерешённых проблем. Название CSS-свойства или test green не является UX-доказательством: приложить screenshot/наблюдение фактического состояния и version.

## 7. Критический обзор перед выдачей

Сначала проверь четыре частых действия: новая задача в проекте; вернуться в предыдущую и продолжить ввод; увидеть результат проверки; прекратить зависшую работу. Каждое должно быть понятно без чтения документации. Затем пройди сложные сценарии: два окна, скрытый renderer, сообщение в очереди, смена роли, несохранённый материал, неизвестный исход отправки и восстановление.

Не объявляй дизайн «хорошим» по условному score 9/10. Отчёт содержит наблюдаемые дефекты: лишняя панель, неверное место действия, потеря состояния, размер/контраст ниже выбранного порога, недоступность с клавиатуры, лишние клики и ошибочное действие. Для привычной операции стартовый target — один прямой клик/shortcut или два шага через меню; это бюджет взаимодействия, не закон доступности. Объясни сознательные исключения.

Визуальная близость достигается знакомой структурой и поведением, а не переносом брендинга или screenshot assets. Референсы и предложения по переносимым функциям — [COMPETITOR_FEATURE_PLAN](COMPETITOR_FEATURE_PLAN.md). Свои иконки лежат в assets/icons; запрещено заменять их случайным набором при каждой генерации экрана.
