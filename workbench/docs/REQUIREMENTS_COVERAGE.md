# Покрытие требований пользователя

Дата сверки: **2026-10-10**. Это матрица выраженных пользователем потребностей, сгруппированных по смыслу, а не обещание закрыть любые будущие потребности разработчика. Источник требований — поручения и последующие уточнения пользователя в этой работе. Последние уточнения имеют приоритет: аналитик помогает писать описание функциональности в выбранном формате; план ведёт агент; панели и базовый browser/terminal нужны сразу; полноценная IDE — позже; личный UI работает в personal_fast.

**Исходники настоящего приложения и целевая установка GigaCode находятся на другом компьютере и для этой проверки недоступны.** Пакет содержит инструкции, определения, переносимые источники и прототипы. Наличие документа, HTML-макета или зелёной локальной проверки не означает реализацию соответствующей функции в приложении пользователя.

## Как читать покрытие

- `specified` — найден конкретный контракт, место в плане и проверяемое условие приёмки.
- `mock-checked` — конкретный сценарий наблюдался только в макете/fixture и имеет отдельный отчёт с версией и границами. Чтение HTML/CSS не даёт этот статус; он не подтверждает real CLI/PTY/MCP или целевую ОС.
- `target-not-run` — соответствующая проверка на настоящей целевой сборке не выполнена здесь. Это не утверждение, что в пользовательском прототипе функции нет: её наличие пока не установлено.

В матрице у всех строк сейчас **контракт `specified`, целевая проверка `target-not-run`**. Отдельный отчёт о макете может подтвердить лишь перечисленные в нём взаимодействия, без повышения всей строки до приёмки приложения. Выполненные локальные проверки переносимых инструментов находятся в [VALIDATION](VALIDATION.md); их результаты не переносятся на новый native backend или Windows PowerShell 5.1 автоматически.

M0–M12 — этапы [плана разработки](GIGACODE_UI_DEVELOPMENT_PLAN.md). D0–D13 — небольшие поставки из [DELIVERY_AND_DOGFOOD_PLAN](DELIVERY_AND_DOGFOOD_PLAN.md), не второй workflow. M12 соответствует D12, optional M11 — D13. «Настройка» ниже — подготовка Workbench перед порученной разработкой, без нового искусственного milestone. Gate — условие приёмки **затронутого среза**, а не требование повторять всю матрицу после каждой опечатки.

## Границы, которые нельзя потерять при реализации

**Уточнение R11/R21/R24:** [CONTEXT_CONTROL_AND_ERROR_RECOVERY](CONTEXT_CONTROL_AND_ERROR_RECOVERY.md) связывает управление контекстом, ручную компрессию, смену модели и 400/413. M2/D2 — фактическая классификация отказа и безопасное ручное восстановление; M4/D4–D5 — подробный inspector и управление следующим pack. Gate: не любой 400 признаётся overflow, неизменный отвергнутый payload не повторяется вслепую, compress/модель применяются по реальному API на безопасной границе, исходные inputs и pending сохранены. Статус остаётся `specified` / `target-not-run`: неизвестны конкретная причина target ошибок, доступность Giga compression/usage и скрытый CLI overhead.

1. **Роль, workflow и разрешения различны.** Role prompt может улучшить поведение, но не заменяет permissions. Главная ACP-сессия, managed worker и native child — разные поверхности. Context-only — честный допустимый способ передачи задания, а не доказанный system override.
2. **Task план, queue и formal workflow связаны, но не одно состояние.** Агент адаптирует план автоматически в разрешённой задаче; очередь хранит пользовательские сообщения; formal stages/checks принимает существующий engine. Перестройка todo, смена роли или новое сообщение не обнуляют attempts, pending и обязательные проверки.
3. **Один источник истины и writer.** Question answer, artifact edit, plan delta, lifecycle command и worker candidate используют сохранённые IDs/revisions/receipts. Ни UI checkbox, ни файл на диске, ни завершение stream не завершают Task автоматически.
4. **Native перенос охватывает и старую обвязку, и новые функции.** Reference docs/assets импортируются адресно; исполняемая семантика controller/memory/validators переносится с проверкой совместимости. Новый app-код ещё не создан этой матрицей, постоянный PS bridge не финальный результат.
5. **Личный режим и масштаб проверки независимы.** personal_fast остаётся режимом пользовательского UI; риск конкретной операции задаёт достаточную проверку. Production/shared последствия учитываются для этой операции, не превращают каждую micro-задачу в большой процесс.
6. **Почтовый пакет и установленное приложение — разные поставки.** Разрешённые текстовые источники/графика не равны готовому Windows installer или лицензии на включение CLI. Подготовка скриптов не является автоматической активацией новых инструкций в уже запущенной сессии.

## Проверка согласованности и известные границы покрытия

При заключительной сверке отдельно проверены: role delivery/permissions, Task/run/CAS и pending, managed-worker queue/quota, автоматический план, questions/artifacts, M3/M4/M6 границы, personal_fast/established_strict и формат поставки. Существенное уточнение последних требований: **R16 реализуется как агентский adaptive plan**, а не только список ручных заметок или отражение жёстких этапов. Его канонический источник — TASK_TODO_PANEL; верхнеуровневые интеграционные формулировки должны ссылаться именно на этот контракт.

Эта матрица не закрывает live gates и не присваивает оценку «всё готово». Реальные неизвестные сосредоточены в исходной архитектуре приложения, Giga runtime/capabilities, Windows окружении, модельном поведении, MCP доступах и пользовательской приёмке. Их нужно превращать в небольшие probes/поставки соответствующего M/D, а не повторно исследовать весь пакет перед каждым шагом.

Не найденное в одном источнике свойство не объявлять отсутствующим во всём приложении. Если target уже реализует часть контракта, сначала подтвердить версию/поведение и переиспользовать evidence. Если новый пользовательский запрос выходит за эту матрицу, добавить принятую связь требование→контракт→gate с историей; не переписывать старые результаты и не расширять scope автоматически.

## Как обновлять отметки

Для нового свидетельства сохранить requirement ID, конкретный сценарий, source/build/runtime/OS revision, входы, observed outcome, evidence ref/hash и ограничения. UI-макет получает только `mock-checked` для наблюдённого сценария; целевой runtime остаётся `target-not-run` до своей проверки. Реальная приёмка выполняется через существующий workflow/evidence и delivery checkpoint, а не правкой текста этой таблицы на «готово».

Читать этот документ как индекс при планировании/аудите, не вставлять всю матрицу в каждый prompt. На рабочий шаг достаточно текущего requirement ID, одного канонического раздела, нужных источников и gate. Найденные стыки пользовательского пути уточняет [PRODUCT_GAP_ANALYSIS](PRODUCT_GAP_ANALYSIS.md); его solved означает достаточную спецификацию, а не implemented/pass. Docs delta и ретроспектива остаются событийными; новый экран или ответ не требует переписывать всю матрицу.
