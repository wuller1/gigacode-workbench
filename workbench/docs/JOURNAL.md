# Журнал и восстановление контекста

Системный промпт требует фиксировать рабочие шаги. Для надёжного автоматического перехвата всех вызовов полноценная оболочка должна записывать pre/post события транспорта GigaCode. В текущем интерактивном пакете `record` предоставляет явную запись; он не наблюдает чужие процессы и не может гарантировать, что агент не пропустил вызов.

## События

Каждое событие в state.json имеет sequence, state_revision, UTC time, event и details. Сохраняются все события запуска, а не только последние сообщения. Переходы pipeline пишутся автоматически. Чтения, поиски, выводы, вопросы, ответы и действия записываются через record.

Виды: observation, decision, question, answer, verification, checkpoint, action_started, action_finished, action_unknown. Для большого очищенного ответа инструмента сохраните файл в evidence/ и передайте `-Evidence` с относительным путём. Контроллер записывает его hash. Для нескольких файлов вызывайте скрипт внутри PowerShell: `& .\gigacode-workbench\workbench.ps1 record -Run <каталог> -Kind observation -Summary <текст> -Evidence @('evidence/one.json', 'evidence/two.json')`. Не передавайте массив через новый процесс `powershell -File`: используйте прямой вызов скрипта либо отдельные записи.

```sh
powershell -NoProfile -File gigacode-workbench/workbench.ps1 record -Run work/gigacode/task-001 -Kind observation -Summary 'Прочитаны действующие требования; источники в приложении' -Details work/gigacode/task-001/fact.json -Evidence evidence/requirements-read.json
```

Пример fact.json — структура пользовательских данных, не фиктивный факт:

```json
{
  "claim": "Проверенное утверждение",
  "classification": "fact",
  "source": {"type": "file", "path": "Путь источника", "revision": "Версия источника"},
  "scope": "Что именно было проверено",
  "requirement_ids": [],
  "next_step": "Что сделать дальше"
}
```

Для решения храните основание, альтернативы кратко, scope и источник согласования. Для рекомендации — proposal ID, проблему, evidence, последствия и статус proposed/accepted/deferred/rejected. Подробную внутреннюю цепочку рассуждений не сохраняйте; для восстановления нужны факты, решения и их краткое обоснование.

## Изменение с побочным эффектом

До изменения вызовите record с kind=action_started и details, содержащим target, intent, expected_result и reconcile. Дополнительно сохраните тип эффекта, authorization_ref, входные версии и параметры без секретов. Контроллер вернёт operation_id.

После действия используйте тот же operation_id:
- action_finished с outcome=verified_success, verified_not_applied или verified_failure и непустым evidence после фактической проверки;
- action_unknown, если результат не установлен.

Любой незавершённый action блокирует completed submit и rework. Отмена не удаляет pending_actions. Для сверки неизвестного исхода в заблокированном состоянии записывайте observation/verification, затем action_finished только по полученным свидетельствам.

Контроллер не выполняет само действие и не проверяет достоверность заявленного outcome. В production host запись события до отправки и сбор реального ответа выполняет адаптер, а не модель. Нельзя устранять pending фиктивным receipt.

## Checkpoint

Используйте `templates/checkpoint.md` и сохраните файл evidence либо artifacts. Привяжите его через record kind=checkpoint. Поля: задача/границы, версии, текущий этап, факты/источники, решения, выполненное, активная работа, вопросы, pending operations, разрешения, рекомендации, результаты проверок и следующий шаг.

Каждый record меняет revision. Поэтому итоговый JSON шаблон этапа получайте через result-template после записей. Старый отчёт после record закономерно отклоняется; заново прочитайте состояние и сформируйте актуальный отчёт.

## Восстановление

```sh
powershell -NoProfile -File gigacode-workbench/workbench.ps1 recover -Run work/gigacode/task-001
powershell -NoProfile -File gigacode-workbench/workbench.ps1 journal -Run work/gigacode/task-001 -After 0 -Limit 50
```

recover возвращает задачу, workflow/этап, результаты, открытые операции и последний checkpoint. По умолчанию показывает до 40 событий после checkpoint и число опущенных; journal возвращает страницы событий с next_after и has_more. Для продолжения после checkpoint используйте его journal_after_sequence. Компактный recover проверяет hashes принятых файлов, последнего checkpoint и событий после него. Полный recover -Full проверяет и выводит весь журнал для расследования/экспорта. Команды не меняют состояние и не повторяют внешние действия. Весь журнал хранится в state.json; не нужно перечитывать его целиком перед каждым шагом.

После восстановления исполнитель:
1. Читает актуальные правила, checkpoint и события после него.
2. Проверяет integrity_problems и источник изменившихся файлов.
3. Сверяет исходники, спецификацию и внешние операции с фактическим состоянием.
4. Записывает восстановленные факты, неизвестное и выбранную точку продолжения.
5. Продолжает через resume/rework только после необходимых решений.

«Полный контекст» здесь означает все сохранённые факты, решения, действия и первичные свидетельства задачи. Незаписанные события, удалённые файлы и недоступные внешние данные восстановить из ничего нельзя. Контроллер не резервирует содержимое evidence автоматически: храните отдельные неизменяемые версии и резервные копии каталога запуска согласно правилам проекта.

Журнал не защищён от намеренного редактирования процессом с доступом к файлам. Для полноценной оболочки нужны журнал событий в транзакционном хранилище, доступ по ролям, immutable evidence, политика хранения и автоматический pre/post перехват.
