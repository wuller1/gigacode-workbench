# Автоматический план задачи: GigaCode ведёт работу, пользователь видит прогресс

Это инструкция реализации для существующего личного GigaCode UI, **не готовая функция приложения**. Основной сценарий: **GigaCode сам составляет план, отмечает текущие и законченные шаги, добавляет, дробит и перестраивает оставшееся по ходу работы**. Пользователь не обязан создавать checklist и вручную проставлять галочки. Ручные заметки — вторичная необязательная возможность.

«План задачи» открывается из правого rail. Панель можно скрыть, переместить, пристыковать в tab group и изменить размер по [PANELS_AND_IDE](PANELS_AND_IDE.md). Это вид **той же Task/run**, а не отдельный workflow engine. Разговор остаётся главным экраном. Plan events обновляют UI обычным кодом; открытие, resize и подсчёт строк не вызывают модель.

## 1. Основной путь и вид панели

1. Пользователь даёт поручение. Если оно содержит несколько содержательных шагов, Giga формирует короткий план в рамках текущего рабочего turn; отдельное «составь todo» не требуется.
2. Перед очередным действием агент показывает текущий шаг; после результата обновляет его состояние. Новое знание может добавить проверку, разделить большой шаг или заменить неподходящий путь.
3. Host получает событие, проверяет binding/scope/revision и сохраняет новую версию. Обычные изменения **в уже разрешённой задаче применяются автоматически**, без approval на каждый add/reorder/complete.
4. Пользователь видит сделанное, оставшееся, blocker и ответственного; при желании открывает объяснение изменения, результат или отправляет уточнение. Сам план не меняет полномочия и не отменяет обязательные критерии Task.

Пример поведения: «Разобраться с отменой → исправить → проверить» после чтения кода превращается в «Разобраться — выполнено → разделить cancel по session → обработать late reply → проверить A/B». Первая выполненная работа остаётся в истории; изменение оставшихся шагов не требует нового run и повторного поручения. Это иллюстрация, не заранее заполненный план для всех задач.

Вверху: «Сейчас: …», роль/assignment, причина ожидания при наличии. Если реальная связь с текущим шагом не передана, показать «Агент работает; шаг не указан», а не угадывать по первому pending. Для параллельных исполнителей — несколько действительно активных строк, а не один глобальный busy.

Строка: небольшой status icon, название действия/результата, короткий owner при необходимости. Никаких пользовательских checkbox у агентских пунктов. Раскрытие показывает source, результат, требуемый уровень проверки и причину перестройки. Доступны фильтры «Осталось / Всё / Блокеры», переход к соответствующему сообщению/файлу, уточнение через composer. Завершённые можно свернуть. Цвет дублируется доступным текстом, keyboard focus сохранён.

Точное оформление: завершённый пункт имеет зачёркнутый заголовок и muted foreground с сохраняющимся контрастом; не снижать opacity всей строки вместе с результатом и controls. Текущий шаг выделяется мягкой заливкой, тонким маркером и подписью «Сейчас». Только при реально выполняющемся действии его status icon спокойно анимируется. Во время ожидания, отмены без подтверждения или stale данных не изображать выполнение. Будущие шаги обычные, без зачёркивания. Та же семантика действует в свёрнутом плане сообщения и в панели. Подробности активности чатов — в [TASK_ACTIVITY_INDICATORS](TASK_ACTIVITY_INDICATORS.md).

Сводка различает **выполненную работу**, **сообщённое агентом завершение без достаточного подтверждения** и **формальные проверки**. Например: «Выполнено 2 · Осталось 3, из них блокировано 1»; при неполной наблюдаемости отдельно «Агент отметил ещё 1». Числа здесь пример. Нет процента готовности продукта по количеству пунктов: агент может законно изменить их число. Blocked — часть remaining, cancelled/superseded не считаются done. Формальные дочерние checks не увеличивают число рабочих пунктов второй раз.

Для однострочной правки допустим один шаг либо отсутствие отдельного плана. Пустое состояние — «Отдельный план не нужен» или «Агент ещё не передал план», по факту. Не создавать пять пунктов ради наполнения панели. Отсутствие plan capability не маскируется вручную заготовленным demo todo.

## 2. Источник обновлений: сначала настоящий протокол

Проверено 2026-10-10: [ACP v1 Agent Plan](https://agentclientprotocol.com/protocol/v1/agent-plan) описывает `session/update` с `sessionUpdate: plan`. В entries передаются content, priority и status (`pending`, `in_progress`, `completed`). Каждое обновление содержит **полный актуальный список**, который заменяет текущую протокольную проекцию. План может меняться в процессе; стабильные entry IDs в этой структуре не описаны. Это контракт протокола, **не доказательство его реализации в GigaCode**.

Pinned Qwen `4360b003a087fe9e57f6ffbe7ba48795980b59c3` даёт конкретный путь для проверки форка:

Native child/parent планы не смешивать. Наличие plan event не даёт blanket гарантии успешного выполнения каждого tool |

Сначала проверить actual Giga tool inventory и сообщения, не переносить Qwen wire extensions/поведение по названию форка. Полученные native IDs использовать только с доказанной семантикой, вместе с plan/binding identity; без неё применять консервативное сопоставление ниже.

Порядок реализации:

- **Native plan events — первый выбор.** На целевом runtime зафиксировать фактические сообщения/schema и проверить живой сценарий. При наличии корректного plan event не строить второй план по парсингу текста. Сохранить raw sanitized snapshot и source identity, затем обновить UI.
- **Собственный host tool/MCP bridge — следующий выбор.** Если native events отсутствуют, реализовать небольшой task-scoped инструмент чтения текущего плана и внесения delta, зарегистрировать через поддержанный Giga MCP/config путь и проверить actual round-trip. Ниже `readPlan/updatePlan` — предлагаемые внутренние операции, **не существующие методы Giga/ACP**; реальные tool names/schema объявляет созданный adapter. Только после регистрации/обнаружения включать инструкции агенту пользоваться им.
- **Текстовый fallback — ограниченный режим.** Явно размеченный structured proposal из обычного ответа можно валидировать в host. Случайный список из прочитанного README не control event. Без надёжного bridge показывать последний сообщённый план с источником/свежестью; не обещать realtime update и не закрывать capability gate по декоративным строкам.

Не нужно ещё одно полное model completion для обновления после каждого чтения: Giga обновляет план как часть текущей работы/tool call. Группировать мелкие чтения в один содержательный шаг. Native и host bridge не пишут конкурирующие планы: на assignment выбирается один authoritative канал; прочие события — диагностика/ссылки.

## 3. Одни данные, три представления и два уровня утверждения

| Тип | Кто ведёт | Основание состояния |
|---|---|---|
| **planned_work — основной adaptive plan** | Агент предлагает действия/изменения; host автоматически валидирует и фиксирует в рамках scope | Progress отражает действие и источник. Done обычного шага подтверждается соответствующим наблюдаемым фактом; одно заявление completed сохраняется как agent-reported, без фиктивного tested/pass |
| **formal_projection — этап/check** | Read-only проекция existing WorkflowEngine/Evidence | Авторитетный status и evidence. Ни агентский plan completed, ни пользовательская отметка не завершают formal stage |
| **manual_note — необязательные заметки** | Пользователь, отдельно от основного плана | Ручная отметка `source=user`, unverified; не tested и не acceptance. Это не default добавления агентских шагов |

**Не требовать теста для каждого чтения.** «Изучить обработчик cancel» может завершиться receipt чтения конкретной revision и кратким найденным фактом. «Сохранить документ» — durable file/version receipt. «Исправить обработчик» — конкретный ChangeSet; отдельный шаг проверки показывает, что поведение ещё нужно испытать. «Проверить live A/B» требует реального результата соответствующего запуска. Task acceptance и обязательные workflow checks определяют, что нужно для общего результата, а не универсальное правило «тестировать любой пункт».

Хранить отдельно progress и assurance: кто сообщил статус, что наблюдается, какой результат/receipt имеется и чего не хватает. Native completed — факт сообщения агента, не автоматическое доказательство исправленного приложения. В UI это допустимо показать как «Агент завершил» с соответствующим источником; без нужного подтверждения не окрашивать formal check в pass. Наличие документа не доказывает его смысловую готовность; один exit 0 не заменяет нужную проверку.

Если planned_work ссылается на formal stages/checks, показать их внутри детали, без двойного подсчёта. По действующему плану отдельно считать confirmed done, remaining и agent-reported completion, ожидающее нужного подтверждения. Последнее остаётся частью remaining при недостаточном основании. Исторические cancelled/superseded доступны в «Изменениях плана», но не увеличивают done.

## 4. Версии и операция updatePlan

Переиспользовать существующие Task writer/storage/event stream; не добавлять отдельный scheduler. Смысловые поля адаптировать к проекту, не внедрять их в legacy schema/ACP payload.

| Область | Контракт |
|---|---|
| Plan | `plan_id`, task/run/assignment refs, source channel/binding generation, `plan_revision`, requirement basis; отдельный agent plan при независимых child assignments связан с родительским |
| Item | Stable host `item_id`, content, owner, dependency refs, source/native snapshot ref, item revision; одинаковые labels не одна сущность |
| Delta | Operation ID, expected plan revision, requirement revision, actor/assignment, операции add/start/report_complete/complete/block/split/supersede/reorder/cancel, краткая причина существенной перестройки |
| Result | Progress + assurance/source, immutable receipt/evidence refs, completion basis; старые outcomes сохраняются, не затираются новым текстом |
| Projection | Последний native snapshot отдельно от host history/identity links; UI filters/layout отдельно от semantic plan revision |

Для собственного bridge `updatePlan` принимает ограниченный delta, проверяет принадлежность Task/assignment, revisions, scope, IDs и ацикличность зависимостей. Сохраняет событие и новую версию атомарно, возвращает receipt/current revision. Дубликат operation ID возвращает прежний результат; stale base требует прочитать актуальный план и пересобрать маленький delta. Не перезаписывать целиком новый план второго автора.

При native ACP snapshot **заменять текущий протокольный список полностью**, как требует протокол, но не удалять прежние snapshots/completion history. Стабильные host IDs сохранять только при надёжном сопоставлении неизменившейся сущности; не склеивать пункты лишь по похожему заголовку. Без native IDs duplicates/split/смена смысла могут быть неоднозначны: создать новые IDs и сохранить uncertain/supersedes связи, не переносить прежний done/evidence наугад. Отсутствующий в новом списке пункт значит removed-from-current/superseded/unknown по фактам, **не completed**. Если агент не передал причину изменения, так и указать; не сочинять rationale.

## 5. Как агент перестраивает работу

| Событие | Автоматическое действие в разрешённом scope | Что сохраняется/проверяется |
|---|---|---|
| Найден необходимый дополнительный шаг | Add с новым ID и связью с целью; не спрашивать об обычном чтении/адресной проверке | Исходные требования и mandatory checks; полезная побочная идея вне scope остаётся recommendation |
| Большой шаг требуется разделить | Split в несколько детей, исходный superseded с ссылками | Уже сделанная часть/receipt не теряется. Дети не наследуют done автоматически |
| Выбран иной способ решения | Supersede прежний остаток, краткая фактическая причина и новый путь | Законченные действия остаются в истории; внешние effects не отменяются от изменения плана |
| Нужно изменить порядок | Validate dependencies и изменить будущий execution plan через existing orchestrator | Active/pending external операция сначала reconciled; перестановка не переносит выполняющийся turn на другой Task |
| Шаг завершён | Update progress с receipt/result подходящего уровня; native claim пометить источником | Formal verification не повышается автоматически; тесты только где нужны по criterion |
| Возник blocker | Block affected item/dependents с причиной и вопросом при необходимости | Независимая работа продолжается. Всё приложение не останавливается ради локального ответа |
| Требование изменилось | Новая basis revision; зависимые done — stale, адресный replan | Unrelated доказанно актуальные результаты сохраняются; engine rework/invalidation не обходится |
| Шаг больше не нужен | Cancel/supersede с причиной, не удалить бесследно | Нельзя исключить обязательный acceptance только для красивого счётчика. Реальное расширение/смена scope требует существующего change path |

Пользовательское уточнение может изменить план автоматически в рамках уже выданного поручения. Не запрашивать подтверждение каждого планового delta. Новые полномочия, непорученная публикация или несвязанный рефакторинг не становятся разрешёнными от записи в todo. Возврат к старому plan snapshot — новая версия/предложение, не откат выполненных действий.

Пользователь может раскрыть подробности, отправить корректировку в composer, временно закрепить вид и добавить отдельную заметку. Переставить строку вручную — display preference; запрос поменять реальный порядок направляется в план с зависимостями. Нельзя редактировать formal check checkbox. Удаление заметки/скрытие панели не cancel CLI/PTY. Общий lifecycle — [ENTITY_LIFECYCLE_AND_EDITING](ENTITY_LIFECYCLE_AND_EDITING.md).

## 6. Recovery, несколько окон и маленькие поставки

Один Task writer принимает события, renderer читает snapshot + ordered tail. Два окна показывают одну версию; поздние события старого binding не меняют текущий план. CAS и event/operation dedup предотвращают двойные строки; malformed proposal остаётся видимым как ошибка/текст, без мутации. После crash восстановить plan/history/drafts, затем reconcile pending outcome. Открытие панели и восстановление UI не повторяют prompt и tools. Engine unavailable — last-known/stale label, не выдуманный текущий успех.

| Карточка | Что реализовать | Приёмка |
|---|---|---|
| **TP1 · M3/D3 — живой источник** | Probe Giga plan events; иначе создать/подключить минимальный host plan tool bridge. Rail panel и реальный источник по binding | Giga сам формирует план и обновляет шаг без ручных галочек. Нет работающего канала — unavailable/partial, не demo success |
| **TP2 · M3/D3 — adaptive updates** | Snapshot/delta + IDs/revisions/history; add/split/supersede/reorder/start/completion, source labels и receipts | В одном задании агент меняет оставшийся план, законченная работа не исчезает. Duplicates, same-title entries и stale delta не склеиваются ошибочно |
| **TP3 · M4/D4–D5 — связи с задачей** | Requirement → plan → actual stage/check/result; affected stale/blocker и existing role/Continue actions | Смена требований и formal rework дают stale; plan completed не пропускает обязательный live check. Нет второго engine или approval на обычный plan update |
| **TP4 · адресная live-проверка** | Обычная многошаговая задача с уточнением, затем hide/reopen/restart и два окна | Plan меняется в UI без спасительного клика; один native/bridge источник, сохранённая история и нужный Task. Runtime недоступен — not_run |

Обязательный плохой случай для нового state path: повтор события, старая generation, split после частичного выполнения либо missing receipt. Для одной label-правки не запускать все CLI tests. Для read-step достаточно реального read/result receipt; для live UI acceptance нужен actual build/scenario. Independent critic проверяет новый контракт/инвалидацию по выбранному маршруту, не вызывается на каждый todo event.

```text
Реализуй TP__ из TASK_TODO_PANEL, personal_fast. Основной сценарий — GigaCode сам ведёт adaptive plan.
Сначала проверь настоящий ACP plan event; иначе создай и проверь task-scoped host tool/MCP bridge.
Не выдумывай готовый Giga todo API. Панель — проекция той же Task, не второй scheduler и не ручной checklist.
Агент обновляет plan в ходе работы без отдельных approvals внутри scope: add/split/supersede/reorder/status.
Сохрани IDs/revisions, done history, фактическую причину и receipts; removed/superseded не completed.
Обычное чтение не требует теста, но formal pass требует своего evidence; agent-reported status пометь честно.
Сделай один вертикальный сценарий и соответствующий bad case. Проверь живую ту же сборку или укажи not_run.
Верни изменение, actual source/receipt и оставшиеся ограничения; не набивай todo для однострочной правки.
```

Связи: [F33](COMPETITOR_FEATURE_PLAN.md), [Task/evidence](TASK_WORKSPACE.md), [роль и binding](ROLE_PROMPT_BINDING.md), [поставки](DELIVERY_AND_DOGFOOD_PLAN.md). На следующий turn передавать текущий краткий план, basis/revision, новый факт и нужную TP-карточку; не весь журнал и пакет документов.
