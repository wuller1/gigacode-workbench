# Проектирование и проверка качества дизайна

Цель — создавать понятный и целостный интерфейс, подтверждать измеримые свойства и сохранять качество при изменениях. Метод не задаёт палитру, стиль, шрифты или компоненты Zidao. Его внешний вид не является эталоном.

Качество оценивается по трём независимым основаниям: пригодность для пользовательской задачи, измеренные свойства реализации и экспертная оценка визуального решения. Хорошие размеры и контраст не доказывают понятную иерархию; мнение о красоте не отменяет обнаруженный дефект. Единого итогового балла нет.

## Процесс проектирования

1. Определить пользователя, задачу, контекст, основной результат и ограничения. У каждого экрана должна быть понятная цель; у каждого значимого элемента — роль в сценарии.
2. Построить пользовательский поток: вход, решение, действие, подтверждение, ошибка, восстановление. Проверить права, доступность данных и риск потери введённого состояния.
3. Сформировать информационную иерархию: что пользователь должен заметить первым, что сравнить, что сделать. Приоритет относится к конкретной области принятия решения; правило «одна кнопка на весь экран» не универсально.
4. Для новой или спорной концепции подготовить несколько осмысленных вариантов, сравнить их по задаче и ограничениям. Для обычного изменения существующего компонента варианты ради вариантов не нужны.
5. Зафиксировать дизайн-контракт: сценарии, состояния, состав информации, правила визуального языка, проектные токены, применимые числовые пороги, выбранная матрица проверок и решения. Отдельно обозначить proposed/approved, implemented и verified.
6. Реализовать все обязательные состояния и переходы. Проверить на реалистичных данных: длинные названия, отсутствие данных, большой объём, ошибки, медленная загрузка и изменение доступов.
7. Измерить свойства, провести содержательное визуальное ревью, исправить подтверждённые проблемы и перепроверить затронутое. Сохранить версию, screenshots и отчёт.

Внешний референс может объяснять настроение или отдельный приём, но не заменяет задачу и проверку. Существующий интерфейс тоже проверяется критически: наследование ошибки не делает её стандартом.

## Измеримые требования

Ниже выбранные базовые критерии. Они не являются полной проверкой соответствия WCAG. Нормативные критерии, проектные цели и эвристики различаются в config/design-quality.json.

| Свойство | Число или условие | Как оценивать |
|---|---|---|
| Контраст обычного текста | Не менее 4.5:1 | По фактическим цветам и фону; без округления перед сравнением |
| Контраст крупного текста | Не менее 3:1 | Крупный: 18pt обычный либо 14pt bold и эквиваленты; ориентировочно 24 CSS px и 18⅔ CSS px при обычной CSS-модели |
| Необходимая графика и признаки компонентов | Не менее 3:1 | Проверить необходимые для распознавания границы/состояния и применимые исключения; не требовать 3:1 от любой декоративной линии |
| Минимальная цель указателя | 24×24 CSS px либо применимое исключение | Проверяются spacing, inline/equivalent и другие исключения; маленький bounding box — кандидат для разбора |
| Перекомпоновка вертикального контента | Ширина 320 CSS px | Без потери информации/функции и лишней двумерной прокрутки, с исключениями для действительно двумерного содержимого |
| Увеличение текста | До 200% | Без потери содержания и функций в пределах применимых условий |
| Фокус | Видим и не полностью закрыт авторским содержимым | Проход клавиатурой, диалоги, sticky-элементы; геометрии без взаимодействия недостаточно |

Порог и исключения текста описаны в [WCAG 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), компонентов — в [WCAG 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html), целей — в [WCAG 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html). Требования к перекомпоновке, увеличению и незакрытому фокусу: [1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [1.4.4](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html), [2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html).

Для полупрозрачности, градиента, изображений, overlay и смешивания контраст нельзя достоверно получить из одной пары CSS color/backgroundColor. Нужен инструмент, учитывающий реальное отображение, или ручная проверка худшего участка. Неизвестный фон даёт unknown. Упрощённый классификатор размера/веса шрифта также не решает все случаи нестандартных шрифтов.

## Проектные числовые цели

Предлагаемая стартовая цель для главных touch-действий — 44×44 CSS px, для основного читаемого текста — 16 CSS px. Это предложения для дизайн-контракта, а не универсальные требования WCAG AA. Плотные таблицы, специальные инструменты и второстепенный текст требуют контекстного решения.

Для обязательных сценариев: 0 подтверждённых дефектов, скрывающих содержание или мешающих действию; 0 необъяснённых нарушений принятых токенов; 100% выбранных обязательных проверок. Допустимые исключения сохраняются явно. Нельзя получить 100%, удалив неудобное состояние из списка после обнаружения проблемы.

Для web-производительности ориентир: LCP ≤2.5 с, INP ≤200 мс, CLS ≤0.1 на 75-м процентиле реальных посещений, отдельно для мобильных и desktop. Лабораторный прогон не равен полевой статистике; INP не доказывается одним Lighthouse запуском. Это показатели взаимодействия/загрузки, а не эстетический рейтинг. [Web Vitals](https://web.dev/articles/vitals)

Время выполнения задачи, успешность и количество пользовательских ошибок задаются после определения протокола и baseline. Отчёт содержит размер выборки и условия. Агент не придумывает пользователей и не выдаёт собственное прохождение за исследование удобства.

## Матрица проверок

До измерения составьте список применимых случаев: экран × состояние × viewport × тема × сценарий взаимодействия. Для каждой строки задайте ID, обязательность, причину включения, expected и evidence. Полное декартово произведение не обязательно: выбранное покрытие обосновывается риском, но его нельзя называть полной матрицей всего приложения.

Стартовые размеры для адаптации: 320, 360, 768, 1280 и 1440 CSS px по ширине, плюс границы реальных breakpoints. Высота, ориентация, браузер, шрифты и pixel ratio фиксируются. Для критических переходов проверьте live resize с сохранением формы, выбора, прокрутки, фокуса и состояния диалога. Перезагрузка страницы на каждой ширине этого не проверяет.

Обязательные состояния выбираются из default, loading, empty, partial-data, error, success, disabled, validation, permission-denied и взаимодействий. Состояния, неприменимые к компоненту, помечаются с причиной.

Покрытие = число выполненных выбранных случаев / число выбранных применимых случаев. Отдельно показывайте passed, failed и unknown. «10 из 10 выполнено» при двух failed не означает готовность.

## Экспертное визуальное ревью

| Критерий | Вопрос ревьюера | Свидетельство замечания |
|---|---|---|
| Пригодность | Можно ли понять и выполнить основную задачу? | Конкретный сценарий и место затруднения |
| Иерархия | Соответствует ли визуальный акцент важности информации и действий? | Аннотированный экран и конкурирующие элементы |
| Ритм и композиция | Объяснимы ли отступы, выравнивания и группировка? | Примеры несогласованных групп и пользовательское последствие |
| Читаемость | Различимы ли смысловые уровни, понятны ли подписи? | Конкретный текст/область, плотность, длина и контекст |
| Поведение | Понятно ли состояние системы и следующий шаг? | Последовательность действий и feedback |
| Целостность | Соответствуют ли повторяющиеся сущности принятым правилам проекта? | Несогласованные экземпляры и источник правила |

Результат каждого критерия: accepted, rework или unknown с кратким обоснованием. Предпочтение «мне нравится другой цвет» без связи с задачей, контрактом или наблюдением не является блокирующим дефектом. Автор может выполнить самопроверку, но host назначает отдельный проход ревью перед итоговой приёмкой существенного нового дизайна.

## Поддержание качества

Токены и компоненты создаются из потребностей проекта: семантические роли цвета, типографики, расстояний, состояний и плотности. Не добавляйте произвольные локальные значения, если существующий токен подходит. Новое исключение требует понятной причины; повторяющееся исключение — повод пересмотреть систему.

Фиксируйте эталон только после принятия конкретной версии. Обновление baseline — отдельное решение с diff и причиной, а не автоматический способ сделать упавший тест зелёным. Для screenshots зафиксируйте данные, viewport, браузер, шрифты и анимации. Допуски различий калибруются на этих условиях; универсальный процент pixel diff не доказывает качество.

Для числовых проверок полезны negative controls: специально нарушенный размер, контраст или layout должен обнаруживаться тестом. Если проверка всегда зелёная, она не подтверждает свойство.

## Инструмент измерения из пакета

`tools/design-metrics.ps1` экспортирует сохранённый внутри JavaScript. Сам PowerShell не выполняется в браузере и не видит DOM. Сначала создайте JavaScript-файл (существующий файл не перезаписывается):

```powershell
powershell -NoProfile -File .\gigacode-workbench\tools\design-metrics.ps1 -OutputPath .\work\design-metrics.js
```

Затем передайте содержимое созданного файла разрешённому браузерному инструменту в контексте тестируемой страницы. Только после этого доступен `DesignMetrics`. Экспорт не означает, что интерфейс проверен. Получение данных:

```js
DesignMetrics.collect(document, {
  productFontSizePx: 16,
  primaryTargetPx: 44,
  maxRecords: 100,
  maxElements: 10000
})
```

Параметры 16 и 44 должны соответствовать принятому дизайн-контракту. `data-design-primary` отмечает главные контролы для отдельного измерения. Сборщик возвращает геометрию, кандидатов, counts, truncated и unknown. Он не считывает тексты/значения полей и не вычисляет итоговую оценку. Inline targets, расширенные label hit areas, intentional scrolling, iframe/shadow DOM, сложный фон, перекрытия, клавиатурная доступность и композиция требуют дополнительных проверок.

`contrastRgb` считает отношение для явно заданных RGB; `textContrastThreshold` предоставляет упрощённый порог conventional fonts. Node-тесты проверяют математику и контракт экспорта. Реальный браузерный сбор на приложении пользователя здесь не выполнялся. Для полноценного автоматического аудита подключите доступные в проекте инструменты accessibility, screenshots и interaction tests; каждый из них тоже имеет пределы покрытия.

## Итоговый вердикт

`ready-for-agreed-scope`: обязательные проверки выполнены, блокирующих дефектов нет, экспертное ревью принято, ограничения и версия указаны. `rework`: есть подтверждённые дефекты. `incomplete`: обязательных свидетельств не хватает. Сохраняйте результат по `templates/design-report.md` и связывайте с требованиями, журналом и текущей версией кода.
