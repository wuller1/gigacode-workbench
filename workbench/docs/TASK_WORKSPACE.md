# Работа с конкретной задачей внутри GigaCode UI

Статус: **проектирование для существующего прототипа, не реализованная здесь функция**. Цель — открывать задачу и прямо в ней обсуждать требования, видеть план, изменения, проверки и материалы. Не нужно вручную собирать результат из нескольких чатов, переключать роли на каждом этапе или повторно объяснять контекст.

Этот документ уточняет M3–M6 и M9–M10 из [плана UI](GIGACODE_UI_DEVELOPMENT_PLAN.md) и N4–N11 из [нативного переноса](NATIVE_WORKBENCH_MIGRATION.md). Он не добавляет второй controller, новый агентный движок или постоянные PowerShell subprocess. Все данные и команды принадлежат уже выбранному Node backend/Electron main; переходы выполняет тот же WorkflowEngine. CLI остаётся неизменным, доступ к нему — через проверенные ACP/config возможности и реальные MCP.

## 1. Минимальный пользовательский путь

Пользователь выбирает уже известный проект и пишет: «При отмене первого чата второй тоже останавливается. Исправь». UI автоматически создаёт Task, сохраняет исходное поручение и открывает обсуждение. Название берётся из первой строки или коротко формируется позже без задержки отправки. Нет мастера из обязательных полей, отдельного нового ТЗ и выбора всего каталога профилей.

Вверху задачи видны цель, проект, текущий шаг/причина ожидания и одно подходящее следующее действие. После первого полезного чтения критерий можно уточнить до «Stop A отменяет A; работа B продолжается» с источником этого ожидания. Это ещё не доказательство исправления. В ходе работы появляются реальный diff и результаты проверки; замечание о несвязанном улучшении остаётся рекомендацией.

Для опечатки в документе достаточно исходного запроса, файла, текущего diff и адресной проверки смысла. Не создавать полный SDD, отдельные панели, агентов, docs-update и retro ради заполнения карточки. Для сложной задачи структура раскрывается по мере появления фактов.

Продолжение и уточнение в открытой задаче сохраняют её ID и существующий run. Пользователь может явно открыть новую задачу, сменить границы или связать прежнюю. Не объединять разные задачи по похожему заголовку и не создавать новый run на каждое сообщение.

## 2. Один Task aggregate и несколько подчинённых представлений

### Иерархия проекта, задач и ролей

Пользовательская иерархия фиксирована: **Project → Tasks → Roles внутри Task**. Project — рабочая область с известными репозиториями, правилами, выбранным design preset, проверенными MCP bindings и памятью проекта. У Project много независимых Task. Роль — способ выполнить часть текущей задачи, а не отдельный проект, задача или обязательный новый чат. Run, stage, attempt, CLI session и окно — технические связи внутри этой модели; не показывай их как конкурирующее дерево навигации.

В sidebar проекты раскрываются в задачи; фильтры «В работе», «Ожидают меня», «Все» строятся из настоящего состояния. В заголовке открытой задачи — проект, название и состояние; текущая роль и меню «Роли» находятся внутри задачи. По умолчанию показывай текущую роль и полезное следующее действие, историю ролей раскрывай по запросу. Пустая вкладка для каждой роли каталога не нужна. Параллельные участники показываются коротким списком с назначенным результатом и состоянием, а основной разговор остаётся единым.

| Уровень | Канонические данные | Не переносится автоматически |
|---|---|---|
| Project | project_id, roots/repositories с идентичностью, принятые правила и их версии, memory namespace, ссылки на browser/MCP profiles, default layout/design policy | Доступы соседних проектов, секреты, полный контекст всех задач |
| Task | Цель, исходное поручение, scope, acceptance, решения/вопросы, артефакты, run links и история участия ролей | Несвязанные рекомендации и чужие черновики |
| Role assignment | assignment_id, task_id, role_id, цель участка, входы/выходы, stage/run refs, статус, действительные permissions/binding refs | Полномочия на публикацию, новая задача, отдельный CLI process без необходимости |

Assignment имеет собственную идентичность: один профиль может возвращаться к задаче несколько раз. Не делай ключом только role_id и не затирай предыдущий результат. Общий реестр описаний ролей может быть глобальным; участие роли и её рабочий контекст всегда относятся к конкретному Task. Spec — опциональная специализация; аналитик сам пишет описание функциональности в нужном формате. Правила переходов и рекомендаций — [ROLE_ROUTING](ROLE_ROUTING.md).

Смена роли сохраняет task_id, исходное поручение, решения, вопросы, артефакты, draft и журнал. Host выдаёт роли краткий адресный пакет по [CONTEXT_BUDGET](CONTEXT_BUDGET.md), вместо всех 14 system prompts и всего лога. В существующей сессии применяется только подтверждённо поддерживаемый механизм смены инструкций/инструментов; если он отсутствует, host создаёт проверяемый handoff в новый binding той же задачи на безопасной границе. Нельзя обещать горячую замену системного prompt в чужом CLI.

Одновременные backend/frontend/QA assignments допустимы для независимых входов и результатов. Один writer владеет каждым CLI binding; backend контролирует владение изменяемыми файлами/worktree и принятие результатов по task/run/requirement revision. Конфликтующие изменения сериализуются либо объединяются явным шагом. Role switch, переключение окна или закрытие панели не отменяют фоновую работу и не меняют её адресата. QA проверяет конкретную версию результата, а не «последние файлы» при продолжающейся записи.

Создание задачи должно занимать выбор проекта и одно сообщение; если проект уже выбран — только сообщение. Настройки проекта наследуются ссылками и версиями без onboarding повторно. Новая задача не загружает память всех проектов. Перенос задачи в другой проект — явное действие с проверкой корней, scope, bindings и сохранением истории; переименование/архивирование не меняют владельцев процессов. Удаление представления не удаляет Task или артефакты.

Проверь путь: две задачи одного проекта → смысловое изменение первой вызывает auto-route только в ней → два окна одной задачи → перезапуск → восстановление. Во всех шагах цель/результаты/permissions должны оставаться привязаны к своему Task; второе окно наблюдает того же владельца записи. Другая задача продолжает работу независимо. Пользовательский результат и контрольные точки разработки описаны в [DELIVERY_AND_DOGFOOD_PLAN](DELIVERY_AND_DOGFOOD_PLAN.md).

В нынешнем reference controller поле task — строка описания в state.json. **Ниже предлагается новая native сущность Task; это не новые поля legacy schema_version=1 и не ACP payload.** Она связывает сущности из плана миграции, не копирует их состояние в независимые хранилища.

| Поле / связь Task | Смысл и источник | Минимум для маленькой задачи |
|---|---|---|
| task_id, project_id, created_at | Стабильная идентичность; project_id из существующего реестра | Создаются автоматически; сходство имён папок не доказывает один проект |
| title, goal, request_ref | Краткое имя, требуемый результат и исходное поручение | Goal можно сохранить дословно; модельная интерпретация не заменяет источник |
| scope, authorization_refs | Разрешённые действия/ресурсы, ограничения, что вне задачи | Ссылка на поручение и текущий проект; не выдумывать разрешение на deploy/push |
| project_mode, routing_decision_ref | personal_fast либо established_strict; отдельно quick/standard/deep и выбранный workflow | Наследовать известный режим и короткое основание маршрута |
| acceptance_refs, requirement_revision | Критерии результата и версия требований | Один ясный критерий достаточен; неизвестное видно, не заполнено заглушкой |
| decision_refs, proposal_refs | Принятые решения и отдельно предложенные улучшения | Пустые списки допустимы; не нужно выдумывать decision для каждого действия |
| question_refs | Вопросы с областью влияния, blocking/nonblocking, версиями и ответами | Только реально возникшие; рекомендации не становятся блокерами автоматически |
| active_run_id, run_refs | Текущий основной run; исторические/заменённые/дочерние runs с причиной связи | Обычно один; состояние каждого хранит WorkflowEngine |
| thread_refs | Основное обсуждение и при необходимости отдельные execution/review chats | Обычно одно; вкладка не создаёт новую ACP-сессию сама по себе |
| artifact_refs, evidence_refs, change_set_refs | Проверяемые материалы и версии изменений | Ссылки вместо копий больших логов/файлов внутри Task |
| external_refs | Реальные внешние документы/задачи с provider, ID/URL, scope и временем чтения | Необязательно; отсутствие внешнего tracker не блокирует локальную задачу |
| task_revision, event_sequence, checkpoint_ref | CAS семантических изменений, порядок событий, точка восстановления | Управляет backend, модель не назначает свои revisions |
| archived_at | Удобство организации списка | Архивирование не отменяет CLI turn и не означает успешного завершения |

Canonical ownership:

- Task хранит цель, scope и связи. Requirement/Decision services хранят версии решений; Artifact/Evidence services — файлы и свидетельства; WorkflowEngine — runs, попытки и переходы; SessionService — ACP lifecycle. Task UI собирает их проекцию.
- В простом случае есть один основной active_run. Исторические runs остаются историей; самостоятельные части при необходимости имеют дочерние runs. Обязательность дочернего результата задаётся зависимостью/критерием, а не фактом, что запущен агент.
- Chat — обсуждение задачи; run — выполнение конкретного workflow; ACP session — runtime разговора с CLI. Их IDs не равны друг другу. Один Task может иметь несколько chats/runs, но это не даёт права одновременно писать два prompt в одну ACP-сессию.
- Binding содержит connection identity/generation и sessionId. Два окна одного чата — наблюдатели одного writer-owner; разные независимые chats — отдельные bindings. Одинаковый sessionId в разных connections не объединяет их. Подробнее — [параллельные сессии](PARALLEL_SESSIONS_FIX.md).
- Импорт legacy run создаёт Task со ссылкой на оригинальное описание и run_id либо использует доказанное прежнее соответствие. Не объединять legacy runs автоматически по равному тексту task; не изменять hashes/IDs старого state.

Новый Task aggregate имеет собственную версию native schema. Legacy workflow/result/state по-прежнему импортируются и экспортируются по [контракту миграции](NATIVE_WORKBENCH_MIGRATION.md); Task metadata не внедряется в них неописанными полями.

## 3. Контекстные виды одной задачи

Это смысловые проекции данных, а не обязательные вкладки над чатом. Обсуждение — основной экран, overview — краткое резюме по запросу, plan — inline-сводка и панель [План задачи](TASK_TODO_PANEL.md), checks/changes/materials — связанные dock views. Компоновка определена в [CHAT_FIRST_DESIGN](CHAT_FIRST_DESIGN.md); редактирование, переименование, архив и удаление — в [ENTITY_LIFECYCLE_AND_EDITING](ENTITY_LIFECYCLE_AND_EDITING.md). У каждого объекта один источник данных независимо от числа открытых представлений.

Это шесть доступных видов, **не шесть постоянно открытых панелей**. По умолчанию — обсуждение и компактная строка задачи. Второй материал раскрывается рядом только при необходимости; на узком окне занимает переключаемую область. Положение/draft/прокрутка сохраняются по task/chat. Выбор вида не вызывает модель.

Перемещаемые/изменяемые по размеру панели, добавление, скрытие, изменение порядка и объединение во вкладки относятся к **текущему M3**, не к далёкому IDE-этапу. Task views, browser, terminal и инструменты используют единый PanelRegistry и сохранённые layouts из [PANELS_AND_IDE](PANELS_AND_IDE.md). TaskWorkspace не создаёт собственный конкурирующий dock/layout manager.

| Вид | Что отображается | Что пользователь может сделать |
|---|---|---|
| **Обзор** | Цель, scope, критерий, текущий этап, последнее подтверждённое изменение, существенная рекомендация, причина ожидания | Уточнить задачу, открыть связанный источник, перейти к нужному действию |
| **Обсуждение** | Основной чат, anchors/count нерешённых вопросов, ответы и краткие ссылки на решения; текущий вопрос — overlay над разговором | Открыть/свернуть вопрос без потери draft, ответить, направить работу, добавить источник; отдельной панели Questions нет |
| **План** | Текущий workflow/stage и реальные зависимости; для quick — одна-две строки | Просмотреть критерий этапа; запросить изменение маршрута/возврат с причиной |
| **Изменения** | Настоящий Git/artifact diff с base и target revision; текущие dirty changes и владение | Открыть файл, сравнить версии, применить уже разрешённую правку через host; отдельно решить публикацию |
| **Проверки** | Acceptance → check → execution/judgment/artifact evidence, актуальность и ограничения | Открыть результат, запустить применимую разрешённую проверку, разобрать failed/stale/not_run |
| **Материалы** | SDD, решения, design contract/report, файлы, изображения, внешние источники и checkpoint | Открыть/сравнить/экспортировать реальный артефакт, увидеть происхождение и права использования |

Не дублировать SDD в пяти документах: формы редактируют один versioned источник; Markdown-экспорт является его явным snapshot. Для импортированного ручного документа сначала сохранить его как источник, а не перегенерировать целиком. View «План» не хранит второй список этапов с независимыми галочками.

Panel instance имеет стабильный view ID, тип, ссылку на материал/resource и binding «следовать выбранной задаче» либо «закреплено за Task». Перенос между dock/tab/window сохраняет этот ID и binding; resource IDs CLI/PTY/browser живут отдельно у backend. Hide/перенос/resize не завершают эти ресурсы и не создают новые процессы. Кнопка закрытия представления отличима от явной остановки ресурса. Фоновый лимит/выгрузка — отдельная наблюдаемая политика, не скрытый side effect layout.

При смене выбранной задачи следящие виды показывают её snapshot, закреплённые сохраняют свою задачу с видимой меткой. Уже отправленное действие относится к captured task/run/session, а не к «активной панели сейчас». Draft и pending permission не переезжают в соседнюю задачу от drag-and-drop. Полноценные IDE-возможности Java/Python/React отложены; они не являются зависимостью Task workspace, настраиваемых панелей или базового просмотра файла/diff.

Обычная карточка не показывает внутренние operation IDs, JSON или весь журнал. Эти сведения доступны в details и evidence. Скрытие технических деталей не удаляет их из store. Тема/иконки/состояния следуют [DESIGN_IMPLEMENTATION_GUIDE](DESIGN_IMPLEMENTATION_GUIDE.md), [GRAPHICS_AND_MOTION](GRAPHICS_AND_MOTION.md) и [ASSET_RIGHTS](ASSET_RIGHTS.md); Task UI не изобретает параллельную визуальную систему.

## 4. Lifecycle: ровно существующие переходы

У Task **нет второго редактируемого workflow status**. Основной статус выполнения — проекция active_run.status; отдельно отображается transport/turn state из SessionService. До выбора/создания run UI пишет «Маршрут ещё не выбран», а не выдаёт отсутствующий статус за ready. Это состояние неполной проекции, не новый переход controller.

| Статус WorkflowEngine | Представление и допустимое действие в Task UI |
|---|---|
| ready | Текущий этап доступен. Если у него уже идёт turn, показывать «Выполняется» из SessionService; повторный click не создаёт второй dispatch |
| waiting_input | Показать блокирующий вопрос текущего этапа. Сохранить реальный ответ и связанную версию; после устранения причины выполнить resume |
| blocked | Показать конкретный недостающий факт/инструмент/предусловие. Resume только после его фактического устранения |
| needs_rework | Показать return_to и причину. Вызвать rework для допустимой цели; универсальная кнопка resume здесь неверна |
| blocked_budget | Показать использованные попытки и остаток задачи. Cancel/resume или новый child не обнуляют budget; пересмотр задачи нужен явно |
| cancelled | Workflow остановлен локально. Resume восстанавливает прежний статус; pending operations остаются |
| completed | Основной run принял комплектный отчёт. Показывать область и версию результата; это не автоматическое разрешение на release и не доказательство любого внешнего эффекта |

Переходы выполняются штатными init/submit/resume/rework/cancel/record операциями native WorkflowEngine. Сохраняются checks/allow_na, exact report keys, revisions, attempt_id, max_attempts и immutable evidence. В [CONTROLLER](CONTROLLER.md) и [JOURNAL](JOURNAL.md) задан их контракт.

Task-wide итог сопоставляется с актуальными обязательными критериями и связанными runs/evidence. Если дочерний обязательный результат не получен или критерий изменился, UI не показывает «Задача выполнена» только потому, что старый основной run completed. Показывает конкретное несоответствие версии/области и оформляет разрешённый rework либо новый связанный run. Это проверка применимости результата тем же host, не независимый ручной переключатель completed.

Пример различия кнопок:

- «Остановить ответ» — session/cancel конкретного активного turn; слот занят до terminal response. При disconnect — unknown/reconcile, не автоматический повтор.
- «Не запускать следующие» — пауза собственной очереди; это не заморозка работающего CLI.
- «Отменить выполнение workflow» — controller cancel; он сам не останавливает внешнюю job/CLI. UI отдельно показывает их исход.
- «Архивировать задачу» — организация списка; сама по себе не отменяет работу.

Pending action с неизвестным исходом блокирует completed submit и rework. Окно/вкладка может закрыться, операция не исчезает. Вопросы stage report содержат **только блокирующее текущий этап**; необязательные вопросы/рекомендации Task не копируются туда и не тормозят независимую работу.

## 5. Команды, revisions и один writer

Renderer читает snapshot+event tail и посылает узкую типизированную команду. Предлагаемый внутренний envelope:

~~~json
{
  "command_id": "<idempotency key одной UI-команды>",
  "task_id": "<Task ID>",
  "expected_task_revision": "<актуальное целое>",
  "run_ref": {
    "run_id": "<если команда относится к run>",
    "expected_revision": "<актуальное целое>",
    "attempt_id": "<актуальная попытка>"
  },
  "action": "<например answer_question>",
  "payload": "<данные по схеме конкретного действия>"
}
~~~

Это пример полей **внутреннего API host**, не готовый JSON для отправки ACP и не настоящие значения. Для чистого просмотра run_ref не нужен. Команда не позволяет передать произвольный shell или выставить статус без проверки. Повтор command_id с тем же payload возвращает прежний результат; с другим payload отвергается.

Правила записи:

1. Единственный backend writer проверяет project/task/window ownership, scope, authorization, expected revisions и допустимость действия. Транзакция фиксирует изменение и событие до публикации UI.
2. Task revision относится к семантическому goal/scope/criteria/decision/link изменению; run revision — к состоянию/журналу контроллера; requirement revision — к содержанию требований; event sequence — к порядку событий. Их нельзя заменять друг другом.
3. Всякая record в run повышает его revision. Итоговый result-template берётся после журналирования. Старая модельная выдача не «освежается» подстановкой новой revision; сначала проверяется применимость её содержания.
4. Открытие вкладки, scroll, hover и выбор строки не меняют accepted requirements/run revision и не вызывают модель. Для сохранения пользовательского layout используется UI state, не журнал агентных действий. Фактические чтения/изменения задачи и операции сохраняются по журналу, без дублирования уже автоматически записанного вызова.
5. Отправка host-owned внешнего эффекта имеет operation_id и pre-event; post-event/receipt фиксирует результат. Потеря ответа → unknown. Повтор UI-команды и повтор внешнего действия — разные вещи, exactly-once наружу не обещается.
6. Task и run изменения координируются в существующем native хранилище, не двумя JSON-файлами разных окон. Долгие операции идут вне DB transaction; их reservation/pending связывается с последующим результатом. Некомплектный artifact не публикуется как accepted.

Один writer хранилища не изолирует файловую систему репозитория. Для одновременных изменений backend отслеживает workspace/resource ownership: отдельные worktrees либо один writer данного checkout и read-only исследователи. Не назначать два независимых агента владельцами одних файлов, не копировать чужой dirty diff в результат текущей задачи. Неподконтрольный shell CLI нельзя заблокировать декларацией Task scope: действуют только реально настроенные native permissions/host boundaries из [MCP_PROTOCOL](MCP_PROTOCOL.md).

## 6. Быстрый контекст конкретной задачи

Приоритет чтения: **текущий Task → актуальный этап → нужные первичные источники → scoped memory/внешний источник при необходимости**. Не начинать каждый ход с полного inventory проекта, всех журналов, всех профилей или всей истории чата.

ContextPacketBuilder использует native Task/Workflow/Memory/Evidence services и формирует versioned пакет:

- packet_version, task_id/task_revision, run_id/stage/run revision/attempt_id;
- одна текущая цель и scope; project_mode, route/profile и применимые ограничения;
- относящиеся к этому шагу acceptance/decision IDs и requirement revision;
- несколько фактов с evidence/source references, revision/hash, областью и наблюдаемым результатом;
- блокирующие unknown/questions, pending operations и точный следующий шаг;
- разрешённые реальные tools/resource scope по актуальному binding fingerprint;
- ссылки на нужные artifact/diff fragments и output contract; manifest загруженных инструкций.

Это retrieval projection, не новая копия полной задачи. Стартовые ориентиры из [FLASH_MODEL_EXECUTION](FLASH_MODEL_EXECUTION.md) — одна цель, до пяти входных источников, до восьми фактов и до трёх критериев. Это настраиваемый ориентир, не обрезание важного контракта: если зависимость не помещается, дать её адресное чтение или осмысленно разделить шаг. Полный текст Task/SDD остаётся доступным по ссылке; модели не предлагают угадывать пропущенный обязательный факт.

Packet запоминает fingerprints входов. Новый primary context или изменившаяся инструкция требует её загрузить; наличие файла в cache не доказывает, что модель уже его видела. Полное обновление prompt делается только по соответствующей причине. Уточнение ответа обновляет затронутые требования/факты и следующий packet, не переписывает весь SDD и не создаёт новый workflow.

Выбор профильной инструкции автоматически производится router по запросу, Project/Task, разрешённому маршруту, stage и выбранному resource. Пользователь видит role/reason/confidence и направляет работу уточнением цели или ожидаемого результата; ручного переключателя «аналитик → backend → QA» нет. Если профиль требует другого process-wide prompt и установленный CLI не поддерживает горячую смену, SessionService создаёт соответствующую сессию/процесс после проверки совместимости; Task/run остаются теми же. Не менять конфигурацию исполняемого turn незаметно.

Модель нужна для нового анализа, неоднозначного решения, содержательной реализации или ревью. Открыть обзор/план, показать diff, проверить schema/hash/CAS, выбрать готовое evidence, отфильтровать материалы и обновить счётчики может обычный код. Отсутствие LLM-вызова на click не делает проверку автоматически успешной: каждый pass требует подходящего факта/исполнения.

## 7. Evidence reuse и точечное инвалидирование

Хранить зависимости результата: criterion/check ID, source path/content hash или Git revision+working-tree fingerprint, requirement revision, tool/method version, input/environment identity, scope и observed_at. «Файл называется так же», «вчера passed» и cached summary недостаточны.

| Событие | Что обновить/инвалидировать | Чего не делать |
|---|---|---|
| Изменён один исходник | Проверки/утверждения, зависящие от его поведения, и доказанные downstream зависимости | Полный reread всех docs/проектов без основания |
| Ответ изменил критерий A | Новая версия A, зависимые решения/проверки/материалы; snapshot SDD delta | Переписать всё ТЗ или сохранить зелёный badge по старому A |
| Изменён tool/schema/environment | Результаты, для которых изменился метод/условия; relevant binding cache | Считать прежний receipt свежим по одному времени |
| Изменён accepted evidence файл | Integrity error, affected acceptance не подтверждена; новая версия отдельно | Пересчитать hash поверх старого evidence и объявить исправленным |
| Изменился только layout UI задачи | Сохранить UI preferences | Инвалидировать кодовые тесты и запускать model review |
| Внешний источник мог измениться | Показать cache stamp/условия свежести; адресное чтение перед существенным использованием | Называть сохранённую копию текущим фактом или автоматически записывать наружу |

Dependency map — механизм host, который ещё нужно реализовать. При неизвестной полноте зависимостей расширить проверку и назвать ограничение; отсутствие ребра в неполной карте не доказывает отсутствие влияния.

**Не менять семантику existing rework:** controller инвалидирует целевой и все последующие этапы. Dependency-selective reuse означает возможность сослаться на ещё применимое прежнее evidence с проверенным основанием, а не сохранить завершённые этапы вопреки rework или перескочить через них. Между runs host помечает зависимые результаты stale и оформляет нужные действия; это не готовая функция reference controller.

UI разделяет «выполнено сейчас», «переиспользовано с проверкой входов», «stale», «failed», «not_run», «unknown», «not_applicable». Сводка coverage имеет реальный знаменатель применимых критериев. 0 tests/все skipped/не тот build не дают pass; модельная оценка не подменяет log инструмента. Реальный Git diff сравнивает указанные ревизии/index/working tree, artifact diff — два сохранённых снимка; рассказ модели об изменениях не является diff.

## 8. Вопросы, SDD delta и конструктивная критика

Question имеет ID, версию, источник, affected requirement IDs, область зависимой работы, варианты при наличии и blocking flag. UI открывает **один текущий вопрос в Task-bound overlay поверх разговора**: options плюс всегда свободный ответ. В раунде допустимы 1–3 связанных вопроса, но они идут через очередь одной Task, без стека окон и вытеснения набираемого ответа. В чате остаются anchor/count нерешённых, которые открывают ту же Question; отдельной панели/иконки Questions в rail нет. Если ответ уже есть в accepted decision/поручении, не спрашивать снова. Независимый дочерний run может продолжаться с явной областью; ожидающий run не выполняет зависимую работу.

Свернуть/закрыть представление/Escape сохраняют question draft и выбор, возвращают focus в исходное доступное место и не создают Answer/resume. При переходе A→B overlay A сворачивается с прежним target; B показывает только свою очередь. Header указывает Task, submit сохраняет captured task/question/revision, а не текущую глобальную selection. Stale callback/ответ из другого окна проверяется backend; draft остаётся при конфликте. Question presentation state принадлежит Task+окну, canonical очередь/ответы — QuestionService. Подробности — [ARTIFACTS_AND_QUESTIONS](ARTIFACTS_AND_QUESTIONS.md).

Tool permission остаётся отдельным адресным request с реальными options/binding/generation. Generic вопрос о требованиях, его свободный текст и сворачивание не разрешают такую операцию. Непрочитанный/свёрнутый blocker остаётся видимым в кратком состоянии; отсутствие ответа не трактуется как принятое рекомендованное решение.

Обработка ответа:

1. Backend проверяет question/version и текущие task/run revisions. Ответ старому диалогу не переписывает обновлённый вопрос.
2. Сохраняет фактическое сообщение пользователя/выбор с источником. Предложение модели и принятое решение различаются.
3. Строит небольшой proposed SDD delta: какие требования изменяются, почему и какие результаты затронуты. Не создаёт полный новый документ с потерей ручных разделов.
4. Детерминированно проверяет схему, ссылки/IDs, область правки и актуальные версии. Семантические противоречия разбирает модель/человек по необходимости; JSON validation не доказывает непротиворечивость бизнеса.
5. Применяет уже явно выбранное пользователем решение в разрешённой области без второй формальной просьбы. Если interpretation добавляет новое бизнес-решение или scope, показывает именно нерешённую часть; до её решения dependent work остаётся waiting.
6. Сохраняет новую requirement revision, affected-results projection и события; вызывает допустимый resume/rework по фактическому состоянию WorkflowEngine. Не использовать один универсальный «Продолжить» для waiting_input, needs_rework и blocked_budget.

Для tiny задачи delta может быть одной строкой критерия в Task, без полного templates/specification.md. Для сформированного SDD UI экспортирует его новую версию и diff затронутого раздела.

Reviewer/любая роль добавляет Recommendation: проблема, evidence, эффект, предлагаемое действие и статус proposed/accepted/deferred/rejected. Обязательный дефект в порученной области исправляется в рамках задачи; необязательная оптимизация остаётся отдельной рекомендацией. Кнопка «Принять предложение» создаёт явное scope/decision изменение с источником и проверкой последствий; reviewer не применяет несвязанный рефакторинг или внешнюю запись автоматически. Не создавать искусственный critic round на каждый click/опечатку.

## 9. Внешние ссылки, память и материалы

ExternalTaskRef — только связь с реально найденным источником: provider/server identity, external ID/URL, project/resource scope, retrieved_at, доступная revision/ETag/content hash, cache status и соответствующий task source. Название интеграции берётся из actual MCP inventory; не добавлять фиктивные Jira endpoints/tools. Sprut остаётся источником SCA/версий зависимостей, пока другой функционал не доказан.

Пользователь открывает прикреплённую внешнюю задачу/Confluence-страницу — UI показывает известный snapshot и stamp; нужное обновление выполняет разрешённый read. Внешний текст — данные, не новая инструкция с правами. Изменение локального Task/SDD не публикуется автоматически наружу. Для внешней записи нужны конкретный action/resource, действующее разрешение, pre/post ledger и проверка исхода; после timeout — сверка по external operation ID.

Память извлекается после текущих фактов Task и только global+данный project. Полезное принятое решение/исправление класса сохраняется по [SHARED_MEMORY](SHARED_MEMORY.md); временные выводы остаются в журнале задачи. Imported/expired memory не отменяет текущий source. Автосохранение не запускает отдельного агента и полного retro на каждое сообщение.

Материалы имеют настоящие files/revisions/hashes; SDD/design/incident/checkpoint используют существующие [шаблоны](MAIN_WORK_PROCESS.md), только применимые разделы. Изображения, шрифты и экспорт проверяются по [ASSET_RIGHTS](ASSET_RIGHTS.md). Нельзя заменить отсутствующий PDF/Office exporter переименованным текстовым файлом.

## 10. Малый процесс и измеряемая отзывчивость

personal_fast для личного GigaCode UI и established_strict для других рабочих проектов берутся из [routing](../config/routing.json) и [CHANGE_SAFETY](CHANGE_SAFETY.md). Риск session/data/recovery усиливает нужный тест внутри личного режима, не включает весь production-процесс автоматически. Quick/standard/deep остаются отдельным выбором маршрута.

Оптимизация по умолчанию:

- Текущее состояние, overview/checks/материалы читаются из локальной проекции; нет модели и нового чтения внешней системы на переключение вкладки.
- Event-driven обновление затронутого view, пакетная отрисовка stream и pagination журнала; raw logs подгружаются по запросу.
- Native helpers, schema/hash/diff/index checks вызываются как сервисы; **0 PowerShell invocations на normal task turn** после native cutover. Legacy bridge только временный по миграционному плану, без второго writer.
- Неприменимый docs update — короткий no-op с основанием в существующем Task. При изменении документа — delta и real docs-impact. Ретроспектива запускается по повторному/существенному событию либо запросу, не по факту закрытия Task.
- Одинаковые факты/решения не дублируются в чат, SDD, checkpoint и память полным текстом: сохраняется источник и нужные представления/ссылки. Подтверждённые ручные документы не перегенерируются без причины.

Пока нет измерений прототипа, не обещать конкретные миллисекунды или экономию токенов. Добавить наблюдения: время открытия Task/перехода к виду, IPC/DB/diff/retrieval и packet assembly отдельно, число model calls/tool calls/PS spawns, объём переданного контекста, memory cache hit с проверкой входов, доля stale evidence, ручные исправления и время до принятого результата. Сравнивать одинаковые задачи и версии. Быстрый рендер cached badge не подтверждает актуальность проверки.

## 11. Восстановление и типичные отказы

После restart backend загружает Task snapshot, active run, checkpoint и tail по sequence. UI reconnect подписывается с last_seen_sequence; повтор не дублирует событие, gap запрашивает отсутствующий диапазон. Model context формируется после проверки источников и pending actions. Не пересылать последний prompt автоматически.

| Сбой | Ожидаемое поведение |
|---|---|
| Два окна одновременно отвечают на вопрос | Один ответ принят по CAS; второе видит конфликт и актуальную версию. Ни один не теряется молча |
| Question overlay A свёрнут/Escape, затем открыта B и пришёл ещё вопрос | Draft/выбор A сохранены, B не получает её target; текущая форма не вытеснена, очередь без modal storm. Reopen из anchor/count восстанавливает тот же вопрос; permission не разрешён автоматически |
| Ответ модели пришёл после смены критерия | Artifact сохраняется как результат прежней базы; acceptance не закрывается без проверки применимости |
| Двойной click «Выполнить» | Один command_id/dispatch; изменение payload с прежним ID отвергается |
| Cancel отправлен, затем пользователь отправляет следующий prompt | Следующий остаётся queued до terminal исходного turn; другая независимая сессия работает |
| CLI упал после возможного MCP write | Pending/unknown видно в Task; recovery сверяет факт, не повторяет effect |
| Старое окно получает поздний update | Connection generation/session binding не позволяет изменить новый чат |
| Внешний документ изменён, cache ещё старый | Видны stamp и stale/unknown условия; существенный вывод не подтверждается старой копией без адресной проверки |
| Reviewer предложил несвязанную оптимизацию | Она остаётся proposal; diff и approved scope не меняются |
| Controller completed, но изменён accepted evidence | Integrity error, Task не показывает прежний pass как актуальный |
| Открытие Task/материала при недоступной модели | Уже сохранённые факты/diff/evidence доступны; новое модельное действие явно недоступно, не имитируется |
| Перенос/скрытие Task/browser/terminal панели во время работы | Сохраняются resource ID и task binding, процесс не дублируется и не останавливается; pinned view не принимает результат другой выбранной задачи |

## 12. Восемь зависимых карточек реализации

Привязки M/N — к существующим [UI-плану](GIGACODE_UI_DEVELOPMENT_PLAN.md) и [native migration](NATIVE_WORKBENCH_MIGRATION.md). Сначала восстановить корректные M0–M2; не прятать проблему сессий под новым экраном. Названия TW — карточки этого дополнения, не ещё один workflow engine.

| Карточка | Зависимости | Ограниченный результат | Приёмка, включая отказ |
|---|---|---|---|
| **TW1 Task aggregate и проекция** | M0–M2; N1–N4 | Сопоставить реальные файлы backend, добавить Task/schema/links и auto-create из поручения; связать один существующий run/chat | Tiny task без wizard; importer не объединяет равные заголовки; stale Task CAS отвергнут; run status остаётся у WorkflowEngine |
| **TW2 Обзор и обсуждение** | TW1; общий PanelRegistry/layout в M3 и нужная часть N10 | Один task header, discussion и task-view registrations; on-demand пустые виды не занимают экран | Move/resize/hide/reorder/tab сохраняют binding/layout, не создают run/prompt/PTY; overview без модели; два окна показывают один snapshot+tail |
| **TW3 Routing и короткий packet** | TW1; N6 | Подключить текущие profiles/workflows и targeted retrieval; один quick-backend/quick-doc end-to-end | Уточнение остаётся в run; unsupported capability блокирует нужное действие; hash change инвалидирует context reuse; никакого PS на turn |

На каждую карточку модели выдаётся только цель, реальные paths/revisions, нужные источники этого документа, критерии, bad case и разрешённая область. После карточки — один короткий результат с evidence и следующей зависимостью, а не новый большой отчёт. Unit/fixture checks подтверждают контракт; живой изменённый Electron/CLI сценарий проверяется там, где затронута интеграция. Никакие проверки прототипа этим документом не объявляются выполненными.
