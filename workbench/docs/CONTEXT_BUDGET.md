# Контекст до 256k: небольшой рабочий набор, полный журнал восстановления

Статус: архитектурный контракт и предлагаемые проверки, **не выполненная настройка GigaCode**. Дата: 2026-10-09. Пользователь сообщил номинальное окно около 256k у большинства используемых моделей. Это ориентир планирования, не подтверждённый лимит каждого alias, провайдера или CLI. Действующий предел устанавливается для конкретной модели и конфигурации. Сохранять каждый рабочий шаг нужно для восстановления; передавать весь журнал модели при каждом ходе не нужно.

Связанные контракты: [Task packet](TASK_WORKSPACE.md), [журнал](JOURNAL.md), [общая память](SHARED_MEMORY.md), [Flash execution](FLASH_MODEL_EXECUTION.md), [нативный перенос](NATIVE_WORKBENCH_MIGRATION.md), [исследованный Qwen](QWEN_BASELINE.md). Правила действуют во всех профилях, с сохранением `personal_fast` для личного UI и подходящего режима других проектов. Экономия контекста не отменяет требования, scope, полномочия или проверки результата.

## 1. Что хранится и что получает модель

| Слой | Содержимое | Загрузка в модель |
|---|---|---|
| Durable event journal | Все наблюдаемые шаги, вопросы/ответы, решения, изменения, проверки; IDs, sequence/revision, источник, результат и ссылки на payload | Только нужный диапазон/delta; остальное доступно адресно |
| Immutable evidence/payload | Очищенные результаты инструментов, версии артефактов, receipts, hashes и bounded source snapshots | Нужные фрагменты, а не весь файл/лог |
| Checkpoint + Task index | Текущая цель, принятые требования/решения, версии, статус этапа, pending effects, вопросы, рекомендации и следующий шаг | Основа восстановления и нового рабочего набора |
| Scoped shared memory | Долгосрочные предпочтения и знания выбранного проекта с происхождением/статусом | Несколько релевантных записей; устаревшее требует проверки |
| Prompt pack | Минимальные актуальные инструкции, факты и материалы конкретного шага | Ограниченный вход текущего обращения |

Journal — фактическая история, checkpoint — производная проекция. Новое свидетельство не переписывает старое событие: добавляется коррекция/замена с источником. Резюме модели не становится authority, не превращает proposed в accepted или unknown в verified. Противоречия сохраняются с обеими ссылками до явного решения. Сжатие не меняет принятые требования, разрешения и workflow statuses.

Полный журнал остаётся на диске/в native EventStore. Сохранность требует работающей записи и доступных evidence; восстановить незаписанный вызов или удалённый источник невозможно. Текущий текстовый пакет предусматривает явный `record`; автоматический host сможет покрывать только реально наблюдаемые им границы. Если Giga не раскрывает внутренние вызовы инструментов, UI обязан показать coverage gap, а не обещать запись всех скрытых шагов.

## 2. Бюджет всего запроса, а не только пользовательского текста

Capability record хранит model alias + фактический model ID, provider, CLI build/config fingerprint, limit kind, значение, источник и время проверки. Не переносить 256k между aliases. Если источник различает maximum input и совместный input+output window, хранить оба ограничения отдельно.

Обозначения для одного обращения:

- `C` — минимальный **подтверждённый совместный** context limit модели, endpoint и CLI; неизвестные ограничения остаются unknown.
- `I` — отдельный подтверждённый input limit, если он существует.
- `P` — весь вход: system/developer/project instructions, tool schemas, накопленная история, новый pack, tool results, изображения/вложения и protocol overhead. Cached input также занимает окно.
- `O` — резерв фактически запрошенного/настроенного maximum output, ограниченный реальным output limit. Учитывать reasoning/output правила провайдера, если они раскрыты; не резервировать только длину видимого ответа.
- `G` — запас на ошибку оценки и известный ожидаемый прирост внутри turn. Его компоненты показываются отдельно; запас не гарантирует вместимость неограниченного tool loop.

Для наблюдаемого полного запроса предлагается ограничение:

```text
allowed_input = min(known I, 0.80 × C, C − O − G)
send only when conservative_upper_bound(P) ≤ allowed_input
```

Отсутствующее `I` не добавляет ограничения; неизвестное `C` не превращается в бесконечность или verified 256k. В таком случае есть только предварительный бюджет собственного pack и явно неполная оценка общей вместимости. До подтверждения использовать небольшой pack, консервативный резерв и проверку реального usage/errors; не показывать «осталось точно 173k». Host не может гарантировать соблюдение формулы для запросов, которые CLI собирает внутри себя и не раскрывает.

Предлагаемые ориентиры **TOTAL input**, включая весь overhead и историю, а не дополнение к ним:

| Контекстный размер шага | Целевой диапазон | Типичная задача |
|---|---:|---|
| quick | 6–12k tokens | Одна ясная локальная правка/вопрос |
| standard | 24–48k | Связанный этап с несколькими источниками и проверкой |
| deep | 64–96k | Обоснованное межкомпонентное исследование |

Это стартовая политика, не измеренный размер пакета и не требование заполнить диапазон. `k` здесь — 1000 токенов. При меньшем реальном окне цели уменьшаются. Если одни system/tools/history уже занимают 14k, quick ≤12k **не выполнен**: показать overhead, выбрать больший обоснованный context tier либо проверенный способ сократить конфигурацию/создать новую сессию. Увеличение tier само по себе не расширяет scope, не меняет `personal_fast` на строгий процесс и не разрешает новые действия. Обязательные сведения нельзя молча обрезать ради цифры.

Считать сериализованный запрос совместимым tokenizer/count API, если он доступен. После ответа сверять с фактическим usage и выяснять расхождение. Если точного счётчика нет — `estimated`, метод, диапазон ошибки, покрытые компоненты и unknown overhead. Простое chars/4 не является точным счётчиком русского текста, кода, JSON и изображений. Как начальный запас для **оценённой** части можно заложить +25%; затем корректировать по наблюдаемым расхождениям. Это не доказанная верхняя граница. Не складывать полный запас повторно, если он уже включён в upper bound.

В usage отчёте отдельно показывать `pack`, `known_total_input`, `estimated_upper`, `unknown_components`, `output_reserve`, `guard`, `limit_source`. Новый MCP/tool schema footprint пересчитать при изменении binding fingerprint. Отсутствие полного каталога в нашем тексте не означает, что Giga перестал отправлять свои tool declarations.

## 3. Пять уровней давления на контекст

Проценты ниже — **предложение host policy**, не настройки или defaults Qwen/Giga. Они относятся к полному input `P/C`, когда он наблюдаем; резерв output и ограничение `allowed_input` могут сработать раньше.

| Уровень | Условие | Действие |
|---|---|---|
| Normal | <60% и хватает резерва | Добавлять только нужные delta; не выполнять профилактическое LLM-резюме каждого хода |
| Attention | ≥60% | Зафиксировать актуальные ограничения/pending, ограничить дальнейшие результаты инструментов, показать источник измерения |
| Prepare | ≥70% | Подготовить проверяемый checkpoint/handoff; выбрать подтверждённое native compression либо следующую сессию после безопасной границы |
| Hold outgoing | ≥80% **или** превышен `allowed_input`/не хватает output reserve | Не отправлять новый управляемый host запрос до сокращения/разделения; текущий turn не обрывать слепым restart |
| Unknown/overflow | Неизвестен полный usage, отсутствуют критичные данные либо получен context-limit error | Показать неопределённость; сохранить факты и исход операции; выбрать адресную проверку/recovery, не повторять тот же turn автоматически |

80% — дополнительный потолок, а не право занять 80% при большом `O`. Tool result внутри turn тоже увеличивает контекст. Для собственных tools host ограничивает возвращаемую порцию/пагинацию; чужую внутреннюю выдачу CLI он не контролирует без подтверждённого API. Возможность остановить следующий dispatch не равна возможности безопасно прервать текущий tool write.

## 4. Как собирать bounded prompt pack

ContextPacketBuilder/PromptAssembler использует существующие Task, Workflow, Memory и Evidence services, не создаёт второй state machine. Пакет имеет `packet_version`, source manifest/hash и следующие обязательные смысловые поля:

1. `project_id`, `task_id/task_revision`, `run_id`, workflow, stage, run revision и attempt_id; выбранный профиль, режим проекта, текущая цель и точный следующий шаг.
2. Принятые requirement/decision/acceptance IDs с текущей requirement revision; краткий обязательный контракт шага, allowed paths/resources и действующие полномочия. Релевантное ограничение нельзя заменить одной непрочитанной ссылкой.
3. Несколько проверенных фактов с evidence IDs, scope, source hash/revision/span и observed_at; hypotheses и неизвестное отдельно.
4. Незавершённые операции и способ reconciliation, блокирующие вопросы, конфликтующие сведения; также адреса неблокирующих вопросов и proposed/deferred рекомендаций, чтобы они не исчезли и не стали обязательной работой.
5. Delta с предыдущего подтверждённо доставленного pack: изменения требований, файлов, результатов и решений; конкретные выходные критерии/schema.

Сначала загрузить применимое ядро и **один текущий профиль/этап**, затем необходимые источники. Не читать на каждом ходе весь SDD, все профили, весь monorepo, shared memory и полный MCP inventory. Catalog/index — навигация; исходный факт извлекается адресно. Переход роли загружает нужные новые инструкции и сохраняет применимые общие ограничения. Если подлинные обязательные правила не помещаются — разделить шаг или увеличить допустимый tier, а не произвольно выкинуть их.

Дешёвый адрес: `artifact/event ID + relative source path + byte hash/revision + span/query + observed_at`. Один path или mtime не доказывает неизменность. Для большого файла: ограниченный поиск → релевантный фрагмент → соседний контекст по необходимости. Для лога: summary/counts, конкретные ошибки и `has_more/next_cursor`; полная очищенная выдача остаётся доступна по payload ref. Усечённый результат явно помечается, не подаётся как полное доказательство отсутствия ошибки.

Существование файла в cache не доказывает, что модель его видела. Manifest фиксирует доставку данной сессии и версию инструкции. После compression/new session прежняя доставка не предполагается автоматически. При сомнении перечитать нужный небольшой фрагмент. Не прикладывать все screenshots повторно: одна актуальная область плюс ссылка на исходник; размер изображения считать по реальным правилам провайдера либо отмечать unknown.

Вид UI, счётчики, сортировку, hashes, CAS, docs-impact и выбор готового evidence вычисляет обычный код. Детерминированный checkpoint собирается из структурированных полей. Модель вызывается для нового анализа/семантического изменения, а не для пересказа неизменного журнала на каждом клике. Docs-impact определяет затронутые документы, но не доказывает их содержательную актуальность.

## 5. Подробное журналирование без раздувания prompt

Host автоматически пишет metadata до/после наблюдаемого чтения, поиска, tool call, изменения, проверки и существенного решения. Один read-only batch может содержать много индивидуально адресуемых steps с отдельными результатами; это не потеря детализации. Ссылки/короткие итоги возвращаются модели один раз. Не заставлять модель выполнять второй `record` для уже автоматически сохранённого вызова.

Перед внешним/файловым изменением durable `action_started` с operationId, target, intent, authorization_ref, исходной revision и reconciliation должен быть зафиксирован **до dispatch**; batching не откладывает эту запись до завершения. После — фактический ответ, проверка и `finished/unknown`. Ошибка записи обязательного pre-event останавливает соответствующий write, а не создаёт успех задним числом. Raw payload очищается от секретов и сохраняется отдельно с hash; журнал содержит источник и coverage. Не сохранять внутреннюю цепочку рассуждений.

Checkpoint создавать на содержательной границе, перед передачей/rollover и при нарастающем давлении, а не после каждого чтения. Поля берутся из [существующего шаблона](../templates/checkpoint.md); checkpoint ссылается на последний включённый event sequence. Пока новый checkpoint не проверен и атомарно committed, предыдущий остаётся действующим. Компрессия model context не удаляет journal/evidence и не обнуляет attempts/budgets.

## 7. Recovery и безопасный rollover

1. Прочитать последний committed checkpoint, Task/run/requirements revisions, pending registry и ограниченный хвост событий после checkpoint cursor. Если tail усечён, дочитать необходимые страницы через `has_more`; отсутствие записи не считается отсутствием операции.
2. Проверить integrity и соответствие project/task. Сверить hashes актуальных исходников, evidence и принятых требований; изменившееся пометить stale и адресно перечитать. При повреждённом checkpoint вернуться к предыдущему валидному и replay журнала кодом, не загружая весь replay в модель.
3. Восстановить constraints, решения, questions, рекомендации со статусами, полномочия, run/stage/attempt и израсходованные бюджеты. Summary не может самостоятельно «закрыть» criterion или вопрос.
4. Сверить незавершённые effects по фактическому состоянию/receipt. Неизвестный write остаётся unknown; не повторять внешний эффект и не присваивать ему success из резюме. Read-only recovery допустим до разрешения unknown, новый исполняющий turn — по действующим guards.
5. Для rollover дождаться terminal/idle текущего turn и урегулировать относящиеся к передаче effects/permissions. Тишина или `cancel_requested` не равны idle. Не запускать второй prompt поверх старого и не пересылать целиком прежний запрос «на всякий случай».
6. Атомарно сохранить handoff и link old→new session, сохранив тот же Task/run/attempt/лимиты. Новый исполнитель получает проверенный pack, текущие инструкции и следующий **невыполненный** шаг. Перезапуск клиента/окна сам по себе не создаёт новую model session; сначала восстановить существующее владение и подписку.

Rollover не отзывает разрешение пользователя в прежнем scope, не создаёт нового разрешения и не расширяет доступ. Если CLI не поддерживает запрошенное продолжение, показать фактическое ограничение. Нельзя одновременно обещать сохранённое скрытое состояние модели и создание чистой сессии.

## 8. Небольшие задачи реализации и проверка давления

Реализовывать отдельно: **CB1** capability/usage accounting и источник лимита → **CB2** bounded packet + manifests/delta → **CB3** durable steps/payload refs и проверяемый checkpoint → **CB4** safe handoff/recovery. Использовать существующие native services. Все пункты — план; целевой CLI на Windows здесь не запускался.

Проверочный сценарий: одна длинная Task проходит **минимум три rollover** в изолированных данных. Внести принятое ограничение, requirement revision change, вопрос без ответа, deferred recommendation, конфликт памяти и внешний эффект с неизвестным исходом. Между передачами скрыть/открыть окно и перезапустить клиент. Проверить:

- Constraints/IDs/requirements, scope, вопросы, статусы рекомендаций и budgets сохраняются без расширения полномочий; stale evidence не используется как current.
- Неизвестный эффект остаётся pending до реальной сверки; ни одно восстановление не дублирует external dispatch. Чаты/проекты не получают чужие факты.
- Pack содержит обязательные поля и укладывается в **измеренный либо явно оценённый** budget с overhead; hidden CLI компоненты отмечены unknown. Удаление старых tool payload из prompt не удаляет их recovery refs.
- Observer даёт **clean** на целых checkpoint+events; **known_bad** отклоняет намеренную потерю constraint/operation/revision или противоречивое резюме; **missing/empty** возвращает insufficient evidence, а не pass.
- Отчёт содержит build/model/provider, метод token count, известные/неизвестные части, вход до/после каждого rollover, фактическое число передач, доставленных шагов, дублей и unresolved effects. Нулевой запуск не является подтверждением экономии или восстановления.

Текстовый пакет даёт правила и reference contracts. Реальные сокращение расхода, полнота авто-журнала и восстановление подтверждаются только измерениями готового host с конкретным GigaCode, без обещания заранее заданного speedup или безграничного контекста.
