# Небольшие поставки и разработка внутри GigaCode UI

Уточнения поставок от 2026-10-10: в **D5/M4** входит автоматический фоновый обмен сессий внутри проекта и между настроенными связанными проектами по [SESSION_COLLABORATION](SESSION_COLLABORATION.md). Отдельного peer composer/recipient/inbox/outbox/panel нет: пользователь видит Task progress/results/actionable blockers, техническая переписка сохраняется в diagnostics. В **D6/M5** основной агент координирует параллельные ветви: пользователь видит роли, модели, действия и результаты, может дать человеческое уточнение в существующей worker card и запросить адресную остановку; общий итог требует интеграционной проверки. Это обязательная поставка по [MANAGED_SUBAGENTS](MANAGED_SUBAGENTS.md). **D7/M6** уже включает создание Giga интерактивного макета, preview, screenshot/замечание и v2; расширение вариантов в D9 не откладывает этот первый цикл.

Цель — как можно раньше передать пользователю пригодную рабочую сборку, затем развивать приложение на реальных задачах внутри него, замечая ошибки и полезные улучшения. Это план для агента на компьютере с исходниками. **Сейчас все пункты ниже не выполнены:** репозиторий приложения и целевая Windows здесь недоступны; пакет содержит инструкции, текстовые исходники и графику, не собранный installer и не доказательство исправлений.

Порядок в продукте: **Project → Tasks → роли внутри Task**. Пользователь открывает проект, создаёт/продолжает задачу и получает результат. Роль определяет способ работы исполнителя внутри задачи; она не требует отдельного верхнеуровневого проекта или ручного создания чата для каждого этапа. Связи chat/run/ACP session сохраняются по [TASK_WORKSPACE](TASK_WORKSPACE.md) и [ROLE_ROUTING](ROLE_ROUTING.md).

## 1. Как читать отметки

D0–D13 — **контрольные точки поставки**, связанные с M0–M12 [основного плана](GIGACODE_UI_DEVELOPMENT_PLAN.md). Это не новые workflows, run statuses или второй controller. Детальные карточки выполняются в существующем Task/WorkflowEngine; отметка D — проекция принятого delivery receipt и фактической версии сборки.

- [ ] означает, что итоговая сборка этого checkpoint ещё не принята. В данном пакете так отмечены все поставки.
- [x] ставится на целевой машине только со ссылкой на build/revision, выполненные обязательные проверки, доступный результат и rollback. Отчёт модели, успешная компиляция или снятый один скриншот сами по себе отметку не закрывают.
- failed / blocked / not_run у отдельных проверок сохраняются как факты. Если checkpoint требует такую проверку, он остаётся [ ]; готовые независимые части не пропадают.
- «Проверить» ниже — короткий пользовательский пробный сценарий после фактической проверки агентом, не перенос всей QA-работы на пользователя.

Не давать модели весь backlog одним prompt. На один проход — маленькая карточка с наблюдаемым результатом, источниками/версиями, разрешённой областью и конкретным плохим случаем. Сложный checkpoint делится на несколько таких карточек, но пользователь получает одну понятную отметку версии. Context budget и подробный журнал разделены по [CONTEXT_BUDGET](CONTEXT_BUDGET.md) и [DESKTOP_OBSERVABILITY](DESKTOP_OBSERVABILITY.md).

Нельзя назвать D2 готовым, если задачи теряются, события требуют клика, A/B смешиваются или recovery слепо повторяет внешнее действие. Можно честно отдать D2 без полного native порта, расширенной автоматизации и IDE, с указанным временным bridge, если он пока реально используется.

D3 — ближайшее развитие первого рабочего интерфейса, не факультативное далёкое улучшение. Browser agent tools и скриншоты включаются в нём; advanced M7 не является условием их первого появления. Нужные tool bridge/permissions/schema проверяются по факту и не возникают от одного renderer browser panel.

Проверки D3/D5 для новых срезов: Files не путает main/worktree, сохраняет dirty buffer и отвергает stale/path-escape операции; папка не загружается целиком в prompt. Custom draft не объявляется установленным, publish/activation проверяют version/scope и существующий binding. Script promotion требует фактических проверок актуального hash/environment и сравнимых измерений; неверный output, отсутствие evidence и production-scope violation блокируют продвижение. Старый проверенный вариант доступен для rollback, а read-only каталог/макет не закрывает runtime gate.

## 3. Рабочая версия не должна уничтожать сама себя

Термины **stable** и **candidate/test** здесь — локальные каналы собственной разработки, не новые роли/статусы WorkflowEngine.

1. **Stable** — последняя реально проверенная версия, в которой пользователь ведёт текущую работу. Её бинарники/runtime и data dir не перезаписываются live-сборкой.
2. **Candidate/test** запускается отдельным app instance с отдельными userData, history/database, runtime selection, IPC ports и browser/session partitions. Не делить один mutable store между версиями. Перенос в candidate выполняется явным snapshot/import на копии с сохранением происхождения.
3. CLI runtime закрепляется за process/connection generation. Candidate не подменяет runtime активной stable session; изменение версии применяется к новым sessions по [BUNDLED_CLI_RUNTIME](BUNDLED_CLI_RUNTIME.md).
4. Тестовые writes выполняются в test checkout/worktree и разрешённых ресурсах. Если один исходный проект открыт обеими версиями, нужен один writer/явное владение. Разные userData не изолируют общий repository, порт, внешнюю job или account rate limit автоматически.
5. Перед smoke сохранить durable task/journal checkpoint и pending operations. Если требуется остановить именно работающий owner, сначала передать/сохранить контекст и закончить либо корректно сверить эффекты. Не убивать единственную рабочую среду, чтобы проверить её replacement.
6. Запуск/сборка/проверка candidate автоматизируется в порученной области; live test использует candidate и явно наблюдаемые IDs. Таймер тишины, закрытая панель или test cleanup не дают права остановить stable CLI/PTY.
7. После зелёных обязательных проверок подготовить отдельный build/receipt. Личная передача пользователю уже входит в поручение; обычные обратимые шаги не требуют новых согласований. Публикация наружу и распространение чужого CLI подчиняются отдельным фактическим правам.
8. Promotion — контролируемая смена запускаемой версии, а не замена файлов под текущим процессом. Перед несовместимой schema migration сохранить проверенный backup; убедиться, какая версия читает какой store. Исторические evidence/hashes не переписываются ради новой схемы.
9. Rollback выбирает предыдущий build/runtime и совместимый snapshot. Новые задачи/события candidate не отбрасываются молча: сохранить их export/journal и восстановить проверенным импортом/reconciliation. Не запускать старую программу на уже необратимо обновлённой БД без подтверждённой совместимости.
10. До готовности D2 сохранить внешний путь восстановления: известную рабочую сборку/команду запуска и инструкции чтения checkpoint. После D2 этот путь остаётся запасным. Разработка внутри приложения не означает зависимость от единственного непроверенного экземпляра.

Полный task history остаётся в durable store; prompt получает короткий packet. Не копировать credentials/секретные env в snapshot для отладки. Отдельные app profiles не означают автоматического права размножать account credentials.

## 4. Что выдавать после каждого checkpoint

Пользователь должен получить результат сразу после пригодной поставки, без ожидания всех M0–M12. Карточка поставки открывается из Task и содержит:

| Поле | Что действительно записать |
|---|---|
| Версия | D checkpoint, source revision/dirty fingerprint, build identity, платформа, CLI/runtimeRef |
| Запуск | Ссылка/путь на реально подготовленную сборку или точная проверенная команда; канал stable/candidate и data profile |
| Что изменилось | 1–3 наблюдаемых результата, связь с Task/acceptance; не перечень внутренних классов |
| Попробовать | До трёх коротких реальных действий с ожидаемым результатом |
| Проверено | Выполненные unit/contract/live checks отдельно, evidence refs и соответствующая revision |
| Ограничения | Отсутствующие возможности, not_run/blocked, временный bridge и другие существенные границы |
| Восстановить | Предыдущий build/runtime, backup/snapshot и проверенный путь возврата; незавершённые операции |
| Обратная связь | Действие «Сообщить об ошибке / предложить улучшение» с текущей Task/version и диагностикой по нужной области |

Пример формы receipt, **не заполненный результат**:

```text
Поставка: D… / build … / candidate или stable
Готово к пробе: …
Запуск: фактический путь/команда …
Проверь: 1) … 2) … 3) …
Проверено: … ; evidence: …
Не проверено / ограничения: …
Откат: … ; сохранённый checkpoint: …
Следующий маленький шаг: …
```

Если обязательный сценарий ещё не выполнен, можно выдать candidate для наблюдения с этим ограничением, но отметка checkpoint остаётся [ ]. Не называть «готовой рабочей версией» сборку, которая не прошла минимальные D2 gates. Отсутствующий installer не заменять скриншотом или обещанием; реальный Windows installer создаётся и проверяется на целевой машине, в текущую почтовую поставку входят только текст и разрешённая графика.

## 5. Обратная связь превращается в работу без лишних шагов

После D2 пользователь начинает маленькую настоящую задачу внутри приложения. UI фиксирует Task/project/build/runtime, выбранный сценарий и доступные correlation IDs; пользователь добавляет ожидаемое/фактическое поведение либо предложение. Локальный diagnostics bundle привязывается к записи, секреты/лишняя переписка не отправляются наружу автоматически.

- Ошибка текущего результата, уточнение acceptance или вопрос продолжают ту же Task. Контроллер делает законный rework/resume по фактическому run state, а не новый фиктивный run ради очищения счётчика.
- Самостоятельный значимый scope становится связанной Task в том же Project. Не размножать Tasks по каждому сообщению/пикселю и не смешивать разные проекты.
- Role routing по [ROLE_ROUTING](ROLE_ROUTING.md) автоматически выбирает подходящий способ работы: analyst описывает/критикует поведение; профиль разработки реализует; qa/reviewer подключаются по применимому маршруту. Пользователь направляет router запросом, ожидаемым результатом и ограничениями; ручного переключателя роли нет.
- Замечание имеет source/build, последствие, минимальный вариант и proposed/accepted/deferred/rejected. Принятый объём выполняется самостоятельно; новая бизнес-развилка с отсутствующим решением задаётся коротким вопросом.
- Regression/повторный серьёзный сбой вызывает адресный разбор/retro; обычный успешный task не вызывает полный отчёт. Проверенные неизменные данные переиспользуются с dependency stamps.

Не ждать отдельного «продолжай» после каждого разрешённого slice. Показывать короткий результат/следующий шаг и двигаться по принятому плану. Если недостающий факт блокирует одну область, сохранять её вопрос и выполнять независимую работу. Максимальная удобная автоматизация не означает автоматическую внешнюю публикацию, ввод неизвестных credentials или повтор unknown effect.

## 6. Приёмочные отказы процесса поставки

Эти проверки запланированы, а не выполнены на отсутствующем репозитории.

| Плохой случай | Требуемое поведение |
|---|---|
| Candidate падает на старте | Stable открывается прежним путём с прежними Tasks; сбой candidate и логи доступны |
| Candidate startup ошибочно выбирает stable userData/runtime | Проверка конфигурации отказывает до mutable access; не продолжать «временно» в общей БД |
| A/B завершились только последовательно | Parallel gate не passed: trace должен доказать перекрытие |
| UI ожил только после клика/reload | D1/D2 остаются [ ]; найденная граница исправляется и проверяется без спасительного input |
| Роль изменилась в Task | Принятые решения/IDs/контекст не теряются; новая роль не создаёт другой Project или неразрешённый scope |
| Есть browser panel, но агент не имеет настоящего tool | D3 browser-agent check unavailable/not_run; UI не заявляет управление и не закрывает checkpoint |
| Во время обновления выполняется внешняя операция | Старый owner/runtime сохраняется либо корректно завершается; unknown сверяется, не replay |
| Rollback не читает новую schema | Используется проверенный совместимый backup; новые события сохраняются для reconciliation, не удаляются |
| Пользователь сообщил defect в текущем результате | Связь с исходным Task/build и acceptance сохранена; применимый rework, без обхода attempts/budgets |
| На машине нет глобального CLI | Bundled candidate должен запуститься по manifest либо явно сообщить конкретный недостающий runtime; скрытого PATH fallback нет |

## 7. Поручение агенту на целевой машине

Продолжи существующий репозиторий по START-GIGACODE-UI и этому плану. Сначала найди фактические source/build/runtime и поставь подробную диагностику, затем последовательно D0–D2. Не отмечай уже выполненными пункты только потому, что они описаны в пакете. После проверенного D2 выдай пользователю рабочую сборку, краткий receipt, сценарий пробы и способ возврата; продолжай D3 и следующие принятые slices.

Веди Project → Tasks → роли внутри Task и один WorkflowEngine. Работай в принятом personal_fast, сохраняй контракты и реальные проверки. Исправляй и собирай candidate отдельно от stable, в которой пользователь уже работает. Базовые browser actions/screenshots нужны в M3; расширение M7 и IDE M12 идут позже. Доставляй полезные результаты по мере готовности, фиксируй обратную связь, не превращай весь план в один блокирующий релиз и не объявляй недоступную проверку выполненной.
