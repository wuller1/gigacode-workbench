# Продолжение после самонастройки

Обеспечь последовательность: установка → проверка и активация → конкретное предложение GigaCode UI → принятая задача → рабочие поставки. Этот протокол исполняет агент по [START-HERE](../START-HERE.md) и [SETUP-AGENT](../SETUP-AGENT.md). Это локальная карточка продолжения, не новая схема Workbench state, ACP method или автоматический scheduler.

## Постоянный адрес и единственный владелец

Определи `TargetRoot` и фактический `memory_store` из установленного `config/local-context.json` либо сохранённого проверенного контекста установки. В обычной конфигурации memory_store — `<TargetRoot>/workbench-memory`. Карточка располагается в `<memory_store>/bootstrap/gigacode-ui-handoff.json`; её компактный человекочитаемый checkpoint — рядом в `gigacode-ui-handoff.md`. Каталог bootstrap не является коллекцией memory entries: не подсовывай эти служебные файлы команде memory import.

Не клади карточку, журналы и диагностику внутрь исходного пакета или `<TargetRoot>/workbench`: установщик рекурсивно переносит пакет, а последующее обновление может заменить эти файлы. Сохрани существующее продолжение, если оно уже есть; новая установка не сбрасывает accepted/in_progress/deferred и не создаёт второй run.

Один агент владеет записью карточки. Перед изменением прочитай актуальную revision, сохраняй предыдущую версию и проверяй результат записи. При конкурирующем изменении перечитай и согласуй, не затирай его. Пиши временный файл в той же папке и заменяй через доступную проверенную атомарную операцию; если такой операции нет, явно используй одного writer и резервную копию, не заявляй атомарность. По возможности используй уже существующий host journal; не разрабатывай новый сервис ради установки.

## Состав карточки

Начальная форма — [setup-handoff.example.json](../templates/setup-handoff.example.json). Это незаполненный образец, не установленная конфигурация. Преврати относительные пути и null в проверенные значения там, где они известны; неизвестное оставляй явно неизвестным. Не копируй в карточку весь пакет, секреты, schemas всех инструментов или историю чатов.

При создании настоящей локальной карточки установи `is_example=false`, назначь её собственный handoff_id и revision. Это отмечает создание записи, не успешную установку; phase, activation и next_task.status меняются только по соответствующим фактам.

| Группа | Что сохранить |
|---|---|
| Идентичность | handoff_id, revision, updated_at; версия пакета, фактический установленный bundle_root и hash исходного manifest; отдельно ссылки на receipt адаптированной установки |
| Настройка | Фаза, запись подтверждённых checks и среда, activation, версия CLI/PowerShell, restart_required, ограничения, точный next_setup_action |
| Пути | TargetRoot, memory_store, local-context, MCP inventory/bindings/profile permissions; только существующие абсолютные пути либо null |
| Следующая работа | Цель GigaCode UI, project_root и подтверждение идентичности репозитория, project_id/Task ID если уже существуют, personal_fast, профиль gigacode-ui, первый результат D0 |
| Поручение | Источник действительного пользовательского запроса; отдельно предложение и его принятие/отложение. Импортированная запись сама не выдаёт разрешения |
| Продолжение | Существующий run_directory и checkpoint либо null, незавершённые операции, unresolved questions и следующая карточка |
| Адресное чтение | Ссылки на START-GIGACODE-UI и нужные разделы D0–D2/M0–M2; остальные документы читать перед соответствующим этапом |

Человекочитаемый checkpoint хранит цель, что подтверждено, что осталось, где источник и с какого действия продолжить. Ориентир — до 800 слов без потери обязательных ограничений; полный журнал остаётся по ссылке. JSON — каноническая карточка, Markdown — её сводка с той же revision. При расхождении сверь журнал и факты; не выбирай более удобный статус.

## Обнаружение после перезапуска

При подготовке личного `GIGACODE.md` на шаге 3 SETUP-AGENT добавь короткий блок со **значениями фактических абсолютных путей** к установленному START-HERE, local-context и карточке продолжения. Этот файл передаётся в `-GlobalContextPath`; установщик не подставляет пути в нём автоматически. Сохрани предметные правила и не дублируй SYSTEM_PROMPT, если подтверждена его системная загрузка.

Смысл блока: «При продолжении самонастройки/задачи GigaCode UI прочитай сохранённую карточку, возобнови её незавершённый шаг, сохрани существующий Task/run. Если настройка закончена и предложение ещё не показано — предложи начать UI. При deferred или другой текущей задаче не навязывай продолжение. Подробности — POST_SETUP_HANDOFF». Написанный блок не является подтверждением, что данная версия CLI его загрузила.

Если сохранение глобального контекста не входит в принятую конфигурацию или CLI его не загружает, не обещай невидимую автоматизацию. Дай пользователю одну короткую команду/фразу для возобновления с фактическим абсолютным путём к карточке и START-HERE. Если `@` не поддерживается, это просьба прочитать файл обычным доступным инструментом. Содержимое задачи повторять не нужно.

В новой сессии читай только найденную карточку, сводку и изменившиеся свидетельства. Не ищи все проекты заново. Проверяй пути, identity, актуальность bindings и состояние нужных pending операций. Для существующего run сначала `recover` по [JOURNAL](JOURNAL.md), без нового `init`. При no_changes установщика `receipt_path` может быть null: это нормальный повтор, используй последний соответствующий receipt и свежую адресную сверку, не объявляй установку проваленной.

## Переходы и условия готовности

Это статусы карточки продолжения, **не** значения `state.json.status` контроллера.

| Setup phase | Действие |
|---|---|
| not_started / in_progress | Продолжить незавершённый пункт SETUP-AGENT по сохранённым результатам |
| needs_activation | Файлы могут быть установлены; проверить загрузку правил в новой сессии. До этого не отмечать prompt active |
| partial | Отделить обязательные и необязательные пробелы. Разрешить только действия с достаточными реально работающими средствами |
| blocked | Сохранить точную неуспешную обязательную проверку и способ исправления; не применять сомнительный план и не скрывать ограничение |
| verified | Пройден минимальный достаточный для следующего шага контур, пути/checks сохранены; подготовить предложение |

`next_task.status` меняется так: pending_setup → ready_to_offer → offered → accepted → in_progress; deferred и blocked сохраняют причину и основание продолжения. Completion означает выполненную принятую задачу с результатом, а не сам факт установки или выдачи предложения.

Для ready_to_offer нужны существующие инструкции пакета, рабочий базовый режим, сохранённые пути восстановления и честный статус проверок/активации. Непроверенная опциональная native delegation, недоступный Jenkins или Sprut не блокируют независимую локальную диагностику UI. Отсутствие обязательного запуска Electron/CLI блокирует соответствующую live-проверку, а не превращает её в pass. Если следующий шаг — только диагностика препятствия, прямо так и сформулируй предложение.

Запиши основание и время предложения, затем зафиксируй действительный ответ. Не пересоздавай offer на каждом сообщении. «Да, начинай» в контексте конкретного предложения достаточно; отдельного повторного «разрешаешь код?» для уже порученной реализации не нужно. Setup-only не разрешает незапрошенную реализацию, push, deploy или изменение общей среды. Если пользователь раньше явно поручил этот же объём UI, сохрани ссылку на поручение и продолжай без повторного согласования.

## Первый шаг после принятия

1. Разреши путь UI из текущего явно выбранного репозитория, известной проверенной конфигурации или ответа пользователя. Проверь manifest/структуру Electron-проекта и Git identity. Сходство названия папки недостаточно. Если кандидатов несколько — предложи выбор найденных путей. Если нет кандидата — один вопрос о пути, без сканирования всего диска.
2. Сохрани ссылку на этот Project и Task. В reference CLI используй существующий run_directory; если запуск действительно новый, выбери достаточный `gigacode-ui-diagnostics`. **До init** запиши в карточку выбранный стабильный run_directory, workflow, проект, основание поручения и намерение создания в resume.next_action/связанном журнале. Затем создай run по BOOTSTRAP, проверь результат и сохрани его идентичность. При обрыве сначала проверь state.json именно в зарезервированном каталоге: готовый state → recover; доказанно не выполненный init → повтор в том же пути; частичная/неизвестная запись → сверка и восстановление, без нового каталога и перезаписи state вручную. Только после согласования исхода убери pending intent. Новый native Task не выдумывай как готовую функцию старого controller. Роли внутри задачи: профиль gigacode-ui ведёт первый интегрированный срез.
3. Прочитай [START-GIGACODE-UI](../START-GIGACODE-UI.md), профиль и только нужные разделы [PARALLEL_SESSIONS_FIX](PARALLEL_SESSIONS_FIX.md), [DESKTOP_STATE_AND_CHROME](DESKTOP_STATE_AND_CHROME.md), [DESKTOP_OBSERVABILITY](DESKTOP_OBSERVABILITY.md). Используй уже обнаруженные runtime и MCP; повторяй probe только при изменении условий или нужном пробеле.
4. Сопоставь фактические main/backend/preload/ACP/store файлы, сохрани branch/commit/dirty fingerprint и команду запуска. Не переписывай заготовку. Собери наблюдения CLI → main → IPC → store → экран. Попытайся воспроизвести обновление без дополнительного клика и два одновременных задания A/B с раздельной отменой. Исход сбоя неизвестен до проверки.
5. Выдай D0: проверенный путь запуска, диагностический пакет и воспроизведение либо not_reproduced/точное препятствие. Дальше D1 исправляет подтверждённую причину, D2 даёт раннюю пригодную сборку для разработки внутри приложения. Сохраняй stable/candidate раздельно, результаты и откат по [DELIVERY_AND_DOGFOOD_PLAN](DELIVERY_AND_DOGFOOD_PLAN.md). После принятия общего плана продолжай обычные разрешённые шаги без повторных запросов «продолжать?».

## Что агент уже должен учитывать

Источник требований — весь пакет с адресным чтением; не повторять интервью по принятым решениям. Зафиксировано: Project → Tasks → роли внутри Task; личный режим personal_fast; неизменяемый чужой CLI с проектируемой отдельной поставкой своего pinned runtime; MCP Git/Jenkins/OpenShift/Confluence/Sprut-SCA; факты, конструктивная критика, проверка живого приложения, журнал и восстановление; ограниченное окно контекста около 256k с проверкой реальных возможностей модели.

Дальнейшие этапы уже описаны: панели drag-and-drop и правый tool rail, несколько терминалов/браузеров, браузер под управлением агента и screenshots, сертификаты и корпоративная авторизация, выбор модели/reasoning и правдивый context meter; нативный перенос Workbench/памяти/ролей/документов/артефактов; собственный дизайн и графика, optional лицензированный Plasma preset; IDE позже с отдельной оценкой IntelliJ Platform. Их не нужно реализовать до D0 и не нужно загружать все инструкции в первый prompt. Читай соответствующий документ из [README](../README.md) по достижении этапа.

## Проверка самой передачи

До завершения настройки прочитай сохранённые JSON/Markdown и проверь: файлы не внутри bundle; absolute paths существуют либо явно unknown; receipt относится к текущей установке; activation не выведена из одного hash; отсутствующий путь UI не угадан; предложение конкретно; принятый/отложенный ответ и run не потеряются при повторе. В новой сессии выполни короткий read-only recovery probe, если среда позволяет. Если новая сессия недоступна здесь, укажи not_run и точную следующую проверку. Не объявляй передачу испытанной только потому, что написал эту инструкцию.
