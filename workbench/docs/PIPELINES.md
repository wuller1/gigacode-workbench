# Каталог pipelines GigaCode Workbench

В каталоге находятся **29 workflows, 9 профилей и 143 этапа**. Актуальные состав и порядок этапов определяют JSON-файлы в `workflows/`; этот документ поясняет их выбор. Это формат **данной оболочки**, а не нативная конфигурация GigaCode, Qwen CLI или MCP. Наличие JSON-файла не доказывает, что конкретная версия CLI умеет запускать такой процесс: чтение описаний, сохранение состояния и вызовы исполнителей реализует host/runner оболочки.

Профиль отвечает за способ работы исполнителя; workflow задаёт порядок работы над конкретным типом задачи. Один профиль участвует в нескольких workflows. Небольшое исправление не обязано проходить discovery и полный SDD. Количество профилей или workflows само по себе не гарантирует покрытия всех задач разработчика: каталог расширяют по подтверждённым пробелам реального проекта.

| [infrastructure](../workflows/infrastructure.json) | Нужно изменить конфигурацию целевого кластера | Проверенное состояние окружения и запись изменения |

| [design-audit](../workflows/design-audit.json) | Нужно оценить и улучшить существующий UI | Измерения до и после, исправления и независимое ревью |
| [design-system](../workflows/design-system.json) | Нужны правила, токены и компоненты продукта | Проверенная версия дизайн-системы и порядок сопровождения |
| [pull-request](../workflows/pull-request.json) | Изменения нужно оформить и представить на ревью | Опубликованный PR и актуальный статус готовности |
| [release](../workflows/release.json) | Нужно выпустить конкретную версию через CI | Доставленный артефакт и подтверждённый результат |

| [retrospective](../workflows/retrospective.json) | Запрос пользователя, инцидент, повторный сбой, переделки требований или новый полезный pattern | Проверяемая причина и небольшие предложения без изменения prompts |
| [gigacode-ui-diagnostics](../workflows/gigacode-ui-diagnostics.json) | Сбой своей Electron/ACP-оболочки | Причина, исправление и реальная проверка приложения |
| [gigacode-ui-feature](../workflows/gigacode-ui-feature.json) | Небольшая функция личной оболочки | Контракт, реализация, live-проверка и handoff |

Обычные маршруты:

- Новая функция: discovery → specification → backend-feature и/или frontend-feature → review → acceptance → pull-request → release. Порядок PR, общей приёмки и релиза согласуется с процессом проекта; часть QA и ревью выполняется ещё во время разработки.
- Ясный локальный дефект с низким риском: quick-backend либо quick-frontend; при необходимой отдельной диагностике — bugfix. PR и release добавляются, если входят в задачу. Полная спецификация нужна при существенной неопределённости поведения или контрактов.
- Изменение функции: behavior-change; при большом влиянии добавляются specification, frontend-feature и data-migration.
- Существующий незнакомый проект: чтение инструкций и целевое исследование в текущей задаче; при самостоятельной задаче исследования — discovery, для небольшого вопроса — quick-answer. Настройка проекта не запускается автоматически.
- Явно порученная настройка нового проекта: onboarding → выбранный рабочий сценарий. Универсальные шаблоны и настройки применяются только по необходимости в запрошенной области.
- Сбой: incident → связанный bugfix, infrastructure или data-migration → проверка восстановления в incident.
- Новый интерфейс без готового дизайна: ux-design → specification либо frontend-feature.
- Качество существующего интерфейса: design-audit; отсутствие устойчивых правил и компонентов может вести в design-system.
- Новая или существенно изменяемая дизайн-система: design-system → применение в frontend-feature → целевой design-audit.
- Документация: сначала определить влияние; при доказанном no-op достаточно записи в текущем журнале, при точечной правке — quick-doc, при смысловом изменении — documentation.
- Ретроспектива: по значимому триггеру или запросу → retrospective; обычное завершение небольшой задачи не запускает полный разбор.

Стрелки между workflows описывают передачу артефактов. Они не означают, что вложенный запуск, ожидание другого workflow и объединение ветвей уже автоматически поддерживаются конкретным runner. Host должен связать исполнения и их версии; при отсутствии такой функции передачу выполняют явно.

## Контракт этапа

Каждый JSON содержит `schema_version`, `id`, `title`, `description` и упорядоченный массив `stages`. У этапа есть:

- `id` — стабильный идентификатор внутри workflow;
- `profile` — один из `analyst`, `spec`, `backend`, `frontend`, `devops`, `qa`, `reviewer`, `diagnostics`, `gigacode-ui`;
- `instructions` — конкретные действия и границы результата;
- `required_artifacts` — логические идентификаторы обязательных результатов, а не заранее созданные файлы и не команды;
- `checks` — критерии перехода с `id`, `description`, `kind` и `allow_na`;
- `capabilities` — потенциально нужные возможности; обязательность определяется применимыми действиями и проверками этапа;
- `rework_targets` — допустимые возвраты только на существующие предыдущие этапы этого workflow.

Нормальный переход ведёт к следующему элементу `stages`. Возврат запускают по указанной причине, связывая её с артефактом или проваленной проверкой. Первый этап не имеет предыдущего этапа: уточнение его входа выполняется в текущем этапе. Переход в другой workflow оформляется как связанная работа и не записывается в `rework_targets`.

У `kind` три значения:

| Kind | Что подтверждает |
|---|---|
| `artifact` | Требуемый результат существует, читается и содержит необходимые сведения |
| `execution` | Действие действительно выполнено и имеет наблюдаемый результат |
| `judgment` | Обоснованное содержательное заключение по доступным свидетельствам |

Для исполнительных проверок полезны точная ревизия, среда, команда или инструмент, идентификатор операции, время и результат. Фраза агента «проверил» сама по себе не подтверждает выполнение. Host должен предоставлять доступ к фактическим результатам действий; декларативный workflow этого доступа не создаёт. Успешный выход процесса CLI также не является доказательством завершения этапа.

Если `allow_na` равен `false`, check обязателен для выбранного маршрута. При `allow_na: true` неприменимость требует предметного обоснования и свидетельства; отсутствие нужного инструмента или неизвестный результат не являются неприменимостью. Инструкции иногда требуют выбрать применимые проверки — например, smoke-сценарий сервиса или проверку опубликованного пакета. Это выбор содержания проверки, а не разрешение отметить весь этап выполненным без действия. Для существенно другого процесса следует выбрать или адаптировать workflow до запуска. Недоступная обязательная проверка остаётся блокировкой.

### Вопросы, блокировки и доработка

- Если отсутствует бизнес-решение, которое меняет корректность или внешнее поведение, этап переходит в `waiting_input` с конкретным вопросом, вариантами при необходимости и объяснением влияния. Уже полученный ответ сохраняется и повторно не запрашивается без новой причины.
- Недоступная интеграция, среда или обязательная проверка — техническая блокировка с описанием зависимости и способа продолжения. Её нельзя скрыть фиктивными данными или успешным ответом.
- Обратимое техническое решение исполнитель может принять самостоятельно в пределах задачи, записав обоснование. Полное отсутствие любой неопределённости не является условием разработки.
- Независимая работа может продолжаться, если её входы известны и host умеет вести её отдельно. Это не даёт права считать заблокированный этап пройденным или выполнять зависимые шаги.
- При доработке существенное изменение входа делает затронутые последующие результаты требующими перепроверки. Нельзя переносить результаты тестов старой ревизии на новый код без основания.
- Число автоматических возвратов и повторов ограничивает runner. По достижении лимита сохраняются результат, последняя причина и конкретное действие, необходимое для продолжения.

Тестовые doubles допустимы в тестах. Согласованный прототип может использовать примерные данные. Оба случая должны быть явно обозначены; они не доказывают работу реальной интеграции и не должны попадать в продукт как незаметная замена функции.

### Capabilities и полномочия

`capabilities` — перечень потенциально нужных возможностей конкретного этапа, **не выдача прав и не разрешение совершить действие**. Недоступность блокирует обязательное применимое действие; неприменимость устанавливается по инструкции/check с обоснованием, а не по отсутствию инструмента. Доступ проверяет host. Runner, читающий JSON, не создаёт MCP-подключения, учётные записи, sandbox и ограничения доступа. Даже наличие `git.push`, `ci.run`, `cluster.apply` или `data.migrate` не заменяет авторизацию пользователя для конкретной цели.

Уже выданные полномочия сохраняются на соответствующую область задачи: повторно спрашивать то же разрешение не требуется. Если действие выходит за эту область, ожидание решения происходит до выполнения. Для применения инфраструктуры, миграции и доставки важны точная цель и версия. Артефакты и журналы не должны содержать лишние секреты или чувствительные записи.

В общих workflows не требуется обязательное подключение базы знаний, кластера или конкретного сервера MCP. Дополнительные источники можно передать как документы либо подключить через разрешённые host-маршруты. `infrastructure` намеренно требует cluster-возможности; `release` описывает выпуск через CI; `data-migration` требует доступ к данным. Отсутствие этих возможностей нельзя компенсировать утверждением, что операция выполнена.

Имена серверов, API и команд берутся из фактической конфигурации проекта. Правила проектирования и проверки дизайна формируются для текущего продукта; внешний вид другого проекта не является заданным эталоном. Каталог не определяет назначение Sprut или реальные имена ваших MCP tools.

## Подробные маршруты

### 1. discovery — исследование задачи

**Вход:** запрос, доступный репозиторий, переданные документы и известные ограничения.

**Этапы:** context → problem → scenarios → options → requirements-check.

**Выход:** `discovery-requirements`, сценарии, решения, ссылки на основания и `discovery-open-questions`.

Сначала проверяется текущее устройство продукта, затем формулируются проблема и границы. Разработка новой функциональности без готового ТЗ начинается здесь. Проверка требований возвращает к контексту при неверном факте, к сценариям при пропуске поведения и к вариантам при нерешённом выборе. Технический эксперимент при необходимости оформляется ограниченной связанной работой с конкретным вопросом, а не готовой реализацией.

### 2. specification — интерактивная спецификация

Автор этапов SDD — analyst; readiness-review выполняет reviewer. Spec остаётся доступной формальной специализацией для других назначенных этапов/проверок. Аналитик также пишет brief, DOCX, stories и сценарии без обязательного полного SDD; выбирай достаточный маршрут по PROCESS_ADAPTATION. Реализация кода — отдельная роль внутри той же задачи.

**Вход:** требования либо достаточно конкретный запрос, фактическое состояние системы и доступные решения.

**Этапы:** baseline → behavior → contracts → readiness-review → implementation-plan → version.

**Выход:** `spec-version`, поведение, контракты, зависимости, план, трассировка требований и открытые вопросы.

Вопросы задаются небольшими группами по влиянию. После ответа проверяются затронутые формулировки. Противоречие содержит обе стороны, источники и последствия. Ревью полноты возвращает к поведению или контрактам; план возвращает к ревью при неподтверждённой готовности. Финальная фиксация возможна только для проверенной версии. Готовность оценивается для выбранной части реализации, а не обязательно для всего будущего продукта.

### 3. backend-feature — серверная функция

**Вход:** версия спецификации либо краткие достаточные требования, контракты и правила проекта.

**Этапы:** preflight → design → implement → validate → review → handoff.

**Выход:** `backend-change`, результаты проверок, ревью и `backend-handoff` для конкретной ревизии.

На этапе design определяются совместимость, API, права и необходимость миграции. Ошибки проверок возвращают к реализации; замечания ревью могут вернуть к проектированию, реализации или доказательствам проверки. При неизвестном внешнем поведении оформляется вопрос в specification. Недоступность реальной интеграции остаётся явной границей подтверждённого результата.

### 4. frontend-feature — интерфейс

**Вход:** пользовательская задача, контракты, ограничения продукта и доступная браузерная среда.

**Этапы:** hypothesis → options → contract → implement → measure → visual-review → handoff.

**Выход:** UX-гипотеза, иерархия экранов, варианты, `frontend-design-contract`, реализация, числовые результаты и отдельное независимое ревью.

Дизайн начинается с задачи пользователя и обоснования структуры, а не с копирования чужого интерфейса. Design contract задаёт геометрию, контраст, viewport/state matrix, методы, пороги и их источники. Нормативные основания отделяются от внутренних целевых значений проекта. Проверяются реальные действия, формы, ошибки, клавиатура и обязательные состояния. `measure` собирает детерминированные измерения, а `visual-review` независимо оценивает иерархию, композицию и ясность. Неизвестная величина не считается pass. Успешные числа не отменяют существенного визуального замечания и не сворачиваются в обещание качества по единому баллу.

Проблемы реализации возвращают к implement, неудачное решение — к options или contract. Затронутые функциональные проверки после исправления повторяются. Отсутствие браузера блокирует обязательную проверку. Передача содержит точную ревизию и пределы подтверждённого результата.

### 5. infrastructure — кластерная конфигурация

**Вход:** однозначная цель, требуемое состояние, репозиторий конфигурации, доступ cluster.read/apply и полномочия на изменение.

**Этапы:** baseline → plan → configure → validate → apply → verify.

**Выход:** план, конфигурация, результаты предварительных проверок, применения и окончательное состояние.

Обязательны наблюдение текущего состояния и проверка конкретной версии конфигурации. До применения существуют план проверки и применимый способ восстановления. Неуспех verify возвращает к плану, конфигурации или операции применения. Восстановление выполняется только предусмотренным и разрешённым способом; откат конфигурации не доказывает восстановление данных. Локальная среда существующего проекта сначала исследуется по его настройкам в текущей задаче; onboarding применяется только для явно порученной настройки нового проекта. Выпуск готового артефакта через CI относится к release.

### 6. acceptance — приёмка

**Вход:** критерии приёмки, точная ревизия, среда и данные.

**Этапы:** basis → cases → execute → triage → conclusion.

**Выход:** план и результаты проверок, дефекты, область повторной проверки и `acceptance-conclusion`.

Дефект содержит воспроизведение, ожидание, факт и окружение. Исправление выполняется связанным workflow; новая ревизия возвращает к basis и затронутым проверкам. Итог может быть «принято», «не принято» или «проверено частично». Последнее не является разрешением считать всю задачу принятой. UI-проверки требуют соответствующего реального инструмента host, а не только текстового описания экрана.

### 7. review — независимое ревью

**Вход:** исходная и целевая ревизии, требования, diff и результаты проверки.

**Этапы:** scope → inspect → verify → verdict.

**Выход:** конкретные замечания, свидетельства их проверки и заключение по ревизии.

Замечания объясняют сценарий сбоя и последствия. Проверка ключевых утверждений включает реальные целевые действия. Новые изменения возвращают к области и содержанию ревью; спорное требование возвращается владельцу спецификации через связанную работу. Неподтверждённая стилистическая предпочтительность не становится блокирующим дефектом автоматически.

### 8. incident — инцидент

**Вход:** симптом, время, окружение, доступные логи и ограничения воздействия.

**Этапы:** triage → evidence → hypotheses → recovery-plan → verify → postmortem.

**Выход:** факты, проверенные гипотезы, связанный план исправления, проверка восстановления и профилактические действия.

Процесс не требует cluster.apply для любого расследования. Внешние данные предоставляются через отдельные разрешённые возможности или экспорт. Исполнительное восстановление выполняется в bugfix, infrastructure либо data-migration; этап verify ждёт реальные результаты этой связанной работы и проверяет исходный симптом. Неподтверждённая причина остаётся гипотезой. Неуспешное восстановление возвращает к фактам, гипотезам или плану.

### 9. onboarding — настройка нового проекта по запросу

**Вход:** явное поручение настроить новый проект, репозиторий, доступная локальная среда и известные ограничения.

**Этапы:** inventory → environment → setup → smoke → handoff.

**Выход:** карта проекта, требования среды, фактический результат запуска, исходные проверки и памятка.

Маршрут активируется только для явно запрошенной настройки нового проекта. Незнакомый существующий репозиторий, отсутствие собственного файла Workbench или обычная ошибка запуска не означают поручения переустроить проект. Для такого репозитория сначала прочитай действующие инструкции и выбери рабочую задачу без setup.

Необходимые внешние доступы отделяются от локальных зависимостей. Используются существующие lock-файлы и принятые инструкции; конкретный стек, расположение репозиториев и набор hooks не предполагаются. Создаются только необходимые запрошенные файлы, готовые настройки не заменяются. Неудачный запуск возвращает к требованиям среды или настройке. Исходные дефекты записываются отдельно от ошибок настройки; памятка помечает непроверенные шаги.

### 10. bugfix — исправление дефекта

**Вход:** симптом и источник ожидаемого поведения.

**Этапы:** reproduce → diagnose → fix → validate → review.

**Выход:** воспроизведение, причина, diff, регрессия и заключение.

Полный SDD не требуется. Если ожидание спорно, сначала нужен бизнес-ответ. Реализацию локального исправления по умолчанию выполняет профиль backend; крупная UI-доработка передаётся в frontend-feature с артефактами диагностики. Провал воспроизведения после исправления возвращает к fix, неверная гипотеза — к diagnose. Невоспроизводимый сбой не объявляется доказанно исправленным только по правдоподобному diff.

### 11. behavior-change — изменение поведения

**Вход:** работающая функция и требуемая дельта.

**Этапы:** baseline → delta → impact → implement → validate → review.

**Выход:** сравнение до и после, план совместимости, реализация и проверка новой и сохраняемой функциональности.

Сохраняемые контракты указываются явно. Малой правке достаточно краткой дельты. Затронутые UI и миграции при необходимости получают связанные workflows. Неожиданное влияние возвращает к impact; спор о поведении — к delta. Ревью проверяет отсутствие скрытого расширения объёма задачи.

### 12. refactor — рефакторинг

**Вход:** конкретная проблема структуры и границы сохраняемого поведения.

**Этапы:** baseline → plan → change → validate → review.

**Выход:** изменение структуры и сравнение поведения до и после.

Baseline выполняется до правки, включая известные исходные сбои. Новые функции и случайно обнаруженные дефекты не смешиваются с рефакторингом без решения о расширении задачи. Если сравнение выявляет изменение контракта, возврат идёт к change либо plan. Ревью проверяет и сохранение поведения, и достижение исходной цели упрощения.

### 13. dependency-upgrade — зависимости

**Вход:** текущие версии, цель обновления и выбранные целевые версии.

**Этапы:** inventory → compatibility → upgrade → validate → review.

**Выход:** согласованные manifest/lock-файлы, адаптации и фактическая матрица совместимости.

Breaking changes берутся из доступных официальных источников. Доступ к ним предоставляет host или пользователь; имя конкретного внешнего инструмента не задано. После обновления выполняются установка, сборка и значимые сценарии. Неуспех возвращает к upgrade, ошибочная оценка совместимости — к compatibility. «Последняя версия» не заявляется без актуального основания.

### 14. data-migration — данные

**Вход:** источник, назначение, требования преобразования, разрешённые среды и полномочия.

**Этапы:** baseline → plan → prepare → rehearse → execute → verify.

**Выход:** миграция, репетиция, запись целевого выполнения и проверка целостности.

До исполнения определяются поведение при частичном сбое, повторный запуск, совместимость версий и применимое восстановление. Репетиция проводится на разрешённых репрезентативных данных. Нельзя придумывать бизнес-значения для заполнения неизвестных полей. Провал постпроверок возвращает к плану, реализации или исполнению по характеру причины. Успешный exit code не заменяет проверку инвариантов данных.

### 15. performance — производительность

**Вход:** симптом, метрика, целевое значение и разрешённая нагрузочная среда.

**Этапы:** baseline → hypotheses → experiment → improve → validate → decision.

**Выход:** измерения до и после, проверенное изменение и решение принять, доработать или отклонить.

Условия измерения и разброс фиксируются. Эксперимент имеет ограниченный вопрос и не объявляется продуктовой реализацией. Если эффект не подтверждается, workflow возвращается к гипотезам; если страдает корректность — к изменению. Результат локального измерения нельзя без основания переносить на production. Итог может обоснованно рекомендовать отказаться от изменения, сохранив полученные знания.

### 16. ux-design — пользовательский опыт

**Вход:** пользовательская задача, доступные исследования и ограничения продукта.

**Этапы:** hypothesis → options → contract → prototype → measure → visual-review → handoff.

**Выход:** UX-гипотеза, иерархия экранов, обоснованный выбор варианта, `ux-design-contract`, прототип, измерения и независимое заключение.

Варианты сравниваются по задачам пользователя и ограничениям. Для локального изменения допустим один вариант с обоснованием; искусственные альтернативы не нужны. Контракт определяет действия, состояния, геометрию, контраст и обязательную матрицу viewport/state coverage с источниками порогов. Прототип отделяется от готовой функции, примерные данные и отсутствующие интеграции помечаются. Экспертный проход не называется исследованием с пользователями. Неудачный путь возвращает к гипотезе, вариантам или прототипу; неподтверждённые измерения остаются неизвестными. Передача в реализацию содержит проверяемые решения, числовые результаты и отдельную экспертную оценку, а не только изображение или общий балл.

### 17. pull-request — PR и обратная связь

**Вход:** изменения задачи, определённая целевая ветка и полномочия на публикацию.

**Этапы:** state → validate → commit → publish → feedback → readiness.

**Выход:** подтверждённые коммиты, URL PR, опубликованная ревизия и актуальный статус готовности.

Чужие изменения не включаются автоматически. Существующие подходящие коммиты можно подтвердить вместо создания дубликата. Замечания и конфликты направляются на связанную доработку, затем возвращают процесс к проверке, коммитам и публикации. Разрешение конфликтов требует сохранения согласованного поведения обеих сторон. Этот workflow не выполняет merge: «готово к слиянию», «ожидает ревью» и «слито» — разные результаты. При необходимости слияние оформляется отдельным явно разрешённым действием host с повторной проверкой состояния.

### 18. release — выпуск через CI

**Вход:** ревизия, версия, результаты приёмки, существующие процессы CI и цель доставки.

**Этапы:** candidate → plan → build → deliver → verify → close.

**Выход:** артефакт с подтверждённым происхождением, результат доставки, проверки и релизная запись.

План различает пакет и сервис, задаёт конкретные процессы и параметры. Доставка использует проверенный артефакт; незаметная пересборка меняет основание проверки. Готовый подходящий артефакт можно подтвердить вместо повторной сборки. Неуспех возвращает к плану доставки или восстановления. Cluster-доступ не является обязательным, если достаточные сведения даёт существующий CI-процесс. Отдельная миграция сохраняет собственные условия и проверки.

### 19. documentation — обновление по влиянию

**Вход:** область запроса, актуальные ревизии, diff задачи, существующие документы и принятые требования.

**Этапы:** impact → delta-checks → selective-review.

**Выход:** `docs-impact`, `docs-delta`, `docs-mechanical` и `docs-conclusion`: карта влияния, изменения разделов, фактические проверки и обоснованный итог.

Изменённые символы, контракты и операционные действия сопоставляются с конкретными утверждениями документации. Существующий долг учитывается отдельно; локальная задача не запускает полную генерацию docs. Обновляются затронутые разделы, индекс и глоссарий — один раз при необходимости. Механические проверки ссылок, схем и snippets предшествуют независимому смысловому ревью, которое требуется только при существенном влиянии. Подтверждённые свидетельства можно использовать повторно после сверки значимых hashes, ревизий и окружения.

Код подтверждает фактическое поведение, но не отменяет согласованное требование: конфликт явно сохраняется и направляется в SDD. Проблема области возвращает к impact, ошибка раздела или проверки — к delta-checks. Внешняя публикация не предполагается автоматически.

Доказанный no-op предпочтительно установить до создания run и записать в исходной задаче. Если run уже создан, он остаётся линейным: неприменимые проверки оформляются с разрешённым `not_applicable`, объяснением и свидетельством; обязательные артефакты сохраняются. Отдельные модельные вызовы для такого оформления не нужны. Детали и границы механизма описаны в [DOCUMENTATION_AND_RETROSPECTIVE.md](DOCUMENTATION_AND_RETROSPECTIVE.md).

### 20. security-review — безопасность

**Вход:** область изменения, ревизия, данные, среды и разрешённые способы проверки.

**Этапы:** scope → model → analyze → verify → findings → closure.

**Выход:** модель угроз, подтверждённые находки, план исправления и заключение с ограничениями.

Проверки выбираются из реальных границ доверия. Сигнал сканера не считается автоматически подтверждённой уязвимостью. Исправления выполняются связанными workflows и перепроверяются. Существенный остаточный риск требует решения уполномоченного владельца; агент не принимает его молча. Заключение ограничено областью, ревизией и выполненными проверками и не гарантирует отсутствие всех уязвимостей.

### 21. design-audit — аудит и улучшение интерфейса

**Вход:** существующий интерфейс, проблемные симптомы, пользовательские задачи, ревизия и браузерная среда.

**Этапы:** scope → baseline → contract → improve → measure → visual-review → handoff.

**Выход:** исходные измерения, план и варианты исправления, `design-audit-contract`, diff, сравнение до и после и независимое заключение.

Сначала измеряется существующий интерфейс на явной матрице страниц, viewport и состояний. Геометрия, контраст и покрытие проверяются отдельно от экспертных наблюдений по иерархии и содержанию. Исправления связываются с конкретными проблемами, а пороги — с нормативным основанием или проектной целью. Нельзя улучшать формальные показатели, скрывая нужное содержание или удаляя сценарий. После исправления повторяются измерения и функциональная регрессия; ревьюер сравнивает реальные исходные и итоговые изображения. Неподходящий подход возвращает к contract, дефект — к improve, неполное свидетельство — к measure. Общий балл не является доказательством хорошего дизайна.

### 22. design-system — правила, токены и компоненты

**Вход:** задачи продукта, аудитория, существующие компоненты, потребители и ограничения команды.

**Этапы:** context → options → contract → implement → measure → visual-review → maintenance.

**Выход:** принципы системы, варианты и обоснование, `design-system-contract`, семантические токены, компоненты, представительные экраны и правила сопровождения.

Система создаётся для текущего продукта. Принципы типографики, пространства, цвета, композиции и содержания обосновываются задачами, а не чужим look. Контракт задаёт API и состояния компонентов, клавиатурное поведение, адаптивность, источники порогов и матрицу покрытия. Проверка включает геометрию, контраст, viewport/state coverage и поведение потребителей. Реальные представительные экраны нужны для независимого визуального ревью: одинаковые токены сами по себе не гарантируют хорошей композиции. Последний этап сохраняет версию, правила добавления компонентов, совместимость и миграцию. Проблемы принципов возвращают к options, контрактов — к contract, реализации — к implement.

## Измеримое качество дизайна

Общая политика находится в `docs/DESIGN_QUALITY.md`, конфигурация порогов — в `config/design-quality.json`, помощник измерений — в `tools/design-metrics.ps1`. Это ресурсы пакета; соответствующие ограничения целевого проекта передаются отдельно. Сам помощник не заменяет исследование пользователя, проверку поведения и независимое визуальное ревью.

Для каждого измеримого критерия design contract фиксирует:

- проверяемую страницу или компонент, viewport, состояние и ревизию;
- величину, метод и фактический результат измерения;
- порог и источник: нормативное основание либо цель конкретного проекта;
- статус проверки и ограничения метода.

Геометрия включает применимые размеры, перекрытия, обрезание и непреднамеренное переполнение. Контраст требует реального основания для используемых цветов; неподдерживаемое наложение, изображение или другая неопределённость не превращается в успешное значение. Viewport coverage и state coverage считаются по явно заданному обязательному набору: проверка нескольких удобных экранов без знаменателя не подтверждает покрытие. Неподдерживаемую автоматикой проверку дополняют обоснованным ручным измерением либо оставляют блокировкой.

Экспертное ревью отдельно проверяет иерархию, композицию, ясность действий, смысл содержания и согласованность. Замечания должны иметь место, наблюдение и пользовательское последствие. Детерминированные метрики полезны для обнаружения дефектов и регрессии, но не гарантируют качество всего дизайна. В каталоге нет единого субъективного score, который автоматически отменяет замечания или неизвестные измерения.

## Практическая адаптация к проекту

В существующем проекте сначала прочитайте действующие инструкции, команды проверки, дизайн-правила и настройки окружения. Не требуйте создать конфигурацию Workbench, если необходимые сведения уже доступны, и не запускайте setup автоматически. Для явно запрошенного нового проекта универсальные шаблоны опциональны и заполняются фактическими значениями. Сопоставление MCP с canonical capabilities делается по реальным инструментам и их воздействию: просмотр сборки и запуск pipeline доставки имеют разный смысл.

Для каждой задачи выбирайте минимально достаточный маршрут. Добавляйте security-review, performance и data-migration по реальному характеру изменения, а не автоматически ко всем правкам. Сохраняйте связи «требование → изменение → проверка» и точные версии. Если несколько исполнителей работают параллельно, host должен изолировать рабочие копии и после интеграции перепроверить совместный результат; последовательный каталог сам по себе такую изоляцию не обеспечивает.

## Быстрые маршруты для небольших задач

Эти маршруты дополняют специализированный каталог. Правила выбора приведены в [ADAPTIVE_EXECUTION.md](ADAPTIVE_EXECUTION.md), декларативная политика — в [routing.json](../config/routing.json). Решение основано на риске, неопределённости, области влияния и внешних эффектах. Формат ТЗ, слово «баг» и число строк сами по себе не требуют полного процесса. Существующий проект не проходит автоматический repo-setup.

### 23. quick-answer — небольшой самостоятельный вопрос

**Вход:** конкретный вопрос и доступные источники. **Профиль:** analyst.

**Этапы:** answer.

**Выход:** ответ и подтверждающие основания. Обычное уточнение в текущей задаче не создаёт отдельный run. Неопределённость обозначается явно; вопрос, требующий полноценного исследования, получает подходящий маршрут.

### 24. quick-backend — небольшая локальная правка

**Вход:** ясное изменение с низким риском и известным ожидаемым поведением. **Профиль:** backend.

**Этапы:** change → validate.

**Выход:** изменение, целевая проверка и актуальный diff. Проверка выбирается по критерию приёмки; дефект возвращает к change. Неожиданное существенное влияние требует пересмотра маршрута.

### 25. quick-frontend — небольшая правка интерфейса

**Вход:** локальное изменение текста, компонента или действия с понятным поведением. **Профиль:** frontend.

**Этапы:** change → validate.

**Выход:** diff и проверка затронутого интерфейса в релевантном состоянии/viewport. Изменённый вид проверяется в браузере; проверка всех экранов не требуется автоматически. Дефект возвращает к change.

### 26. quick-doc — точечная правка документа

**Вход:** конкретная правка и понятный источник. **Профиль:** analyst.

**Этапы:** edit → validate.

**Выход:** проверенный фрагмент и diff. Проверяются затронутые утверждения, ссылки и применимые примеры; независимый полный аудит документа не добавляется автоматически. Дефект возвращает к edit.

Факты, операции и свидетельства сохраняются. Другие агенты, полный SDD, мутации, полный тестовый набор, новые тесты, документация и ретроспектива не обязательны автоматически. Проверка выбирается по критерию приёмки; допустимый `not_applicable` имеет предметное обоснование. Для визуально изменённого UI отсутствие браузерной проверки остаётся блокировкой, но полная матрица всех экранов для каждой опечатки не требуется.

При неожиданном риске, блокирующем неизвестном или недоступной необходимой проверке quick получает `blocked` с причиной и предложением конкретного standard/deep workflow. Передаются версии и артефакты, исполнение поверх блокировки не продолжается. Смена workflow не подразумевает уже реализованного автоматического переключения runner. Сокращён статический состав работы; фактическое ускорение требует измерений.

## Ретроспектива по событию

### 27. retrospective — причина и небольшие предложения

**Вход:** запрос пользователя либо значимое событие: инцидент, повторный сбой, переделки требований или новый полезный pattern; существующий журнал и доступные свидетельства.

**Этапы:** cause → proposals.

**Выход:** `retro-cause` и `retro-proposals`: факты и проверенная причина либо обозначенная гипотеза, затем ноль–три обоснованных предложения с проверкой и условием отката.

Диагност исследует связанный набор событий, аналитик предлагает небольшое действие: уточнить решение, сократить дублирование, изменить routing или исправить инструмент. Полный разбор каждого участника и всех прошлых задач не требуется. Недостаток фактов возвращает к cause; отсутствие полезной правки допустимо с основанием.

Маршрут не применяет изменения к prompts, конфигурации, репозиториям и внешним сервисам: capabilities ограничены чтением, результаты сохраняются локально в run. Штатные события берутся из существующего журнала без отдельного модельного вызова на событие. Ретро не обязательно после каждой маленькой задачи; расписание и периодическая агрегация создаются только по явному запросу. Подробности — [DOCUMENTATION_AND_RETROSPECTIVE.md](DOCUMENTATION_AND_RETROSPECTIVE.md).

## 28. gigacode-ui-diagnostics

Короткий маршрут исправления личной Electron-оболочки: реальное воспроизведение, причина, правка и целевая живая проверка без полного SDD или релизного процесса.

**Этапы:** reproduce → isolate → fix → live-verify → review.

Существующий прототип, неизменяемый CLI и короткие итерации; для затронутого ACP/CLI-поведения обязательна реальная Electron/CLI проверка. См. [GIGACODE_UI.md](GIGACODE_UI.md).

## 29. gigacode-ui-feature

Четыре этапа функции личной Electron-оболочки: краткий сценарий, реализация, целевой проход в настоящем приложении, проверка результата. Без обязательного полного SDD, релизного процесса, docs или ретроспективы.

**Этапы:** scope → implement → live-acceptance → review.

Существующий прототип, неизменяемый CLI и короткие итерации; для затронутого ACP/CLI-поведения обязательна реальная Electron/CLI проверка. См. [GIGACODE_UI.md](GIGACODE_UI.md).
