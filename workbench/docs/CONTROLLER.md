# Локальный контроллер этапов

`workbench.ps1` — исполняемый reference controller на Windows PowerShell 5.1, без сетевых запросов и внешних зависимостей. Он дополняет ручной/агентский запуск этапов и может быть использован как образец для backend вашей оболочки.

## Команды

| Команда | Действие |
|---|---|
| `list` | Список маршрутов |
| `validate` | Проверка определений workflow, профилей и ссылок возврата |
| `init -Workflow ID -Task TEXT -Project PATH -Run PATH` | Новый запуск в несуществующем каталоге; фиксирует копию workflow |
| `status -Run PATH` | Текущий этап, последний результат и счётчики |
| `prompt -Run PATH [-ContextMode full\|role\|stage]` | Контекст этапа; full включает общие инструкции и профиль, role — профиль, stage — только этап и состояние |
| `result-template -Run PATH` | JSON для текущего отчёта с защитой от устаревания |
| `submit -Run PATH -Result FILE` | Принятие отчёта либо фиксация ожидания/блокировки/возврата |
| `resume -Run PATH -Note TEXT` | Продолжение после фактического ответа/разблокировки |
| `rework -Run PATH -Target STAGE -Reason TEXT` | Возврат и инвалидирование результатов начиная с указанного этапа |
| `cancel -Run PATH -Reason TEXT` | Остановка локального процесса workflow |
| `verify -Run PATH` | Проверка наличия и hash принятых артефактов |
| `record -Run PATH -Kind KIND -Summary TEXT` | Запись рабочего события, решения, ответа или checkpoint |
| `recover -Run PATH [-Full]` | Компактное восстановление с checkpoint либо полный экспорт |
| `journal -Run PATH -After N -Limit 50` | Страница событий после указанного sequence |

Пути с пробелами заключайте в кавычки. Из кода вызывайте через список аргументов, без shell=True и без подстановки текста задачи в shell. Контроллер сам не исполняет текст задачи или отчёта как код.

По умолчанию prompt использует full. Сокращённые режимы допустимы только если пропущенные инструкции уже присутствуют в текущем контексте модели и их SHA-256 совпадает с manifest в выводе. Это не автоматическое кэширование: факт загрузки отслеживает host/агент. Новая сессия, потеря контекста или изменение файла требует повторной загрузки. Во всех режимах сохраняются актуальные этап, проверки, revision и attempt_id.

## Состояния

`ready` означает, что текущий этап можно выполнять в пределах действующих разрешений. Агент не передаёт отдельный статус running; управление активным процессом находится у host.

`waiting_input`, `blocked` и `needs_rework` останавливают автоматическое продвижение. `waiting_input` требует непустых questions, `blocked` — blockers, `needs_rework` — допустимого return_to. Для первых двух нужен `resume`; для третьего — `rework`.

`blocked_budget` возникает при превышении `-MaxAttempts` (по умолчанию 3 входа в этап). Отмена и продолжение не сбрасывают этот статус. Нужен пересмотр задачи и новый запуск, связанный со старым; нельзя автоматически создавать новые запуски для обхода лимита.

`cancelled` останавливает локальный workflow. `resume` после отмены восстанавливает предыдущее состояние, включая ожидание, обязательный возврат и превышенный лимит. Это не останавливает внешнюю сборку или процесс GigaCode: их статус проверяет host отдельно.

`completed` означает, что каждый этап получил комплектный успешный отчёт. Повторное submit запрещено. Для пересмотра завершённого процесса можно явно вызвать rework.

## Принятие отчёта

Отчёт должен содержать актуальные run_id, workflow, stage, revision и attempt_id. При любом изменении состояния revision растёт; старые отчёты отклоняются. Переход к следующему этапу и возврат также меняют attempt_id.

Для completed обязательны: summary, source_revision, spec_revision, точный набор артефактов и проверок. Файлы должны быть непустыми и находиться внутри `artifacts/` или `evidence/` каталога запуска. Пути через symlink/junction запрещены в этой реализации, в том числе для ссылки внутрь run. Для каждой проверки требуется хотя бы один файл свидетельства. `not_applicable` разрешён только при allow_na и с обоснованием. `fail` и `not_run` не позволяют завершить этап.

Для execution сохраняйте реальный протокол: средство проверки, аргументы/параметры без секретов, версия кода, окружение, время и результат. Контроллер не проверяет, что этот текст достоверен: для автоматического доверия host должен собирать свидетельства из результата инструмента, а не из пересказа модели.

После завершения этапа сохраняются SHA-256 его файлов. Изменение принятого файла блокирует новое submit/prompt/verify. При доработке используйте rework и новые имена файлов; исторические записи и hashes сохраняются, но сам контроллер не делает резервную копию содержимого старого файла.

При прямом rework можно выбрать текущий или любой ранее пройденный этап, например после изменения требований. Если состояние needs_rework, цель обязана совпасть с return_to последнего отчёта. Результаты целевого и всех последующих этапов архивируются как устаревшие.

## Надёжность и границы

Запись state.json выполняется через временный файл и атомарную замену. Изменения одного запуска защищены локальным lock-файлом. После аварии контроллер не удаляет чужую блокировку автоматически: сначала нужно убедиться, что другой процесс не работает. Предполагается локальная файловая система; сетевые файловые системы и распределённая конкуренция не проверялись.

Фиксируется определение workflow, но CORE и профили читаются из установленного пакета. Поэтому не обновляйте пакет во время активного запуска; для production host фиксирует также версию и hashes всего набора инструкций.

source_revision и spec_revision проверяются только как непустые строки. Изменение исходников вне артефактов не обнаруживается автоматически. Host должен связывать проверки с commit и digest рабочего дерева; до реализации этой функции агент делает эту сверку явно и отражает её в evidence.

Один запуск последовательный. Между разными запусками нет общего планировщика, изоляции репозиториев, управления процессами, cross-run инвалидирования или транзакций MCP. Копия state.json не является неподделываемым журналом; пользователь/процесс с доступом к файлам может его изменить. Это не security boundary.

Подробнее о pre/post записях, pending actions, неизменяемых свидетельствах событий и восстановлении — [JOURNAL.md](JOURNAL.md).

## Совместимость текстовой поставки

Файл .ps1 создаётся на целевой машине из source/workbench.txt по scripts.json. Цель — Windows PowerShell 5.1, FullLanguage и штатный .NET: JSON codec компилируется из текста через Add-Type без поставляемой DLL. Здесь runtime проверен на PowerShell 7/macOS, а 5.1 — статическим анализом; запуск на Windows обязателен при установке.

Workflow digest сохраняет Python JSON schema 1 для строк, целых чисел, null и логических значений. Дробные/exponent числа в пользовательских workflow metadata намеренно отклоняются, чтобы не принять несовместимый hash. Старые workflow/state проверять перед продолжением; не переписывать неизвестную схему.
