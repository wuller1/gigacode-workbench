# От элементов макета к работающему приложению

Дата: **2026-10-10**. Это карта реализации и проверки, не список уже выполненных функций. Прочитаны текущие `work/design-revision/workspace.js` и основная разметка `work/design-revision/chat-first.html`: меню, динамические панели, обработчики и демонстрационные данные. Эти рабочие исходники макета служили материалом аудита; они не являются обязательной runtime-зависимостью почтового пакета.

**Целевой репозиторий Electron и GigaCode на компьютере пользователя здесь недоступны.** Работающая функция reasoning подтверждена пользователем: её нужно сохранить и перенести, а не заново доказывать её существование. Остальные сведения о target требуют адресного чтения исходников и проверки. Наличие обработчика в макете, DOM-проверки или картинки не доказывает работу ACP, PTY, browser, MCP, storage или нового приложения.

Основной порядок остаётся в [плане M0–M12](GIGACODE_UI_DEVELOPMENT_PLAN.md), выдача сборок — в [D0–D13](DELIVERY_AND_DOGFOOD_PLAN.md). **38 групп `UI01…UI38`** ниже — ссылки на небольшие срезы этих этапов, **не новые milestones, workflow engine или независимые галочки готовности**. Сейчас все строки имеют статус `specified / target-not-run`; отметки заполняются только ссылкой на конкретный результат целевой проверки. Тесты макета имеют отдельный статус `mock-checked` только в пределах своего отчёта. Обновлённые локальные экраны архива/настроек не считаются target runtime только потому, что их формы работают в макете.

Названия backend owners обозначают ответственность внутри уже существующего framework. Сначала найти настоящий module/service; не создавать по новому классу, store и процессу на каждую строку. Project → Task → роли остаётся основной иерархией, chat/run/ACP session — связанные исполнения. UI-команда не завершает workflow сама.

## Что нельзя перенести из макета как готовую реализацию

1. **Один fixture enum не равен production state.** В JS встречаются упрощённые `running/waiting/completed`; реальные execution, workflow, plan, unread и delivery состояния уже определены профильными документами. Сохранить их отдельные owners и проекции. Demo `completed` не становится выполненной проверкой или подтверждённой всей Task.
2. **Локальная форма не равна runtime-действию.** `add-project`, `fork`, window/Copy требуют настоящих owners; экран Settings уже демонстрирует локальные формы, но не target CLI apply. UI02/UI05/UI01/UI16/UI30 задают owner и gate. Нельзя оставить общий toast «описано в пакете» в выпущенной функции; допустим конкретный unsupported state с причиной и полезным следующим шагом.
3. **Create/edit/delete — это не удаление файлов по умолчанию.** Project removal меняет каталог приложения, Task trash — её lifecycle, Close view — layout. Native history delete, resource stop и purge требуют своих подтверждённых путей. Полные формы Project/Session CRUD из EL1–EL6 не исчезают из scope лишь потому, что в макете показана часть меню.
4. **Подготовить запрос не означает выполнить.** Create mockup готовит composer; context apply требует фактического механизма; worker cancel получает terminal отдельно. Прежняя peer send форма исключена из целевого UI: broker работает автоматически в разрешённом scope, технический обмен доступен только audit/debug. Каждая стадия имеет actual receipt. Просмотр панели не запускает compression/publish/agent; рабочий scheduler автоматически запускает разрешённое сотрудничество по полезной dependency, не по клику на inbox.
5. **Persistence и docking проверяются заново.** Макет переносит группу, а не доказывает отдельное tab docking; не все данные переживают reload. Product принимает UI24/UI35 только на настоящем store и runtime. Это известные границы демонстрации, не повод строить новый controller.
6. **Недостающие узкие детали уже привязаны к существующим срезам.** Поиск/clipboard/links, Project health/relink, settings readback и full CRUD проверяются карточками выше. Они не создают нового общего milestone. Для обнаруженной новой кнопки сначала добавить её к соответствующей строке и определить owner/receipt; не обещать функцию одним label.

## Как агенту выполнить карту по этапам

1. Прочитать сохранённый setup/task handoff, установить реальные root/source/build/CLI версии и текущий delivery checkpoint. Следовать [START-GIGACODE-UI](../START-GIGACODE-UI.md). Не повторять setup, не переустанавливать уже настроенный проект, не читать весь каталог для D0. Если нужного target repo нет, сохранить конкретный blocker вместо заявления об исправлении.
2. Выбрать **самый маленький незавершённый срез текущего этапа**: сначала устойчивые M0–M2 и ранняя D2, затем отдельные M3 controls; M4 native Task/контекст/память/peer broker; M5 managed coordination; M6 обязательный mockup; M7/M8 расширения; M9/M10; IDE M12 позже. Не ждать всех элементов M3/M6 ради первой полезной промежуточной сборки.
3. Для среза взять одну строку карты, применимый раздел канонического документа, настоящие component/service paths и конкретный сценарий. Preserve working reasoning, текущий framework и процесс проекта. Правила сокращения контекста — [CONTEXT_BUDGET](CONTEXT_BUDGET.md); правила personal_fast и applicable checks — [ADAPTIVE_EXECUTION](ADAPTIVE_EXECUTION.md).
4. Найти существующего owner; реализовать тонкий UI→service→receipt путь и один отрицательный сценарий именно изменённой логики. Не добавлять fake ACP методы, скрытый model API, CLI patches или постоянный PS subprocess. Tool доступ появляется от реально подключённого MCP/host enforcement, не от текста role prompt.
5. Запустить candidate с отдельным user-data/runtime. Проверить реальные rendered state и действие на той же source/build revision; automation fixture и native CLI observation различить. Минимум evidence: ввод, адресная сущность/revision, действие, наблюдаемый outcome, применимая проверка и граница unknown. Снимок экрана подтверждает только то, что на нём видно.
6. Сохранить результат через действующий Task/run/evidence, затем обновить delivery projection с ссылкой на receipt. Ни нажатие кнопки, ни terminal, ни правка этой таблицы не принимают stage автоматически. При pending/unknown outcome не повторять эффект вслепую. Docs delta только по изменённому контракту, retro — по существенному событию.
7. Передать пользователю рабочую сборку/путь запуска: что изменилось, короткий сценарий проверки, ограничения, evidence и rollback. Сохранять stable среду разработки. Следующий небольшой срез выбирать по обратной связи внутри текущего scope; существенное расширение оформить явно. Здесь подготовлена карта инструкций — никаких из этих target gates этот документ не объявляет пройденными.

Общий индекс потребностей — [REQUIREMENTS_COVERAGE](REQUIREMENTS_COVERAGE.md). Он отвечает «какое требование покрыто», эта карта — «какая видимая деталь реализуется каким малым шагом». Оба документа адресные справочники; истинный прогресс остаётся у существующего Task/WorkflowEngine и подтверждённых delivery receipts.
