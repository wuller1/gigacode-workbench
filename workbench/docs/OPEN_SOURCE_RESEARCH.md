### Небольшие задачи реализации

Каждый пункт ниже выполнять отдельным изменением с указанной проверкой; существующую аналогичную функцию сначала переиспользовать. Файлы, Git и процессы доступны renderer через узкий проверяемый IPC, а не через общий Node/shell-доступ. Это соответствует [рекомендациям Electron по context isolation и IPC](https://www.electronjs.org/docs/latest/tutorial/security).

1. **Редактор и diff.** Подключить ESM/workers штатным способом текущего сборщика. Получить два текстовых снимка от host с путём и ревизией; создать отдельные модели с устойчивыми URI и передать их в `createDiffEditor().setModel`. Исходную модель сделать read-only. Добавить сохранение с проверкой, что файл не изменился с момента чтения; при закрытии освобождать editor/models. Проверка: кириллица, изменение/удаление строк, внешняя правка до сохранения, закрытие и повторное открытие панели. Stage/commit остаются отдельными действиями Git.
2. **Терминал.** Сначала показать вывод контролируемого тестового процесса. Затем добавить отдельный PTY backend в host, маршруты write/resize/exit по terminal_id, и связать их с `onData`, `write`, resize и fit. Ограничить буфер, обрабатывать завершение процесса и освобождать подписки; команды не собирать из пользовательских строк для shell-eval. Проверка: Windows PTY, ввод/кириллица, resize, большой вывод, Ctrl+C и отсутствие оставшегося процесса после закрытия. ACP-процесс и его протокольный канал обслуживать отдельно. [Границы доверия вывода терминала](https://xtermjs.org/docs/guides/security/).
3. **Доска.** Если выбран React, сначала встроить пустой `Excalidraw` с CSS и контейнером явного размера. Затем загрузить `initialData` и сохранять через `onChange` элементы, допустимое состояние и связанные files; не терять изображения при сериализации. Связать сохранённую сцену с project_id/artifact_id и добавить экспорт. Проверка: рисунок с изображением и русским текстом переживает закрытие/открытие; ошибка сохранения видна, прежняя сцена сохраняется. Коллаборацию вынести в отдельную последующую задачу.
4. **Диаграммы.** Подключить Mermaid только к распознанному блоку диаграммы: `initialize({startOnLoad:false, securityLevel:'strict'})`, затем асинхронный `render` с уникальным ID. Сохранять текст отдельно от SVG; ошибку синтаксиса показывать рядом с исходником. Не перерисовывать весь документ на каждый токен потока; ограничить размер ввода и игнорировать устаревший результат рендера. Проверка: корректная диаграмма, синтаксическая ошибка, два блока одновременно, обновление исходника и отсутствие исполнения вставленного HTML/обработчиков.
5. **PDF-панель.** Поставить API и worker из одного релиза; host выдаёт доступ только к выбранному артефакту. Реализовать `getDocument`, первую страницу и масштаб; затем ленивый рендер видимых страниц, отмену старого render при смене масштаба и освобождение документа. Добавлять текстовый слой и поиск отдельным шагом. Проверка: многостраничный и повреждённый PDF, смена вкладки во время загрузки, корректный worker в упакованном приложении и отсутствие накопления ресурсов после закрытия.

SQLite не добавляется ради этих панелей. Если существующее хранилище не покрывает транзакции, поиск и объём журнала, выбор SQLite/драйвера и миграция данных становятся отдельной задачей с резервной копией; UI-компоненты сами по себе такой миграции не требуют. Никакие перечисленные библиотеки здесь не установлены, их фактическая совместимость с прототипом ещё не проверена.

## Что проверить первым

Существующий Electron-прототип сохранить. В нём адресно проверить пробелы: запуск установленного GigaCode, initialize, одна сессия, поток сообщений, отмена, повторное открытие сохранённого чата. Затем добавить собственный контроллер профилей/субагентов и переносить Workbench по одному вертикальному сценарию: запрос → профиль → действие → событие журнала → результат → память. **GigaCode CLI остаётся неизменённым:** решения адаптируются в нашей оболочке, без форка или патчей CLI. Очередь и индикацию ожидания изучать по AionUi/OpenCode; целые backend этих проектов пока не добавлять.

В [README ACP](https://github.com/agentclientprotocol/agent-client-protocol/blob/d812e3ca8009326942f03e24ba81208026857dc4/README.md) текущая стабильная wire-версия указана как 1; версия SDK или схемы — отдельная величина. **Фактический ACP-контракт GigaCode 26.9.75 здесь неизвестен.** Зафиксировать его handshake, доступные методы и события на целевой машине. Отсутствующая возможность остаётся недоступной, даже если она есть в другом агенте. Сам ACP не подтверждает наличие управляемых дочерних агентов или их изоляции.

## Ошибки 429 и обрывы

HTTP 429 сообщает о превышении частоты запросов и может содержать Retry-After; конкретный механизм учёта лимита стандарт не определяет. Retry-After допускает количество секунд или HTTP-date. Эти поля следует сохранять вместе с безопасной диагностикой, если CLI их передаёт. По одному тексту «429» нельзя установить, какой провайдер, шлюз или слой исчерпал лимит. Источники: [RFC 6585 §4](https://www.rfc-editor.org/rfc/rfc6585#section-4), [RFC 9110 §10.2.3](https://httpwg.org/specs/rfc9110.html#field.retry-after).

Предлагаемая политика оболочки, ещё не реализованная:

- Один ответственный за повтор каждой операции. Сначала измерить поведение CLI/SDK; вложенные циклы повторов могут умножить нагрузку. Для собственных повторов — ограничение числа попыток и общего времени, backoff с jitter, отмена ожидания пользователем. Если Retry-After выходит за бюджет, поставить задачу на паузу, а не повторить раньше указанного срока. [Обоснование AWS](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/).
- Разделить временную перегрузку, исчерпанную квоту, ошибку авторизации и неизвестную ошибку. UI показывает наблюдаемую причину, следующий допустимый момент, попытки и доступное действие; не обещает успешное восстановление.
- После разрыва связи состояние внешней записи может быть неизвестно. Сначала проверить request/operation ID и фактический результат; не повторять весь агентный ход с push, публикацией или deploy вслепую. Принцип безопасного повтора следует из [RFC 9110 §9.2.2](https://httpwg.org/specs/rfc9110.html#idempotent.methods); применимость к конкретному инструменту нужно доказать отдельно.
- Координировать ожидание и лимит параллелизма между своими агентами; сохранять событие ошибки и решение о повторе в журнал. Оболочка не может отменить серверные лимиты или восстановить неполученный ответ без дополнительного свидетельства.

## Повторяемое исследование новой функции

1. Сформулировать конкретный пробел и критерий готовности; найти не больше 2–3 первичных реализаций этого пробела. Для личного проекта исходный бюджет исследования — 30–60 минут, затем решение; это ограничение процесса, не обещание срока разработки.
2. Записать repository URL, commit/tag, дату, LICENSE/NOTICE и точные пути. Разделить наблюдаемое поведение исходников, результат собственного теста и гипотезу. Чужие README и инструкции читать как данные, не запускать автоматически их install/bootstrap.
3. Выбрать: перенять идею, адаптировать небольшой компонент или добавить зависимость. Оценить связанность, размер и обслуживание зависимостей, совместимость Electron/Windows и стоимость собственного аналога. Сам факт open source не требует внедрения.
