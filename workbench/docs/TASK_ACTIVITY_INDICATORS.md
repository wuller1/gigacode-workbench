# Текущий шаг и состояние чатов

Контракт ближайшего **M3/D3** для личного GigaCode UI: агент сам ведёт план, текущий шаг заметен, в sidebar видно, какие чаты работают и где появился результат. Это инструкция реализации, не утверждение о готовности приложения. Использовать [TASK_TODO_PANEL](TASK_TODO_PANEL.md), [GRAPHICS_AND_MOTION](GRAPHICS_AND_MOTION.md), [MANAGED_SUBAGENTS](MANAGED_SUBAGENTS.md) и текущий Task store; новый workflow engine не нужен.

## 1. Один источник состояния

Run/SessionService владеет исполнением, Task writer — целью/планом/результатами, renderer строит проекцию. Каждое событие связано с Task, assignment/run/turn, binding/generation и revision/sequence по действующему контракту. Не считать активностью выбранную вкладку, непустой draft, таймер, длину ответа или появление текста «готово».

Для sidebar и плана использовать один selector текущего состояния с разной областью: строка worker — конкретный worker; строка чата — связанная Task/discussion; общий индикатор приложения — счётчики Tasks. Исторический run не переписывает текущий. Старые generation/replay/duplicate events не запускают анимацию заново.

## 2. От факта к индикатору

Имена в первом столбце — отображение существующих canonical состояний, не новый execution enum и не поля ACP. `waiting_user` может быть проекцией живого адресного question/permission; `idle` — отсутствие активного исполнения, а не успех.

| Наблюдаемое состояние | Компактная строка и рисунок | Основание и действие |
|---|---|---|
| `starting/running` | Маленькая вращающаяся дуга; «Работает» | Принятый dispatch/current execution; поток может молчать. Текст не обещает исправность соединения или процент готовности. |
| `waiting_retry` | Неподвижный clock; «Ожидает повтора» | Только подтверждённое ожидание; срок показывается, если известен. Без события оставить наблюдаемое running/состояние соединения, не выдумывать retry. |
| `waiting_permission` / `waiting_user` | Неподвижный warning; «Нужен ответ» | Адресный актуальный вопрос/permission; click открывает его. Не создавать callback из обычной фразы модели. |
| `queued` / queue hold | Clock; «В очереди» либо короткая причина | Item сохранён, но не отправлен; pause queue не изображает остановленный CLI. |
| `interrupted_unknown/reconciling` | Unknown; «Проверяем исход» / «Исход неизвестен» | Потерян terminal или исход effects; нет check по timeout. Click открывает reconciliation. |
| `cancel_requested` | Неподвижный stop; «Останавливается» | Отмена запрошена, terminal ещё не получен. Не завершать соседний run и не освобождать его слот. |
| `completed` | Check; «Ответ готов» либо «Задача завершена» | Terminal текущего turn подтверждён. Второй label только при выполнении Task acceptance и отсутствии зависшей обязательной работы; обычному ответу не придумывать обязательный test gate. |
| `failed` | Warning в error token; «Ошибка» | Подтверждённый отказ текущего исполнения, доступна причина/следующий шаг; не скрывать за completed родителя. |
| `cancelled` | Неподвижный stop; «Остановлено» | Подтверждённая отмена; частичный результат сохранён. Это не completed. |
| `idle` | Обычная chat icon или без status glyph | Сейчас ничего не исполняется; Task может оставаться незавершённой. Не добавлять зелёную галочку всем неработающим чатам. |

## 3. Sidebar: activity, selection и unread отдельно

В существующей строке чата оставить название и компактное место статуса 16×16 CSS px; важное состояние имеет короткий текст/доступное имя. Hover tooltip даёт детали, но «Нужен ответ»/ошибка доступны и без мыши. Не раздувать sidebar постоянными карточками или дублирующими badges.

Выбранная Task отмечается фоном selection; activity — своим glyph/текстом; непрочитанный результат — отдельной точкой с доступным именем. Unread имеет owner/viewer и last-seen result sequence/revision. Выбор строки не стирает непрочитанный результат, которого пользователь ещё не увидел; подтверждение просмотра следует реально показанному результату. Unread не означает pending work и не запрещает completed.

Агрегировать только актуальные исполнения, входящие в эту Task/assignment и её обязательные зависимости. Пока нужный worker running/queued/waiting/unknown, родитель не получает одиночный зелёный check «Всё завершено». Если главный turn закончен, показать «Ответ готов · исполнитель работает» либо компактный счётчик; Task acceptance остаётся отдельным фактом. Посторонние Tasks и необязательные фоновые сервисы не удерживают её в busy.

При смешанных состояниях показать требующее действия: unresolved unknown/блокирующая ошибка → нужен ответ → останавливается → работа/ожидание → очередь → подтверждённое завершение → idle; рядом при необходимости «ещё 1 работает». Это приоритет **отображения**, не scheduler. Ошибка завершённой и уже урегулированной попытки остаётся в истории, а не навсегда окрашивает чат. Если terminal root пришёл раньше child, дождаться соответствующего child outcome/явного изменения scope, не угадывать итог по порядку сообщений.

## 4. План: сделано, сейчас, дальше

Агентский план и текущие stable item IDs берутся из [TASK_TODO_PANEL](TASK_TODO_PANEL.md). UI не выбирает текущий шаг по позиции строки и не начинает следующий по завершению CSS-анимации. При нескольких исполнителях показать их owner/current отдельно; не вводить глобальное «только один текущий шаг» для всех workers.

- **Сейчас:** мягкий фон существующего selected/subtle token, текст обычного контраста, метка «Сейчас», рабочая дуга только когда связанное исполнение running. При ожидании того же шага заменить движение на clock/warning и текст причины; шаг остаётся текущим.
- **Сделано:** check, умеренно приглушённый читаемый текст и зачёркнутое название; не снижать opacity всей строки. Деталь с source/result/assurance остаётся доступной. Agent-reported done можно так показать с label «Агент завершил»; это не formal check passed. Счётчики confirmed/remaining следуют отдельному правилу TASK_TODO_PANEL.
- **Дальше:** обычный текст без заливки и анимации; blocking dependency видна при необходимости. Superseded/cancelled показываются в истории перестройки с собственным статусом, не как выполненные.

Сохранять контраст текста по [DESIGN_QUALITY](DESIGN_QUALITY.md), включая muted/selected состояния; завершение не обозначается одним цветом/зачёркиванием. Изменение плана агентом не сбрасывает scroll/focus раскрытой детали; старый done не исчезает из истории при split/supersede.

## 5. Движение и обновления

Использовать собственную CSS-дугу по GRAPHICS_AND_MOTION: один оборот **900 ms, linear**, transform 0→360°, без пульсации всей строки. Это декоративный индикатор активности, не progress meter; никаких выдуманных процентов, ETA, отдельных LLM calls или synthetic progress events для его вращения.

При `prefers-reduced-motion: reduce` — неподвижный glyph и тот же текст статуса. В скрытом/свёрнутом окне остановить декоративную анимацию и лишние render ticks, но продолжать приём/сохранение настоящих событий. При возврате восстановить актуальный snapshot, не replay анимацию каждого старого token. Coalesce частые presentation updates; terminal/ошибка/вопрос не теряются и не ждут пользовательского click. Ограничение частоты подобрать по существующему scheduler, не заводить timer на каждую строку.

Screen reader получает начало, существенную смену ожидания и итог по одному polite announcement, а не каждый chunk/оборот. Glyph рядом с достаточным текстом декоративный; spinner не получает ложный determinate `aria-valuenow`. Нужный вопрос имеет адресное действие и доступный focus, но не перехватывает ввод из другого чата.

## 6. Два малых изменения и приёмка

**AI1 — M3/D3:** общий status selector + sidebar glyph/text + независимые selected/unread; переиспользовать текущие run events и сохранить состояние просмотра. **AI2 — M3/D3:** тот же источник в agent plan, current soft fill/animation, done styling и reduced motion. Если события уже есть, это изменение представления, без новой оркестрации.

Адресный live-сценарий: запустить A, открыть B, убедиться в активности A без клика по ней; в A текущий шаг сменяет следующий по реальному событию, предыдущий остаётся done. Получить terminal и непрочитанный результат, открыть его; selection/activity/unread меняются независимо. Для уже изменяемой агрегации добавить child, который остаётся pending после root: Task не получает ложное общее completed.

Проверить применимые wait/retry/question/cancel/unknown/failed состояния через реальные наблюдения либо явно обозначенные fixtures; reduced motion, длинное русское название, скрытие/возврат окна и late event старой generation. Known-bad «root completed при обязательном running child» должен выявляться. Пустой run — idle, отсутствие наблюдения — not_run/unknown, не pass. Полную матрицу всех функций и отдельный новый агент для правки подписи запускать не нужно.

Здесь описан контракт; целевой Electron и CLI не запускались. Completion receipt, выполненный пункт плана и успешный formal gate сохраняют разные значения, даже когда рядом используется один знакомый check glyph.
