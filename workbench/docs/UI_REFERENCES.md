# Дизайн рабочего инструмента GigaCode UI

Направление: спокойное плотное рабочее пространство с ясной иерархией, несколькими независимыми задачами и быстрым доступом к результатам. В центре находится работа пользователя, а не поток служебных сообщений агента. Внешний вид Zidao не переносится. Ни один референс не требует копировать фирменные цвета, логотип или всю структуру продукта.

## Визуальные референсы

При подготовке пакета 9 октября 2026 года просмотрены официально опубликованные примеры интерфейсов. Ниже оставлены только ссылки на страницы правообладателей и описание полезных принципов; чужие изображения не встроены в пакет и не предназначены для переноса в приложение. Наблюдения относятся к конкретной демонстрации, а не обязательно текущей сборке продукта. Самостоятельный дизайн и инструкции задаются в [DESIGN_IMPLEMENTATION_GUIDE.md](DESIGN_IMPLEMENTATION_GUIDE.md), графика и анимации — в [GRAPHICS_AND_MOTION.md](GRAPHICS_AND_MOTION.md). Правила использования материалов — в [ASSET_RIGHTS.md](ASSET_RIGHTS.md).

### R1 Codex и спокойная основа рабочего пространства

[Официальная публикация с примером интерфейса](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex).

Наблюдаемое визуальное решение: светлая навигационная колонка отделена от основной области мягкой сменой поверхности; строки задач компактны; центр оставляет много свободного пространства; composer закрепляет нижнюю часть композиции; верхние команды не спорят с рабочей областью. Для нашего UI это основной ориентир иерархии и сдержанности. В заполненном чате свободное место отдаётся содержимому; большой пустой экран не становится обязательным шаблоном.

### R2 Claude Code и рабочие панели

[Официальная демонстрация редизайна](https://claude.com/resources/articles/claude-code-desktop-redesign). Наблюдения ниже сделаны по опубликованной обложке встроенного видео Anthropic.

Наблюдаемое визуальное решение: нейтральные тёмные поверхности, тонкое разделение панелей, preview/diff/terminal собраны в рабочую сетку, технические данные используют моноширинное оформление, ввод находится внизу чата. Для нашего UI полезны соседство чата и материалов, компактные заголовки панелей и локальность состояния. Плотность конкретной демонстрации не принимается как обязательная: читаемость проверяется на рабочей Windows, русском тексте и масштабировании.

### Как превратить референс в реализацию

Для корпоративных frontend/UX задач отдельно подготовлен [Plasma / SDDS SERV stylepack](CORPORATE_DESIGN_REFERENCES.md): лицензированный небольшой набор токенов, optional зелёный preset и recipes таблиц/форм. Он выбирается по design contract конкретного проекта и не заменяет default оформление этой оболочки. Лицензия и источник перенесённых материалов сохранены в пакете.

R1 помогает обсудить иерархию; R2 — соседство разговора и рабочих материалов. Итоговая композиция, токены и компоненты проектируются самостоятельно по задачам нашей оболочки. Не обводить screenshot, не воспроизводить узнаваемое фирменное оформление и не извлекать assets из Desktop. Для каждого экрана дать модели точный recipe из [руководства](DESIGN_IMPLEMENTATION_GUIDE.md), требуемые состояния и способ проверки.

## Предлагаемая компоновка

```text
+------------------+----------------------------------+----------------------+
| Проекты          | Название задачи   профиль/модель | Diff | Файл | Browser|
|  Проект A        | состояние: работает / ждёт       |----------------------|
|    Чат 1  running|                                  | выбранный материал   |
|    Чат 2  waiting| разговор и проверяемый результат |                      |
|  Проект B        | tool cards раскрываются по делу  |                      |
|                  |                                  |                      |
| Агенты           | очередь следующего ввода         |                      |
| Поиск            | composer и вложения              |                      |
| Настройки        | отправить / отменить             | terminal по запросу  |
+------------------+----------------------------------+----------------------+
```

Это начальный wireframe. Layout определяется реальным содержимым. На узком окне правая панель становится переключаемой вкладкой, sidebar сворачивается, composer остаётся достижимым. Имена задач и ошибки не обрезаются без способа прочесть целиком. При двух открытых окнах состояние зависит от выбранного чата, а не от глобального «активного окна».

## Небольшой дизайн контракт

Сначала зафиксировать 5–8 семантических цветовых ролей, шкалу текста, шкалу интервалов, состояния интерактивных элементов и focus. Использовать один набор primitives в sidebar, chat, inspector и dialogs. Не подбирать независимые отступы и радиусы на каждом экране. Цвет усиливает текстовый статус, но не заменяет его.

Основное действие — отправка текущего ввода; во время работы рядом видны очередь и отмена с точным смыслом. Retry не выглядит как успешное продолжение. Permission показывает действие и владельца сессии. Ошибка сохраняет ввод, историю и путь восстановления. Empty state объясняет один следующий шаг; не заполняется декоративным dashboard.

Служебные панели по умолчанию компактны. Полные logs, токены, JSON и транспортные поля находятся в раскрываемой диагностике. Удаление этих деталей из обычного потока не удаляет evidence из хранилища. Информация о цене/контексте отсутствует или помечена unknown, если CLI её не сообщает.

## Измерения

Следующие значения — предлагаемые стартовые цели личного desktop-проекта, которые уточняются после baseline на рабочем компьютере. Они не являются доказательством качества и не выдаются за универсальный стандарт.

| Критерий | Начальная цель | Как проверять |
|---|---|---|
| Размеры окна | 1440×900, 1280×800, 960×720; Windows scale 100% и 150% по доступной машине | Реальный Electron, записать CSS viewport и scale; скриншот и действия |
| Целостность layout | 0 непреднамеренных перекрытий, недостижимых действий и потерь ввода | Bounding boxes + действие/keyboard, длинный текст и ошибка |
| Покрытие состояний | Проверены все применимые обязательные состояния выбранного сценария | Знаменатель задан до теста; not_run виден отдельно |
| Контраст и focus | По классам и источникам из DESIGN_QUALITY, без подмены px/pt | Реальные computed colors, compositing, keyboard focus; неизвестные цвета не считать passed |
| Локальная реакция на выбор чата | p95 ≤150 мс после прогрева на тестовой истории | От события ввода до первого устойчивого UI; минимум 30 измерений; отдельно длительность загрузки данных |
| Редактирование ввода | p95 задержки локальной реакции ≤50 мс в тестовом сценарии | Набор текста во время streaming, фиксировать метод и устройство |
| Сохранность | 0 потерянных подтверждённых пользователю сообщений в проверенных restart/crash сценариях | Сверка store, UI и operation IDs; это результат заданных случаев, не абсолютная гарантия |
| Большая история | Работоспособность на выбранной fixture, например 1000 сообщений | Время открытия, прокрутка, RSS; хранить размер fixture и сравнение, не выдумывать memory budget |

Время ответа модели и сети измерять отдельно. Уменьшение p95 UI не достигается скрытием статуса загрузки или потерей данных. Сравнивать одинаковые fixtures/версии/условия; агрегировать реальные measurements, а не оценки vision-модели.

## Три обязательных пользовательских потока

1. **Два чата.** Открыть A и B в двух окнах, начать обе задачи с реальным перекрытием, переключиться, вернуться, отменить A. У B сохраняются вывод, ввод и состояние. После restart видна непротиворечивая история.
2. **Обрыв.** Во время A отключается её transport или воспроизводится проверенный failure fixture. UI показывает ожидание/неизвестный исход, позволяет отменить дальнейшие попытки, B продолжает работу. Нет второго prompt с тем же неизвестным действием.
3. **Материал.** Агент создаёт файл, пользователь открывает artifact/diff справа, возвращается к чату и комментирует его. Материал относится к правильной версии, ввод и место чтения сохранены.

Для каждого потока проверить normal/loading/empty/error/permission и длинное содержимое, если состояние применимо. Не запускать всю матрицу после каждого изменения слова; после изменения базового layout или session ownership она обязательна.

## Работа vision модели

Передать реальные before/after одной сборки и viewport, цель сценария и измерения. Попросить не «оценку 9/10», а максимум несколько находок: место → наблюдение → препятствие пользователю → предлагаемое исправление. Для состояния/поведения требовать действия и events; один screenshot их не доказывает. Подробный prompt находится в [FLASH_MODEL_EXECUTION.md](FLASH_MODEL_EXECUTION.md).

На первом подключении намеренно создать известный дефект в отдельной fixture: перекрытое действие, слабый контраст или потерянный draft. Проверка обязана его заметить. Если нет — исправлять измеритель/задание, а не объявлять экран хорошим. После этого применять выбранный способ к настоящему UI.

## Порядок реализации

Сначала M1–M2 и достоверные состояния. Затем sidebar/chat/composer с токенами, потом inspector с одним diff/file viewer. Следом keyboard/layout/performance, затем browser/artifacts/canvas. Каждое добавление проверяется в общей композиции. Готовые компоненты и ограничения их подключения перечислены в [open source research](OPEN_SOURCE_RESEARCH.md); сам перенос библиотеки не создаёт согласованный дизайн.
