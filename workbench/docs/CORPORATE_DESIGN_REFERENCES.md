# Корпоративное оформление: Plasma / SDDS SERV

Дополнительный набор для frontend/UX задач корпоративных проектов. Пользователь разрешил перенос сберовских материалов при соблюдении их лицензий. Здесь уже перенесены **24 цветовых токена SDDS SERV под MIT**, полная лицензия и происхождение; подготовлен отдельный применимый preset. Это не смена default оформления Workbench и не утверждение соответствия внутреннему брендбуку Сбера.

Файлы: [optional preset](../config/design-presets/sber-plasma.json), [исходные токены](../assets/sber-reference/plasma-token-subset.json), [LICENSE](../assets/sber-reference/LICENSE.txt), [источник и hashes](../assets/sber-reference/SOURCE.md). Preset имеет `status: proposed_not_applied`: в этом пакете нет реализованного theme loader или уже изменённого пользовательского приложения. Выбор фиксируется в [design contract](../templates/design-contract.md) конкретного проекта/экрана. Существующие утверждённые правила проекта имеют приоритет.

## 2. Что уже можно переносить из этого пакета

Вложенный subset содержит точные CSS variable/value pairs из `packages/themes/sdds-themes/src/css/sdds_serv__light.css` и `sdds_serv__dark.css`, по 12 на тему. Package LICENSE — MIT, copyright Salute Devices; полный текст сохранён без изменений. Отбор/перевод в JSON не меняет значений. [Лицензия выбранного пакета](https://github.com/salute-developers/plasma/blob/fe399bad3bfa7ffe4eea233c258d944c866e9815/packages/themes/sdds-themes/LICENSE.txt).

В resolved preset восемь явных соответствий используют исходные нейтральные значения: light canvas/subtle/hover/border и dark canvas/surface/subtle/border. Остальные цвета, размеры и recipes — предлагаемая адаптация. Raw accent, text и alpha-токены тоже сохранены для проверки происхождения, но **не все автоматически применяются**. `#RRGGBBAA` нельзя трактовать как непрозрачный RGB; итоговый цвет зависит от подложки. Более тёмный light CTA и более светлый dark CTA выбраны для конкретных проверенных пар, не выданы за фирменные значения.

Лицензия выбранных code/theme файлов не служит общим разрешением на логотипы, товарные знаки, сайт, screenshot или font binaries. SB Sans из CDN не вложен; доступны только системные font names `Segoe UI, system-ui, sans-serif`, без распространения шрифта и без обещания одинакового рендера на каждой системе. Если в реальном корпоративном проекте уже есть разрешённые брендовые assets/fonts, переиспользовать подтверждённый источник и условия проекта; не запрещать их просто по названию. Проверять rights один раз на version/hash и при изменениях. [Правила assets](ASSET_RIGHTS.md).

JS/CSS самих компонентов, изображения и иконки Plasma здесь не скопированы. При реальном подключении MIT-компонентов можно переиспользовать разрешённый код и документационные примеры с notices точной версии; отдельно проверить зависимости/вложенные assets. Не нужно переписывать лицензированный компонент с нуля только ради «своего» кода. Не ставить полный SDK, если текущий проект уже решает задачу и достаточно semantic token mapping. Никаких новых ролей/workflow этот stylepack не добавляет.

## 3. Конкретное направление для корпоративного экрана

Цель: много полезных данных и понятные формы, спокойные нейтральные поверхности, один сдержанный зелёный акцент действия. Не делать зелёными все заголовки, панели и строки; не украшать рабочий реестр градиентным hero, иллюстрацией банка или карточками без самостоятельного смысла. Ниже — **проектные значения**, а не нормативные требования Сбера.

| Часть | Точный стартовый recipe |
|---|---|
| Основной layout | Нейтральный canvas; content padding 24 px, на узком экране 16 px. Заголовок, описание/metadata, toolbar, основной материал. Между смысловыми секциями 24 px |
| Иерархия текста | Page title 24/32 px; body/table 14/20; редактируемый текст формы 15/22; metadata 13/18. Не уменьшать основной текст ради числа колонок |
| Сетка | Шаг 4 px; label → field 8; поля 16; группы 24. Ровные baseline и единая ширина полей внутри логической группы |
| Controls | Высота 36 px, комфортный вариант 40; радиус 8. Подписи по содержимому; длинный русский label не скрывать без чтения. Размеры — цели проекта, не автоматически доказанная accessibility |
| Таблица | Строка минимум 40 px, optional compact минимум 36; многострочный контент увеличивает высоту. Заголовок колонок не исчезает без смысла; sticky header не перекрывает focus. Горизонтальный scroll внутри таблицы допустим при ясных признаках и достижимых колонках |
| Акцент | Один primary action на локальную задачу; остальные neutral/secondary. Selected — мягкая поверхность плюс checkbox/индикатор, а не только зелёный текст. Focus 2 px с offset 2 px |
| Поверхности | У общего content нет обязательной карточки. Граница нужна для отделения содержимого/controls; `borderSubtle` декоративный, `borderControl` — для нужной видимой границы. Радиус самостоятельной панели 12 px |
| Motion | Локальные состояния 120 ms, небольшая panel transition 160 ms; reduced motion отключает лишнее движение. Loading только от наблюдаемого состояния, без фиктивного процента |

Предлагаемые resolved цвета полностью записаны в preset. Примеры: light canvas `#F9F9F9`, surface `#FFFFFF`, text `#1E261F`, accent `#146C32`, hover `#105A29`; dark canvas `#080808`, surface `#171717`, text `#F0F5EF`, accent `#A9D6A6`, hover `#C0E1BB`. Это **адаптация**. Для точного внутреннего бренд-стандарта использовать предоставленный/доступный утверждённый contract проекта, а не переименовывать этот JSON в официальный.

## 4. Экран «реестр + детали» — готовая последовательность

1. Выбрать один реальный сценарий, например «найти запись, увидеть детали и изменить разрешённое поле». Установить источник данных, scope, права, состояния и критерий успеха. Для prototype явно использовать fixture; не выдавать её за работающий backend.
2. Сверху: название реестра и короткое описание; справа одно основное действие, только если оно нужно сценарию. Ниже один toolbar: поиск, наиболее частые 1–3 фильтра и счётчик реального результата. Редкие фильтры — раскрытие; не добавлять пустые фильтры ради вида.
3. Таблица занимает доступное место. Названия/описания слева, числа/суммы справа, даты в одном принятом формате; units и timezone видимы там, где влияют на решение. Primary identifier открывает детали с клавиатуры; row click не мешает выделению текста и дочерним controls.
4. Детали открывать существующим способом проекта: отдельный route либо pane. Для pane старт 360–480 px и проверка оставшейся ширины таблицы; при нехватке места отдельный полноширинный view с возвратом к фильтру/scroll. Не навязывать новый docking framework корпоративному приложению.
5. Form: постоянный label, обязательность по настоящему правилу, helper до ошибки; validation message объясняет исправление и связан с полем. При submit ошибка не очищает введённое; focus переходит осмысленно, общий error summary нужен при нескольких удалённых ошибках. Disabled объясняется контекстом, а не одной opacity.
6. Toolbar/state: `loading`, «нет записей», «нет совпадений фильтра», access denied, error/retry и success различаются. Empty не выглядит как 0 результатов до ответа. Массовое действие появляется только после реального выбора, показывает количество и область; повторная отправка не создаёт дубликаты.
7. После сохранения показывать подтверждённый результат и обновлять затронутые данные. Смена темы/вкладки не сбрасывает filter, selection, draft или dirty state. Красивый toast до ответа сервера не считается успехом.

## 5. Компоненты и правила выбора

Ниже названия exports, проверенные в [SDDS SERV index этого commit](https://github.com/salute-developers/plasma/blob/fe399bad3bfa7ffe4eea233c258d944c866e9815/packages/sdds-serv/src/index.ts). Это не обещание совпадения props между версиями или вертикалями. Читать type definitions выбранного пакета и 1–2 relevant examples, не всю библиотеку. В неизвестном/не-React stack применить recipe и tokens через существующие primitives; не начинать repo setup автоматически.

| Нужда | Reference / кандидат | Приёмка приложения |
|---|---|---|
| Действие | `Button`, `IconButton`, `ButtonGroup` | Реальные default/hover/focus/pressed/loading/disabled; accessible name, повторный dispatch под контролем |
| Ввод | `TextField`, `TextFieldGroup`, `Select` | Label и errors связаны; значения не теряются, keyboard работает. Свойства сверены с установленными typings |
| Реестр | `Table`, `Pagination` | Stable row ID, сортировка/filter/paging согласованы с backend; выбор не относится к другой строке после reorder |
| Структура | `Tabs`, `Drawer` | Активный view и focus согласованы; скрытая панель не остаётся в Tab order, возврат сохраняет draft |
| Статус | `Badge`, `Toast`, `Skeleton` | Текстовое значение и правильное время показа; отсутствие данных не имитируется постоянно движущимся skeleton |
| Пояснение | `Tooltip` | Не единственный способ прочесть обязательную информацию; доступен keyboard, не скрывает target |

При существующем Plasma/SDDS dependency сначала переиспользовать его. При новом выборе — небольшой integration probe одного поля, таблицы и focus, проверка bundle/runtime совместимости; не заменять текущую библиотеку всего проекта из-за одного стиля. Документированный [MCP для Plasma](https://plasma.sberdevices.ru/web/how-to-mcp/) может быть источником API после проверки реального server/version/tools, но здесь он не установлен и не обязателен. Не запускать `latest` автоматически и не придумывать его tool names.

## 6. Контраст, состояния и содержательная оценка

Для resolved непрозрачных цветов выполнены два независимых расчёта относительной яркости sRGB: обычная арифметика и Decimal с precision 50. Числа ниже округлены **для отображения**; сравнение выполнялось до округления. Для первых пяти строк взят минимум среди canvas, surface, subtle, hover, selected. Правила применимости норм, крупного текста, focus/targets и исключений — в [DESIGN_QUALITY](DESIGN_QUALITY.md).

| Пара / минимум | Light | Dark |
|---|---:|---:|
| Основной текст / обычные поверхности | 13,15:1 | 10,95:1 |
| Вторичный текст / обычные поверхности | 6,74:1 | 8,31:1 |
| Metadata / обычные поверхности | 4,69:1 | 5,77:1 |
| Control border / обычные поверхности | 3,40:1 | 3,77:1 |
| Focus / обычные поверхности | 5,52:1 | 7,40:1 |
| Текст CTA / accent | 6,52:1 | 9,97:1 |
| Текст CTA / hover | 8,34:1 | 11,42:1 |
| Текст CTA / pressed | 10,26:1 | 8,59:1 |
| Success text / success background | 6,24:1 | 7,71:1 |
| Warning text / warning background | 6,40:1 | 7,48:1 |
| Error text / error background | 6,13:1 | 7,45:1 |
| Info text / info background | 5,99:1 | 7,77:1 |

Например, гипотетический белый `#FFFFFF` на исходном SDDS `--surface-accent: #1A9E32` даёт 3,51:1; на light hover `#1EB83A` — 2,63:1. Это расчёт **этих двух сочетаний**, а не аудит готового SDDS Button: его actual foreground/font/state здесь не исследованы в браузере. Поэтому не назначать такой фон и белый мелкий текст по догадке. Наш resolved preset использует другие проверенные пары.

Не применять opacity к измеренному мелкому тексту и не заменять токен «почти таким же» без нового расчёта. Focus на CTA нужен с видимым offset/соседней поверхностью: совпадающий focus и fill без зазора может исчезнуть, несмотря на строку таблицы. Selected/hover отличаются также фактическим состоянием/маркером, ошибки — текстом и связью с полем. Data visualization требует labels/legend/units и альтернативы одному цвету: не превращать все серии в оттенки зелёного, где их нельзя различить. Chart palette утверждается отдельно на нужных данных; этот preset не заявляет её проверенной.

Живая приёмка выбранного экрана: штатное состояние + существенная ошибка/empty + keyboard/focus; длинные русские labels/данные; исходное рабочее окно и одно узкое/масштабированное состояние по влиянию. Для изменения базовой темы проверить обе темы и основные изменённые компоненты. Зафиксировать CSS viewport, масштаб Windows при доступной машине, сборку и фактические computed colors. Для правки подписи не запускать все проектные матрицы заново. Числовые пары не доказывают удобство, логичность структуры или готовность приложения; визуальный critic проверяет именно задачу и реальные before/after.

## 7. Пять коротких шагов для модели исполнителя

1. **Выбор.** Найти stack, существующие tokens/components и принятый design contract. Записать один проектный выбор `sber-plasma`, точную область и источник; default Workbench не менять. Сохранить полезные существующие компоненты.
2. **Один срез.** Выбрать реестр/форму/детали и перечислить применимые состояния. Для понятной локальной задачи достаточно короткого design delta, не нового большого SDD.
3. **Токены и компоненты.** Прочитать только preset, source/license record и выбранные component typings. Подключить semantic roles с локальной областью темы. Не вставлять global theme в browser preview/соседний проект; не добавить CDN/font/иконки без необходимости.
4. **Проверка.** Показать настоящий экран той же сборки, измерить изменённые пары/геометрию и пройти действия. Один адресный плохой случай — потеря draft, неизвестный результат сохранения, недостижимое поле либо недостаточный contrast; не выдать fixture pass за live proof.
5. **Результат.** Сохранить delta design contract, evidence и third-party notice. Отчёт: реализовано / измерено / экспертные findings / unknown; не «официально соответствует Сберу» и не magic score. Новая зависимость/версия повторяет rights-check; неизменный источник — reuse по hash.

Готовое поручение:

> Оформи только выбранный корпоративный экран по optional preset `sber-plasma` и существующим правилам проекта. Используй вложенные лицензированные Plasma/SDDS tokens и готовые компоненты, если они совместимы с уже установленным stack; не меняй весь UI framework. Сохрани LICENSE/source notices. Структура: цель → toolbar → основные данные → детали/форма; зелёный акцент только для значимых действий. Прочитай нужные разделы этого руководства, а не все документы Workbench. Сохрани поля/фильтры/draft, проверь реальный happy path и один плохой случай. Покажи evidence текущей сборки и честные ограничения. Если данные/права/дизайн противоречат источнику, обозначь конкретное противоречие; не закрывай его декоративной заглушкой.

Перенос токенов, JSON-валидация, проверка происхождения и расчёты сделаны при подготовке пакета. Установка библиотеки, live UI, keyboard и Windows rendering на пользовательском проекте **не выполнялись**.
