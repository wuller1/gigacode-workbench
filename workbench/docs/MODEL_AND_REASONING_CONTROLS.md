# Модель и reasoning рядом с полем ввода

Дата: **2026-10-10**. Пользователь прямо подтвердил: **выбор reasoning уже реализован и работает в его GigaCode UI**. Это исходный факт задачи, а не предполагаемая будущая возможность. Репозиторий UI и установленный GigaCode 26.9.75 здесь недоступны: конкретные component paths, IDs, значения и способ подтверждения настройки выясняются по существующей реализации. Не выключать рабочий selector и не объявлять всю функцию unknown из-за отсутствия этих файлов в текущем исследовании.

Задача ближайшего **M3/D3** — удобно разместить существующие model/reasoning controls рядом с composer, сохранить поведение и устранить только обнаруженные ошибки состояния. Не переписывать adapter ради сходства с upstream; CLI остаётся неизменённым. Документ дополняет [MODEL_AND_CONTEXT_CONTROLS](MODEL_AND_CONTEXT_CONTROLS.md): контекст/usage остаются там, доставка очереди — в [SMART_MESSAGE_QUEUE](SMART_MESSAGE_QUEUE.md), роли — в [ROLE_PROMPT_BINDING](ROLE_PROMPT_BINDING.md). Не создавать второй settings store.

## 1. Начать с работающего пути

1. Найти нынешний selector, источник списка моделей/режимов, обработчик выбора, backend/IPC service, transport-вызов и сохранение настройки. Искать по фактическим labels/IDs, `reasoning`, `thinking`, `effort`, `configOptions`, `set_config_option`; отсутствие последнего имени не доказывает отсутствие функции.
2. В живом приложении выбрать два **уже доступных** значения, зафиксировать прежний и новый UI state и безопасную форму вызова/ответа: IDs, типы, binding и результат, без ключей доступа и текста разговора. Отдельно проверить, когда значение применяется: сразу к настройке либо к следующему запросу.
3. Сохранить короткую карту `UI → handler → service → adapter → confirmation` с путями/ревизией. Если механизм отличается от ACP configOptions, сохранить рабочий механизм; перенос контрола не требует смены протокола.
4. Переиспользовать компонент либо вынести его представление над тем же service. Не копировать selector вместе с независимым local state и вторым сетевым effect. Старое и новое места не должны отправлять две команды за один выбор.
5. Проверить затронутый сценарий после переноса. Если обнаружится отсутствие подтверждения, добавить адресную сверку в существующий service; не начинать новый глобальный capability/setup pipeline и не перенастраивать проект.

Непроверенная **новая модель или дополнительное значение** имеет свой статус. Это не отменяет уже работающие проверенные варианты. При ошибке чтения оставить последнюю подтверждённую настройку с пометкой stale и доступным повтором чтения; не показывать пустой список как «модель не поддерживает reasoning».

## 3. Внешний вид и точный смысл значений

В компактной строке composer: **модель · reasoning**; контекст доступен непосредственно под вводом. Роль остаётся отдельным выбором ответственности. Reasoning button показывает короткое текущее значение; menu содержит допустимые варианты, selected state и краткое описание там, где оно помогает выбору. На узком окне допустим общий popover модели с reasoning непосредственно рядом, без перехода в глобальные настройки.

| Реальный вид настройки | Представление |
|---|---|
| Список effort values | Отобразить фактические values/labels и порядок; не дорисовывать отсутствующие Low/High/Max. Перевод label не меняет wire value. |
| Только включение/выключение | Два варианта с реальными IDs. `default` может означать включение с параметрами провайдера; не показывать фиктивный Medium. |
| Default | «По умолчанию» только при наличии такого выбора/проверенного reset. Это не числовой бюджет, не Off и не гарантия одного уровня у всех моделей. |
| Mandatory/fixed | Показать доступное фиксированное значение/пояснение. Не предлагать Off, если его нет. Не считать неподвижность контрола ошибкой сама по себе. |
| Числовой budget в существующей реализации | Сохранить реальную единицу, диапазон, шаг и семантику reset. Не переводить произвольное число в «интеллект %» и не добавлять slider только по наличию budget в исходниках Qwen. |
| Временная ошибка чтения или отсутствующий новый mapping | Последнее подтверждённое значение + краткая причина. Недоступен только неподтверждённый вариант; работающий путь не удаляется. |

Показывать **выбрано для следующего запроса** отдельно от **применено в текущей сессии/turn**. Например, пользователь выбрал иной режим во время ответа: рядом «После текущего ответа»; детали показывают actual и pending. Не менять задним числом подпись уже выполненного сообщения. Readback подтверждает настройку CLI, но не объём скрытых рассуждений модели и не гарантированное качество ответа. Не логировать hidden chain-of-thought ради такой проверки.

Кнопка доступна с клавиатуры, selected value читается screen reader; Escape закрывает menu без применения, focus возвращается к контролу. Изменение не отправляет prompt и не очищает draft. Длинные русские labels не вытесняют Send/Stop; фактические размеры и focus проверить в изменённом экране по [DESIGN_IMPLEMENTATION_GUIDE](DESIGN_IMPLEMENTATION_GUIDE.md), без новой матрицы всех экранов.

## 4. Одно состояние и применение со следующего turn

Переиспользовать Task settings service и existing session adapter. Минимальная **внутренняя запись host, не ACP schema**:

```text
settingsIntent: taskId / assignmentId / settingsRevision / operationId
desired: modelRouteRef + optionId/value + source
observed: bindingId + connectionGeneration + modelRouteRef
          optionsSnapshotRef/hash + currentValue + observedAt/provenance
application: pending | applying | confirmed | failed | uncertain
turnCapture: turnId + settingsIntentRef + confirmedSnapshotRef
```

Точные поля согласовать с существующим store, не создавать параллельные DTO ради документа. `confirmed` означает подтверждённую настройку конкретного binding. Идентификатор модели включает реальный route/provider, когда это различается в проекте; одинаковый display name не объединяет endpoints.

1. Выбор фиксируется Task writer по revision. Если turn активен, его captured settings не меняются; новое намерение ждёт безопасной границы. Разрешение выбирать во время ответа не означает мгновенную смену уже выполняющегося запроса.
2. До следующего dispatch тот же scheduler ждёт terminal текущего turn и разрешение pending/unknown effects. Он закрывает admission для этой session на время применения, не все Tasks приложения.
3. При смене модели применить её существующим вызовом, принять свежий полный snapshot, затем проверить допустимость выбранного reasoning. При неизменной модели не выполнять лишний model setter.
4. Применить допустимый reasoning через прежний adapter и принять подтверждение. Для обычного value сравнить фактический результат; для default использовать подтверждённую семантику reset/нормализации. Буквальное неравенство `default` и возвращённого tier не всегда ошибка; произвольный иной tier не объявлять нормализацией без основания.
5. Зафиксировать observed snapshot и receipt, затем допустить prompt с этим capture. Failure/timeout не превращать в confirmed. Несколько setter calls не являются атомарной транзакцией CLI: модель могла смениться, reasoning — нет. Показывать реальное частичное состояние и удержать только зависящую отправку.
6. Поздний ответ другой generation/старого намерения не затирает новое. Если протокол не даёт revision, сериализовать изменения на binding и использовать существующий correlator; собственный sequence не выдавать за remote revision.

Обычный выбор относится к Task/assignment. «Сделать для новых задач проекта» — отдельное явное действие, если оно уже поддерживается. Не включать глобальное сохранение через Qwen persistence extension или редактирование provider settings просто при каждом click. Существующие пользовательские preferences сохранить при миграции.

## 5. Очередь, смена модели и повторы

- **Queue item закрепляет намерение при enqueue.** Если на экране выбран pending reasoning, сообщение ссылается на него, а не незаметно на прежний actual. Последующий выбор другого значения не меняет старые items. «Применить к ожидающим» — адресное действие по [SMART_MESSAGE_QUEUE](SMART_MESSAGE_QUEUE.md).
- **Смена модели пересобирает доступные controls.** Старый selection остаётся в истории/намерении, но не считается применимым новой модели. Удалить несовместимую проекцию active knobs; не стирать пользовательские configuration files или бюджеты через собственный provider patch. Использовать реальный новый default/readback. Если queued item требует неподдержанный explicit value, held с предложением допустимого выбора, без скрытой замены.
- **Retries уже отправленного turn** не захватывают новые настройки composer. Не добавлять retry целого ACP prompt ради apply reasoning. Семантические ошибки «unknown value/unsupported option» требуют обновить options или исправить mapping; повтор того же запроса их не решает.
- **Provider/CLI fallback** показывать только по фактическому событию/receipt: запрошенная и сообщённая использованная модель различаются. Принять обновлённые options для дальнейшей работы, не переносить прежние knobs автоматически. Без такого события фактическая provider model остаётся неустановленной; UI её не угадывает.
- **Reconnect/restart:** восстановить намерение и последний known snapshot, затем сверить binding актуальным поддержанным способом. Не replay pending setter вслепую при неизвестном исходе; сначала выяснить текущую настройку. Не повторять прежний user prompt для проверки выбора.
- **Параллельные Tasks/окна:** выбор A меняет A; B не получает его через глобальную переменную. Два окна одной Task видят один pending/confirmed state. Stale edit получает conflict/current snapshot, не last-write-wins без проверки.

## 6. Карточки реализации и адресная приёмка

| Карточка | Малый результат | Нужное свидетельство |
|---|---|---|
| **MR1 — существующий mapping** | Найдены прежний selector/service/calls и реальные значения; один короткий before-сценарий | Пути, build/revision, безопасный request/confirmation shape. Не требовать полного runtime inventory. |
| **MR2 — перенос в composer** | Тот же source/service, доступный menu рядом с model, старый выбор сохранён | Live выбор двух доступных значений, один setter на действие, draft/focus сохранены. |
| **MR3 — pending и очередь** | Desired/actual различаются; apply перед dispatch сериализован существующим scheduler | Долгий A1 → выбрать иной режим → enqueue A2 → terminal A1 → apply/readback → A2. A1 не меняется задним числом. |
| **MR4 — зависимости и recovery** | Смена модели, полный snapshot, конфликт/timeout без ложного успеха | Неподдержанный value, default normalization, два окна, reconnect/late response; проверяются только затронутые пути. |

Начинать с MR1/MR2; не задерживать полезный перенос до универсального каталога всех провайдеров. MR3/MR4 дополняют найденные пробелы существующего механизма, а не требуют переписывать всё. Local fixtures разрешены для последовательностей ошибок; их результат отдельно от живого Giga.

Минимальные отрицательные проверки: неподдержанный value не подтверждается; response для B не меняет A; полный snapshot без прежней опции удаляет stale active control; неуспешный apply не выпускает требующий его queued prompt; выбор при активном turn не создаёт второй prompt; отсутствие наблюдения не становится pass. Проверить также корректный ответ и default с нормализованным readback, чтобы валидатор не отвергал рабочий случай. Это checks конкретной логики настроек, не обязательный повтор после изменения одной подписи.

Готовность переноса: пользователь выбирает уже поддержанный reasoning из composer, видит настоящий applied/pending статус, текущий turn и соседние Tasks не меняются, сохранённые предпочтения и очередь работают по контракту. Здесь проведено **исследование источников и подготовка инструкции**; target UI не запускался, его новые проверки не объявлены пройденными.

## 7. Короткое поручение исполнителю

> Перенеси существующий выбор reasoning рядом с моделью в composer. Функция уже работает — сначала найди и сохрани нынешний source/service/adapter и значения. Прочитай разделы 1, 3 и нужную карточку 6; разделы 2/4/5 открывай только при изменении соответствующего mapping или состояния. Не меняй CLI, provider configuration и framework. Покажи один before/after сценарий на текущей сборке; сохрани draft, Task binding и реальные значения. Если затрагиваешь busy/queue apply, различай desired/confirmed и проверь один отрицательный сценарий. Не добавляй универсальные tiers, неподтверждённые методы и новый retry loop. Отчёт: изменённые места, реальное действие/подтверждение, ограничения. Не читай весь пакет на каждом ходе.
