# Адаптация профилей к уже подключённым MCP

Эта инструкция предназначена для агента, которому пользователь поручил самостоятельно настроить Workbench под существующие инструменты GigaCode. Такое поручение разрешает прочитать необходимые настройки и сделать обратимые изменения файлов профилей и их привязок. Сохрани действующие MCP-подключения, endpoints, способы авторизации, секреты и настройки проектов. Подключать новые серверы, менять права учётных записей, настраивать репозиторий или выполнять производственные операции для этой адаптации не требуется.

Контракт ролей находится в [profile-capabilities.json](../config/profile-capabilities.json), общие правила — в [CORE.md](../CORE.md), контракт операций — в [MCP_PROTOCOL.md](MCP_PROTOCOL.md). JSON — декларативная политика для адаптера. Текущий контроллер не читает её как механизм выдачи инструментов и не обеспечивает изоляцию MCP.

## Что настроить

У каждой из девяти ролей есть `allowed_potential`: верхняя граница возможностей, которые могут понадобиться по её назначению. `read_only_default` содержит кандидатов на чтение, а не разрешённые без проверки вызовы. На конкретном этапе выдавай пересечение:

1. Возможностей роли.
2. Возможностей workflow, необходимых для применимых действий и проверок этого этапа, плюс подтверждённое чтение контекста из context_read_policy при конкретной необходимости для задачи. Это позволяет аналитику читать нужный Confluence, не добавляя право записи или полный обход серверов.
3. Подтверждённых привязок к реальным инструментам и ресурсам.
4. Действующих прав host и области, уже разрешённой пользователем для задачи.

Присутствие возможности в матрице не требует её использовать и не выдаёт разрешения. Если нужная возможность отсутствует у роли или этапа, исправление декларации должно соответствовать назначению и задаче; молча расширять набор инструментов нельзя. Запись в локальные артефакты, журнал и общую память — служебная операция основного host в фиксированных каталогах Workbench. Субагент возвращает факты/решения родителю для записи; это не основание выдавать reviewer общий shell или внешние права. Ограниченный служебный интерфейс исполняет родитель, а текущий интерактивный режим честно сохраняет свои пределы изоляции.

| Сервер пользователя | Предметная область | Возможности после проверки инструментов |
|---|---|---|
| Git | Репозитории, изменения, ветки и запросы на слияние | `git.read`, `git.pr.read`; действия `git.branch`, `git.commit`, `git.push`, `git.pr.write`, `git.merge` по фактической схеме |
| Jenkins | Состояние сборок, логи, запуск заданий | `ci.read`; `ci.run` отдельно |
| OpenShift | Состояние ресурсов и операции кластера | `cluster.read`; `cluster.apply` отдельно и с точным окружением/namespace |
| Confluence | Чтение и публикация знаний | `knowledge.read`; `knowledge.write` отдельно |
| Sprut | SCA: версии библиотек, зависимости и их уязвимости; назначение подтверждено пользователем | `security.scan.read`; `security.scan.run`, только если сервер действительно предоставляет запуск анализа |

Ни одна строка не доказывает наличие конкретного инструмента. Sprut здесь не является трекером задач или SAST. Инструменты для `tracker.*`, браузера, локальных файлов, тестов, данных и метрик обнаруживаются отдельно; отсутствие необязательного провайдера не мешает настроить доступные роли.

## Один проход настройки

### 1. Установить фактический контекст

Поставка для переноса содержит исходные тексты, а не уже установленные runtime-скрипты. Сначала выполни процесс `SETUP-AGENT`: восстанови предусмотренные `.ps1` из `source/*.txt` на целевой машине и затем используй созданные локальные скрипты проверки. Не предполагай, что `.ps1` были приложены к письму или уже установлены.

Прочитай только необходимые инструкции и конфигурационные участки. Сверь `/about`, `/help`, `/mcp` и `/tools` в целевой сессии или эквивалентные подтверждённые средства обнаружения. Названия GigaCode и MCP-команд основаны на [проверенной документации совместимости](GIGACODE_COMPATIBILITY.md); детали сборки 26.9.75 нужно подтвердить на компьютере пользователя. На этой машине эта сборка не запускалась.

Определи область установки профилей: существующая проектная или пользовательская конфигурация. Сохрани существующие файлы и их контрольные суммы перед обратимым изменением. Не переписывай весь `settings.json`, `GIGACODE.md` или каталог агентов из шаблона. Наличие незнакомого проекта не запускает onboarding, установку зависимостей, линтеров, CI, форматтеров или генерацию полной документации. Настройка нового проекта — отдельное явное поручение.

### 2. Обнаружить и классифицировать инструменты

Для каждого подходящего реального инструмента зафиксируй:

- Точное имя в target runtime, идентичность сервера и входную схему либо локальную ссылку на её снимок с hash.
- Наблюдаемые/документированные эффекты: чтение, изменение файлов, запуск задания, загрузка данных, изменение удалённого состояния; ограничения параметров, если один инструмент объединяет несколько действий.
- Доступный ресурс: репозиторий, пространство Confluence, Jenkins job, кластер/namespace, SCA-проект. Не сохраняй секретные значения или пользовательские данные из ответа.
- Источник подтверждения и статус: `verified`, `unconfigured`, `unavailable` либо `unknown_effects`; дату, версию и условия проверки.

Имена из старой обвязки и описания MCP — подсказки для поиска. Они не заменяют фактический список инструментов этой сессии. MCP-аннотация о чтении полезна, но сама по себе не доказывает отсутствие побочных эффектов. Неизвестный инструмент не попадает в активный список по умолчанию.

Разделяй чтение отчёта и запуск анализа Sprut. Запуск может создать запись анализа, передать manifest или исходный код и занять ресурсы сервиса. Аналогично получение состояния Jenkins не равно запуску job, а чтение OpenShift не равно применению манифеста. У широкого shell/универсального API нет безопасного ограничения только по его имени: если host не ограничивает команды или параметры, один allowlist не создаёт режим чтения.

### 3. Сохранить проверенные привязки и адаптировать роли

Запиши факты в `<TargetRoot>/workbench-memory/mcp/tool-inventory.local.json`, а привязки — в соседний `bindings.local.json` по структуре [bindings.example.json](../config/bindings.example.json). `<TargetRoot>` — фактический каталог установки, выбранный в процессе setup. Метаданные MCP находятся в общей памяти отдельно от обновляемого bundle и сохраняются при его переустановке. Это локальные файлы адаптера, не автоматически исполняемые настройки GigaCode. В каждой проверенной привязке заполни `provider`, `tool`, `input_schema_reference`, `resource_scope`, `actual_effects`, `status`. Добавь сведения о проверке и fingerprint, не подставляя секреты. Для инструмента с несколькими операциями сохрани ограничения параметров и отметь, может ли runtime их реально обеспечить. Необнаруженные возможности сохраняются как `unconfigured`.

Файл bundle `config/local-context.json` связывает `memory_store`, `bindings_ref`, `inventory_ref` и `profile_permissions_ref` с фактическими локальными путями. В общей памяти достаточно ссылки на inventory, hash схем и кратких ограничений. При переносе старого известного контекста сохрани его происхождение и дату; старые имена инструментов и разрешения требуют сверки перед активацией. Не копируй секреты, сырые настройки авторизации и полные ответы MCP в общую память. Она не заменяет механизм хранения учётных данных.

Если настройка требует нескольких инструментов для одной возможности, явно сохрани все проверенные операции в локальном inventory и используй локальное расширение bindings с описанной версией; не пытайся упаковать несколько имён в строку `tool`. Контроллер не интерпретирует bindings, поэтому формат такого расширения обязан понимать фактический адаптер.

Для каждой роли составь короткую карту доступных действий, областей, недоступных возможностей и ограничений. Подключай её вместе с существующим `profiles/<role>.md`, сохраняя смысл роли, CORE и workflow. Не копируй полный каталог инструментов во все prompts. Не создавай фиктивные инструменты или успешные результаты проверки. Недоступность применимой обязательной операции должна быть видна исполнителю до её выполнения.

### 4. Создать нативные адаптеры только при подтверждённой поддержке

При совпадении имени существующего агента проверь происхождение и сохрани доменные правила. Установщик использует фиксированные workbench-<profile>.md и не поддерживает произвольное переименование. Если безопасная адаптация не установлена, не передавай -IncludeAgents; последовательные профили остаются доступны. Не подменяй неизвестный пользовательский профиль автоматически.

Для создаваемого адаптера `tools` обязательно заполняется только точными проверенными именами в формате, который принимает целевая сборка. Публичное описание поля не заменяет проверку синтаксиса значений через доступный пример/созданный runtime файл и `/agents manage`. Не оставляй поле отсутствующим: по документированному поведению тогда наследуется весь MCP-набор родителя. Пустой список нельзя считать запретом всех инструментов без проверки его фактического поведения. Если подходящих инструментов нет или allowlist не подтверждён, не активируй такой нативный агент.

`disallowedTools` может дополнительно исключать инструменты, но нельзя автоматически заменять отсутствие проверенного разрешающего списка одним списком запретов. Более разрешительный `approvalMode` родителя может иметь приоритет над настройкой ребёнка. Не повышай режим одобрения родителя ради работы роли. Проверяй видимый набор инструментов, применяемые разрешения, ограничения ресурса и наличие альтернативных путей через shell. Заявляй только проверенные свойства; наличие YAML и текста «только чтение» не является доказательством изоляции.

Если сборка не поддерживает проверенное ограничение инструментов, отключи делегирование, требующее изолированного режима. Используй интерактивный профиль в основной сессии с явно указанными ограничениями: доступный родителю набор остаётся шире профиля, действия выбираются по инструкциям и существующим разрешениям, техническая изоляция не подтверждена. Задачи, которым необходима именно изоляция, до её обеспечения остаются заблокированными. Не включай автоматически все инструменты в качестве fallback.

### 5. Выполнить безопасную проверку и выдать результат

Canary-проверка использует только уже разрешённые инструменты чтения и известный ресурс: например, получение метаданных репозитория, состояния существующей сборки, сведений о ресурсе без содержимого Secrets или существующего SCA-отчёта. Не создавай ветку, PR, запись Confluence, сканирование, Jenkins job или изменение кластера ради проверки настройки. Не проверяй запрет реальной попыткой производственного изменения; если невозможно безопасно подтвердить ограничение, зафиксируй его как неизвестное.

Итог настройки содержит: созданные/изменённые локальные файлы и резервные копии, обнаруженные роли и инструменты, привязки со статусами и областями, проверенные свойства runtime, выполненные чтения с фактами, оставшиеся ограничения и способ отката. Общего утверждения «права безопасны» или «все профили готовы» без пооперационных свидетельств быть не должно.

Не задавай дополнительные вопросы о том, что можно найти в настройках или инструментах. Продолжай доступную часть настройки самостоятельно. Вопрос нужен только для факта, который действительно блокирует требуемое действие: например, несколько неразличимых целевых окружений. Отсутствующий необязательный сервер просто остаётся непривязанным. Уже данное разрешение на задачу или настройку применяется повторно без повторных запросов подтверждения.

## Повторное использование без лишних проходов

Inventory строится один раз при адаптации, затем переиспользуется по fingerprint: версия runtime, идентичность серверов, нормализованные имена и схемы инструментов, релевантные права и области. Хешируй только несекретную проекцию, не сырые настройки с токенами. Обновляй изменившуюся часть при смене сборки/сервера/схемы/прав, исчезновении инструмента, отказе доступа или явном запросе пользователя. Успешный hash старого файла сам по себе не доказывает, что удалённые разрешения не изменились; учитывай сигналы host и ошибки вызова.

На переходе этапа сопоставь короткую карту текущей роли с применимыми capabilities и действующей авторизацией. Полная повторная инвентаризация каждого сервера, запуск canary на каждом этапе и повторное чтение всех prompts не нужны. Контекст роли хранит ссылку/hash актуального inventory и только нужные привязки. Изменение области задачи может потребовать другого ресурса и разрешения, даже когда схемы инструментов остались прежними.

Матрица и инструкции не включают автоматическое подключение серверов, изменение их account permissions или программный dispatcher. Это проверяемый процесс самостоятельной адаптации на целевой машине; исполнение и подтверждение фактических ограничений остаются обязанностью GigaCode/host и его адаптера.
