# Что перенести из сильных агентных интерфейсов

Проверка источников: **2026-10-09**. Это проект решений для существующего личного GigaCode UI, а не отчёт об уже работающих функциях. Прочитаны официальные документы и указанные исходники; конкурентные приложения и сборка пользователя в этом исследовании не запускались. GigaCode CLI остаётся готовым внешним продуктом: никаких патчей, приватных hooks и подмены его агентного движка.

Главное заимствование — связный рабочий цикл: **написать → уточнить во время работы → увидеть изменение → проверить → продолжить или восстановить**. Второстепенные controls раскрываются в месте действия. Сохраняется **Project → Tasks → роли внутри Task**, единый разговор и существующий WorkflowEngine. Наличие функции в Codex, Claude или upstream Qwen не доказывает доступность соответствующего метода в установленном GigaCode.

## 1. Какие решения действительно стоит перенести

| Решение | Выбор и причина | Что именно делаем у себя; что не переносим |
|---|---|---|
| Claude: разговор и рабочие материалы в одном пространстве | **Adapt — сейчас.** Пользователь видит ход работы и может проверить файл без переключения продукта | Спокойный transcript, свёрнутые tool rows, нижний composer; diff/browser/terminal открываются по месту и сохраняют состояние. Не клонируем оформление, assets и весь набор панелей сразу. Основа — D2/D3, расширение материалов D7 |
| Codex: queue/steer, review из разговора, side/fork | **Adapt — по возможности.** Эти действия решают разные пользовательские задачи | Queue реализуем в host; steer только через подтверждённый CLI-механизм. Review привязываем к ревизии, side question отделяем от нового направления работы. Кнопка с неподдержанным действием не изображает успех |
| Cursor: быстрые вмешательства и откат с просмотром | **Adapt.** Короткая обратная связь ценнее постоянного dashboard | Ответ на вопрос, комментарий к diff, очередь уточнений, просмотр snapshot перед восстановлением. Различаем файлы, историю разговора и внешние эффекты; не обещаем универсальный Undo |
| VS Code: явная идентичность session/workspace и несколько представлений | **Adapt — фундамент.** Помогает нескольким окнам не смешивать работу | Task/session/workspace/window — разные сущности; одно окно не владеет всей задачей. Peer chat с общими файлами не выдаём за изоляцию. Не переносим VS Code extension host целиком |
| Cline: различать восстановление файлов и разговора | **Adapt.** Пользователь понимает последствия восстановления | Наш dialog сначала показывает затрагиваемые версии и dirty files. History branch сохраняет исходный журнал. Автоматическое snapshot после каждого tool call откладываем: Giga может не раскрывать границу, а цена на большом repo не измерена |
| Continue и Roo: декларативные роли/инструменты | **Adapt идею схемы; reject полный runtime.** Роль должна иметь проверяемую область работы | Наши девять ролей и реальный capability inventory; проверка прав до dispatch. Не копируем prompt целиком, обязательную цепь подагентов и обобщённое «MCP разрешён» как право на любые записи. Roo — архивный источник, не живая зависимость |
| Aider: маленький явный контекст плюс ориентир по repo | **Adapt.** Полезно для Flash-моделей и больших проектов | Видимые file/selection chips, source revisions, адресное извлечение; карту символов добавляем только после измерения поиска. Не подключаем Python runtime Aider ради одного алгоритма |
| OpenCode: явное восстановление/повтор и локальная организация диалога | **Adapt представление, reject второй backend.** Не нужно два конкурирующих владельца агента | Переносим идею понятного состояния ожидания и отдельного результата операции. Сначала наблюдаем повторы установленного Giga/SDK; подтверждённые слои Qwen не доказывают их наличие в форке. Не добавляем blind whole-prompt replay |
| Monaco, xterm.js, Dockview core и viewers | **Use как зависимости после проверки стека.** Это готовые ограниченные компоненты | Редактор/diff, terminal renderer и docking имеют свой контракт и lazy load. Файлы, PTY, процессы и permissions остаются в нашем host. Не считаем UI-библиотеку готовой IDE или контроллером ресурсов |
| Remote/cloud agents, широкое computer use, marketplace, полноценная IDE | **Defer.** Не нужны для первого надёжного повседневного цикла | Отдельные пользовательские slices D13 либо IDE D12. Не требуются до D2/D3 и не дают права автоматически загружать данные или управлять всем desktop |

**Не переносить:** автоматический setup существующего repo; глобальную роль/модель на все задачи; безлимитные агенты и повторы; автоматическую публикацию transcript; новый run на каждое сообщение; зелёное «готово» по финальному тексту модели; импорт конкурентного backend ради похожей кнопки. Эти ограничения защищают удобство: они предотвращают потерю работы и непредсказуемое расширение задачи.

## 3. Что можно взять готовым, что придётся адаптировать

«Размер» ниже — **инженерная оценка области интеграции**, не измеренный bundle size, срок или стоимость. `S` — один ограниченный adapter/view; `M` — сервис, persistence и несколько UI paths; `L` — отдельный runtime/подсистема. До установки измерить фактические package/worker/native dependency размеры и старт на целевой сборке. Уже существующий эквивалент в прототипе имеет приоритет.

## 5. Контракты интеграции, без которых похожий UI будет обманывать

Имена ниже обозначают **области ответственности нашего host**, не обязательные новые классы/сервисы и не названия ACP-методов. Сначала найти их эквиваленты в прототипе. Не плодить второй state store или runtime ради соответствия документу.

| Контракт | Минимальные данные и инвариант | Кто владеет |
|---|---|---|
| **Task / View binding** | `projectId, taskId, chatId, assignmentId, runRef, workspaceRef`; окно хранит view ref, не глобальную active session | Существующий Task writer; renderer — проекция snapshot + ordered tail |
| **Session / Turn** | `connectionGeneration, sessionId, requestId, turnId, capturedSettings, outcome`; не более одного in-flight prompt на binding; cancel_requested не завершает его | SessionService и единственный dispatch owner |
| **Queue item** | `itemId, draftRevision, contextRefs, settingsRevision, expectedTaskRevision, status`; queued/editable отдельно от dispatching/sent/unknown | Durable host queue; acknowledgement протокола и receipt различаются |
| **Capability snapshot** | Runtime/version/schema hash, observed supported options/methods/tools и freshness; `unknown` отдельно от `unsupported` | Реальный adapter; UI не выводит способность из бренда/названия модели |
| **Approval / external operation** | Request/tool/target/arguments hash + scope + binding + decision + receipt; user choice применяется только к совпавшему запросу | Permission/operation boundary, один хозяин retry и reconciliation |
| **ChangeSet / Restore** | Base/current file hashes, workspace, touched paths, snapshot coverage/omissions, external effect refs; restore — проверяемая запись при idle | File/Git ownership; текстовая история не является транзакцией файлов |
| **Evidence / result** | Source/build/requirements revision, actual command/target, outcome, artifact hash, measured/unknown; ledger неизменяемый | Evidence service; модель лишь описывает наблюдения и предлагает вывод |
| **Panel / resource** | Panel ID/type/content ref отдельно от process/browser/PTY owner; hide/reorder/layout restore — только представление | PanelRegistry + соответствующий resource owner |

Для каждого adapter проверить цепочку **пользовательское действие → durable intent → реальный вызов → correlated result → видимое состояние**. Между записью intent и внешним вызовом crash возможен: локальная идемпотентность не доказывает exactly-once внешнего эффекта. При неизвестном исходе показать unknown и согласовать результат, а не повторять автоматически.

## 6. Как должен выглядеть привычный, но самостоятельный интерфейс

По умолчанию экран состоит из sidebar, разговора и нижнего composer. В sidebar — проекты и их задачи, новый чат, поиск и настройки. В компактном заголовке — название задачи и понятное состояние; **постоянный правый task dashboard не нужен**. Роль/модель/reasoning находятся рядом с вводом. Не выводить всегда одновременно project metadata, все stages, approvals, budget и девять агентов.

Результат агента остаётся читаемым сообщением; перед ним tool activity свёрнута в несколько строк. После него — только возникшие полезные действия: открыть изменённые файлы, посмотреть проверки, продолжить. План, Changes, Checks и материалы — контекстные виды той же Task, открываемые по потребности. Материал можно пристыковать сбоку, но закрытая панель не означает потерянную работу. Вложение и комментарий к строке возвращаются в текущий composer с понятной ссылкой.

У composer различаются состояния: idle → send, working → queue + stop, pending approval → конкретная inline card, retry/disconnected/unknown → причина и допустимое действие. Черновик доступен во всех состояниях. Клавиша Enter имеет одну объяснённую семантику, а steer не маскируется под обычную отправку. Переключение задачи не перепривязывает уже отправленный запрос.

Использовать собственные [токены и component recipes](DESIGN_IMPLEMENTATION_GUIDE.md), [иконки](ICON_LIBRARY.md) и [motion](GRAPHICS_AND_MOTION.md). Знакомые взаимодействия можно спроектировать самостоятельно; чужие logos, screenshots, fonts или закрытый код не нужны для этого результата.

## 7. Порядок внедрения и настоящие gates

**Сначала D0–D2:** F01/F02/F04/F12/F19 и минимальные F07/F08/F20. Полезный результат — задача выполняется, показывается без клика, не смешивается с соседней и продолжается после restart. Не ждать всего каталога возможностей, чтобы начать безопасный dogfood.

**Следующая поставка D3:** закончить рабочее место: F03 с честным fallback, F05 choices/free-text answer bridge, F13–F15, F21 status, F23–F25, F26 basic material view, F28/F29/F31 basics и F33 «План задачи». Это реальные browser tools/PTY, материалы, вопросы и удобный composer; не набор незапущенных кнопок. Точные подзадачи выбираются из выявленных пробелов текущего прототипа.

**Затем D4–D6:** единая Task, requirement/evidence revisions, bounded context/memory, автоматические роли и только нужные managed workers. F05/F06/F16–F18/F22/F30/F32 и authoritative связи F33. Микро-задачи по-прежнему проходят быстрый маршрут одним подходящим исполнителем.

**D7–D10:** глубокие diff/review/restore, материалы, проверяемый browser preview, design и Git/integrations. F08–F11/F26/F27 и соответствующие расширения F21/F24. Rich review не отменяет ранний просмотр изменения D2. D11 доводит поиск/настройки/упаковку; D12 — IDE; D13 — выбранные дополнительные функции.

Для каждого slice:

1. Назвать существующие файлы/владельца, видимый сценарий, `use/adapt/defer/reject`, source/license и конкретную границу Giga. Если функция уже есть, исправить её пробел вместо параллельной реализации.
2. Выбрать **один** обычный сценарий и относящийся к нему отрицательный: stale response, unknown outcome, dirty file, unsupported capability, duplicate input или restart. Для чистой label-правки не прогонять весь каталог.
3. Реализовать contract/state сначала, затем видимое действие. Unit/adapter test проверяет инвариант; actual Electron test проверяет реальный click/keyboard → effect → display на той же сборке. Лог вызова не доказывает отображение.
4. Записать build/source/runtime, before/after evidence, измеренные startup/response/jank/storage изменения по применимости и limitations. Нет доступа к runtime — `not_run`, а не «готово». Числа и ускорение не придумывать.
5. Добавить маленькую поставку к существующему D receipt. Измерить на одинаковой задаче число обязательных действий пользователя, повторы объяснения контекста, потерянные/смешанные события и время до проверяемого результата. Оптимизация принимается только при сохранении quality gate; маркетинговый feature count не метрика качества.

## 8. Короткое задание для реализующей Flash-модели

```text
Работай в существующем GigaCode UI, personal_fast. Реализуй только F__ из COMPETITOR_FEATURE_PLAN.
Прочитай выбранную строку, её R-кандидат, нужный интеграционный контракт и текущий D milestone.
Найди в repo настоящий UI/framework, owner состояния и CLI adapter; назови фактически затрагиваемые файлы.
Сохрани Project→Tasks→роли, chat-first экран, текущие принятые требования и неизменный Giga CLI.
Сначала скажи: что уже есть, какой один пробел исправляешь, use/adapt/defer и почему.
Проверь actual capabilities. Не изобретай ACP flags/methods и не импортируй целый чужой runtime.
Сделай один вертикальный путь: действие → сохранённый intent → реальный вызов → receipt → UI.
Проверь обычный и указанный отрицательный сценарий; для runtime функции нужен живой тот же build.
Результат: изменённое поведение, файлы/revision, выполненные проверки с evidence и unknown/not_run.
Не отмечай D завершённым по финальному тексту модели. Если не проходит — сузь причину, максимум две
попытки семантического исправления, затем конкретный blocker/следующий маленький шаг без fake success.
```

На следующий turn передавать выбранные F/R/contract, текущий diff и краткий evidence ledger. **Не вкладывать этот документ, девять конкурентных repo и всю историю задачи в каждый prompt.** Процесс разработки описан в [FLASH_MODEL_EXECUTION](FLASH_MODEL_EXECUTION.md); архитектура рабочего продукта остаётся в native host.
