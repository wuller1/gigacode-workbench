# Адаптивное выполнение: quick, standard, deep

Небольшая задача получает небольшой процесс, но сохраняет проверку фактов, границы поручения и подтверждение результата. Глубина выбирается по риску, неопределённости, области влияния и внешним эффектам. Файл ТЗ, слово «баг», первая задача в проекте или число строк сами по себе не определяют глубину.

Машиночитаемое описание находится в [config/routing.json](../config/routing.json). Это декларативная политика для host и исполнителя. Локальный `workbench.ps1` исполняет выбранный workflow; наличие конфигурации не означает, что он автоматически классифицирует задачу, вызывает модель или переключает процесс.

## Сначала использовать существующую задачу и проект

Обычный вопрос, уточнение требования, исправление замечания и ответ на открытый вопрос относятся к текущей задаче. Для каждого сообщения не создаётся новый run. Сохраняются уже полученные решения, полномочия, проверенные факты и журнал.

Существующий проект по умолчанию считается уже настроенным: читаются нужные действующие инструкции и настройки. Автоматические `repo-setup`, onboarding, замена `GIGACODE.md` или перезапись проектных команд при первом запросе не выполняются. Недоступная команда сначала рассматривается как конкретная проблема среды, а не разрешение переустановить проект.

Настройка нового проекта — отдельная явно выбранная пользователем задача. По явному запросу изучить незнакомый существующий проект можно провести исследование только чтением, например через discovery. Это не разрешает настройку среды. Маршрут onboarding с действиями настройки выбирается отдельно при соответствующем поручении; он не является скрытой частью каждой первой задачи.

## Четыре основания выбора

| Основание | Вопрос | Что исключает quick |
|---|---|---|
| Риск | Каковы последствия неверного изменения? | Существенный риск данных, доступа, совместимости или пользовательского ущерба |
| Неопределённость | Известны требуемый результат и сохраняемые гарантии? | Отсутствует влияющее на корректность бизнес-решение или источники конфликтуют |
| Область влияния | Понятны затронутые пути и потребители? | Неизвестное влияние, публичная граница или межсистемное изменение |
| Внешние эффекты | Какие ресурсы реально изменяются? | Публикация, доставка, общие данные или неизвестный исход внешнего действия |

Обратимый технический выбор внутри ясной задачи не требует автоматически ни полного SDD, ни вопроса пользователю. И наоборот, одна строка в проверке прав может требовать глубокого процесса. Опечатка в тексте о платежах сама по себе не означает изменение платёжной логики: оценивается воздействие правки.

Классификация пересматривается при новых фактах. Это не право снимать проваленную проверку ради более простого маршрута. Существенное изменение требований, контрактов или области влияния фиксируется вместе с причиной выбора другого процесса.

## Быстрые маршруты

| Workflow | Этапы / профиль | Обязательный результат |
|---|---|---|
| [quick-answer](../workflows/quick-answer.json) | Один этап analyst | Краткий ответ и проверяемые основания |
| [quick-backend](../workflows/quick-backend.json) | Два этапа backend | Локальная правка, целевая проверка и просмотр итогового diff |
| [quick-frontend](../workflows/quick-frontend.json) | Два этапа frontend | Локальная правка и проверка затронутого интерфейса |
| [quick-doc](../workflows/quick-doc.json) | Два этапа analyst | Точечная правка документа и проверка изменённого фрагмента |

Это процессы одного исполнителя. Привлечение других агентов, полный SDD, мутационные проверки, полная матрица экранов, новые тесты, общий тестовый прогон, обновление документации и ретроспектива не требуются автоматически. Они добавляются при конкретной необходимости либо выбирается подходящий standard/deep workflow.

**quick-answer** нужен для самостоятельного небольшого вопроса, результат которого требуется сохранить. Обычный вопрос внутри уже активной задачи обрабатывается в её контексте. Утверждение получает источник: текущий код, фактический ответ инструмента, предоставленные данные или явное решение пользователя. Общие знания не выдаются за проверенное состояние проекта. Содержательная рекомендация приветствуется, но выдумывать недостаток ради роли критика не нужно.

**quick-backend** сначала фиксирует короткий критерий результата и вносит изменение, затем выполняет выбранную проверку и пересматривает итоговый diff. Достаточная существующая проверка может быть использована без создания нового теста. Новый тест нужен, когда существенное изменяемое поведение иначе остаётся незащищённым. Самостоятельный просмотр diff не называется независимым ревью; при необходимости независимой оценки выбирается standard/deep.

**quick-frontend** не запускает новое проектирование для исправления локального текста, отступа или простого действия. При визуальном или интерактивном изменении реальный UI открывается в релевантном состоянии и viewport. Проверяются затронутые свойства: например, для длинного текста — обрезание и соседние элементы, для действия — результат и предусмотренная ошибка. Набор размеров и состояний расширяется по вероятному влиянию, а не до всех экранов автоматически. Если внешний вид и взаимодействие не менялись, браузерная проверка может быть неприменима с обоснованием. Если они менялись, отсутствие браузера — блокировка обязательной проверки.

**quick-doc** исправляет выбранный фрагмент в его контексте. Проверяются существенные утверждения, затронутые ссылки, пути и форматирование. Опечатка не требует тестов приложения. Изменённый исполнимый пример или структура документационной сборки могут требовать реального запуска соответствующей проверки. Нельзя утверждать, что пример исполнялся, если он был только прочитан.

Артефакты содержат компактное свидетельство результата. Один содержательный файл может включать несколько логических разделов, если host позволяет ссылаться на него; не нужно переписывать одинаковые сведения в большие документы. Операции и факты при этом остаются в журнале.

## Целевая проверка и неприменимость

Проверка выбирается до объявления готовности и привязывается к критерию приёмки. Это может быть тест существующего поведения, проверка типов, линтер, сборка, фактический просмотр UI, сравнение diff или проверка источника. Наблюдение и запуск тестов — разные виды свидетельств, их нельзя смешивать в отчёте.

В quick workflows некоторые checks имеют `allow_na: true`. `not_applicable` допустим только с объяснением, почему конкретный вид проверки не относится к изменению, и свидетельством области изменения. Например, для исправленной опечатки в README не нужен тест приложения, но прочтение итогового фрагмента и diff остаётся обязательным. Недоступный необходимый инструмент, провал, неизвестный результат и отсутствие времени не являются неприменимостью.

Объявленные capabilities — требования к возможностям host, а не команда немедленно запускать каждый доступный инструмент и не выдача полномочий. Host проверяет конкретные действия. Если для обязательной проверки нет возможности, её нельзя превратить в `not_applicable`.

После последней правки проверяется актуальное содержимое: commit сам по себе недостаточен при незакоммиченных изменениях. В свидетельстве указывается ревизия или идентификатор состояния рабочей копии. Исправление, внесённое после теста, требует пересмотра затронутых проверок.

## Когда переходить к standard или deep

**Standard** подходит для нетривиального поведения, нескольких связанных компонентов и задач, которым нужна специализированная проверка. Выбирается конкретный сценарий: backend-feature, frontend-feature, behavior-change, bugfix, refactor, dependency-upgrade, specification, review или другой соответствующий workflow. Все специалисты одновременно не требуются.

**Deep** нужен при существенных рисках, сложной миграции, межсистемном эффекте, явном полном аудите или широкой неопределённости. Например, используются data-migration, security-review, infrastructure, incident, design-system. Сам выбор deep не означает обязательность каждого вида проверки: состав определяется риском и целью.

Если quick обнаружил неожиданный риск, блокирующее неизвестное, неограниченное влияние или недоступность необходимой проверки, этап получает `blocked`. Записываются:

- что установлено и что именно мешает корректно продолжить;
- затронутые требования и выполненные изменения;
- предлагаемый конкретный standard/deep маршрут и необходимое решение;
- версии и свидетельства, которые можно передать дальше.

Quick не продолжается поверх блокировки и не объявляется завершённым. Связанный новый запуск или изменение маршрута оформляются явно; история сохраняется. Сам каталог не обеспечивает автоматическое переключение workflow. Если нужен бизнес-ответ, его получают в соответствующем аналитическом процессе, не подставляя значение по умолчанию.

## Повторное использование свидетельств

Предыдущий результат можно использовать, если подтверждена актуальность его входов. Для этого сохраняются проверка или утверждение, источник, ревизия/хеш, версия требований, метод или команда, данные и окружение, область покрытия, фактический результат и время.

Повторно проверяются только затронутые зависимости. Один и тот же файл по прежнему пути или запись «раньше было зелёным» не доказывают актуальность. Изменение релевантного кода, требования, окружения, входных данных, зависимости или метода проверки делает связанный результат требующим пересмотра. Нарушение целостности свидетельства запрещает его использование.

Повторное использование отмечается ссылкой на прежний результат и основанием его применимости. Оно не называется новым запуском. Старый receipt не доказывает текущее состояние изменяемой внешней системы: нужный факт проверяется адресным чтением. Неизвестный исход записи сначала выясняется, а не повторяется автоматически.

## Журнал и восстановление без повторения всей работы

Факты, операции, решения и значимые рекомендации фиксируются всегда. Если host уже автоматически сохраняет действия, второй противоречивый ручной журнал не создаётся. Запись содержит краткое основание, объект, версию и реальный результат, без подробного внутреннего рассуждения и лишних секретов.

Для обычного продолжения достаточно проверенной компактной сводки, последнего checkpoint, событий после него и необходимых исходных артефактов. При большом хвосте событий используется последовательное адресное чтение. Полная история нужна для аудита/экспорта, повреждения, пропуска журнала, противоречивых записей или конкретного расследования, а не для каждой микро-задачи.

Свидетельства зарегистрированных событий и принятых результатов сохраняются неизменными. Новая версия записывается под новым именем. Продолжение проверяет актуальность и целостность, но не должно повторять успешные действия только ради заполнения тех же документов.

## Документация, ретроспектива и отчёт

Если документированное поведение, контракт и эксплуатационные действия не изменились, обновление документации может быть no-op с коротким обоснованием. Если изменение затрагивает документ, обновляется соответствующий фрагмент; полный аудит документации автоматически не запускается.

Ретроспектива выполняется по событию: повторный сбой, существенный неожиданный риск, дефект процесса, неверное свидетельство/восстановление либо явный запрос пользователя. Успешная микро-задача не требует отдельного ретроспективного процесса. Полезное наблюдение можно оставить в текущем журнале.

Финальный ответ кратко сообщает результат, проверку, ограничения и существенную рекомендацию при наличии. Технический след хранится отдельно. Эти маршруты сокращают **статический состав процесса**: один или два этапа вместо полного цикла и отсутствие обязательных дополнительных ролей. Конкретное ускорение, токены и время подтверждаются только сравнительными замерами на реальных задачах; заранее они не обещаются.
