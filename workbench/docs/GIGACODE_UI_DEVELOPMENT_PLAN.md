# План развития GigaCode UI без изменения CLI

Цель — полноценный личный рабочий инструмент поверх установленного GigaCode CLI: параллельные чаты, восстановление, управляемые исполнители, профили, память, инструменты, артефакты и удобное рабочее пространство. Развитие начинается с существующего Electron-прототипа. Это проектный план, а не описание уже реализованных возможностей. Он не требует обучения моделей, собственного агентного движка вместо CLI или изменения кода CLI.

Первыми закрываются пользовательские сбои: независимая работа в нескольких окнах, обновление состояния без клика и пустого экрана, управляемое восстановление после обрывов и 429. Подробная диагностика и проверка живого приложения предшествуют новым функциям. Полный будущий набор не загружается одним заданием в Flash-модель. Для каждой карточки используются [короткий пакет задачи](FLASH_MODEL_EXECUTION.md), несколько актуальных источников и конкретная проверка.

Прямой отдельный model API — возможный будущий самостоятельный backend, но не скрытая подмена выбранного CLI и не зависимость этого плана.

## Где живёт функциональность

| Область | Реализует оболочка | От чего зависит |
|---|---|---|

| Роли и результаты внутри Task | Role routing, принятые требования, показываемые delivery/check receipts | Project → Tasks → роли; отдельные chat/run/session IDs не меняют эту пользовательскую иерархию |
| Настраиваемые панели/tab groups, basic browser/terminal | Общий PanelRegistry/layout и независимые runtime resource owners уже в M3 | Move/hide не создаёт и не завершает CLI/PTY/browser; IDE не нужна |
| Актуальное состояние и собственная рамка окна | Event delivery/reconciliation в M0–M1; custom chrome и window controls в M3 | Состояние приходит без клика/reload; команды проходят проверенный IPC к владельцу окна |
| Запуск и остановка CLI, транспорт, запросы | Process manager и ACP adapter | Фактические команды запуска/ACP fork |
| CLI вместе с приложением | Runtime manifest/resolver, exact-path spawn, pin версии за connection generation | Подтверждённые права поставки, runtime dependencies и clean-machine probe; без скрытого global PATH fallback |
| Одновременные чаты | Реестр сессий, очередь и маршрутизация | Несколько sessionId в процессе либо проверенные отдельные CLI-процессы |
| История после перезапуска | Собственное сохранение отображаемых событий | Продолжение той же model session только при подтверждённом load/resume |
| Пауза | Пауза очереди новых запросов | Настоящая пауза выполняемого turn только при специальном API; cancel не равен pause |
| Ветвление чата | Новый чат и явно выбранный перенос контекста | Нативный fork/rewind — только если поддержан; файлы и внешние действия не откатываются от ветвления текста |
| Профили, workflows, память, рекомендации | Prompt assembler, scheduler, memory service | Поддержанные CLI инструкции/настройки; ограничения инструментов исполняет host/MCP |
| Управляемые субагенты | Собственные задачи с отдельными сессиями и журналом | Не обещает управление скрытыми нативными субагентами CLI |
| Модель и изображения | Capability registry, проверка вложений, selector | Доступные модели/режимы и форматы ввода именно через этот CLI и провайдера |
| Tokens, цена, размер контекста | Отображение полученных значений | Если CLI не сообщает — unknown; приблизительные локальные оценки подписывать отдельно |
| Повторы после 429 | Планирование, ожидание, интерфейс, reconciliation | Видимость ошибки и исхода, уже существующие повторы CLI; не повторять вслепую весь turn |
| Git, diff, editor, terminal, worktrees | Локальные сервисы, UI и/или существующий Git MCP | Собственные полномочия, Windows и репозиторий |
| Jenkins, OpenShift, Confluence, Sprut | Адаптеры существующих MCP и панели | Реальные tools/schema/доступ; Sprut — уязвимые версии зависимостей |
| Документы, код, изображения, диаграммы, PDF | Реестр артефактов и viewers | Работа с файлами/генераторами; рендер текста не означает наличие PDF/Office export |
| Расширенная browser automation и preview в M7 | Реальные MCP/automation поверх базового BrowserService M3 | Совместимый Electron и явно подключённый инструмент автоматизации |
| Базовые agent browser actions/screenshots уже M3 | Проверенный adapter/MCP к BrowserService: navigate/read/click/fill/screenshot | Actual schema/permissions и target identity; открытая вкладка сама по себе не tool |
| IDE Java/Python/React в M12 после M10 | Реальные language/debug/build adapters поверх editor/PTY/Task | Наблюдаемые SDK/protocols целевой машины; M11 необязателен |
| Интерактивные UI-макеты внутри оболочки уже M6; canvas расширяется в M8 | Giga создаёт versioned artifact; общие ArtifactService/BrowserService показывают preview, screenshots и замечания | Реальный agent bridge и отдельная изоляция исполнения; не требует IDE или изменения CLI |
| Расписание, наблюдение, фоновые задачи | Локальный scheduler и persistence | Компьютер/процесс должны работать; после сна применять явную политику пропущенных запусков |
| Голос, OCR, image generation, remote control | Опциональные внешние адаптеры | Не появляются из ACP автоматически; отдельный реальный сервис и проверка |

Максимум функций достигается расширением оболочки и инструментов. Отсутствие возможности CLI не следует скрывать кнопкой, которая выглядит рабочей. Предлагать честную альтернативу: «новый чат с контекстом» вместо неподдержанного native resume, «остановить следующие задания» вместо «заморозить агента».

## Архитектура для существующей заготовки

Ниже логические компоненты, а не обязательные названия каталогов. В M0 сопоставить их существующим файлам. Для личного проекта достаточно модулей в одном приложении; микросервисы не нужны.

```text
Electron windows / renderer
        | typed narrow IPC
        v
Existing backend or Electron main
  SessionService ---- EventStore ---- Task/Profile/Memory services
        |                   |                  |
  CapabilityRegistry   Artifact registry   Scheduler / MCP adapters
        |
  AcpAdapter ---- ProcessManager ---- installed GigaCode CLI

Separate untrusted surfaces: browser / HTML preview / generated app
```

Renderer отображает состояние и посылает команды, но не владеет CLI-процессом. Reload окна переподключает наблюдателя, а не создаёт новый prompt. Если прототип уже имеет отдельный backend, он остаётся единственным владельцем сессий; не создавать второй manager в main.

Минимальные внутренние сущности: Project, Task, PanelInstance, Chat, CliProcess, AcpSession, Turn, Operation, Event, Approval, Artifact, AgentTask, Evidence, MemoryEntry. Начать только с нужных M0–M2. Каждый ID имеет одну область действия. Внутренний `chatId` не равен ACP `sessionId`, `turnId` не равен JSON-RPC `requestId`. Связь хранится явно; имена внутренних полей не отправляются CLI как придуманные поля ACP.

Пользовательская иерархия — Project → Tasks → роли внутри задачи. Роль не создаёт новый проект/обязательный чат; профиль разработки получает принятый scope и продолжает ту же Task. Stable app и candidate/test из [плана поставок](DELIVERY_AND_DOGFOOD_PLAN.md) имеют раздельные data/runtime selection и контролируемую promotion/rollback. Разработка внутри приложения не должна убивать его единственный рабочий экземпляр.

Инварианты:

1. Один активный prompt на одну ACP-сессию; следующие задания остаются в её очереди. Параллельность — между разными сессиями.
2. Ключ ожидаемого RPC включает соединение и requestId; ключ событий — соединение и sessionId. После рестарта новый connection generation не принимает запоздалые события старого.
3. UI-команда имеет operationId, ожидаемую ревизию и владельца. Двойной клик/повтор IPC не создаёт второй dispatch. Это локальная дедупликация, а не гарантия exactly-once внешнего эффекта.
4. Единственный writer сохраняет событие перед публикацией окнам. Snapshot имеет номер последовательности; подписчик получает хвост после него, обнаруживает пропуски, не дублирует завершённые блоки. ACP chunks без upstream ID нельзя дедуплицировать только по одинаковому тексту: одинаковые фрагменты могут быть законными.
5. Cancel, permission reply, tool update и ошибки принадлежат конкретной сессии/запросу. Общий флаг busy допустим только как производная сводка.
6. Renderer lifecycle, task lifecycle и CLI lifecycle разделены. Закрытие окна по умолчанию не теряет чат; действие «остановить задачу» явно управляет процессом/turn по возможностям.
7. После обрыва активные операции получают unknown outcome до reconciliation. История UI не доказывает завершения внешнего действия.
8. Модель предлагает результат; проверки состояния, схемы, revisions, разрешений и evidence выполняет код. Prompt не является механизмом изоляции инструментов.

Хранилище сначала использовать существующее. Если его нет, начать с одного локального writer и транзакционного embedded store, а не синхронизации нескольких JSON из разных окон. SQLite — возможное решение после проверки совместимого драйвера с Electron ABI. Содержимое больших файлов хранить отдельно, в БД — metadata/hash. Сохранять миграции, резервную копию и тест восстановления. Не переносить всё на новую БД только ради одной ошибки маршрутизации.

## M0 Наблюдаемость и воспроизведение

**Результат:** известен путь события CLI → main/backend → IPC → store → selector/render, воспроизводятся parallel failure и зависание/пустое состояние; live harness запускает проверяемую сборку.

- M0.1 Прочитать доступные версии, команды и текущую архитектуру. Создать короткую карту модулей и capability report `verified/absent/unknown` с источником и версией. Не угадывать флаги GigaCode по имени Qwen.
- M0.1a Снять runtime inventory/probe для [bundled CLI](BUNDLED_CLI_RUNTIME.md): фактические executable/dependencies, версии/hash, launch contract, источник и права распространения. Подготовить manifest/resolver внутри текущего backend. Права upstream Qwen не доказывают права поставки GigaCode; неизвестное явно блокирует именно распространение, не локальное исследование установленной копии.
- M0.2 Ввести подробный локальный коррелированный журнал по [DESKTOP_OBSERVABILITY.md](DESKTOP_OBSERVABILITY.md): spawn/exit, initialize, session/prompt/update/permission/cancel/error, main/IPC delivery, store apply, renderer commit и lifecycle окна. Сохранять timestamps, IDs, connection generation, sequence/revision и outcome; наблюдаемость готовится до исправления. Ограниченный flight recorder и кнопка пакета диагностики дают агенту факты через проверенный локальный read-only доступ/MCP. Без секретных env/token и бесконтрольного полного prompt; ACP stdout отдельно от диагностического stderr.
- M0.3 Запустить настоящий Electron с тестовым user-data directory и установленным CLI. Проверить build identity, открыть два окна, создать A/B, получить реально пересекающуюся активность. Если запрос слишком короткий, использовать безопасную детерминированную тестовую операцию с наблюдаемым барьером через разрешённый инструмент.
- M0.4 Сравнить доступное поведение установленного Desktop на том же простом сценарии. Сохранить отличие handshake/создания сессий, если оно наблюдается. Desktop не менять.
- M0.5 Воспроизвести «обновилось только после клика» и пустой экран без последующего пользовательского input: связать source event seq с received/applied/rendered seq, проверить subscription gap, stale snapshot и ошибки renderer. Прочитать [DESKTOP_STATE_AND_CHROME.md](DESKTOP_STATE_AND_CHROME.md); не объявлять причиной framework, GPU или ACP без различающего trace.
- M0.6 Подготовить отдельный candidate/test userData/runtime, исходную рабочую сборку и backup/restore probe. Контрольная точка D0 сохраняет реальные paths/build/evidence; пока нет исходников/целевого запуска, она не выполнена.

**Приёмка:** видимый сбой связан с конкретными session/request/process IDs и границами доставки/отрисовки; исходные logging receipts сохранены. Есть failing либо честно not_reproduced сценарий, в котором после dispatch не выполняется клик, hover, смена focus или reload для «починки». Проверить также фон/возврат окна. Playwright поддерживает Electron экспериментально, поэтому сначала проверить запуск с текущей версией и способом сборки; browser-only тест не заменяет Electron. [Официальный API](https://playwright.dev/docs/api/class-electron).

**Первый маленький шаг:** сквозной receipt dispatch/update/store/render одной сессии, затем второй; расширять подробный локальный журнал по найденной границе, сохраняя bounded buffers. Это диагностика приложения, без обязательной внешней telemetry-платформы.

## M1 Независимые сессии и стабильное состояние окон

**Зависимость:** M0; сначала [диагностический playbook](PARALLEL_SESSIONS_FIX.md).

- M1.1 Исправить подтверждённое владение chat→session. Создание сессии single-flight на chat, внутри одного соединения разные чаты получают разные sessionId. Между независимыми процессами одинаковые значения sessionId допустимы: ключ включает connection generation. Реестр не хранится в одном `currentSession` renderer.
- M1.1a Process owner получает явный runtimeRef с version/hash/absolute launch paths; connection generation сохраняет выбранный runtime на весь lifecycle. Не искать другой глобальный CLI при ошибке bundled запуска. Неподготовленный bundle — видимый статус; допустимый development runtime выбирается явно. До пользовательского release выполнить ранний packaging probe на целевой среде без глобально установленного CLI, без изменения самого CLI.
- M1.2 Ограничить одну активную отправку на сессию; очередь хранит отдельные queued/running/terminal элементы. Переключение окна не меняет адрес уже отправленного запроса.
- M1.3 Привязать update/permission/cancel к session и connection. Отписывать listeners при detach; повторное открытие окна не умножает обработчики. Один чат в двух окнах — два представления одной сессии, а не две независимые записи.
- M1.4 Реализовать выбранную стратегию: multiplex только после проверки; отдельный CLI-процесс на чат как совместимый вариант, если одновременные процессы поддержаны на этой установке. Лимиты и общие файлы авторизации/истории также проверить. Не запускать одновременно два владельца одной модели сессии.
- M1.5 Исправить доказанную границу state delivery в своей оболочке: один runtime owner, подписки до потери событий, согласованные snapshot/sequence replay, неизменяемые либо корректно наблюдаемые store updates для реального framework, generation guard старых окон. Gap/out-of-order приводит к reconciliation у владельца, не к повтору prompt или записи старого snapshot поверх новых событий. Ошибка renderer даёт видимое состояние и восстановление, не молчаливый blank screen. Сначала эти исправления и live-проверка, затем новые UI-функции.

Sequence для gap detection относится к конкретному подписанному stream либо использует cursor/watermark: отфильтрованное событие общего лога не считается потерянным. Transport seq и workflow revision не взаимозаменяемы.

**Приёмка:** A/B работают с доказанным перекрытием; ни один фрагмент ответа/approval не переходит соседу; cancel A не прерывает B; close/reload одного окна выполняет выбранную политику; повтор подписки и поздний ответ не меняют новую сессию. Проверить также одинаковое значение sessionId в двух разных соединениях: чаты не должны объединиться. Новое событие отражается без pointer/focus/reload; subscribe/snapshot race, пропуск seq, reopen и background/foreground не теряют tail и не показывают ложную пустоту. Reload используется только в отдельном recovery-тесте, никогда как исправление дефекта. Целевые unit/contract плюс live Electron/CLI на той же source/build revision.

**Заимствовать:** идеи очереди AionUi; конкретный session lifecycle — из ACP и Qwen baseline. Не копировать внутренний daemon Qwen как публичное ACP API.

## M2 Обрывы и 429 без дублирования работы

**Результат:** пользователь видит причину, ожидание и возможность отмены; сомнительный исход не маскируется успешным повтором.

- M2.1 Разделить состояния transport и turn. Минимум: queued, starting, running, waiting_permission, waiting_retry, cancel_requested, reconciling, completed, failed, cancelled, interrupted_unknown. Это внутренние состояния UI. Создать таблицу разрешённых переходов и тестов. Отправка session/cancel означает cancel_requested, а не terminal. Слот сессии занят до итогового ответа текущего prompt; после подтверждённого disconnect — interrupted_unknown и reconciliation. Поздние updates продолжают обрабатываться, ожидающие permission requests завершаются отменой по реальному ACP контракту. Следующий prompt не запускается поверх отменяемого.
- M2.2 Для каждой границы установить владельца повторов: CLI/model API, MCP, запуск процесса, собственный запрос. Если CLI уже повторяет запрос, оболочка наблюдает; она не запускает ещё одну полную копию prompt по таймеру тишины.
- M2.3 Собственный retry применять только к операции с доказанным безопасным повтором. Предложение начальных настроек: до 3 повторов на такую операцию, максимум 120 секунд автоматического ожидания, exponential backoff с jitter; Retry-After учитывать, если он доступен. Если сервер просит ждать дольше бюджета — остановить автоматические попытки и показать срок. Эти числа — настраиваемая политика UI, не лимиты Qwen/GigaCode.
- M2.4 Rate limiter по реальному аккаунту/провайдеру, а не только по окну. Начать с 2 одновременно активных чатов, уменьшать до 1 при подтверждённом давлении 429; это выбранная стартовая настройка, не доказанная оптимальная ёмкость. Очередь не теряет задания, пользователя не переключают на другую модель без выбранной политики.
- M2.5 После crash проверить доступный load/resume и состояние внешних операций. При неподдержанном restore предложить новый чат с кратким контекстом; не переслать последний prompt автоматически. Restart процесса и retry turn — разные операции.
- M2.6 По [CONTEXT_CONTROL_AND_ERROR_RECOVERY.md](CONTEXT_CONTROL_AND_ERROR_RECOVERY.md) различать context overflow, размер payload/вложения, несовместимый request/model/reasoning и неизвестную причину 400/413 по фактическому error source/schema. Не считать любой 400 переполнением и не повторять неизменный отклонённый запрос автоматически. Сохранить inputs/receipts/pending и предложить применимое ручное восстановление: изменить состав следующего запроса, поддержанную компрессию либо модель после безопасной границы. Unknown предыдущего эффекта сначала reconcile; наличие команды в Qwen не доказывает её вызов через Giga ACP. Полный inspector — M4, базовая диагностика отказа и безопасное следующее действие нужны M2.

- M2.7 Подготовить SC0 из [SETTINGS_AND_CONFIGURATION](SETTINGS_AND_CONFIGURATION.md): один versioned SettingsService/schema/apply registry поверх existing settings, источник effective value и captured config revision. Начать с recovery/queue/quota policies M2; проверить сохранение, валидацию, ошибку диска и readback фактического применения. Saved, pending и applied различаются; active turn/internal retry сохраняют свою конфигурацию. Не создавать параллельный settings store и не угадывать CLI flags. Полный экран появляется M3, advanced native policies — M4.

После проверенных минимальных state/session/recovery инвариантов и baseline Task M3 выдать **D2 — первую пригодную dogfood-сборку**, не ждать всех M3–M12 функций. Пользователь начинает малые реальные задачи; отсутствие full native M4 честно указать. Ближайшая D3 доводит удобные panels/browser/PTY M3, не откладывая их за портом. Delivery gates и rollback — [DELIVERY_AND_DOGFOOD_PLAN.md](DELIVERY_AND_DOGFOOD_PLAN.md).

**Приёмка:** управляемые transport failures тестируются через собственный adapter/test double; они помечены simulated. Реальный happy path и отмена ожидания проверяются в Electron. Нельзя намеренно создавать нагрузку до 429: использовать реальные очищенные traces/локальный fault injector. Проверить cancelled timer, shutdown, отсутствующий Retry-After, auth error без retry, unknown write без replay и независимость B от ошибки A.

**Заимствовать:** классификацию и UI состояния из OpenCode, адаптируя к фактической видимости CLI. Дефолты исходников другого проекта не копировать как политику GigaCode.

- M4.1 Перенести 14 profiles/29 workflows, SYSTEM_PROMPT/CORE и routing в native Catalog/WorkflowEngine. Сохранить schema/revisions/attempt_id/hash/checkpoint/pending. Импорт на копиях, parity/round-trip, затем смена единственного writer; не вести два mutable state store.
- M4.2 Расширить Task aggregate: goal/scope/project_mode/acceptance/decisions/questions/todos/artifacts/evidence/revisions/threads/runs и lifecycle metadata. Контракты [ENTITY_LIFECYCLE_AND_EDITING](ENTITY_LIFECYCLE_AND_EDITING.md), [TASK_TODO_PANEL](TASK_TODO_PANEL.md) используют тот же writer; overview/discussion/plan/changes/checks/materials — on-demand views общего PanelRegistry. Task status и formal todo status проецируются из действующего run; второй controller и независимые галочки этапов запрещены.
- M4.3 Versioned Task-first packet содержит текущий критерий, роль/stage, релевантные источники, pending и следующий шаг. Task/requirement/run revisions различаются; CAS результата проверяет run/stage/revision/attempt_id. Profile выбирается маршрутом, пользователь может направлять работу без ручной смены роли на каждом шаге. [ROLE_PROMPT_BINDING](ROLE_PROMPT_BINDING.md) добавляет compiled fingerprint, runtime-supported delivery и отдельные desired/prepared/active состояния. Context-only не становится system override; смена startup parameters требует проверенной session/process границы, не глобального env update.
- M4.4 Questions/answers и SDD delta сохраняются с источником/версией по [ARTIFACTS_AND_QUESTIONS](ARTIFACTS_AND_QUESTIONS.md): stable question ID, Task-bound overlay с inline-входом, варианты плюс свободный ответ, revision guard, связь с требованиями и actual delivery. Minimize не закрывает blocker и не теряет draft; отдельная панель вопросов не вводится. Blocking вопрос останавливает зависимый run, рекомендация не становится блокером; form submit не подменяет native permission callback. Todo projection обновляется от тех же событий; ручная отметка не завершает formal check. Изменённые зависимости делают evidence stale; неизменное переиспользуется с основанием. Rework сохраняет инвалидирование всего suffix. Docs/retro — только по применимости.
- M4.5 Native memory: scope/provenance/status, импорт старых знаний как needs_verification, global+текущий project search и событийное сохранение полезного. Внешние Task refs читаются через actual MCP; локальная правка не публикуется наружу автоматически.
- M4.6 Подробное управление контекстом по [CONTEXT_CONTROL_AND_ERROR_RECOVERY](CONTEXT_CONTROL_AND_ERROR_RECOVERY.md): inspector actual/estimated/unknown компонентов, выбранные материалы и их версии, preview следующего pack, ручная компрессия только через проверенный mechanism. Ограничения, принятые требования, pending effects и evidence refs не исчезают ради уменьшения цифры. Checkpoint/handoff сохраняет Task/run/attempt/budgets; смена модели/новая session не replay. Управляемый host pack и скрытый контекст CLI показываются раздельно; нет обещания удалить внутреннюю историю без API.
- M4.7 Минимальный автоматический фоновый peer broker по [SESSION_COLLABORATION](SESSION_COLLABORATION.md): сессии одного проекта и явно связанные frontend/backend проекты обмениваются внутренними адресными сообщениями и разрешёнными versioned artifact refs. Отдельные peer panel/recipient selector/inbox/outbox/composer не создаются; пользователь видит прогресс Task, результат и действительно требующий его решения blocker. Технические message IDs/receipts сохраняются в diagnostics, а не заполняют разговор. Использовать существующие Task writer, SessionService, message queue и quota owner; реальный host MCP bridge сначала реализовать, зарегистрировать и проверить по actual schema. Не выдавать имена предлагаемых tools за существующий ACP RPC и не менять CLI. Link policy один раз задаёт внутренние project/Task/recipient, направления и допустимые материалы; авторизованный обмен выполняется автоматически без каждого ручного approval. Связь не даёт доступ ко всему репозиторию, памяти или инструментам другого проекта. Busy recipient получает queued item; принудительный steering/второй prompt запрещён без проверенного механизма. Сохранить stable message/correlation IDs, dedup и provenance, различать запись broker, передачу и наблюдаемую обработку. Replies не запускают бесконечный автоматический диалог; unknown delivery не вызывает blind resend.

- M4.8 Расширить existing services по SC3 [SETTINGS_AND_CONFIGURATION](SETTINGS_AND_CONFIGURATION.md) и AR4 [ARCHIVE_AND_RETENTION](ARCHIVE_AND_RETENTION.md): native role/context/memory/parallel/network/peer policies с источником, ревизией, применением и actual enforcement; atomic archive hierarchy с worker/peer/queue races и recovery. Один writer/CAS; изменение policy не пересобирает уже captured turn и не выдаёт новое разрешение. Не создавать второй экран конфигурации или архив поверх другого store. Проверить stale setting edit, одновременный child dispatch/archive и restore с отозванной peer link.

- M4.9 Выполнить CP1–CP4 [CUSTOM_PROFILES](CUSTOM_PROFILES.md): canonical scoped ProfileRegistry с immutable versions/validation/publish/history, агентская помощь purpose→bounded draft→пример проверки, actual activation через существующий ROLE_PROMPT_BINDING и safe boundary. Редкие deduplicated рекомендации исходят из повторяющейся потребности: сначала существующий профиль/коррекция, затем новый proposal. Рекомендация не переписывает, не публикует и не активирует профиль сама; порученное пользователем создание выполняется в разрешённом scope без согласования каждого edit. 14 bundled profiles/29 workflows не меняют счёт от пользовательских drafts. Проверить два окна, stale publish, доступ scope, совместимость actual tools и version capture/target trial.
- M4.10 Выполнить SL1–SL3 [SELF_OPTIMIZING_SCRIPT_LIBRARY](SELF_OPTIMIZING_SCRIPT_LIBRARY.md): native script registry поверх существующих ArtifactRegistry/EventStore/WorkflowEngine, короткий поиск релевантного reuse, validation code/runtime/input/effect hashes и измеряемое ограниченное продвижение/откат версий. SL0 — инструкции повторного использования уже сейчас, не обещание готового runtime registry. Ordinary helpers улучшаются автоматически внутри порученного scope по evidence latency/context/failure; incidental optimization production-кода вне scope остаётся recommendation. Изменённый код/окружение не наследует старый test pass. Нет отдельного optimizer LLM на каждый шаг, unbounded benchmark или расширения permissions; schema/native store реально реализуются и проверяются. 12 portable source entries и почтовый запрет executable files остаются прежними.

**Приёмка:** tiny fix без wizard/full SDD; уточнение не создаёт run; два окна не принимают stale ответ; unknown не становится фактом/pass; новый критерий не сохраняет старый зелёный badge. Restart восстанавливает Task/run/pending/views. Personal_fast не превращается в production-mode от наличия backend; established_strict сохраняется для других рабочих проектов. После cutover — ноль PS invocation на turn, один writer и проверенный import/recovery.

Для M4.9–M4.10 проверить custom draft против активного capture, stale publish/чужой scope, реальный role binding; для скрипта — несовместимое окружение, изменённый hash, wrong output, некорректный benchmark и rollback. Более быстрый результат с нарушенным контрактом не продвигается; missing/empty evidence не pass. Автоматическое улучшение helper не изменяет неразрешённый production-код и не сбрасывает budgets.

Для M4.7 проверить автоматический A→B и ответ в одном проекте, затем frontend→backend по включённой межпроектной связи без ручной отправки/выбора получателя. В основном UI видны только полезный прогресс, итог и actionable blocker; технический trace доступен в diagnostics. Проверить внутреннего адресата при смене активной Task, очередь занятой B, повтор одного message ID, restart между сохранением и dispatch, отозванную связь и неизвестный исход. Несвязанный проект не получает payload; message само по себе не становится пользовательским разрешением/принятым требованием и не обходит acceptance. Включение связи выполняется один раз, обычные сообщения в её scope не вызывают permission-dialog на каждом шаге. Это baseline M4/D4–D5, независимый от создания workers M5.

## M5 Управляемые собственные субагенты

Подробный controller managed workers — [MANAGED_SUBAGENTS.md](MANAGED_SUBAGENTS.md); это расширение существующих Scheduler/SessionService/WorkflowEngine, не второй движок. Native children CLI показываются отдельно с фактически доступным контролем. Инструкции каждого исполнителя привязываются по [ROLE_PROMPT_BINDING](ROLE_PROMPT_BINDING.md).

- M5.1 AgentTask привязан к каноническому Task и хранит parent, цель, профиль, модель alias, workspace, входные evidence, лимиты, статус и результат. Один worker — отдельный chat/session; coordinator — сервис, не бесконечный разговор моделей друг с другом.
- Независимые Tasks/AgentTasks планируются параллельно по DAG зависимостей, квоте и действительным ограничениям ресурсов; зависимые узлы ждут принятый результат. Роль не равна обязательному отдельному worker: для маленькой задачи оставить одного исполнителя, если делегирование не даёт пользы. Общая activity в разговоре Task показывает фактические running/queued/completed/failed counts; открывает карточки нужных workers, их цель/текущий шаг/ожидание и outcome в этой же Task по [TASK_ACTIVITY_INDICATORS](TASK_ACTIVITY_INDICATORS.md). Completed worker не означает автоматически принятый общий результат; неизвестные и обязательные pending зависимости видимы.
- M5.2 Добавить start/cancel/queue pause/details и человеческое уточнение в существующей worker card; команды применяются только к управляемым оболочкой исполнителям. Это не отдельный интерфейс peer-переписки: внутренние сообщения между агентами идут автоматически в фоне. Они используют уже созданный M4.7 broker по [SESSION_COLLABORATION](SESSION_COLLABORATION.md), сохраняя assignment/Task scope и ту же очередь. Не создавать второй mailbox/transport; новое сообщение во время turn очередится, если проверенного steering API нет.
- M5.3 Параллельные writers получают отдельные worktrees при возможности Git; иначе один writer и read-only исследователи. Перед интеграцией проверить diff/base revision, конфликты и общий smoke. Нельзя безопасно изолировать filesystem лишь текстом prompt.
- M5.4 Планировщик соблюдает общую квоту и лимит глубины. Стартовые цели: coordinator + до 2 workers, глубина 1, без самопорождения при блокировке. Все их LLM turns, включая пользовательские чаты и coordinator-вызов, делят общий лимит M2 — до 2 активных managed turns на quota scope; это не два дополнительных слота каждому типу. Скрытый native fan-out остаётся unknown без подтверждённого enforcement. Политику менять по измеренному эффекту; не создавать reviewer для каждой опечатки.
- M5.5 Сравнить Flash-модели на коротких собственных задачах, сохранить version/provider/settings и pass/fail. MiMo vision подключается после проверки реального image input через CLI. Модель не получает роль на основании слова Flash или непроверенного рейтинга.

**Приёмка:** две независимые карточки действительно перекрываются по времени в доступной квоте, а зависимая ждёт результат; inline counts/карточки соответствуют адресным событиям и открываются без смены Task. Один общий результат появляется после интеграции/применимой приёмки, а не после первого completed child. Cancel одного worker не гасит остальных; зависимая задача ждёт реальный артефакт; просроченный результат отклоняется; исчерпание бюджета не обходит лимит созданием нового child. Tiny задача не создаёт workers только ради назначения разных ролей.

Giga выпускает v2; v1, её screenshot и annotation остаются доступны, ссылка другой Task не переключает target. Проверить запрещённый доступ из preview и ошибку JS без падения host. Приёмка требует наблюдаемого сценария на целевой сборке, а не заранее нарисованной картинки или текста «макет готов»; capture/dependencies и ограничения записаны. Это часть M6/D7, а не optional feature.

Базовый browser, общая панель, agent navigate/read/click/fill/screenshot уже работают в M3. Здесь расширяется автоматизация и доказательная проверка приложения, а не впервые появляется доступ агента или второй browser/layout implementation.

- M7.1 Расширить уже проверенный M3 adapter/MCP для многошаговых проверок, поддержанных frame/вкладочных сценариев и диагностики. BC4 [BROWSER_WORKSPACE_CONTROLS](BROWSER_WORKSPACE_CONTROLS.md) расширяет supported device/touch/UA/DPR emulation и воспроизводимые capture recipes; реальные границы target важнее декоративного selector.
- M7.2 Привязать действия к tab/frame/navigation revision и Task ownership; после навигации перепроверять target. Формы, cookies, download и внешние эффекты имеют permissions. Move/hide панели не меняет target.
- M7.3 Добавить PreviewManager: запуск разрешённого dev server, наблюдаемые readiness/порт/build/process ownership и явная остановка. Конфликт порта не разрешается убийством неизвестного процесса.
- M7.4 Связать screenshot/DOM/console/network с конкретным build/state и Task evidence. Неподдержанная automation команда явно недоступна, не имитируется.

**Приёмка:** агент реально находит UI-дефект действием, исправляет и повторяет сценарий; evidence соответствует вкладке/build. Stale target после navigation отвергается, чужой Task не управляет вкладкой; remote page не вызывает filesystem IPC. Изоляция контекстов — необходимая основа, не самостоятельная гарантия полной защиты. [Electron context isolation](https://www.electronjs.org/docs/latest/tutorial/context-isolation).

- M9.3 OpenShift: read health/events/logs, контекст namespace/cluster, diff конфигурации, применяемое изменение и проверка rollout. Не подменять доступ политикой из prompt.

- M9.5 Панель MCP: реальная inventory/schema, профильные bindings, доступность, latency/error, cache с инвалидированием. Инструменты выбираются по назначению и воздействию; отсутствие tools/list или enforcement отмечается явно.

**Приёмка:** реальные read-only вызовы на доступной среде и один разрешённый сценарий изменения с подтверждённым исходом. Долгие операции сохраняют external ID, восстановление опрашивает его вместо повторного запуска. Для маленького docs change анализируется diff и правится только затронутый раздел.

## M10 Удобство и эксплуатация личного инструмента

Bundled CLI уже проверен в ранней упаковке. Здесь добавить staged download/import, проверку manifest/hash/прав, атомарное включение и rollback runtime для новых задач по [BUNDLED_CLI_RUNTIME.md](BUNDLED_CLI_RUNTIME.md). Активные sessions сохраняют свою версию до terminal; её файлы не заменяются под работающим процессом. CLI runtime не означает, что в поставку входят Git/JDK/Python и project dependencies; наличие каждого toolchain проверяется отдельно.

- Расширить baseline Archive/Settings M3 и native M4 по AR5 [ARCHIVE_AND_RETENTION](ARCHIVE_AND_RETENTION.md) и SC4 [SETTINGS_AND_CONFIGURATION](SETTINGS_AND_CONFIGURATION.md): scoped export/import, backup/restore, проверенная миграция и opt-in retention с preview последствий и защитой зависимостей. Архив не автоудаление; retention по умолчанию не стирает pending/evidence. Полнотекстовый поиск расширяется на чаты/артефакты/память в разрешённом project scope; index производный и восстанавливаемый.
- Довести уже существующие настройки M3/M4: безопасный перенос схемы, export без credentials, backup/migration receipt, update/rollback runtime и диагностика применённой версии. Model/reasoning, темы и базовые связи уже доступны раньше; M10 не является их первым экраном. Секреты не хранятся в prompt, журналах или экспортируемом пакете настроек.
- Усилить уже введённый в M3 PTY/Browser/Panel lifecycle: восстановление layouts, ограничение буферов, диагностика и shutdown без неучтённых ресурсов. Повторно создавать terminal service в M10 не нужно.
- Локальные schedules/watchers после ручного включения: дедупликация, pause/delete, статус последнего запуска, политика после сна/перезапуска. UI показывает, что выключенный компьютер не выполняет задачу.
- Измерения cold start, streaming, длинной истории, RSS/CPU на 1/2/нескольких сессиях; анализировать bottleneck до оптимизаций. Добавить support export без секретов.
- Упаковка и обновление личного приложения с сохранением data dir; сначала проверка установки/обновления/отката на своей Windows, без обязательного enterprise release процесса.

**Приёмка:** восстановление из backup на чистом тестовом data dir с settings/Archive identities и schema migration; retention dry-run не удаляет protected references, failed import не портит текущие данные; crash не теряет принятый prompt; index rebuild не меняет историю; shutdown не оставляет неучтённый CLI/PTY. Полный regression запускается перед крупной интеграцией, а не после каждого изменения текста.

## Порядок выдачи карточек модели

Последние уточнения UX1–UX4 из [DAILY_WORK_REFINEMENTS](DAILY_WORK_REFINEMENTS.md) реализуются внутри существующих поставок: возврат к изменениям — M3.10; адресный разбор ошибки — M3.11; удобный переход к результату — M3.3/M3.10–M3.11 и форматы M6; рекомендация в связанную незапущенную Task — M4.4. Это небольшие связки существующих services, без дополнительного общего milestone или обязательного LLM-вызова при открытии задачи.

OPS1 из того же документа уточняет существующий admission: M2 сохраняет resource hold, M3 показывает причину и безопасное действие, M10 расширяет выгрузку проверенно idle ресурсов. Не путать локальную нехватку ресурсов с 429 и не прерывать busy/unknown ради нового запуска.

Одна карточка — один наблюдаемый результат и обычно один архитектурный участок. Если фактически затронуто несколько слоёв, связать их контрактом и разбить на проверяемые части; не применять искусственный лимит строк. Следующую карточку формировать по реальному diff и проверкам, а не только по заявлению исполнителя.

Поставки отмечаются D0–D13 по [DELIVERY_AND_DOGFOOD_PLAN.md](DELIVERY_AND_DOGFOOD_PLAN.md), сейчас все [ ]. Первая пригодная версия D2 выдаётся сразу после её gates; далее работать над candidate отдельно от используемой stable. Каждый пригодный checkpoint отдаёт пользователю реальную сборку/запуск, до трёх пробных действий, проверенные evidence, ограничения и rollback. Обратная связь продолжает текущую Task либо создаёт связанную при существенном отдельном scope; новая роль не обнуляет задачу, budgets и историю.

Для M0–M2 обязательные evidence: source/build/CLI versions, input scenario, timing overlap, correlated events, видимый результат и отдельные исходы unit/contract/live. Для M3 уже нужны действия агента/скриншоты реального browser; M7 доказывает расширенный сценарий. Для M6 нужен зарегистрированный настоящий артефакт и полный интерактивный mockup-цикл со screenshot, замечанием и сохранёнными v1/v2; для M9 — external operation ID. Шаблоны промптов и модельная приёмка находятся в [FLASH_MODEL_EXECUTION](FLASH_MODEL_EXECUTION.md).

После карточки сохранить одну короткую запись: что изменилось, зачем, что проверено, что осталось неизвестным, следующий шаг. Обновлять только затронутую документацию; ретроспектива нужна по повторному сбою или полезному открытию. Подробные tool logs хранятся как evidence и не пересказываются в десяти документах.
