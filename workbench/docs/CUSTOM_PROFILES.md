# Собственные профили и помощь агента при их создании

Статус: контракт развития GigaCode UI. Портативный Workbench 1.3 содержит **14 встроенных профилей**; произвольные новые IDs не становятся поддержанными его controller от добавления JSON. Ниже проектируется пользовательская библиотека native host: экран в M3.12, полноценные версии и исполнение в M4.9/D5. Работа пользовательского приложения по этим сценариям здесь не проверена.

Профиль отвечает на вопрос «какую работу выполняет этот исполнитель и как проверить её результат». Он не является новым Project/Task, моделью, полномочием или отдельным движком. Создание роли не запускает весь каталог агентов. Основа — [ROLE_PROMPT_BINDING](ROLE_PROMPT_BINDING.md), [SETTINGS_AND_CONFIGURATION](SETTINGS_AND_CONFIGURATION.md), [ROLE_ROUTING](ROLE_ROUTING.md) и [нативный перенос](NATIVE_WORKBENCH_MIGRATION.md).

## 1. Библиотека в Settings → Роли

Показать встроенные и пользовательские роли одним списком: название, одно предложение о назначении, область «Приложение / Этот проект», последняя опубликованная версия, наличие черновика и доступность исполнения. Фильтры «Все / Пользовательские / Архив»; поиск по имени и назначению без вызова модели. У проекта видны источник и наследуемое значение. Не добавлять отдельный dashboard ролей в основной чат.

Основные действия: **Создать**, **Помочь подобрать**, **Копировать**, **Открыть инструкции**, **История версий**, **Архивировать / Восстановить**, **Импорт / Экспорт**. Из composer достаточно ссылки «Управление ролями». Создание не теряет черновик текущего разговора и не меняет его исполнителя.

«Копировать» доступно для `analyst`, `spec`, `architect`, `backend`, `database`, `designer`, `frontend`, `security`, `devops`, `qa`, `reviewer`, `diagnostics`, `technical-writer`, `gigacode-ui`, а также пользовательской роли. Копия получает новый стабильный ID и provenance исходной версии. Встроенный ID/файл не перезаписывается; обновление bundle не перетирает пользовательские изменения. Клонировать analyst ради иной подписи не обязательно: сначала предложить label/default проекта, если ответственность остаётся прежней.

В details раздельны: **Опубликовано v3**, **Черновик**, **Используется в этой Task v2**, **Применение ожидается**. Сохранённый текст не обозначается «установлен в CLI». Реальный статус доставки показывается по binding receipt, а не по словам модели.

## 2. Создание через короткий разговор

Wizard содержит три компактных представления: **Назначение → Черновик и пример → Версия**. Помощник может вести тот же процесс разговором внутри Settings. Не требуется заполнять техническую анкету или читать все профили.

1. Пользователь описывает повторяющуюся работу и желаемый результат, например «Проверять изменения интеграций по контрактам и объяснять влияние на потребителей». Агент читает выбранную базовую роль и только релевантные доступные факты проекта. Он не просматривает все репозитории/логи ради предложения.
2. Сначала сравнить варианты: существующая роль с кратким Task packet; небольшой project override; новая роль для устойчивой иной ответственности. Показать одну рекомендуемую альтернативу и причину. Явное поручение создать новую роль не заменять бесконечным спором о необходимости.
3. При недостатке существенных фактов задать 1–3 коротких вопроса; варианты ответа дополняются свободным текстом. Сведения из доступного inventory не спрашивать у пользователя повторно. Текущая рабочая Task продолжает независимую работу; ждёт только зависящее от ответа действие.
4. Составить bounded draft: назначение/границы, входы, последовательность, выход/критерии, совместимые workflow refs, потенциальные capabilities и источники. Обосновать, что читается всегда, а что — по триггеру. Не копировать в роль все CORE, SDD, дизайн, ретро и проверки всех профессий.
5. Показать короткий пример «вход → ожидаемый вид результата → когда остановиться». Это **иллюстрация**, не выданный за выполненный run. Показать diff с базой, объём инструкций и фактическую доступность необходимых инструментов.
6. Сохранить draft либо опубликовать immutable версию. «Опубликовать» означает добавить версию в локальную библиотеку; это не внешний publish/deploy и не назначение в занятой Task. Доступны действия **Опубликовать и включить для этого проекта** / **Оставить отключённым**. После включения router сам решает, когда версия лучше подходит задаче; пользователь не выбирает профиль текущей Task вручную.

Если пользователь уже поручил создать/настроить профиль, выполнить разрешённые обратимые шаги без повторного запроса на каждый файл. Review example остаётся доступным, но не вводит обязательный независимый reviewer или дополнительный approval поверх данного поручения. Если поручение было только предложить варианты, оставить предложение; не публиковать и не применять его самостоятельно.

## 3. Один registry, версии и области

**ProfileRegistry** — роль существующего CatalogService/InstructionRegistry для профилей; **PromptComposer** — тот же PromptAssembler из native migration. Это названия ответственности, не требование завести вторую БД или параллельные services. WorkflowEngine остаётся единственным владельцем этапов/checks, SessionService — доставки инструкций. RoleCatalog — read projection этого registry.

Предлагаемые внутренние сущности host, **не ACP/CLI settings schema**:

```text
Profile
  profileId, origin(builtin|custom), scope(app|project), projectId?
  displayName, description, metadataRevision, archivedAt?
  publishedVersionRef?, sourceProfileVersionRef?

ProfileVersion (immutable after publish)
  profileId, versionId, parentVersionRef?, schemaVersion, contentHash
  purpose, exclusions, inputContract, workSteps, outputContract
  contextualReadTriggers, workflowRefs, capabilityPolicyRef
  instructionRef, budgetPolicyRef, provenanceRefs, validationReceiptRef

ProfileDraft
  draftId, profileId, basedOnVersionRef?, expectedProfileRevision
  content, draftRevision, validationSummary, updatedBy

ProfileRecommendation
  proposalId, scope, evidenceRefs, comparedProfileVersionRefs
  changeKind(use_existing|adjust|create), proposedDelta, reason
  expectedRegistryRevision, state(proposed|accepted|dismissed|stale)
```

ID не выводится из изменяемого имени, пути или позиции списка. Переименование — metadata change, смысловое изменение инструкций — новая версия. Published version хранит точные bytes/hash и dependencies. CAS и operation ID обеспечивают одно применение команды; конфликт двух окон сохраняет оба черновика для сравнения, а не побеждает последняя запись.

App-роль доступна разрешённым проектам; project-роль ограничена одним Project. Настройки следуют app→project→task в рамках разрешённого scope. Project может включить конкретную версию app-роли в router catalog или создать явный project override, привязанный к конкретной базовой версии. Override — адресный delta с собственной версией и preview итогового prompt; он не подменяет ту же базу глобально и не тянет автоматически future latest. Upgrade базовой версии создаёт отдельный diff/валидацию. Не поддерживать произвольную рекурсивную цепочку overrides в первом срезе.

Task/assignment/queued turn фиксируют router-selected `profileId + versionRef + effective instruction hash + workflow snapshot + capability fingerprint`, включая override refs. Project catalog policy задаёт enabled/disabled/version eligibility и optional routing hints, но не pin текущей роли; старые captured bindings остаются прежними. Авторизация проверяется по актуальной policy, поэтому capture старых permissions не отменяет revoke. Model/reasoning отдельно используют существующий adapter и [MODEL_AND_REASONING_CONTROLS](MODEL_AND_REASONING_CONTROLS.md); профиль не объявляет возможности модели по её имени.

## 4. Короткий шаблон инструкций и workflow

Стартовый product target — примерно **400–900 слов overlay**; это ориентир, не лимит всех моделей и не повод обрезать существенное ограничение. Показывать actual tokens только при доступном соответствующем tokenizer/usage, иначе оценку с методом либо unknown. Учитывать общий prompt/tools/history по [CONTEXT_BUDGET](CONTEXT_BUDGET.md). Длинную справку вынести в scoped source refs с read triggers.

```text
Название и назначение: одна устойчивая ответственность.
Применять, когда: 2–4 конкретных признака задачи.
Не решать самостоятельно: границы scope/компетенции.
Входы: обязательные факты и где их найти; что действительно спросить.
Порядок: 3–6 шагов внутри назначенного этапа, пропуск неприменимого.
Результат: нужный artifact/ответ, источники, ограничения, следующий шаг.
Критерии: наблюдаемые признаки готовности; неизвестное/возврат.
Инструменты: потенциальные capabilities, required/optional, effects/scope.
Контекст: ссылки и триггеры; общий CORE не дублировать.
Пример: короткий вход и ожидаемая форма, помеченная как иллюстрация.
```

Обычная роль сначала переиспользует совместимый существующий quick/standard маршрут. **Роль не равна workflow**: новый профиль не требует нового пайплайна. Если работа требует отличающихся стадий, помощник предлагает отдельный workflow draft в схеме native WorkflowEngine, с role refs и проверяемыми входами/выходами. Publish роли не делает непринятый workflow действующим и не снимает checks текущего run.

Новый native engine разрешает ссылки только на зарегистрированные доступные версии и проверяет совместимость stage contract. Legacy portable controller знает только зарегистрированные builtin IDs из поставки. Не передавать custom ID в него и не объявлять неизвестный маршрут успешно проверенным. Custom role внутри старой Task требует явного применимого изменения assignment/route через writer; stage snapshot не редактируется в обход rework/requirements history.

Нельзя превращать review собственного результата в независимую проверку переименованием роли. Нельзя включать полный SDD/docs/retro/E2E в каждую задачу из шаблона. Для одного понятного исправления — одна подходящая роль и адресные критерии; более строгий контракт рабочего проекта сохраняется.

## 5. Проверки draft и разумная проба

Быстрая локальная проверка при Save/Publish: schema/IDs/refs, доступность обязательных входов, совместимость stage/output, отсутствующие версии, циклические зависимости, budget estimate, placeholders бизнес-правил, неподдержанные tool bindings и известные конфликты с core/project policy. Не проверять семантику регулярным выражением с обещанием полной корректности.

Содержательная проверка нужна для созданного агентом draft и значимого изменения: «требует код, но запрещает любые изменения», «обещает проверку, но нет источника фактов», «обязует писать во внешнюю среду без scope». Агент исправляет конкретный delta; отдельный critic — только по риску/выбранному workflow. Не повторять полный аудит неизменных инструкций на каждый label edit. Cache проверки зависит от version hashes, policy/workflow refs и inventory fingerprint; изменение значимой зависимости инвалидирует затронутую проверку.

Структурно неверную версию не публиковать. Корректный профиль можно сохранить с честно указанной недоступной внешней capability; отсутствие required access блокирует соответствующее **исполнение**, а не всю библиотеку. Не считать optional tool обязательным при любом входе.

**Попробовать** — короткая отделённая trial Task с выбранной версией, одним репрезентативным входом и одним адресным плохим случаем, когда это полезно. Preview примера не делает LLM call. Реальный model trial запускается по действию/поручению пользователя с понятным scope; для роли с writes использовать безопасную fixture/изолированную область и реально проверенные права. Не утверждать наличие sandbox только из названия режима. Без него возможен read-only/плановый пример с явно ограниченным свидетельством.

Trial не обязан включать live MCP или E2E для текстовой специализации. Новый механизм доставки/изоляции проверять на целевом adapter; неизменный проверенный mechanism переиспользовать по fingerprint. Результат: inputs/version/build, наблюдения, evidence, pass/failed/not_run для фактически выполненного. Пример «модель сказала готово» не подтверждает доступ, system placement или качество кода. Две неудачные содержательные попытки — сузить задачу/показать проблему, не запускать безграничное улучшение профиля.

## 6. Инструменты, применение и fallback

Capabilities берутся из **реально обнаруженного** inventory по [MCP_PROFILE_SETUP](MCP_PROFILE_SETUP.md). Помощник подбирает минимальные required/optional действия и сверяет actual tool names/schema/effects/resource scope; provider label не является tool ID. Sprut — SCA зависимостей, не автоматически tracker/SAST. Ни prompt, ни profile publish не дают полномочий.

Расчёт применимых действий: potential policy роли ∩ нужные stage/context действия ∩ проверенные bindings ∩ действующие host permissions/Task scope. Unknown effects/missing map не означают «разрешить всё». Уже действующее разрешение используется без нового вопроса на каждый вызов; действительно новый privileged access проходит существующую policy. Роль не создаёт новые endpoint/auth settings скрыто и не хранит секреты в prompt.

Выбор опубликованной версии проходит единственный [ROLE_PROMPT_BINDING](ROLE_PROMPT_BINDING.md): desired → подготовка → безопасная граница → фактическая доставка/receipt. При занятой session — pending следующего разрешённого шага; неизвестный исход внешних writes сначала сверяется. System/native agent/context-only различаются. При необходимости нового process сохраняются прежние Task IDs, requirements, effects, budgets и текущий рабочий контекст.

Модель не получает редактор registry как неограниченный способ переписать себя: рекомендации являются данными, команды публикации/активации валидирует host в разрешённом пользовательском scope. Read-only gate действителен только при реальном enforcement; если обязательная изоляция отсутствует, блокируется эта форма исполнения и предлагается допустимый интерактивный вариант, без выдуманного safety pass.

Если ранний bootstrap должен подготовить пользовательскую роль до M4.9, агент читает **фактическую** схему/поддержанные пути установленного Giga и адаптирует существующий формат с проверенными tools. Текст host spec не копируется как готовый `.gigacode` config. Native subagent definition не доказывает поддержку custom main-session role. Если нужной поверхности нет, сохранить Markdown draft и конкретный способ context-only trial/ограничение; не добавлять ручной role selector и не писать «установлено» после простого создания файла.

## 7. История, архив и перенос

История показывает diff, автора, происхождение, validation/trial receipts и Tasks с captured версией. **Вернуться к версии** выбирает сохранённый immutable snapshot для будущего назначения либо создаёт новую версию на его основе; не переписывает выполненные turns/evidence. Upgrade/rollback prompt не откатывает реальные изменения кода и внешней среды.

Archive исключает профиль из новых автоматических предложений/назначений; restore возвращает его в библиотеку без запуска. Активный run продолжает captured версию при действующих permissions. Для будущего использования archived/отсутствующей роли показать «Восстановить / Пересчитать маршрут»; router не выбирает незаметно backend или похожую роль. Завершить уже согласованное исполнение по сохранённому snapshot можно, но отсутствие обязательного snapshot/binding — конкретный blocker.

Удаление draft не удаляет опубликованные версии. Удаление пользовательской роли сначала означает archive/trash по [ENTITY_LIFECYCLE_AND_EDITING](ENTITY_LIFECYCLE_AND_EDITING.md); purge не разрушает referenced snapshots/accepted evidence. Router catalog rules со ссылкой на удалённое показываются unresolved; новые назначения не стартуют с другой ролью автоматически. Восстановление не повышает старые privileges.

Text export: versioned host spec + Markdown instruction + безопасные source/license refs и manifest hashes; без credentials, env dump, приватных Task payloads, auth/server secrets и claimed permissions. Недоступные локальные ссылки явно unresolved, файлы проекта не включаются автоматически. Import показывает diff/происхождение и создаёт draft с новым ID; совпавший label не overwrite. Update существующего custom profile возможен только как явный versioned import с CAS. Не исполнять embedded команды и не загружать внешние refs автоматически; imported инструкции проходят те же проверки перед publish/use.

## 8. Рекомендации без разрастания ролей

Триггеры: прямое «помоги подобрать/создать»; повторяющаяся работа, для которой пользователь несколько раз менял одни и те же инструкции; стабильный результат разбора конкретной неудачи. Сигналы брать из уже существующих scoped events/decisions, а не дополнительного анализа всей истории после каждого сообщения. Редкость повторов — configurable product policy, не магическое число, доказывающее пользу роли.

RoutingService сначала детерминированно сопоставляет purpose/results с существующими профилями и предыдущими рекомендациями. Вызов модели нужен только для неоднозначного сравнения или уже порученной разработки draft. Пустое открытие Settings, token stream, rename, краткая задача и обычная смена stage не вызывают новую рекомендацию.

Одна компактная карточка: **«Часто проверяете интеграционные контракты. Можно уточнить reviewer для этого проекта»**, ссылка на 1–2 допустимых источника, ожидаемая польза, изменение объёма/инструментов, кнопки **Посмотреть черновик / Не предлагать**. Сначала existing role, затем небольшой override, затем новый профиль. Принятие предложения на draft не равно publish/activation; совмещённое действие с этими последствиями называется явно. Рекомендация не переключает занятую Task и не создаёт worker.

Dedupe по scope/problem fingerprint и сравниваемым версиям, cooldown и dismiss сохраняются. После изменения registry предложение становится stale и адресно пересчитывается. Accept — idempotent command с expected revisions; два окна не создают две роли. Не воскрешать отклонённую идею без нового основания и не применять project-рекомендацию глобально. Никаких scheduled фоновых обзоров без поручения пользователя.

## 9. Карточки реализации и проверяемые границы

| Карточка | Шаг | Результат и отрицательный контроль |
|---|---|---|
| **CP0 — библиотека** | M3.12/D3, в Settings | Показывает 14 builtins и реально доступные custom records, source/versions, clone/create draft. Если backend ещё нет, draft не назван исполняемым. Открытие/поиск/rename не запускают модель, роль или другую Task. |
| **CP1 — версии и области** | M4.9/D5 | ProfileRegistry поверх одного store: immutable publish, CAS, app/project refs, history/archive/import/export. Два окна со stale revision не overwrite; project override не меняет app/соседний проект; archive не удаляет active snapshot. |
| **CP2 — помощник создания** | M4.9/D5 после CP1 | Назначение → bounded draft → example/diff → publish; reuse существующей роли/workflow. Противоречивый draft даёт адресную ошибку; imported fake tool/schema и secret не выдаются за готовый binding. Поручение «предложи» остаётся предложением. |
| **CP3 — исполнение профиля** | M4.9/D5 после CP1 и проверенного delivery adapter | Automatic route, version capture, pending→actual receipt, optional scoped trial. Изменение catalog eligibility не меняет active turn; late ACK другой Task не активирует роль; required unavailable capability не получает false pass. |
| **CP4 — рекомендации по delta** | M4.9/D5 отдельным малым срезом после CP2/CP3 | Использует existing events, registry и scoped proposals. Один повторяющийся случай → полезный existing/override/new вариант; dismiss/dedupe/stale и accepted-once проверены. Обычная микрозадача не порождает роль/worker/LLM-аудит. |

Автоматизировать invariants: schema/refs, hash stability, immutable versions, CAS/idempotency, scope leakage, stale binding/proposal, no implicit permissions, secrets in export, archive dependency preservation. Негативный fixture должен действительно отклоняться; пустой registry custom ролей нормален, отсутствие builtins/required versions не скрывать.

На реальной целевой сборке пройти один полезный путь: клонировать профиль, уточнить один результат, просмотреть пример, опубликовать и включить в Project catalog, затем создать подходящую малую задачу и проверить automatic route + delivery receipt/наблюдаемое поведение. Изменить опубликованную версию во втором окне во время работы: первый turn сохраняет capture, следующий safe-boundary пересчёт получает подходящую enabled версию, другая Task не меняется. В composer нет ручного role picker. Если проба только context-only, отчёт так и говорит. Нет требования выполнять live deploy или весь UI regression ради редакции текста роли.

## 10. Короткое поручение агенту разработки

```text
Реализуй только CP<n> в существующем GigaCode UI. Прочитай соответствующую
карточку, разделы 3/6 и нужный раздел ROLE_PROMPT_BINDING/Settings.
Сначала найди текущие catalog, prompt assembler, workflow writer и adapter.
Переиспользуй их; не добавляй второй registry/engine и не меняй CLI.
Укажи текущую версию/scope, один полезный сценарий и один плохой случай.
Сохрани активные bindings и существующие права. Новые поля — host DTO,
не выдуманные ACP/config поля. Выполни только применимые проверки.
Верни изменённые места, observed receipts и pass/failed/not_run отдельно.
```

Для конкретной правки читать соответствующий раздел, а не отправлять весь документ и весь каталог ролей каждой модели. Библиотека увеличивает полезные специализации, а не обязательный контекст каждого хода.
