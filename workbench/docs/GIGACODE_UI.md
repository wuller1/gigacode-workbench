# GigaCode UI: Electron-оболочка и проверка настоящего приложения

Профиль `gigacode-ui` работает с frontend, backend личной оболочки и подключением GigaCode CLI через ACP. Он нужен, когда отдельные тесты зелёные, а пользовательское действие в приложении остаётся сломанным. Это инструмент одного пользователя: скорость и короткие работающие изменения важнее production-процесса. В этот пакет не передан репозиторий самой оболочки и не выполнена диагностика её текущего бага: приведён процесс получения доказательств и проверки исправления, а не заключение о причине.

Готовый прототип пользователя — исходная точка разработки. Практический вход и подробный план развития находятся в [START-GIGACODE-UI.md](../START-GIGACODE-UI.md) и связанных там материалах. CLI используется как готовый внешний компонент: без его патчей, monkeypatch, форка или изменений установленного кода. Собственные session/run services, persistence, retry coordination, оркестрация и UI принадлежат оболочке; доступ к CLI — через фактически поддержанный ACP, документированную конфигурацию и MCP.

## Выбор объёма

- `gigacode-ui-diagnostics`, 5 этапов: версия и живое воспроизведение → причина → исправление → живой повтор → отдельное ревью. Выбирается для порученного исправления реального дефекта. Если поручено только исследование, не начинай стадию изменения без соответствующей задачи; передай факты и незаконченный статус.
- `gigacode-ui-feature`, 4 этапа: краткий сценарий/контракт → реализация → целевая живая приёмка → проверка и передача. Подходит для функциональных изменений оболочки и модулей artifacts/browser/mockups. Краткий контракт может занимать несколько пунктов: цель, владение, важные ошибки, способ проверки; полный SDD не обязателен.
- Для локального текста, документации или другого изменения без эффекта на сессии/CLI используй подходящий quick route. Правила этого профиля можно добавить к нужному этапу как предметный контекст; это не требует подмены profile ID в уже начатом запуске или полного набора проверок всех модулей.

Host назначает этап и отдельное ревью. Смена роли сама по себе не доказывает независимость: проверяющий должен оценить исходники и свидетельства, а не принять самоотчёт автора. Дополнительные субагенты не запускаются автоматически.

Не добавляй обязательные release gates, production hardening, полный docs/retro цикл или E2E всех модулей. Измерения и проверка охватывают изменённый пользовательский сценарий и связанные риски. Узкая граница IPC или сохранности данных нужна и личному приложению; её проверяют там, где конкретная функция её затрагивает.

## Что считается доказательством

| Уровень | Что проверяет | Чего не подтверждает |
|---|---|---|
| Unit, reducers, контрактные тесты с fake transport | Локальная логика, воспроизводимый порядок событий, негативные ветви | Поведение установленного CLI и живого окна |
| Интеграция с настоящим CLI | Реальный transport, согласованные версии/схемы, session/request/stream lifecycle | Отображение, маршрутизацию между окнами и фактические действия пользователя в Electron |
| Настоящий Electron с настоящим CLI | Изменённый путь от действия в окне до видимого результата с реальным backend | Непроверенные версии, платформы, окружения и соседние сценарии |

Все три результата записываются отдельно. Запуск живого Electron с подставленным ACP-сервером остаётся полезной интеграционной проверкой с моком. Он не удовлетворяет `real-app-observed`. Screenshot показывает состояние, но не доказывает весь переход; к нему нужны действия, наблюдения и корреляция. Логи объясняют происходящее, но не заменяют пользовательское свидетельство.

Это различение силы свидетельств, а не требование каждый раз писать три новых тестовых набора. Для узкого изменения выбирай затронутые проверки, переиспользуй неизменившиеся результаты и пройди целевой живой сценарий. Отсутствующий нижний уровень помечается честно; необходимый `real-app-observed` остаётся обязательным.

Gate `real-app-observed` имеет `kind: execution` и `allow_na: false`. Если нужный runtime или UI-наблюдение недоступны, сохрани подготовленную работу и укажи `blocked`. Если дефект `not_reproduced`, сохраняется полезный результат исследования, но исходный баг не объявляется исправленным. Нельзя обходить gate новой формулировкой «unit passed» или молча уменьшенным объёмом.

## Связь исходников, сборки и запущенного окна

Перед наблюдением составь короткий паспорт запуска:

- Репозиторий, commit и идентификация изменений рабочей копии; время сборки и входные команды.
- Пути и идентификаторы собранных main/preload/renderer; способ установить, какие именно ресурсы загрузил Electron. Зафиксируй dev server либо packaged build и релевантные environment/config.
- Версии Electron, CLI, SDK и согласованного ACP; фактическая команда CLI из проекта/справки установленной версии.
- Тестовое окружение, viewport/масштаб, окна и сессии; идентификатор прогона и расположение свидетельств.

Не принимай один build label на экране за независимое доказательство актуальности всего bundle. Сопоставь его с путём запуска и используемыми артефактами. После изменения backend, preload или CLI-adapter перезапуск/пересборка выполняется по правилам проекта; старый запущенный процесс не становится новой ревизией от изменения исходника.

## Проверка параллельных сессий

Это план эксперимента, а не установленная причина текущего бага.

1. Зафиксируй ожидаемый контракт: какие окна/вкладки могут владеть сессией, должна ли она продолжаться при закрытии окна, что означает cancel и как разрешения привязаны к запросу. Отсутствующее существенное решение уточни, не угадывай.
2. Создай карту диагностических идентификаторов: run, window/webContents, UI-session, ACP-session, process, transport/connection generation, request/turn, subscription. Это собственная схема наблюдения; реальные имена полей ACP берутся из установленной версии.
3. Организуй два различимых запроса A и B в разных окнах. Сначала дождись наблюдаемой активности A, затем запусти B до завершения A. Докажи пересечение интервалов действия настоящих сессий. Случайная пауза и последовательные ответы не доказывают overlap.
4. Для детерминизма используй разрешённые контролируемые входы и барьеры на стороне теста. Fake transport подходит для точного порядка в unit-тесте; последний прогон обязан пройти через настоящий CLI. Если реального перекрытия добиться не удалось, соответствующая проверка остаётся непроведённой.
5. Сопоставь поток и итог каждого запроса с его владельцем. Проверь текст, состояние running/completed/error, разрешение, отмену и элементы управления в обоих окнах. Поздний ответ старого подключения не должен незаметно изменить новую сессию.
6. Повтори затронутые переходы из таблицы ниже. Достаточность покрытия объясняется причиной/изменением; обязательные для исходного дефекта варианты нельзя исключить после неудачи.

| Переход | Наблюдаемый инвариант, если он входит в принятый контракт |
|---|---|
| Одновременный stream A и B | Части ответов, статусы и итог попадают своим владельцам; активность одной сессии не блокирует другую общим mutable-флагом |
| Cancel A при активной B | Отмена адресована A; B продолжает согласованное поведение; поздние события A обработаны явно |
| Permission в A | Вопрос, выбранное решение и возобновление относятся к нужному запросу; B не получает чужое разрешение |
| Переключение, reload или close окна | Подписки и состояние восстанавливаются/очищаются по контракту; нет дублирования обновлений и переноса данных в соседнее окно |
| Crash или reconnect | UI показывает реальный исход; восстановление не выдаёт старое событие за новое и не повторяет внешнюю операцию с неизвестным результатом |
| Новая сессия после завершения старой | Идентификаторы и поколения различимы; обработчики старой сессии не владеют новым состоянием |

Для каждого обязательного сценария сохрани: условия, конкретные шаги и ожидание; факт до исправления; факт после; порядок/интервал overlap; корреляцию; screenshot/video и состояние; ревизию. Для гонки предпочтительна запись действия с временной шкалой. Несколько успешных повторов повышают уверенность, но сами по себе не доказывают устранение всех гонок: нужны причинный анализ и регрессионная защита.

## Архитектура и владение

Начинай с текущего проекта. Один authoritative mutable `busy` или `currentSession` не представляет независимые сессии; общий UI-индикатор может вычисляться из карты состояний. Проверяй не только renderer store, но и backend maps, ключи запросов, транспорт, listeners, persistence и cleanup. Гипотеза о глобальном флаге должна быть проверена на реальном пути данных.

| Вариант | Что подтвердить до выбора | Компромисс |
|---|---|---|
| Отдельный процесс CLI на сессию | Поддерживаемый запуск, стоимость процессов, независимость ресурсов, auth/config и согласованное завершение | Более явная граница отказа, но больше процессов и работы по управлению жизненным циклом |
| Несколько сессий через один процесс/transport | Именно установленный CLI поддерживает нужные независимые операции и их overlap; маршрутизация, cancel и lifecycle реально проверены | Возможность уменьшить накладные расходы ценой более сложного общего транспорта и общей границы отказа |

Ни один вариант не назначается заранее. Поддержка session identifiers в протоколе не доказывает корректную параллельность конкретного GigaCode fork. Глобальная очередь может быть допустимой продуктовой политикой, но введение её вместо требуемой параллельности является изменением требования, а не незаметным исправлением.

## Будущие модули

| Модуль | Контракт, который нужно определить | Живая проверка затронутого пути |
|---|---|---|
| Артефакты | Владелец project/session, версия, путь/доступ, тип содержимого, сохранение, открытие и восстановление | Артефакт создаётся реальным действием, открывается в правильной сессии, переживает предусмотренный restart и не подменяет артефакт соседа |
| Браузер | Владелец вкладки, навигация/загрузки, профиль хранения, permissions, граница недоверенной страницы и IPC | Пользователь открывает страницу, действие адресуется нужной вкладке, недоверенное содержимое не получает непредусмотренных полномочий |
| Макеты и preview | Источник, статус прототипа, редактирование, сохранение, связь с требованием, безопасный preview и экспорт | Создание/правка/повторное открытие работают в настоящем UI; макет явно отличается от реализации продукта |

Не передавай remote page или generated HTML широкие Node/IPC-возможности. Спроектируй узкий мост, проверку отправителя, аргументов и владельца ресурса; изоляция содержимого и разрешения относятся к архитектуре приложения, а не к одному текстовому запрету. Полезные основы описаны в [Electron context isolation](https://www.electronjs.org/docs/latest/tutorial/context-isolation) и [Electron security](https://www.electronjs.org/docs/latest/tutorial/security). Эта рекомендация не означает, что безопасность текущего проекта уже проверена.

## Версии инструментов и источники

Перед изменением CLI-интеграции прочитай [QWEN_BASELINE.md](QWEN_BASELINE.md). Сверяй собственный adapter с закреплённым исходным кодом Qwen Code, чтобы сохранять максимальную совместимость: session lifecycle, события, согласование capabilities, обработка ошибок и ownership. Дальше сопоставь конкретную установленную версию GigaCode со схемой и поведением этой базы. Не создавай второй несовместимый протокол вокруг удобных предположений; нужное расхождение fork документируется адресно.

Установленный GigaCode Desktop может быть дополнительным источником наблюдений: доступные пользователю читаемые файлы, логи, конфигурация и разрешённая диагностика показывают использованные формы запросов, capabilities и жизненный цикл. Сверяй wire shape и метаданные, маскируй идентификаторы пользователя и секреты; не сохраняй полный prompt или поток персонального содержания. Наличие такого приложения не гарантирует доступ к transport hooks или закрытым API. Не модифицируй Desktop/CLI и не обходи ограничения ради наблюдения. Необнаруженный метод остаётся неподтверждённым.

В исследованном Qwen Code direct ACP различаются несколько сессий в одном процессе и повторный prompt внутри одной сессии: новый prompt той же сессии прекращает предыдущий и ожидает его завершения. Поэтому базовый контракт host — не более одного выполняющегося turn на ACP-сессию; параллельные задачи получают разные сессии. Это ориентир из [закреплённой Qwen-базы](QWEN_BASELINE.md), который нужно проверить на GigaCode. Очереди и admission limits отдельного daemon-режима нельзя приписывать direct ACP или fork. Если два окна отображают одну сессию, они должны разделять её единую модель состояния и согласованное управление, а не притворяться двумя независимыми сессиями.

Публичный [ACP v1 session setup](https://agentclientprotocol.com/protocol/v1/session-setup) описывает создание сессии после инициализации и условную поддержку загрузки по capability. Применимость этого контракта к GigaCode устанавливается по фактической версии и согласованной схеме. Не переносите автоматически новые методы или черновую версию из главной страницы протокола. Методы resume/close, режим транспорта и флаги запуска должны подтверждаться установленным CLI; upstream Qwen не является доказательством поведения fork.

[Playwright Electron API](https://playwright.dev/docs/api/class-electron) документирован как experimental. Его можно рассмотреть для запуска и наблюдения настоящего приложения, если он совместим с версиями и архитектурой проекта. Выбор инструмента не заменяет доказательства real CLI, актуальной сборки и выполненного пользовательского сценария. Используйте действующие команды проекта; этот пакет не задаёт выдуманный универсальный launcher.

Состояние источников проверено 9 октября 2026 года. Новые внешние API перед реализацией сверяются с версиями проекта. Подтверждённые сведения, выбранная архитектура и ссылки на evidence сохраняются в общей памяти через host; полные транскрипты, секреты и сырые пользовательские данные не копируются. Документация обновляется по влиянию, ретроспектива — по своим триггерам.

## Обрывы и 429: один управляемый слой повтора

Сначала найди происхождение ошибки и уже существующий retry: renderer/adapter, CLI/provider SDK, MCP-сервер, shell либо gateway. Сохрани доступные code, источник, время, session/request/operation и информацию о приёме запроса, без credentials. Не приписывай любую строку «429» модельному API и не считай ACP стандартизованным источником конкретных HTTP-полей.

HTTP 429 означает ограничение частоты; ответ может включать Retry-After. Это возможность ответа, а не гарантия, что CLI передаст заголовок оболочке. Проверяй фактически доступные данные. [RFC 6585, раздел 4](https://www.rfc-editor.org/rfc/rfc6585#section-4)

Предлагаемый контракт оболочки:

1. Для одной логической операции есть один владелец retry и общий budget попыток/прошедшего времени. Сначала учти повторы внутри CLI/SDK; не перемножай их повторами UI, main и ACP-adapter. Если внутренний механизм неуправляем, внешний слой наблюдает и ограничивает свою работу, а не обещает общий бюджет, которого не видит.
2. Повтор разрешён лишь для классифицированного временного сбоя и безопасной операции. Доступный Retry-After задаёт нижнюю границу ожидания; добавь ограниченный backoff с jitter без более раннего запроса. Для нераспознанного значения используй документированное fallback-поведение; не выдумывай время восстановления квоты.
3. После отправленного prompt, запуска tool или MCP-записи обрыв может оставить `unknown outcome`. Сначала сверка по имеющемуся ID и состоянию либо реально поддерживаемая идемпотентность. Без этого повтор полного prompt может заново выполнить уже сделанные действия. «Повторить безопасный транспортный шаг» и «повторить всю работу агента» — разные операции.
4. UI показывает источник, ожидание/следующую попытку, использованный budget, отмену и итог. Cancel останавливает ожидание и предотвращает новые попытки; отдельно показывается исход уже отправленной работы. Исчерпание квоты, неверная конфигурация и постоянный отказ не запускают бесконечный цикл.
5. Проверка включает контролируемый 429/обрыв, соблюдение задержки, cancel во время ожидания, отсутствие двойного prompt/tool execution и честный unknown. Fault injection подходит для детерминированных ошибок; целевой пользовательский путь дополнительно проверяется в настоящем приложении с реальным CLI, не создавая намеренную нагрузку на провайдера.

## Путь переноса Workbench в UI

Делай небольшие завершённые части. Сроки и ускорение без замеров не обещаются.

| Шаг | Минимальный работающий результат | Критерий готовности |
|---|---|---|
| 1. Сессии и восстановление | Две независимые сессии, правильные потоки/отмена, один контролируемый retry, сохранённый статус при обрыве | Исходный баг воспроизведён и устранён в живом приложении; неизвестный исход не показан успехом |
| 2. Профили и маршруты Workbench | Выбор подходящего маршрута и текущей роли, единый владелец переходов, видимые проверки/блокировки, журнал и общая память | Одна маленькая задача проходит от запроса до подтверждённого результата; нет нового полного процесса для каждой микроправки |
| 3. Управляемые субагенты | Host назначает отдельные задачи, сохраняет связь parent/run/stage/session, budget и допустимые инструменты; показывает ожидание и передачу результата | Отмена/сбой ребёнка не теряет чужую сессию; завершение подтверждено результатом, а не только выходом процесса; делегирование включается по пользе |
| 4. Артефакты, браузер и макеты | Один нужный модуль за раз с видимым владельцем, сохранением и узкой границей доступа | Пользователь создаёт/открывает/восстанавливает результат в целевом живом сценарии; соседняя сессия остаётся независимой |

Перенос в UI не обязан менять текстовые контракты и формат истории одновременно. Сначала используй существующий контроллер как единственный механизм переходов либо введи явно проверенный совместимый adapter. Не допускай, чтобы renderer и backend независимо принимали один и тот же stage result. Подбор решений из открытых проектов и принципы дизайна описаны отдельно в [UI_REFERENCES.md](UI_REFERENCES.md); источники помогают выбрать подход, но не требуют точного клона Codex или Claude.

Максимальная будущая функциональность строится по реально доступным границам. Собственная очередь может быть приостановлена до отправки следующей работы; true pause активного CLI turn требует отдельного подтверждённого контракта. Cancel с повторной отправкой не подменяет resume, а ветка истории UI не является rewind модели. Управляемые субагенты оболочки могут владеть отдельными проверенными сессиями; управление скрытыми нативными агентами CLI не обещается без API. Для каждого такого элемента UI храни supported/unsupported/unknown и включай действие только после проверки. Неизвестное поведение не маскируется кнопкой, которая ничего не делает.
