Пользователю нужен перенос **метода проектирования и проверки**, а не внешнего вида Zidao. В Workbench не переносятся палитра, шрифты, компоненты, продуктовые экраны и учебные правила Zidao.

Источник исследования: локальный репозиторий Zidao, HEAD `e2e9f612cd771b602881ce778cbfabdcf1b2bc09`, ветка `codex/agent-migration`, чтение 9 октября 2026 года. ## Что измеряется и какие числа реально есть в источнике

Следующие числа — **пороги или конфигурации конкретного проекта Zidao**. Они не объявляются универсальным стандартом для любой платформы. Независимый framework должен выбрать и обосновать собственные значения с учётом платформы, аудитории и актуальных первоисточников.

| Контроль | Записанное значение/правило Zidao | Граница вывода |
|---|---|---|
| Размер нажатия | Primary ≥44 px; некоторые малые choice/play-контролы ≥36 px | Checklist C1. Это проектное разделение классов; 36 px нельзя автоматически переносить на все мобильные элементы |
| Размер читаемого текста | Минимум 16 px для ученического текста | Checklist T3; не универсальный размер любого текста в другом продукте |
| Центровка | Ось зоны ±2 px; отдельно центр нарисованного SVG-глифа через `getBBox`, не только кнопки | `design-flawless.mdc`. Проверять применимость оптической центровки к конкретному элементу |
| Стабильность действия | Позиция основного действия не должна непредсказуемо прыгать между состояниями | `design-staging-bar.mdc`; нужна серия измерений одного экрана |
| Теснота и наложение | В описании harness указан зазор между интерактивными элементами <8 px как находка; наложение проверяется отдельно | `design-flawless.mdc`; порог не доказывает удобство сам по себе |
| Переполнение | Нет горизонтального переполнения; весь длинный контент и действия достижимы | Checklist L3–L5; допустимая вертикальная прокрутка не считается дефектом сама по себе |
| Контраст | В источниках встречаются 4.5:1 и 3:1 для разных классов | Не копировать классификатор вслепую: формулировки Checklist P3 и `app/qa/designAudit.mjs` различаются; последний использует условие `font-size` в px. В независимом framework классы и единицы нужно сверить с первоисточником |
| Малые окна | 375×667 и 390×844 | Исторические обязательные случаи чек-листа, не полный перечень поддерживаемых устройств |
| Opening probe | 390×844, 1280×900, reduced motion | Реально объявленная матрица `app/qa/runDesignOpeningAll.mjs`; это не проверка всех страниц, языков и платформ |

Измерять нужно после завершения влияющих анимаций: в источнике отдельно описаны ложные результаты промежуточной геометрии. Также проверяется, что браузер показывает текущую версию исходников. Изменение CSS на диске без обновившегося рендера не является свидетельством исправления. Источник: `.cursor/rules/design-flawless.mdc`.

## Формат свидетельства

Для каждого проверяемого случая сохранять:

- версию кода и макета; страницу/вид экрана и состояние;
- платформу, контейнер/позу, язык, тему, размер текста и настройку движения;
- точную проверку, порог, измеренное значение и результат;
- шаги воспроизведения, команду и код завершения там, где это автоматическая проверка;
- screenshot/trace и ссылку на находку;
- один из статусов: `проверено`, `дефект`, `не проверено`.

Источник схемы: `docs/course_redesign/rethink/DAY_SCREEN_CHECKLIST.md`, §Приёмка. Адаптация схемы для Workbench — инженерное решение комплекта, не заявление о нативной функции GigaCode.

## Пределы доказательств

Статичный снимок не доказывает движение; эмуляция окна не доказывает физический сгиб устройства; зелёные unit-тесты не заменяют просмотр интерфейса; экспертная гипотеза не является наблюдением пользователя. Исторический результат относится к измеренной версии. Именно эти границы полезно сохранить в другом проекте.

В этой задаче проверено наличие и содержание источников. **Ни одной новой визуальной проверки Zidao или GigaCode здесь не проведено.** Числа приведены для прослеживаемости процесса, а не как готовая визуальная спецификация нового продукта.
