# GigaCode CLI внутри дистрибутива оболочки

Требование: приложение поставляется со своей закреплённой версией GigaCode CLI и запускает её независимо от глобально установленного `gigacode`. CLI не модифицируется. Это проект реализации, а не готовый установщик: дистрибутива GigaCode 26.9.75 и исходников пользовательской оболочки на этой машине нет. Почтовый пакет содержит инструкции и статичную графику; сам будущий desktop-дистрибутив по своей природе будет содержать исполняемые компоненты.

## 1. Граница поставки

Включить в сборку официальную или разрешённую владельцем копию **точной поставки GigaCode**, необходимый ей runtime и production dependencies. Если поставка — самостоятельный исполняемый файл, проверить её реальные внешние зависимости. Если это Node-пакет, установить его production closure в отдельном runtime-каталоге и включить совместимую закреплённую версию Node. Не использовать системный Node или встроенный в Electron процесс как незаметную замену: проверить предусмотренный поставщиком entry point, engines и способ запуска.

Лицензия Qwen не подтверждает условия конкретного GigaCode fork, его моделей и включённых компонентов. На рабочей машине найти источник поставки, LICENSE/NOTICE и условия включения в личную сборку; сохранить нужные уведомления по [ASSET_RIGHTS](ASSET_RIGHTS.md). Не извлекать закрытый CLI из установленного Desktop, не обходить защиту и не объявлять право распространения по доступности файла. Пока подтверждения нет, готовить runner/manifest/test harness с явно отсутствующим runtime; не распространять спорные файлы и не выдавать это за завершённый bundled package.

Самостоятельный CLI runtime не означает, что все инструменты проектов уже установлены. Git, PowerShell, JDK/Maven/Gradle, Python environments, Node проектов, MCP executables и внешние серверы имеют отдельную inventory. Показывать, что требуется конкретному проекту, не устанавливать все toolchains ради запуска чата. Будущий IDE-план — [PANELS_AND_IDE](PANELS_AND_IDE.md).

## 2. Каталоги и manifest — внутренний контракт оболочки

Предложенная структура, которую нужно адаптировать к фактическому packager:

```text
resources/
  cli-runtimes/
    <runtime-id>/
      runtime-manifest.json
      vendor/                 исходная поставка CLI
      node/                   только если действительно требуется
      licenses/               реальные лицензии и notices
userData/
  runtime-selection.json      выбранная проверенная версия
  workbench/                  задачи, журнал, индексы
  cli-state/                  только через подтверждённый механизм CLI
```

`runtime-id` включает версию, платформу/архитектуру и идентификатор содержимого; точный формат внутренний. Поля manifest: schemaVersion, runtimeId, vendor/version, platform/arch, поставщик/source reference, CLI entry file, аргументы запуска проверенного режима, Node entry/version при необходимости, SHA-256 файлов, notices, adapter compatibility ID и дата проверки. Это **не поля ACP**, не новые flags GigaCode и не обещание существующих настроек fork.

CLI и Node, запускаемые как процессы, размещать на реальной файловой системе вне `app.asar`, а не рассчитывать на виртуальные пути. `cwd` — каталог проекта, а не runtime или архив. Конкретные `extraResources`/unpack-настройки выбрать по используемому сборщику; не менять packager ради одного каталога. В Electron путь ресурсов доступен через `process.resourcesPath`. Ограничения ASAR на рабочие каталоги и запуск требуют проверки именно упакованной сборки. [Electron ASAR](https://www.electronjs.org/docs/latest/tutorial/asar-archives), [Electron process](https://www.electronjs.org/docs/latest/api/process)

Каталог поставки неизменяемый в рабочем режиме. История, авторизация, кэш, MCP-настройки и пользовательские файлы не записываются в `resources` или `Program Files`. Возможность отдельного профиля/config/data directory для CLI должна быть подтверждена; не выдумывать `--user-data-dir`, переменные окружения или `HOME` overrides по аналогии с Electron. Если CLI неизбежно использует часть общей пользовательской конфигурации, честно отметить это в capability report: независимость версии executable и изоляция пользовательских данных — разные свойства.

## 3. Runner: только точный runtime

1. Main/backend выбирает `runtimeId`, проверяет platform/arch, manifest, существование файлов и их целостность. Hash подтверждает байты относительно manifest, но не происхождение: источник и доступная подпись проверяются отдельно. Не перехешировать большую поставку на каждый token; проверять при установке/изменении и использовать подтверждённую неизменную версию.
2. Запускать абсолютный путь к vendor executable либо включённому `node.exe` с документированным entry point. Аргументы — массив, без конкатенации пользовательского ввода в shell. Если поставщик даёт только wrapper, исследовать его штатный вызов; `.cmd` не считать автоматически прямым executable для `spawn(..., shell:false)` на Windows. Не патчить CLI ради обхода этого различия.
3. Не искать CLI в `PATH`, не вызывать `npx ...@latest`, не скачивать latest при каждой новой задаче, не переключаться молча на глобальный GigaCode при ошибке своего runtime. Ошибка становится `runtime unavailable` с диагностикой и действием восстановления.
4. Проверить фактическую версию, startup и ACP handshake на выбранной поставке. Сохранить protocol/capabilities и их привязку к runtime; существующая версия Qwen из [QWEN_BASELINE](QWEN_BASELINE.md) не доказывает совместимость fork.
5. Каждый `CliProcess` и `Connection` хранит runtimeRef/hash, PID, connection generation и adapter version. Ключ сессии включает connection identity/generation; одинаковый `sessionId` в другом процессе не конфликтует. Renderer выбирает собственный chat/task, а не путь произвольной программы.
6. stderr, exit, launch error и ACP stdout разделены. Не смешивать диагностические строки с JSON-RPC. Сохранять безопасные launch metadata и корреляцию по [DESKTOP_OBSERVABILITY](DESKTOP_OBSERVABILITY.md), без токенов и полного env.

Существующие стратегии multiplex или процесс на чат сохраняются: наличие bundled CLI само по себе не доказывает ни одну из них. Проверить параллельность и общие файлы CLI по [PARALLEL_SESSIONS_FIX](PARALLEL_SESSIONS_FIX.md). Избегать повторной установки/config discovery для каждого окна; окна получают представление уже известного runtime/service.

## 4. Настройки, MCP и авторизация

Разделить managed defaults приложения, пользовательские предпочтения, проектные инструкции и секреты. Импорт существующих полезных настроек/знаний выполнять адресно с источником и отчётом по SETUP-AGENT и PROCESS_ADAPTATION; не копировать целиком пользовательский home, токены и историю в дистрибутив. Секреты задаются пользователем на машине запуска и не встраиваются в installer/manifest/журнал.

Передавать bundled CLI только подтверждённые данной версией способы system prompt, профиля и MCP. Проверить, откуда CLI фактически читает конфигурацию и не смешиваются ли сессии разных проектов. Использовать общую inventory/bindings по профилям; отсутствие подтверждённой изоляции указать явно. Изменение CLI/SDK версии требует повторной проверки этих границ, даже если название команды осталось тем же.

## 5. Обновление и откат

Для первой рабочей версии **обновлять оболочку и CLI вместе** одним проверенным дистрибутивом; самостоятельный сетевой updater CLI не нужен. Не смешивать проверенную оболочку с незапланированным глобальным обновлением. Встроенное самообновление vendor CLI отключать только документированным способом, если оно присутствует и это разрешено; не придумывать flag и не патчить поставку. Если отключить его штатно нельзя, зафиксировать ограничение и проверить поведение read-only runtime, не обещать полностью фиксированный executable при самоперезаписи.

Позднее отдельное обновление runtime возможно: получить точную доверенную поставку → staging → целостность/условия/совместимость → smoke одной и двух сессий → атомарно выбрать её **для новых процессов**. Активный процесс продолжает работать со старой immutable-поставкой до завершения; UI/лог показывает runtimeRef. Нельзя заменить файлы под работающим CLI, автоматически переотправить незавершённый prompt или объявить session/load доступным без capability.

Сохранить предыдущий runtime до завершения его процессов и проверки новой версии. Откат выбора executable не является откатом внешних действий или миграций пользовательской истории. До обновления сохранить совместимые данные и описать необратимые изменения; при неизвестной совместимости не открывать старой версией новые данные без проверки. Очистка старых runtime выполняется только когда на них нет живых ссылок.

## 6. Карточки реализации

| Карточка | Изменение | Проверка результата |
|---|---|---|
| R0, M0 | Inventory своей поставки, license/entry/runtime/dependencies и prototype manifest | Версия/источник подтверждены, неизвестное явно записано; нет установки из неподтверждённого latest |
| R1, M1 | Resolver и runner с абсолютным путём; runtimeRef в process/connection/log | В системном PATH лежит отличающийся dummy `gigacode`, но запускается только bundled-путь; отсутствие/повреждение своего runtime даёт объяснимую ошибку |
| R2, первая packaging-проверка | Packager включает runtime и notices вне ASAR; config/data остаются вне read-only каталога | Упакованное приложение работает из пути с пробелами/кириллицей при отсутствии глобального CLI/Node, если Node входит в поставку; нужные внешние project tools учитываются отдельно |
| R3, до приёмки M3 | Одна сессия, две параллельные, cancel, reconnect, сохранность состояния на bundled runtime | Live Electron + настоящий включённый CLI, корреляция показывает правильную версию и владельцев; не только mock adapter |
| R4, M10 | Обновление вместе с приложением, сохранение предыдущей поставки и контролируемый откат | Активная задача не перезапускается; новая выбирает новую версию; ошибочная поставка не делает старую недоступной |
| R5, позже по необходимости | Отдельный управляемый runtime updater | Подпись/источник, staging, capabilities, rollback и несовместимая history migration проверены на тестовой копии |

Минимальная матрица на целевой Windows: нет глобального CLI; установлен другой CLI; нет системного Node при включённом Node; непривилегированный пользователь; пробелы/кириллица в путях; read-only installation directory; отсутствующий/изменённый runtime; две задачи/два окна; неудачное обновление. Отсутствие сети должно позволять открыть локальный UI/историю, но не доказывает доступность внешней модели и MCP. Результаты фиксировать отдельно, `not_run` не превращать в pass.

Готовность: агент способен предъявить путь реально запущенного bundled executable, его версию/hash, ACP capabilities и live-свидетельства. До этого выполнена только подготовка или упаковка, а независимость от глобальной установки остаётся непроверенной.
