## Сессии, параллельность и маршрутизация

**Qwen подтверждено:** `QwenAgent` хранит `Map<string, Session>`, создаёт сессии с `cwd` и MCP-настройками и маршрутизирует `prompt` по `sessionId`. `initialize` объявляет поддержку загрузки сессии, list/resume и поддержанные виды prompt-контента. Это основание для multiplex нескольких сессий в одном процессе, но не обещание неограниченной параллельности. [acpAgent.ts:3926](https://github.com/QwenLM/qwen-code/blob/4360b003a087fe9e57f6ffbe7ba48795980b59c3/packages/cli/src/acp-integration/acpAgent.ts#L3926), [initialize:5468](https://github.com/QwenLM/qwen-code/blob/4360b003a087fe9e57f6ffbe7ba48795980b59c3/packages/cli/src/acp-integration/acpAgent.ts#L5468), [newSession:5753](https://github.com/QwenLM/qwen-code/blob/4360b003a087fe9e57f6ffbe7ba48795980b59c3/packages/cli/src/acp-integration/acpAgent.ts#L5753), [prompt:7038](https://github.com/QwenLM/qwen-code/blob/4360b003a087fe9e57f6ffbe7ba48795980b59c3/packages/cli/src/acp-integration/acpAgent.ts#L7038).

Для **одной** direct-ACP сессии новый `Session.prompt` прерывает предыдущий pending prompt, затем ожидает его завершения перед продолжением. Поэтому очередь пользовательских сообщений в нашей оболочке должна по умолчанию держать **один активный ход на session**. Независимые параллельные чаты используют разные session IDs. Это отличается от очереди HTTP-демона. [Session.ts:5342](https://github.com/QwenLM/qwen-code/blob/4360b003a087fe9e57f6ffbe7ba48795980b59c3/packages/cli/src/acp-integration/session/Session.ts#L5342), [Session.ts:5406](https://github.com/QwenLM/qwen-code/blob/4360b003a087fe9e57f6ffbe7ba48795980b59c3/packages/cli/src/acp-integration/session/Session.ts#L5406).

`session/update` содержит session ID; результат `session/prompt` и сообщения обновления — разные элементы жизненного цикла. В оболочке нужны таблица JSON-RPC request IDs и отдельная привязка `process/connection → sessionId → UI chat`. Permission request также нужно привязывать к породившей его сессии и запросу. Смена активной вкладки не меняет адресата событий. [Session.ts:8474](https://github.com/QwenLM/qwen-code/blob/4360b003a087fe9e57f6ffbe7ba48795980b59c3/packages/cli/src/acp-integration/session/Session.ts#L8474), [официальный ACP prompt turn](https://agentclientprotocol.com/protocol/v1/prompt-turn), [session setup](https://agentclientprotocol.com/protocol/v1/session-setup).

**Решение для Giga UI:** выбирать между process-per-chat и multiplex по фактам установленного форка. Первый вариант обеспечивает отдельную границу сбоя и launch-конфигурацию ценой дополнительных процессов; второй экономит запуск, но требует проверенной изоляции событий, разрешений, отмены и конфигурации. Оба — решения host, а не универсальное требование ACP. Не переносить в продукт цифры памяти или скорости из upstream документации без измерения на целевом компьютере.

Профили с разными launch-time system prompts могут требовать разных процессов или групп процессов по конфигурации: Qwen строит параметры сессии из `this.argv`. Наличие нескольких сессий не доказывает наличие публичного per-session setter для system prompt. Отправленная обычным prompt роль не должна называться системным override. [acpAgent.ts:15452](https://github.com/QwenLM/qwen-code/blob/4360b003a087fe9e57f6ffbe7ba48795980b59c3/packages/cli/src/acp-integration/acpAgent.ts#L15452).

## Отмена, разрешения и восстановление

**Qwen подтверждено:** `session/cancel` отменяет pending prompt указанной сессии и ещё ожидающие admission вызовы; это не команда завершения общего процесса. В обработке permissions AbortSignal прекращает ожидание, а ответ с option ID, которого не было в предложенных вариантах, отвергается. [acpAgent.ts:7183](https://github.com/QwenLM/qwen-code/blob/4360b003a087fe9e57f6ffbe7ba48795980b59c3/packages/cli/src/acp-integration/acpAgent.ts#L7183), [permissionUtils.ts:196–251](https://github.com/QwenLM/qwen-code/blob/4360b003a087fe9e57f6ffbe7ba48795980b59c3/packages/cli/src/acp-integration/session/permissionUtils.ts#L196).

**Правила оболочки:** после отправки cancel показывать «отмена запрошена» до подтверждённого терминального исхода. Нельзя считать уведомление cancel откатом уже выполненной записи в Git/MCP/кластер. При закрытии вкладки отменять только её работу; при multiplex не убивать процесс других чатов. Поздний permission response или событие старого connection generation не должны разрешать новую операцию. Не утверждать успех при EOF, падении процесса или неизвестном исходе внешнего действия; сначала выполнить reconciliation из журнала.

В Qwen есть дополнительные методы, например `qwen/control/session/close`, а часть расширений требует private parent capability. **Это не стандартный ACP и не автоматически доступный API GigaCode.** Не копировать private-токены, не внедряться во внутренний runtime и не модифицировать CLI. Подобную функцию включать только при документированном/наблюдаемом интерфейсе установленного продукта. [status.ts:175](https://github.com/QwenLM/qwen-code/blob/4360b003a087fe9e57f6ffbe7ba48795980b59c3/packages/acp-bridge/src/status.ts#L175), [acpAgent.ts:9659](https://github.com/QwenLM/qwen-code/blob/4360b003a087fe9e57f6ffbe7ba48795980b59c3/packages/cli/src/acp-integration/acpAgent.ts#L9659).

## HTTP daemon — отдельная поверхность

Современный Qwen также имеет `qwen serve`: HTTP/SSE control plane над ACP. Документация описывает несколько sessions на один ACP child рабочего пространства; default `sessionScope: single` может прикреплять клиентов к общей беседе. Отдельные чаты нельзя моделировать простым повторным attach без проверки режима создания. [qwen-serve.md:14](https://github.com/QwenLM/qwen-code/blob/4360b003a087fe9e57f6ffbe7ba48795980b59c3/docs/users/qwen-serve.md#L14), [qwen-serve.md:980](https://github.com/QwenLM/qwen-code/blob/4360b003a087fe9e57f6ffbe7ba48795980b59c3/docs/users/qwen-serve.md#L980).

В **bridge этого snapshot** есть отдельная FIFO, default cap 32 live sessions и default 5 accepted pending prompts на session, включая активный. Эти значения конфигурируются; они не являются лимитами direct ACP, гарантией производительности или данными о GigaCode. Bridge проверяет admission до добавления в очередь. [session-control-plane.ts:2367](https://github.com/QwenLM/qwen-code/blob/4360b003a087fe9e57f6ffbe7ba48795980b59c3/packages/acp-bridge/src/session-control-plane.ts#L2367), [admission:10988](https://github.com/QwenLM/qwen-code/blob/4360b003a087fe9e57f6ffbe7ba48795980b59c3/packages/acp-bridge/src/session-control-plane.ts#L10988), [FIFO:11665](https://github.com/QwenLM/qwen-code/blob/4360b003a087fe9e57f6ffbe7ba48795980b59c3/packages/acp-bridge/src/session-control-plane.ts#L11665).

Наличие Qwen daemon не означает его наличия в установленном форке. Наш Electron-прототип может оставаться прямым ACP-клиентом. Переход на daemon — только после проверки доступности и отдельного решения, без требования менять CLI.

## 429 и повторные попытки: где уже есть retry

| Слой в проверенном Qwen | Что видно в коде | Значение для UI |
|---|---|---|
| Обычный HTTP/API retry | `retryWithBackoff`: default 7 attempts с первой попыткой, initial 1500 ms и exponential cap 30 s; учитывает abort | Не повторять целый ACP prompt, пока CLI ещё исполняет свою попытку |
| Provider SDK | Default OpenAI provider передаёт `maxRetries`, default 3 | Внутри CLI уже возможен дополнительный уровень retry; нельзя считать 7 общим числом HTTP-запросов |
| Rate limit внутри stream | Отдельный default budget 10 retries, initial 60 s, max delay 5 min; возможны конфигурационные overrides | Пауза может принадлежать CLI, а не «зависшему» UI |
| Восстановление stream | Отдельные бюджеты replay/continuation; условия учитывают уже доставленный контент и tool calls | Внешний повтор prompt не заменяет внутреннее восстановление stream |

Core генерирует внутреннее событие `StreamEventType.RETRY`, а API retry имеет логирование. **Внутреннее событие само по себе не доказывает наличие публичного ACP countdown/attempt события.** Если установленный Giga не передаёт эти поля в wire contract, UI показывает нейтральное ожидание и фактически прошедшее время; точный номер попытки не выдумывается. Stderr остаётся диагностикой, не подтверждением завершения tool operation. [llm-chat.ts:3881](https://github.com/QwenLM/qwen-code/blob/4360b003a087fe9e57f6ffbe7ba48795980b59c3/packages/core/src/core/llm-chat.ts#L3881), [API retry:5249](https://github.com/QwenLM/qwen-code/blob/4360b003a087fe9e57f6ffbe7ba48795980b59c3/packages/core/src/core/llm-chat.ts#L5249).

**Контракт нашей оболочки без изменения CLI:** model-request retry остаётся у CLI. Собственный retry допустим только для своей очереди/соединения с конечным budget, отменой и jitter, когда операция безопасна и её исход установлен. Не ставить второй бесконечный цикл вокруг ACP prompt и MCP writes. При разрыве после dispatch сохранять draft, session mapping и неизвестный исход; сначала проверить состояние. При превышении собственного deadline запросить отмену и дождаться/зафиксировать её результат. Настройку native retry менять только через подтверждённую schema установленного Giga и в согласованной области действия.

## Профили, system prompt и native agent files

Qwen подтверждает `--system-prompt` и `--append-system-prompt` для main session текущего запуска. Контекстные файлы продолжают участвовать в сборке prompt. `QWEN_SYSTEM_MD` может заменить базовый prompt файлом, но это специфичная для Qwen переменная, а не стандарт ACP. ## Headless не равен ACP

Qwen документирует `-p`, JSON/stream-json output и продолжение через `--continue`/`--resume`. Headless stream-json имеет собственные `type`/`session_id` сообщения; его нельзя разбирать ACP JSON-RPC parser. Документация отдельно оговаривает состояние развития stream-json input. Для UI с permissions и несколькими чатами сначала использовать уже существующую ACP-интеграцию прототипа; headless оставлять отдельным проверенным адаптером. [headless.md:18–57](https://github.com/QwenLM/qwen-code/blob/4360b003a087fe9e57f6ffbe7ba48795980b59c3/docs/users/features/headless.md#L18), [formats:221–253](https://github.com/QwenLM/qwen-code/blob/4360b003a087fe9e57f6ffbe7ba48795980b59c3/docs/users/features/headless.md#L221), [официальная headless документация](https://qwenlm.github.io/qwen-code-docs/en/users/features/headless/).

## Что проверить на компьютере с целевым GigaCode 26.10.6

Этот раздел актуализирован под текущую цель 26.10.6; прежняя цель 26.9.75 и датированные факты исследования выше остаются историческими. Сначала прочитай фактическую версию выбранного executable. Это приёмочная программа, **не список уже проведённых проверок**. Использовать существующий прототип оболочки и установленный GigaCode Desktop как наблюдаемый пример, не извлекать из него секреты и не модифицировать CLI.

1. Зафиксировать версию executable, launcher, `--help`, доступную schema, рабочий каталог, sanitized launch args и источник config. Не переносить `.qwen` paths/env в `.gigacode` механической заменой без проверки.
2. Записать очищенный ACP handshake и реальные capabilities. Проверить создание, prompt, streaming, конечный ответ, load/resume только при заявленной поддержке. Отличать UI chat ID от ACP session ID и connection generation.
3. В двух тестовых чатах проверить параллельность, отсутствие смешивания chunks/tools/permissions, перезапуск и привязку восстановленной истории. Для multiplex повторить в одном процессе; отсутствие поддержки оставить явным результатом, а не чинить форк.
4. В одной сессии проверить второе сообщение во время работы и выбрать UI queue/interrupt поведение. Отмена одного чата не должна прерывать соседний. Проверить отмену во время generation, permission wait и retry wait; отдельно зафиксировать неизвестный исход после аварийного завершения.
5. В изолированном тестовом окружении получить либо воспроизвести записанную 429/transport-error трассу: выяснить, что уже повторяет CLI и какие retry-данные действительно доступны UI. Проверить бюджет собственной очереди, cancel, сохранение draft и отсутствие повторного MCP write. Не создавать rate-limit нагрузку на рабочий сервис ради теста.
6. Проверить способ применения профиля и область действия: append/override/startup-only, сохранение native правил, отсутствие изменения чужих чатов/проектных настроек. Если hot switch не поддержан, UI создаёт новую соответствующую сессию/процесс или явно предлагает смену со следующего запуска.
7. Прогнать UI приёмку на реально запущенном Electron-приложении: prompt → streaming → tool/permission → completion; cancellation, reconnect, two-chat routing, unknown capability и source-backed error. Скриншот сам по себе не доказывает работу ACP.

Результат интеграции — таблица возможностей **конкретной установленной сборки** со статусами `observed`, `documented_only`, `unsupported`, `unknown`, ссылками на очищенные traces и версии. Qwen baseline помогает выбрать проверки и сохранить близкую архитектуру; он не заменяет проверку форка и не требует менять его код.
