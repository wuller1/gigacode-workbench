# Последний проход: меньше ручных переходов в повседневной работе

Дата: 2026-10-10. Дополнения приняты в план как небольшие сценарии поверх существующих services. Они не создают новый framework, общий gate для каждой задачи или причину откладывать первую рабочую сборку. Это инструкции реализации; целевой GigaCode UI здесь не запускался.

## UX1. Вернуться в задачу и быстро понять изменения

**Триггер:** пользователь возвращается в Task после другой задачи или перезапуска; после его last-seen cursor появились существенные события. Над сохранённым местом чтения показать одну раскрываемую строку: «Пока вас не было: готов результат, нужен ответ». Не добавлять постоянный dashboard. Внутри — максимум три сгруппированных изменения со ссылками на сообщение, конкретную версию артефакта или актуальный вопрос. Остальное открывается как обычная история.

Task projection строит сводку из EventStore и viewer cursor детерминированно. Открытие Task не вызывает LLM, не запускает новый turn и не сбрасывает scroll/draft. Streaming tokens, heartbeat и каждое tool-событие не попадают в сводку. «Просмотрено» меняет только пользовательский cursor; не принимает результат и не закрывает formal checks. Unread result нельзя считать прочитанным только потому, что окно стало foreground.

**Когда:** M3.10/D3, существующие UI15/UI35; использовать [TASK_ACTIVITY_INDICATORS](TASK_ACTIVITY_INDICATORS.md) и [TASK_WORKSPACE](TASK_WORKSPACE.md). **Минимальная проверка:** A работает, пользователь в B; возврат в A показывает новый artifact и вопрос, сохраняет позицию и draft, не стартует CLI. Повторный просмотр не дублирует события; stale вопрос ведёт к текущей версии.

## UX2. «Разобрать» непосредственно у ошибки

**Триггер:** failed check, ошибка tool, browser или CLI. В details одного события показать действие «Разобрать». Оно формирует короткий диагностический запрос с event ID, симптомом, build/source revision, релевантными log/screenshot refs и unknown effects. Состав запроса виден пользователю; большие логи остаются ссылками. Нельзя передавать модели секреты или автоматически все журналы проекта.

Использовать Diagnostics exporter, TaskPacketBuilder и существующую очередь. При busy session запрос очередится в исходную Task. Captured task/session/revision не меняется от клика по другой задаче; operation ID устраняет двойное добавление. Простое начало разбора не повторяет неудачный tool, не даёт разрешение менять произвольный код и не преобразует unknown write в failure. Partial logs остаются явно partial.

**Когда:** M3.11/D3 на основе M0–M2, semantic binding M4. [DESKTOP_OBSERVABILITY](DESKTOP_OBSERVABILITY.md), [SMART_MESSAGE_QUEUE](SMART_MESSAGE_QUEUE.md). **Минимальная проверка:** после выбора B разбор ошибки A попадает в A ровно один раз; неизвестный publish не переисполняется; недостающие логи не выдаются за полную картину.

## UX3. Результат, которым можно сразу воспользоваться

**Триггер:** агент подготовил полезный пользователю результат, в том числе промежуточный. В обычном итоговом сообщении дать: что получилось; что проверено и какие ограничения остались; один основной переход. Документ открывает конкретную версию; код — относящийся к результату diff; UI — проверенный preview и короткий пользовательский сценарий. Простой текстовый ответ не требует дополнительной карточки.

Host проверяет существующие result/evidence refs, версию и доступ. Не вводить вторую сущность «финальный отчёт». Если launch binding неизвестен, показать инструкцию, а не кнопку с угаданной shell-командой. «Открыть результат» не означает принять stage, выполнить deploy или отправить документ. Старая ссылка продолжает показывать старую версию, а изменившийся критерий делает соответствующую оценку stale.

**Когда:** M3.3/M3.10–M3.11/D3; дополнительные форматы M6/D7. [ARTIFACTS_AND_QUESTIONS](ARTIFACTS_AND_QUESTIONS.md), [DELIVERY_AND_DOGFOOD_PLAN](DELIVERY_AND_DOGFOOD_PLAN.md). **Минимальная проверка:** ссылка после новой редакции открывает ожидаемую версию; отсутствующий preview не становится рабочим по одному label; результат удобно проверить без ручного поиска пути в логах.

## UX4. Сохранить полезную рекомендацию отдельной задачей

**Триггер:** агент нашёл полезное улучшение вне текущего объёма. Рядом с рекомендацией — «Отложить в отдельную задачу». Создать связанную незапущенную Task с короткой целью, rationale и versioned source refs. Исходная работа продолжается. «Начать сейчас» — отдельное действие; можно просто отложить рекомендацию без новой Task.

Recommendation projection и Task writer используют одну идемпотентную команду с `originRecommendationRef`. Не копировать целиком чужую историю, память или разрешения. Изменение исходной рекомендации не переписывает уже созданную цель. Если пользователь уже поручил конкретное исправление внутри scope, агент выполняет его, а не превращает любое замечание в backlog.

**Когда:** M4.4/D4–D5; [TASK_WORKSPACE](TASK_WORKSPACE.md), [ENTITY_LIFECYCLE_AND_EDITING](ENTITY_LIFECYCLE_AND_EDITING.md). **Минимальная проверка:** двойное нажатие даёт одну Task, не запускает worker; связь проектов проверяется обычной policy; созданная цель и источник сохраняются после restart.

## Порядок внедрения

Первым выполнить UX1, затем UX2 в уже затронутых экранах M3. UX3 — правило отображения результата, а не отдельный большой экран. UX4 подключить при native Recommendations/Task writer M4. Эти уточнения расширяют существующие сценарии Task/activity, questions, artifacts, diagnostics и recommendations, не меняя исходные 43 группы требований. Приоритет — уменьшить ежедневные переключения, копирование логов и потерю полезных предложений. Не добавлять ежедневный LLM-отчёт, постоянный оптимизатор или обязательный onboarding перед простой задачей.

## OPS1. Понятное ожидание, когда занят лимит ресурсов

Если admission limit занят неактивными CLI/MCP/browser ресурсами, показать конкретную причину ожидания новой работы. Это локальный resource hold, а не provider 429 и не повод повторить prompt. Process/Session owner может освободить только принадлежащий приложению ресурс с доказанным idle, сохранённым checkpoint и проверенным способом reopen/resume. Если этих условий нет, предложить адресное закрытие выбранного ресурса; не завершать busy, waiting_input или unknown по таймеру.

Использовать уже описанные process/RSS limits в [MANAGED_SUBAGENTS](MANAGED_SUBAGENTS.md) и runtime policy [TASK_WORKSPACE](TASK_WORKSPACE.md). **Когда:** M2 admission, M3 понятное состояние; расширенная автоматическая выгрузка M10. **Проверка:** маленький fixture cap занят тремя idle ресурсами, новая Task ожидает с причиной; безопасное освобождение даёт ровно один dispatch. Busy/unknown сохраняются. Общее число процессов, их владение и бюджеты наблюдаются фактически; заранее выдуманный лимит не выдаётся за возможности компьютера.
