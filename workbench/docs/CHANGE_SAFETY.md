# Изменение работающего кода и строгая проверка

Этот документ разделяет два режима работы вместе с [CORE](../CORE.md) и [адаптивным процессом](ADAPTIVE_EXECUTION.md). **Пользователь запросил строгий порядок для других рабочих проектов, а не для личного GigaCode UI.** Работающий production/shared-код включает исходники, используемые действующими сервисами, библиотеками и другими командами, ещё до новой выкладки.

## Выбор режима проекта

| Режим | Где применять | Как работать |
|---|---|---|
| `established_strict` | Другие рабочие, production и общие проекты | Согласованная область изменения, сохранение контрактов, отдельное принятие сопутствующих оптимизаций, тщательные проверки по влиянию и условия восстановления. |
| `personal_fast` | Личный GigaCode UI по явному указанию пользователя | Существующая заготовка, небольшие самостоятельные изменения внутри поручения, конструктивная критика, принятый процесс дизайна и проверка затронутого сценария. Без обязательной полной regression-матрицы, production gates, отдельного reviewer/QA/отрицательного контроля каждой правки и новых согласований обычных действий. |

Это обозначения правил процесса, не встроенные CLI flags или обещание автоматического enforcement. Режим устанавливается по поручению и реальному проекту; если контекст уже известен, не задавай новый вопрос ради формальности. Не превращай личный проект в production-процесс из-за наличия backend, Git или Jenkins. Если отдельное действие затрагивает настоящую общую/production-систему, ограничения применяются к этому действию, а не ко всему личному UI.

В обоих режимах сохраняй чужие изменения и явно принятые контракты, не выдумывай результаты, не ослабляй тесты ради зелёного статуса и не обещай отсутствие всех регрессий. Для `personal_fast` достаточно конкретного эффекта: реальное перекрытие A/B при исправлении параллельности, адресный сценарий отмены при её изменении, соответствующее состояние Electron при правке renderer. Общие принципы качества — [ZIDAO_PROCESS_TRANSFER](ZIDAO_PROCESS_TRANSFER.md). **Остальные строгие требования этого документа предназначены для `established_strict`; не переносить их полным списком в каждую личную карточку.**

## Что разрешает задача

- Явное поручение исправить дефект/добавить функцию разрешает необходимые изменения этой области и обычные технические решения внутри принятого контракта. Ранее выданные разрешения сохраняются, пока совпадают область, ресурс и условия; повторное подтверждение каждого инструмента не нужно.
- «Рекомендации по оптимизации приветствуются» означает право исследовать и предложить улучшение. Это не разрешение попутно переписать работающий модуль, обновить зависимости, поменять архитектуру, контракт, общую конфигурацию или поведение соседней функции. Уже явно порученная оптимизация выполняется в своём согласованном объёме.
- Несвязанную оптимизацию оформляй кратко: наблюдаемая проблема/измерение → ожидаемая польза → минимальный вариант → затронутый контракт → риски → проверки. Без измерения называй ускорение гипотезой. Продолжай основную задачу; применяй предложение после принятия, если оно не было разрешено раньше.
- Исправление исходников, запись в main/master/release, push/merge, публикация, deploy и миграция production — разные действия. Разрешение на одно не подразумевает остальные. При необходимости нового решения сначала подготовь конкретный diff/план и объясни, какой эффект выходит за имеющуюся область.

## Перед правкой

1. Зафиксируй текущую цель, исходный commit/рабочую копию, dirty changes, владельцев файлов и целевую среду. Прочитай затронутое поведение, потребителей и существенные гарантии: API/форматы, данные, ошибки, права, порядок операций и совместимость.
2. Используй уже подходящую ветку/рабочую копию задачи. Если нужны изменения в общей основной ветке или параллельная работа, host сначала выделяет изолированную ветку/worktree при доступности Git. Не выполняй reset/clean, не переключай ветку поверх пользовательского diff, не копируй все dirty changes вслепую. Проверь, что изоляция начинается с нужного состояния; новая clean-копия не содержит автоматически незакоммиченные предпосылки.
3. Без Git используй разрешённую отдельную рабочую копию либо сохранённые исходные версии конкретных меняемых файлов с проверкой актуальности. Невозможность сохранить чужую работу блокирует затронутую запись, но не чтение и подготовку.
4. До реализации выбери критерий результата и проверки сохраняемого поведения по риску. Существующий падающий тест или известная проблема baseline фиксируются отдельно; нельзя приписывать их новой правке либо использовать как оправдание нового сбоя.
5. Держи diff минимальным по смыслу. Не добавляй форматирование соседних файлов, cleanup, lockfile churn, массовое переименование и upgrades без связи с задачей. Необходимую сопутствующую правку обоснуй её зависимостью от порученного результата.

## Проверки по влиянию

| Изменение | Достаточный целевой набор определяется так |
|---|---|
| Текст, отступ, косметика без изменения контракта | Итоговый diff и затронутое состояние/размер реального UI, если оно меняется; проверка источника/ссылки для документа. Полная production-матрица и новые автоматические тесты не обязательны. |
| Локальное поведение рабочего компонента | Критерий результата, существенные границы и ошибки, связанные существующие тесты и сохраняемый контракт ближайшего потребителя. Добавить тест, если значимое поведение иначе не защищено. |
| Session/IPC, concurrency, permissions, retry, persistence | Воспроизводимая регрессия, положительный и отрицательный сценарии, адресность/изоляция и фактическая интеграция затронутых процессов/хранилища. Для CLI-пути нужен настоящий установленный CLI; для независимого renderer достаточно соответствующей проверки Electron. |
| Публичный API, интеграция, миграция, зависимости | Контракты и затронутые потребители, старые/новые данные или версии по области изменения, реальная интеграция в разрешённой среде и применимый план восстановления. Расширять regression по найденному влиянию, не по числу изменённых строк. |
| Разрешённая оптимизация | Сначала корректность и сохранённое поведение; затем сопоставимые измерения до/после на одинаковых данных/среде. Учитывать шум, нагрузку, память/CPU или другие относящиеся к цели показатели. Не заявлять ускорение по одному удобному запуску или ценой потери функции. |

Для критичных session/data изменений проверяй применимые риски: действительно одновременные A/B, отмена A при живой B, завершение отмены до нового turn, позднее событие старого соединения, двойной dispatch, restart, stale revision, ошибка записи и неизвестный исход внешней операции. Используй управляемые барьеры/fixtures вместо случайного ожидания «вроде одновременно». Не запускай весь список на правке, которая не затрагивает эти гарантии.

## Тест должен обнаруживать дефект

Для существенного исправления покажи воспроизводимый неуспех на дефектной версии и успех после исправления. Если прежнее окружение недоступно либо проверяется новая критичная гарантия, используй безопасный отрицательный контроль: проверка должна обнаружить намеренно неверное состояние/нарушение именно этой гарантии в отдельном fixture или временной тестовой копии. Сохрани, что именно проверено; это не превращает недоступную старую production-среду в проверенную. Контроль не выполняется на production и не остаётся в итоговом diff. Полный mutation-testing каждого изменения не требуется.

Зелёная сборка, наличие файла теста и exit code 0 не заменяют assertions. Для автоматического прогона сохраняй выбранный набор, число найденных/выполненных/пропущенных случаев, если runner их сообщает, и убедись, что нужный сценарий действительно исполнен. `0 tests`, все skipped, таймаут/ошибка инфраструктуры, другая ревизия и отсутствие нужного инструмента — не pass. Для ручного сценария нужны действия, входы и наблюдаемый результат, а не выдуманное число тестов.

Не удаляй упавший тест, не отключай проверку, не увеличивай допуск и не обновляй snapshot только ради зелёного результата. Если тест ошибочен или контракт явно изменён, укажи основание изменения ожидания и проверь новый критерий. Тест, повторяющий новую реализацию без независимого ожидаемого поведения, не доказывает её корректность.

Моки/локальные fault injectors полезны для воспроизводимых отказов, но помечаются simulated и не заменяют обязательную настоящую интеграцию. Живые проверки выполняются в разрешённых тестовых каталогах/окружениях; не создавай реальный 429, потерю данных или сбой production для демонстрации устойчивости. Если существенная обязательная проверка недоступна, зафиксируй `blocked/not_run` и точный следующий шаг; независимая подготовка может продолжаться.

## Приёмка, применение и восстановление

Перед передачей проверь финальный diff, нужную сборку и применимость свидетельств после последней правки. Сохрани одну компактную запись или ссылки на существующие evidence: цель/разрешённая область, база и итоговая ревизия, изменённое и сохраняемые контракты, выполненные проверки с результатами, ограничения, непринятые рекомендации и следующий шаг. Не дублируй это в нескольких отчётах. Для требующего независимого ревью изменения проверяющий изучает diff и доказательства, а не принимает самоотчёт автора.

Способ восстановления зависит от эффекта. Для локального кода — отмена собственного diff без потери последующих чужих правок; для выпуска — известный артефакт/конфигурация, критерий остановки и разрешённый возврат; для данных — отдельно совместимость, backup/restore или проверенный forward repair. Наличие команды rollback не доказывает восстановление данных. Не запускай откат или повтор неизвестно завершившейся операции без проверки текущего состояния и действующей области разрешения.

Готовность означает прохождение применимых критериев на указанной версии. Сообщай, какие риски проверены и какие остались; не обещай, что «ничего не сломается» во всех условиях. После зелёных адресных проверок расширяй или повторяй их только при новом изменении, отказе либо конкретном незакрытом риске.

Эти документы задают поведение агента. Они не включают автоматически branch protection, sandbox, права MCP, перехват действий или CI gates. Техническое соблюдение обеспечивается фактически настроенным host, Git/CI и инструментами; отсутствие такого контроля указывается честно.
