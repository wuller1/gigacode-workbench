# Автоматический выбор следующей роли внутри задачи

Статус: контракт для реализации в GigaCode UI, а не уже работающий переключатель установленного CLI. Приложение рекомендует полезное продолжение по состоянию задачи и само выполняет обычные переходы в пределах уже порученной работы. Пользователь управляет целью и границами; ему не нужно вручную выбирать весь каталог специалистов на каждом шаге.

Источники текущего каталога: [routing.json](../config/routing.json), [workflow definitions](PIPELINES.md), [потенциальные capabilities ролей](../config/profile-capabilities.json). Согласовать реализацию с [PROCESS_ADAPTATION](PROCESS_ADAPTATION.md), [Task workspace](TASK_WORKSPACE.md), [CONTEXT_BUDGET](CONTEXT_BUDGET.md), [нативными сервисами](NATIVE_WORKBENCH_MIGRATION.md) и [CHANGE_SAFETY](CHANGE_SAFETY.md). Ни этот документ, ни декларативный routing сами не запускают переходы в существующем PowerShell controller.

Выбор роли отделён от её доставки: [ROLE_PROMPT_BINDING](ROLE_PROMPT_BINDING.md) определяет базу/project policy/overlay/packet, fingerprint и подтверждённую границу active. Для делегирования использовать [MANAGED_SUBAGENTS](MANAGED_SUBAGENTS.md), сохраняя единый Scheduler и run acceptance. В composer находится read-only role chip с reason/confidence/history, а не selector каталога. Эти документы читаются только при реализации соответствующего участка.

## 1. Четыре независимых решения

| Решение | Что меняет | Чего не даёт автоматически |
|---|---|---|
| Роль `profileId` | Способ выполнения текущей работы: analyst, frontend и т. д. | Новые права, новый проект, отдельного subagent или новую CLI-сессию |
| Маршрут и этап `workflowId/stageId` | Порядок работы, входы, результаты и обязательные checks | Право пропустить неудобный gate сменой роли |
| Глубина `quick/standard/deep` и режим проекта | Соразмерность проверок; `personal_fast` либо `established_strict` | Разрешение считать unknown успешным или самовольно менять production-код |
| Модель и транспорт исполнения | Подтверждённые возможности исполнителя, бюджет и способ обращения | Обещание качества по названию модели или поддержку недокументированного hot switch |

Отдельно хранить политику автоматизации, описанную ниже. Изменение модели, размера контекста или роли не меняет её. В существующем workflow назначенная роль этапа берётся из сохранённой версии определения. Нельзя поверх неё записать произвольный `profileId` и объявить контракт выполненным. Изменение маршрута — явное versioned решение с причиной и сохранением истории; это не новый пустой run для обхода blockers, attempts или review.

## 2. Две политики взаимодействия

| Политика | Обычный разрешённый следующий этап | Когда нужно новое решение пользователя |
|---|---|---|
| `assisted` — default для `established_strict` | Автоматически продолжать однозначный переход выбранного маршрута, если входы/checks готовы, полномочия действуют и исполнитель доступен. Коротко показать следующий шаг | Не хватает scope/продуктового решения, меняется маршрут существенно либо есть несколько значимых вариантов. Показать рекомендацию с конкретным действием |
| `automaticWithinScope` — default для личного `personal_fast` по поручению пользователя | Дополнительно автоматически выбирать разрешённую локальную ветку по проверенным правилам маршрутизации, сохраняя основание | Те же границы полномочий, обязательные gates и реальные blockers. Этот режим не разрешает публикации, деплой или расширение ресурсов сам по себе |

В обеих политиках профиль всегда определяет router. Разница относится к автономности следующего **действия**, а не к способу выбора роли. Для этой личной оболочки пользователь уже поручил максимальную автоматизацию: не требовать ещё одного opt-in для `automaticWithinScope`. Это не переносит тот же default действий на остальные рабочие проекты.

Сохранение policy в Task или явного project default не распространяет текущую авторизацию на будущие задачи. Автоматический выбор `reviewer` не превращает самопроверку автора в независимую: если маршрут требует независимого review, завершение остаётся заблокированным до отдельного исполнения или явного допустимого изменения маршрута. Router не задаёт вопрос «какую роль выбрать»; пользователь отвечает только за действительно новое продуктовое решение, scope или внешний effect.

Примеры границ:

- «Добавь фильтр и проверь» уже включает подходящую реализацию и необходимые локальные проверки. После краткого уточнения не требовать повторного разрешения «можно писать код?».
- «Проанализируй и составь описание» разрешает анализ и документ. После готовности предложить **«Начать реализацию описанного фильтра»**, показывая область изменения; принять нажатие как новую явную инструкцию, а не задним числом приписывать её исходному запросу.
- «Подготовь план деплоя» не разрешает применение плана. Если сам деплой уже поручен в конкретное окружение, переиспользовать это разрешение, соблюдая действующие проверки и дополнительные требования среды. Смена на devops не выдаёт `cluster.apply`.
- Отсутствующий runtime, непроверенный внешний исход или существенное противоречие — blocker затронутого действия; предпочтение автоматизации не делает его pass.

## 3. Встроенные роли и типичные основания перехода

Это матрица выбора, а не обязательная цепочка всех ролей. Один профиль может выполнить несколько этапов подряд в одном Task и одним исполнителем.

| ID | Когда полезен | Следующий проверяемый материал / граница |
|---|---|---|
| `analyst` | Нужно понять задачу, предложить варианты, самому написать brief, SDD, user stories, сценарии, DOCX или уточнить существующий материал | Версия документа с границами, источниками, критериями и открытыми вопросами. Реальный DOCX требует доступного exporter; запись документа не запускает код |
| `spec` | Нужны формальные контракты, проверка противоречий/полноты на явно назначенном profile=spec этапе; specification сам по себе не назначает эту роль | Уточнённый контракт и readiness по конкретной версии; не обязательный второй автор любого brief |
| `architect` | Нужны межсистемные границы, ADR, совместимость, migration/recovery или разделение широкой реализации | Проверенная карта, решение/trade-offs, контракты и порядок; не обязательный слой для локальной правки |
| `backend` | Готова достаточная для текущего scope постановка серверной/внутренней логики, и реализация поручена | Изменение кода, адресная проверка, review применимого маршрута |
| `database` | Меняется схема, запрос, индекс, migration или целостность/производительность данных | Versioned migration/query plan, rehearsal, integrity и измерения; применение общей БД передаётся devops |
| `designer` | Нужно спроектировать flow/states, макет, design contract, assets или корпоративный UI kit | Версия прототипа/системы с audit/handoff; реализация продукта передаётся frontend |
| `frontend` | Нужны интерфейс, визуальная структура, состояния и их реализация | Design contract по влиянию, экран/компонент и доказательство реально изменённого UI; не полный design audit для подписи кнопки |
| `security` | Нужно проверить trust boundary, dependency/SBOM/Sprut report или устранение конкретного риска | Findings/remediation и evidence для точной revision; не общий checklist и не автоматический deploy |
| `devops` | Задача касается сборки, окружения, доставки или инфраструктуры | План/конфигурация и подтверждённый результат разрешённых операций в точном окружении |
| `technical-writer` | Нужно адресно обновить документацию, DOCX/PDF или knowledge base и проверить публикацию | Точный delta, механические/содержательные проверки и receipt целевой версии |
| `qa` | Нужно сопоставить требования с поведением, выполнить сценарии и разобрать расхождения | Наблюдённый результат с revision/environment; неподнятое приложение не может пройти live check |
| `reviewer` | Нужна независимая критика готового изменения, документа или обязательный review этапа | Findings/verdict по принятой версии; переименование автора в reviewer само по себе не создаёт независимость |
| `diagnostics` | Причина сбоя ещё не установлена; нужны воспроизведение и локализация | Воспроизведение, причинная гипотеза с проверкой и границы исправления; профиль не становится автором произвольного patch |
| `gigacode-ui` | Развитие личной Electron-оболочки, ACP, parallel sessions, native Task/panels и recovery | Один интегрированный исполнитель для узкого среза; живое наблюдение нужного сценария на текущей сборке, обязательный review выбранного маршрута |

Возможность действия вычисляется по подтверждённым project bindings, реальным permissions, central target rules и task scope. Роль/этап выбирают полезный контекст и процесс, но не урезают bound tools и не расширяют полномочия. Название роли не является security boundary. Git, Jenkins, OpenShift, Confluence и Sprut не подключаются заново при каждом переключении. Sprut здесь — проверка уязвимостей зависимостей/SCA согласно имеющимся сведениям, а не выдуманный tracker. Подробности — [MCP_PROFILE_SETUP](MCP_PROFILE_SETUP.md).

## 4. Реальные маршруты, которые host должен сохранить

Цепочки ниже прочитаны из текущих JSON. В runtime источник истины — валидированное определение и его snapshot у run; не парсить эту таблицу как исполняемую конфигурацию.

| Сценарий | Workflow и фактические этапы с ролями |
|---|---|
| Малый самостоятельный вопрос | `quick-answer`: `answer:analyst` |
| Ясная локальная правка кода | `quick-backend`: `change:backend → validate:backend` |
| Ясная локальная UI-правка | `quick-frontend`: `change:frontend → validate:frontend` |
| Малое изменение документа | `quick-doc`: `edit:analyst → validate:analyst` |
| Исследование неопределённой функции | `discovery`: `context:analyst → problem:analyst → scenarios:analyst → options:analyst → requirements-check:reviewer` |
| Формальная спецификация | `specification`: `baseline:analyst → behavior:analyst → contracts:analyst → readiness-review:reviewer → implementation-plan:analyst → version:analyst` |
| Backend-функция | `backend-feature`: `preflight:backend → design:backend → implement:backend → validate:backend → review:reviewer → handoff:backend` |
| Frontend-функция | `frontend-feature`: `hypothesis:analyst → options:frontend → contract:frontend → implement:frontend → measure:qa → visual-review:reviewer → handoff:frontend` |
| Диагностика обычного дефекта | `bugfix`: `reproduce:diagnostics → diagnose:diagnostics → fix:backend → validate:qa → review:reviewer` |
| Инфраструктура | `infrastructure`: `baseline:devops → plan:devops → configure:devops → validate:devops → apply:devops → verify:devops` |
| Личный GigaCode UI: функция | `gigacode-ui-feature`: `scope:gigacode-ui → implement:gigacode-ui → live-acceptance:gigacode-ui → review:reviewer` |
| Личный GigaCode UI: дефект | `gigacode-ui-diagnostics`: `reproduce:gigacode-ui → isolate:gigacode-ui → fix:gigacode-ui → live-verify:gigacode-ui → review:reviewer` |

Не выбирать `bugfix` механически по слову «баг»: в нём `fix` назначен backend. Для другой области выбрать подходящий существующий маршрут либо обоснованно изменить определение/план через host, не подменять роль скрыто. Для маленькой достаточной локальной правки самого UI допустим `quick-frontend` или `quick-backend` по области с нужными UI-ограничениями; его назначенные роли и checks остаются действительными. Четыре/пять этапов `gigacode-ui-*` нужны при соответствующем scope, не при каждой косметической правке.

Standalone `acceptance` использует qa, `review` — reviewer. Это не повод запускать оба после любой quick-задачи. `documentation` имеет `impact:technical-writer → delta-checks:technical-writer → selective-review:reviewer`; документация запускается по изменению поведения/контракта/операционных шагов и применимости проверок. `security-review` использует security с отдельной проверкой qa; dependency inventory/compatibility — security, реализация обновления — backend. Неизменившаяся документация — обоснованный no-op, а не фиктивно проведённый review. Ретро запускается по полезному событию/запросу; чистая микро-правка не порождает отдельные docs/retro/SDD задачи. Остальной каталог выбирать по [routing](../config/routing.json), а не последовательно исполнять все 29 workflow.

## 5. Как host вычисляет рекомендацию

Предлагаемый `RoleRoutingService` — часть native Task host, а не ещё один автономный агент. Вход: исходный и последний пользовательский запрос, Project type/stack/rules/connections, текущая цель/авторизация, accepted requirement versions, active workspace/resource refs, unresolved blockers и их scope, stage contract, валидность evidence, task/run revision, project mode, capabilities и состояние исполнительной сессии.

1. Принять уже записанное событие: новое поручение, принятый ответ/требование, stage result, инвалидированное evidence, найденный blocker, изменение tools/прав или прикрепление значимого resource. Не вызывать маршрутизатор модели на каждую букву, token, focus или обычное открытие вкладки.
2. Проверить active Task/run и snapshot маршрута. Уточнение остаётся в нём; смена окна/модели не сбрасывает scope, budgets, pending и rework.
3. Вычислить готовность текущего этапа локальными валидаторами. Проверять версии, обязательные artifacts/checks, `allow_na`, актуальность подтверждений; семантическую полноту требований брать из результата применимого анализа с источником, а не из счётчика заполненных полей.
4. Если этап готов, сначала рассмотреть следующий предусмотренный этап. Если scope завершён — завершить работу/показать результат; не искать следующую роль ради активности. При blocker определить минимальное действие, которое его действительно разрешает.
5. Применить четыре измерения routing: риск, неоднозначность, влияние, внешние эффекты. Профиль выбирать по требуемому результату; название технологии или наличие ТЗ сами по себе не причина deep/SDD.
6. Сопоставить candidate с действующим scope, policy и verified capabilities. Выход: `stay`, `auto_transition`, `blocked` либо `complete`. Router сохраняет `profileId/version`, reason, confidence, factors/evidence refs, альтернативу и условие пересчёта. Это host decision, а не новый статус старого controller.
7. Если классификация остаётся содержательно неоднозначной, один ограниченный model call получает цель, Project/Task/stage/resource context, конкретные варианты и необходимые факты. Ответ — кандидат со ссылками/неизвестными, валидируемый host; модель не выдаёт себе полномочия. Router всё равно выбирает provisional роль. Один предметный вопрос допустим только если неизвестный факт меняет контракт или безопасный следующий шаг; пользователь не выбирает профиль из списка.

Cache ключ включает task/run revision, workflow/profile hashes, применимые request/project/resource/requirement/evidence versions, capabilities/authorization fingerprint и interaction-policy revision. Неизменный ключ — переиспользовать решение, не повторять LLM-call. При новом существенном факте пересчитать только зависимое. Duplicate события не создают новую карточку; пользовательская коррекция цели инвалидирует решение. Потерянный/непроверенный факт не заполнять догадкой ради автоматического перехода.

## 6. Объяснение выбора без role picker

Расположение: read-only role chip в нижней строке composer и одна компактная строка около следующего действия; раскрытие показывает факторы, confidence, evidence и captured/actual state. Не modal, не новый chat и не selector. Для автоматического разрешённого перехода достаточно краткого статуса «Frontend · реализует принятый фильтр» с доступной историей.

Пример после **analysis-only** задания:

> **Следующая роль: frontend (92%).** Принята версия v3; открытых блокирующих вопросов по фильтру нет. Следующий результат: фильтр в существующем экране и проверка выбранного сценария. Сохранятся требования, ответы и ссылки на материалы. Изменения ограничены этим экраном; публикация не входит.
>
> **Начать реализацию** · Продолжить только уточнение

Кнопки здесь определяют расширение или сохранение **scope**, а не роль: в обоих вариантах router сам выберет применимый профиль. Если реализация уже поручена, переход выполняется без повторного вопроса. Для blocker показывать конкретное отсутствующее условие и доступное действие; обычная «Продолжить» не обходится с ним как с предупреждением. Чтобы исправить неверный выбор, пользователь уточняет цель/ожидаемый результат обычным сообщением; host пересчитывает route и хранит причину.

## 7. Атомарность, контекст и реальное переключение исполнителя

Предлагаемый неизменяемый `AutomaticRoleDecision` хранит `decisionId`, `taskId/runId`, `expectedTaskRevision`, source/target profile+version, workflow/stage snapshot refs, request/project/resource factors, reason/confidence/evidence refs, next artifact, конкретный scope delta, authorization ref либо missing condition, capability fingerprint, policy revision и `selected/prepared/pending/active/failed/unknown`. Это внутренний контракт UI, не формат ACP и не команда GigaCode.

Применение выполняет один Task writer: сверяет revision и факты, фиксирует automatic decision и отдельную новую авторизацию только при её явном предоставлении, возвращает один receipt. Повтор события с тем же operation ID возвращает тот же receipt; устаревший decision отклоняется и пересчитывается, ничего не исполняя. В двух окнах выигрывает один CAS, второе получает текущее состояние. Локальная идемпотентность **не означает exactly-once внешних tool effects**. Если подготовка исполнителя не удалась, решение остаётся с `pending/blocked` причиной; не имитировать состоявшийся переход и не терять run.

Порядок применения:

1. Зафиксировать выбранный переход и нужные входы. Дождаться безопасной границы текущего turn. Запрос отмены не равен завершённому turn; не запускать второй prompt той же session. Pending внешние операции сначала reconcile либо явно оставить блокирующими соответствующие действия, не повторять неизвестные writes.
2. Сохранить checkpoint и evidence refs с текущими revisions. Сохранить task/chat/run IDs, accepted requirements, вопросы/ответы, drafts и counters; новый исполнитель не создаёт новую задачу без пользовательского намерения.
3. Проверить capabilities будущей роли и фактические tool permissions **до** подключения/вызова инструментов. Переиспользовать проверенный inventory по fingerprint; передавать только нужные refs, не весь MCP-каталог и не секреты. При отсутствии mapping не включать все tools через наследование.
4. Выбрать поддержанный способ применения инструкции. [GIGACODE_COMPATIBILITY](GIGACODE_COMPATIBILITY.md) подтверждает форматы native agents, но не универсальный runtime профиль/hot switch главной сессии. Нельзя выдумывать ACP method, CLI flag, приватный setter system prompt или monkeypatch. Смена прикладного task packet в существующей сессии допустима лишь в пределах доказанной поверхности; прежние фактические permissions от неё не исчезают.
5. Если нужная изоляция/инструкции требуют новой поддержанной сессии — создать её после checkpoint, связав новую generation/session с тем же Task/run; старую сессию сохранить в истории. Если способ недоступен, показать ограничение и оставить соответствующее действие blocked, а не обещать изоляцию prompt-текстом. Новая сессия не должна заново отправлять выполненные операции.
6. Передать минимальный pack по [CONTEXT_BUDGET](CONTEXT_BUDGET.md): актуальная цель/scope, одна роль/этап, relevant accepted decisions, необходимый delta и evidence refs, blockers/pending, ближайшая приёмка. Не перечитывать весь каталог ролей, журнал и templates; cached delivery считать действительной только при подтверждённых версиях в текущем контексте.
7. Записать фактическую готовность нового исполнения и только затем отправить следующий разрешённый prompt. UI показывает настоящий профиль/сессию/статус, а не заранее выставляет новую роль как уже выполняющую работу.

Готовность в пункте 7 не означает доставку context-only инструкций: до отправки они prepared/pending; transport dispatch и наблюдаемое принятие/исполнение фиксируются раздельно по ROLE_PROMPT_BINDING. Отдельный ACP acceptance ack не предполагается. Timeout после возможной отправки — unknown/recovery без replay; подпись уже полученного ответа сохраняет captured role/model независимо от нового выбора в composer.

Binding всегда `taskId/runId → role/workflow/stage → execution binding`; фокус окна — только отображение. Рекомендация из A не меняет B, его model или permissions. Не хранить единственный глобальный `currentRole` для dispatch. Возврат к предыдущей роли откатывает выбор маршрутизации с новой записью, **не** Git diff, файлы, деплой или уже выполненные tools. Реальный undo требует отдельной понятной операции и проверки исхода.

Вопрос о продуктовом решении проходит versioned форму/свободный ответ по [ARTIFACTS_AND_QUESTIONS](ARTIFACTS_AND_QUESTIONS.md); это не runtime permission callback. При смене роли вопросы, материалы и [план задачи](TASK_TODO_PANEL.md) остаются у того же Task; ручная отметка не открывает следующий formal stage. Архив/корзина/удаление по [ENTITY_LIFECYCLE_AND_EDITING](ENTITY_LIFECYCLE_AND_EDITING.md) не являются обходом pending, бюджета или активации новой роли.

## 8. Пять небольших карточек реализации

Выполнять последовательно, используя существующие native services. Не заменять ради этой функции всё хранилище/оркестратор. Каждый срез предъявляет собственный diff, targeted checks и честное состояние live-проверки.

| Карточка | Реализовать | Приёмка и отрицательный пример |
|---|---|---|
| `RRole1` — факты и resolver | Ввести role binding/proposal DTO, источник catalog snapshot, deterministic resolver и cache по revisions. Проверить все builtin IDs и применимый scope | Готовый quick остаётся quick; однотипные события не порождают новые proposals. Unknown evidence, missing capability, несовместимая роль этапа и необоснованный complete отвергаются |
| `RRole2` — переход Task writer | Automatic apply, expected revision, idempotency receipt, scope instruction, policy revision, событие перехода и recovery | Два окна дают один локальный transition; stale decision ничего не запускает. Повтор/перезапуск не очищает budget, rework и pending external outcome |
| `RRole3` — объяснимый chip | Компактные role/reason/confidence/factors/следующий результат, selected→captured→actual, понятный scope delta; без dropdown/profile picker | Уже разрешённая работа не спрашивается снова; analysis-only не пишет код до новой scope-инструкции. Коррекция цели пересчитывает роль, unresolved gate остаётся видимым |
| `RRole4` — применение роли | Связать checkpoint, idle boundary, session adapter, permissions и минимальный pack; reuse verified inventory | Busy/cancel-requested не запускают второй prompt; unsupported hot switch явно ограничен. Переход A не меняет B; новый session не переигрывает MCP writes и не наследует все tools при отсутствии mapping |
| `RRole5` — живой вертикальный срез | В настоящем UI пройти brief → разрешённая реализация → targeted check, затем analysis-only → карточка → явная команда; сохранить evidence той же сборки | Карточка/роль/артефакт обновляются без reload, drafts и требования сохранены. Mock resolver не считается доказательством живого перехода CLI или контроля его скрытых tools |

Обязательная адресная критика перед приёмкой: не возникла ли лишняя смена роли, повторное интервью, незаметное расширение scope, смешение A/B, пропуск независимой проверки или ложное обещание изоляции? Автор делает эту самопроверку; отдельный critic нужен по выбранному маршруту/риску, а не на каждый клик. Возврат по findings ограничен существующим budget; после двух неудачных содержательных попыток одной проблемы сузить шаг/эскалировать по [Flash execution](FLASH_MODEL_EXECUTION.md), не создавать бесконечную цепочку qa → reviewer → analyst.

Минимальный набор сценариев: ясная микро-правка без полного SDD/docs/retro; authoring SDD силами analyst без обязательного второго автора; формальный маршрут со всеми положенными checks; analysis-only без auto-code; уже разрешённая реализация без повторного вопроса; неверно распознанная цель и пересчёт без ручного role picker; missing permission; unavailable live runtime; stale/double apply; два параллельных Task; restart с pending operation; reroute после принятого изменения требований. Для негативных сценариев наблюдать отсутствие запрещённого dispatch, а не только красивый текст кнопки.

## 9. Короткое поручение исполнителю

> Выполни только карточку RRoleN в текущей архитектуре. Прочитай её, действующий Task/run contract, нужную роль и относящиеся к изменению исходники; не загружай весь пакет. Сначала покажи входные факты и одну проверяемую границу результата. Следуй реальным workflow/profile IDs, существующему scope и runtime capabilities. Не добавляй ACP hot switch, новый сервис прав или скрытую CLI-модификацию без подтверждённого интерфейса. Сохрани контекст, pending и revisions. Проверь один нормальный сценарий и адресный плохой случай этой карточки; live UI/CLI называй проверенным только после настоящего наблюдения. Верни изменение, evidence refs, ограничения и ближайший следующий шаг.

Этот контракт должен сделать выбор роли незаметной повседневной помощью, сохранив видимость существенных решений. Числа переходов, prompts и время до результата измеряются на реальной реализации; уменьшение задержки и отсутствие новых ошибок здесь ещё не доказаны.
