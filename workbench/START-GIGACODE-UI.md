# Разработка существующего GigaCode UI

Это входная инструкция для агента на компьютере с репозиторием GigaCode UI, GigaCode CLI 26.9.75 и установленным GigaCode Desktop. Цель — развить существующую личную Electron-оболочку, начиная с параллельных чатов и состояния, которое зависает до клика или показывает пустое окно. Конечная поставка должна использовать собственный закреплённый CLI runtime при подтверждённом праве его распространения. Исходный код UI и целевая установка на машине автора пакета отсутствуют; описанные ниже изменения ещё не выполнены в приложении.

Если пришёл после самонастройки, сначала используй карточку по [POST_SETUP_HANDOFF](docs/POST_SETUP_HANDOFF.md): действительное поручение, путь проекта, доступные runtime/MCP, memory_store, ограничения, существующие Task/run и checkpoint. Не повторяй установку и интервью. Если предложение ещё не принято, покажи его по [START-HERE](START-HERE.md); при ранее порученной работе продолжай без нового подтверждения. При неизвестном репозитории нужен только его путь, а не повтор всех требований.

## Запрос для начала работы

Передайте агенту этот текст, заменив только путь к пакету, если он другой:

```text
Прочитай @gigacode-workbench/START-GIGACODE-UI.md и действуй по нему в текущем репозитории GigaCode UI. У меня не работают независимые параллельные сессии в нескольких окнах; состояние иногда обновляется лишь после клика, а пустой экран требует reload. Начни с подробного локального журнала CLI/main/IPC/store/render и доступного агенту пакета диагностики. Воспроизведи и исправь подтверждённые причины, проверь настоящий Electron с настоящим GigaCode CLI: обновления без дополнительного клика, A/B с перекрытием, cancel и восстановление. Затем обрывы/429, сразу M3 — собственные кнопки окна без стандартного menu bar, настраиваемые панели, базовые browser/terminal, реальные agent navigate/read/click/fill/screenshot и Task bindings; M4 — полный native Task/Workbench. Учти собственный закреплённый CLI runtime по BUNDLED_CLI_RUNTIME, без скрытой зависимости от глобального PATH; права распространения проверить. Расширенная browser automation — M7, Java/Python/React IDE — позже M12 после M10. CLI не изменяй. Сохрани существующую заготовку, не создавай новый проект. Работай короткими проверяемыми задачами, фиксируй факты и рекомендации. Не объявляй успех по мокам, сборке или unit-тестам; недоступную обязательную проверку покажи с точным ограничением и следующим шагом.
```

Если пакет уже установлен вне репозитория, используйте его фактический абсолютный путь. Установка Workbench и разработка UI — разные действия: для диагностики приложения не требуется заново настраивать репозиторий или сначала переносить всю обвязку.

Работай по [DELIVERY_AND_DOGFOOD_PLAN.md](docs/DELIVERY_AND_DOGFOOD_PLAN.md): D0–D13 — отметки реальных поставок, сейчас все не выполнены. Самая ранняя пригодная версия D2 выдаётся после устойчивого пути Project → Task → результат → восстановление, без ожидания всего набора функций. Роли работают внутри Task по [ROLE_ROUTING.md](docs/ROLE_ROUTING.md). Stable и candidate/test используют раздельные данные/runtime; не уничтожай единственную среду, из которой ведётся разработка. После каждого пригодного checkpoint дай сборку/проверенный запуск, короткую пробу, ограничения, evidence и rollback.

## Первый рабочий цикл

Найти реальные модули main/backend, preload/IPC, transport, session registry, chat store и отправку prompt. Сохранить карту «логический компонент → путь и символ в этом репозитории». Не создавать файлы по придуманным путям из примера. Встроенный backend может уже решать часть задач — расширять его. Зафиксировать фактический абсолютный путь CLI, runtime/dependencies, версии/hash и launch arguments. Проектируемый bundled runtime проверяется отдельно: runtimeRef закрепляется за connection generation; скрытого fallback к глобальному CLI нет.

До исправлений связать события по build/window/chat/process/connection/session/request/turn и received/applied/rendered sequence. Подробный локальный журнал, bounded flight recorder и кнопка диагностического пакета должны объяснять потерю состояния, не только печатать ошибки. Агент получает пакет через фактический локальный read-only доступ/MCP; не объявлять вымышленный tool. Секреты и credentials не включать в диагностический экспорт.

Выполнить запуск и наблюдать два настоящих окна A/B. Для A и B использовать различимые безопасные задания в тестовых каталогах. Доказать, что A ещё работает при старте B. Сохранить обезличенные события с window/chat/process/session/request/turn и временем, видимый симптом и соответствие source/build/runtime. Последовательные ответы не доказывают параллельность.

Проверить отдельно три гипотезы: повторное использование sessionId; общий mutable currentSession/busy; ошибочная маршрутизация либо повторная подписка. Для зависания интерфейса проверить путь owner → IPC → store → selector/render, race подписки/snapshot, stale revision и renderer errors. После dispatch наблюдать live UI без клика, hover, смены focus или reload для оживления; фон/возврат — отдельный сценарий. Если причины неразличимы, дополнить диагностику и повторить. Нельзя объявить причину по похожему примеру Qwen.

Сформировать одну карточку изменения: наблюдаемый дефект, подтверждающие события, затронутые файлы, инвариант, проверка до/после, что не входит в эту карточку. Исправить подтверждённую причину, выполнить целевые проверки, затем повторить live-сценарий. Проверить cancel A при активной B, subscription/snapshot gap и переподключение/закрытие окна по принятой политике. Reload не исправление; правильное reconciliation не пересылает prompt. Не расширять этот шаг до переписывания всего UI.

Если штатный Electron test runner недоступен, сначала исправить запуск тестового приложения или выполнить инструментально наблюдаемый ручной сценарий. Скриншот без действий и корреляции — только визуальное свидетельство. Проверка web dev server не заменяет main/preload/ACP в Electron. Статусы: passed, failed, not_run, blocked; последние два никогда не превращаются в passed.

## Как использовать установленный Desktop

Установить его фактическую версию и доступные способы диагностики. Читать только необходимые доступные логи, конфигурацию и поставляемые читаемые файлы. Сопоставить формы initialize/session/new/prompt/update/cancel и запуск процесса, если они наблюдаемы. Сохранять минимум без токенов, личной переписки и секретных env. Это источник совместимости, а не повод копировать всю реализацию или изменять Desktop/CLI. Если поток закрыт для наблюдения, зафиксировать отсутствие свидетельства; не придумывать флаги отладки и не обходить защиту.

## Возобновление после обрыва

Использовать существующий источник прогресса: Task/run, journal/recover и evidence, если они уже доступны. Пока такого хранилища нет, временный CURRENT.md в принятом каталоге работы содержит цель, текущую карточку, ссылки на факты, revision/build, проверки, pending и ближайшее действие; рядом — журнал/evidence. После native cutover CURRENT становится только проекцией/экспортом, не вторым writer. Перед наблюдаемым внешним действием записать намерение; после — фактический исход. Unknown сначала сверяется, не повторяется автоматически.

После перезапуска читать compact recovery/current checkpoint и нужный фрагмент журнала; проверить актуальность файлов, runtime и процесса. Task revision, run revision/attempt_id и ACP connection generation не смешивать. Не пересоздавать план с нуля, не перечитывать весь репозиторий, не повторять завершённые действия автоматически. Уточнение в текущей задаче не создаёт новый run. Неизвестные операции остаются видимыми.

## Продолжение разработки

При работе над файлами открыть [FILE_EXPLORER](docs/FILE_EXPLORER.md): FE1–FE4 уже M3.14/D3 дают дерево фактического Task workspace/worktree, bounded поиск/preview, наблюдение изменений, attachments и безопасные file actions. Не угадывать root по cwd и не загружать папку целиком в контекст. M6 подключает общий Buffer/EditSession с CAS, M12 — языковые функции; дерево/просмотр не ждут IDE.

При создании/настройке собственного профиля читать текущую карточку [CUSTOM_PROFILES](docs/CUSTOM_PROFILES.md): M3.12 — library и редактируемый draft, M4.9/D5 — versioned registry, рекомендации агента, validation и actual activation по CP1–CP4. Девять bundled профилей не переименовываются в «9 плюс уже установленные custom»; draft/recommendation не означает установленный или активный prompt/tool policy. Выбранная версия захватывается на безопасной границе через существующий role binding.

Перед повторяющейся автоматизацией читать SL0/релевантную запись [SELF_OPTIMIZING_SCRIPT_LIBRARY](docs/SELF_OPTIMIZING_SCRIPT_LIBRARY.md): сначала reuse подходящего проверенного скрипта, не весь каталог в prompt. M4.10/D5 добавляет native registry, validation и измеряемое продвижение/откат SL1–SL3. Новая версия тестируется на актуальных code/environment hashes; прошлый pass не переносится на изменённый код. Оптимизация идёт в уже разрешённом scope, не расширяет production-права и не запускает отдельную LLM на каждый шаг. Текстовый почтовый пакет не получает executable scripts; 12 существующих source entries остаются прежними. Эти документы читать по срезу/событию, не добавлять ко всем handoff целиком.

Для текущего UI-среза открыть нужную строку [UI_IMPLEMENTATION_MAP](docs/UI_IMPLEMENTATION_MAP.md), а не загружать всю карту в prompt. При изменении policy/config/recovery читать применимые SC0–SC2 [SETTINGS_AND_CONFIGURATION](docs/SETTINGS_AND_CONFIGURATION.md): M2 вводит versioned SettingsService и проверку применения, M3 — поиск, scopes/наследование/reset и pending до безопасной границы. Уже работающие model/reasoning controls сохранить; setting saved не означает applied к активному turn. M4 добавляет advanced role/memory/peer policies, M10 — перенос/backup/update, не первый экран настроек.

При archive/restore читать AR1–AR3 [ARCHIVE_AND_RETENTION](docs/ARCHIVE_AND_RETENTION.md): уже M3/D3 нужны отдельный Archive browser, project-scoped поиск/фильтры, read-only просмотр и восстановление прежних IDs. Архив не завершает работу скрыто: active/queued/pending descendants требуют guard; явный stop не считается завершённым до наблюдаемого terminal, unknown остаётся recovery. Restore не replay и не запускает CLI автоматически. M4 расширяет atomic hierarchy/worker/peer cases; opt-in retention/export/backup — M10. Эти документы читать по событию работы, не добавлять целиком к первому D0 или каждому handoff.

M0–M2 закрывают живую диагностику, параллельность, стабильное состояние, обрывы и 429. Сразу следующий M3 — [настраиваемые панели](docs/PANELS_AND_IDE.md): add/hide/move/resize/reorder/tab groups, сохранённые layouts, настоящий базовый browser и PTY в общем registry. В M3 агент уже получает реальные navigate/read/click/fill/screenshot по [AGENT_BROWSER_AND_IDENTITY.md](docs/AGENT_BROWSER_AND_IDENTITY.md); фактический adapter/MCP проверяется, вкладка сама по себе не выдаёт инструмент. Собственные minimize/maximize/restore/close заменяют стандартный menu bar; hide/move панели не завершает и не дублирует процесс. Baseline [Task workspace](docs/TASK_WORKSPACE.md) связывает поручение, текущие chat/run и материалы без wizard и ручной смены профиля.

M4 переносит весь Workbench в текущий native backend и расширяет Task aggregate, решения/вопросы, SDD delta, checks/evidence, routing и память. WorkflowEngine остаётся один: legacy task — строка, новый Task хранит связи/требования, а результаты принимаются по revision/attempt_id действующего run. Конечный normal turn не запускает PowerShell. Далее — управляемые исполнители M5, viewers/editors и первый интерактивный UI-макет внутри оболочки M6, расширенная browser automation M7 поверх browser M3, расширение визуального проектирования/canvas M8, интеграции M9 и эксплуатация M10. IDE Java/Python/React — отдельный M12 после M10, без зависимости от optional M11; не задерживать ради неё текущий workspace.

Собственный CLI runtime готовить и проверять при ранней упаковке, до пользовательского release: целевая среда без глобального CLI, точный manifest/launch, фактическое разрешение на распространение. M10 добавляет атомарное обновление/rollback для новых задач; живые sessions сохраняют закреплённую runtime version до завершения. Git, JDK, Python и другие project toolchains не объявлять автоматически включёнными вместе с CLI.

Для M3 пройти живые UX-сценарии: задача → состояние/следующий шаг → материал/check; переключение task/chat с сохранением draft/scroll; 429/обрыв с видимым восстановлением; настройка панелей мышью и клавиатурой, собственные кнопки окна. Считать фактические действия и локальные задержки; предложенные targets не выдавать за измеренные результаты. Собственные [иконки](docs/ICON_LIBRARY.md) и assets/icons.json/SVG импортируются как assets, документы — как адресный reference corpus, не как PS runtime.

Режим личного UI — personal_fast; у других рабочих проектов сохраняется established_strict. Риск конкретного действия добавляет применимую проверку, не превращает всё личное приложение в production-процесс. Между маленькими обратимыми шагами в порученной области не требуются повторные разрешения. Неопределённое бизнес-решение, расширение согласованного scope или недостающий обязательный доступ требует конкретного уточнения; независимые шаги продолжаются.

Обоснованные улучшения предлагать отдельно от обязательного исправления: проблема → польза → минимальный вариант → цена/ограничение. Не встраивать незаказанный крупный redesign в исправление сессий. Конечная цель — нативный перенос всей обвязки плюс новая функциональность. Используй [NATIVE_WORKBENCH_MIGRATION.md](docs/NATIVE_WORKBENCH_MIGRATION.md); временный PowerShell bridge не считается завершённой интеграцией.

Адресные контракты следующих срезов, **не дополнительный список чтения D0**:

- M3: [CHAT_FIRST_DESIGN](docs/CHAT_FIRST_DESIGN.md) задаёт один разговор/composer, левую навигацию и контекстные панели без обязательной полосы Task tabs. [TASK_ACTIVITY_INDICATORS](docs/TASK_ACTIVITY_INDICATORS.md) добавляет анимацию действительно выполняемого шага и статус задач слева, включая отметку завершения: selection, busy и unread раздельны; terminal turn не объявляет Task принятой. [ARTIFACTS_AND_QUESTIONS](docs/ARTIFACTS_AND_QUESTIONS.md) — baseline preview реальных материалов и Task-bound overlay вопросов поверх разговора, с вариантами плюс свободным текстом. Draft/Answer receipt уже сохраняются для restart; received/delivered/applied различаются. Эти функции выдаются малыми срезами, не задерживая D2 до полной реализации.
- M4: тот же Task store расширяется полным native lifecycle/todos/questions/evidence, authoritative requirement/decision delta и affected-only resume; [ROLE_PROMPT_BINDING](docs/ROLE_PROMPT_BINDING.md) определяет сборку, версию и фактическую активацию инструкций. Пользовательский prompt не называется системным, форма вопроса не имитирует неподдержанный CLI tool.

- M5: [MANAGED_SUBAGENTS](docs/MANAGED_SUBAGENTS.md) задаёт очередь, квоты, отмену, recovery и принятие результатов управляемых исполнителей. Независимые Tasks/AgentTasks запускаются параллельно по реальным зависимостям/ресурсам; inline activity открывает адресные worker cards и результат в той же Task. Один worker на каждую роль не обязателен, tiny задачи не получают лишний fan-out. M6 расширяет форматы, редактирование и настоящий export материалов по ARTIFACTS_AND_QUESTIONS. Обязательный результат M6 — Giga сам создаёт интерактивный UI-макет внутри оболочки по [NATIVE_MOCKUP_ARTIFACTS](docs/NATIVE_MOCKUP_ARTIFACTS.md): реальный preview, screenshot связанного состояния, замечание пользователя и новая версия с сохранённой предыдущей. Переиспользовать ArtifactService/BrowserService и подтверждённый agent bridge, не менять CLI; первый цикл не ждёт canvas M8, IDE или поддержки всех форматов.
- [COMPETITOR_FEATURE_PLAN](docs/COMPETITOR_FEATURE_PLAN.md) читать только при выборе соответствующей функции; идеи не расширяют согласованную карточку автоматически.

В M4 нужен автоматический фоновый обмен между сессиями по [SESSION_COLLABORATION](docs/SESSION_COLLABORATION.md): в одном проекте и между явно связанными frontend/backend проектами. Пользователь не управляет технической отправкой: отдельных peer composer/recipient/inbox/outbox/panel нет; в Task видны прогресс, результаты и actionable blockers, техническая история доступна по необходимости в diagnostics. Host broker использует существующие Task/SessionService/queue; для вызова агентом реализуется и проверяется настоящий MCP bridge, без нового вымышленного ACP RPC или изменения CLI. Межпроектная связь один раз задаёт внутренние адреса, область материалов и политику; разрешённый обмен запускается автоматически без каждого ручного согласования. Занятая сессия получает очередь до безопасной границы, не второй prompt/forced steer. M5 переиспользует этот путь для workers; простой обмен не ждёт M5. Полученное сообщение не наследует полномочия отправителя и не объединяет project memory.

При работе над composer/доставкой открыть [SMART_MESSAGE_QUEUE](docs/SMART_MESSAGE_QUEUE.md): draft/queued/dispatch различаются, pause не cancel, активный turn не получает второй prompt. При работе над лентой открыть [TRANSCRIPT_AND_MARKDOWN](docs/TRANSCRIPT_AND_MARKDOWN.md): компактные tool groups с видимыми ошибками/approval, source-specific Copy, безопасный GFM и streaming без потери scroll/selection — базовый M3; богатые artifact viewers расширяются в M6. Для проверки полноты карточки использовать нужные строки [REQUIREMENTS_COVERAGE](docs/REQUIREMENTS_COVERAGE.md) и связанные пункты [PRODUCT_GAP_ANALYSIS](docs/PRODUCT_GAP_ANALYSIS.md), а не читать эти каталоги полностью перед D0.

При ошибке 400/413 или работе над контекстом открыть только применимый раздел [CONTEXT_CONTROL_AND_ERROR_RECOVERY](docs/CONTEXT_CONTROL_AND_ERROR_RECOVERY.md). M2 различает источник/причину отказа и даёт безопасное ручное восстановление без blind resend; M3 добавляет компактный context popover возле composer, M4 — подробный inspector и управление материалами. Ручная компрессия использует проверенный механизм. Не считать любой 400 переполнением окна, не выдавать текст `/compress` за работающий ACP API и не менять модель уже отправленного turn. Этот документ не обязателен целиком для первого D0.

Сразу после пригодного D2 предложи пользователю выполнить настоящую малую задачу внутри приложения и продолжай разработку следующей candidate. Ошибки/уточнения текущего результата сохраняются в той же Task; отдельный значимый scope получает связанную Task в Project. Не ждать готовности IDE или всех интеграций для первой полезной поставки; не просить новое разрешение на каждый уже порученный обратимый шаг.

В M3 пользователь ожидает правую полосу инструментов, drag-and-drop панелей, несколько терминалов с выбором установленной оболочки и несколько browser tabs/panels. Постоянные кнопки «Справа/Снизу» не нужны; доступен клавиатурный/context-menu способ. **Пользователь подтвердил: reasoning уже выбирается и работает в его UI.** Сохранить текущие backend/adapter calls, значения и настройки; перенести selector рядом с моделью в composer по [MODEL_AND_REASONING_CONTROLS](docs/MODEL_AND_REASONING_CONTROLS.md), не строить его заново как неизвестную возможность. Здесь не проверены конкретные values/readback, поэтому их исследовать в действующей реализации; demo choices не выдавать за actual. Индикатор контекста — по [MODEL_AND_CONTEXT_CONTROLS](docs/MODEL_AND_CONTEXT_CONTROLS.md). IntelliJ/open-source решение относится к позднему M12 по [IDE_PLATFORM_DECISION](docs/IDE_PLATFORM_DECISION.md), не задерживает раннюю рабочую сборку.

При работе над browser открыть BC1–BC3 [BROWSER_WORKSPACE_CONTROLS](docs/BROWSER_WORKSPACE_CONTROLS.md): уже M3.5/D3 нужны URL/navigation/tabs, размеры CSS viewport, orientation/zoom и actual DPR/resolution readback; агент получает только реально реализованные scoped set/read/capture. Requested/emulated CSS viewport не выдаётся за физическое разрешение дисплея или полную эмуляцию устройства. BC4 добавляет подтверждённую advanced device/touch/UA/DPR emulation в M7/D8; baseline DPR readback не обещает setter. Уже работающие target controls сохраняются; базовый browser не откладывается.
