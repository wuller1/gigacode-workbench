# Contributing to the corporate UI kit

## Before implementation

Open or link a task with the user problem, affected consumers, owner, measurable acceptance, compatibility impact and intended release channel. Search the registry before adding a new concept. Prefer a new state or composition when a new component would duplicate semantics.

A proposal contains:

- interaction and content contract, including loading, empty, partial, stale, offline, permission, error, conflict and success states that apply;
- keyboard path, accessible name/description, focus behavior, zoom/text-scaling behavior and reduced-motion behavior;
- light, dark and high-contrast token usage;
- 320, 768, 1024, 1440 and 1920 constraints where the component can appear;
- asset origin and license evidence;
- expected consumer impact, migration path and rollback.

## Pull request path

1. Add or update the machine-readable registry first.
2. Update tokens or source without bypassing semantic names.
3. Add gallery fixtures for every applicable variant and state.
4. Add unit and interaction tests for behavior, automated accessibility checks, and deterministic visual baselines.
5. Run the catalog, type, package-content, license/provenance and consumer-fixture checks.
6. Request design-system and accessibility owners. Security review is additionally required for dependencies, HTML injection, URL handling, persistence or privileged integration.
7. Resolve review comments in source; never approve a new baseline only to make a failing visual check green.

The PR description lists changed contracts, screenshots/diffs generated by CI, checks, known limits, release classification and migration notes. A generated screenshot alone does not verify behavior.

## Token changes

- Primitive palette and scale tokens are internal.
- Components consume semantic tokens.
- A semantic token rename/removal is breaking unless an alias and deprecation window preserve behavior.
- Every theme defines the same semantic paths.
- Contrast is measured for actual foreground/background/state combinations; a palette swatch does not prove compliance.

## Component completion gate

A component moves from `specified` to `reference-source`, then `candidate`, then `stable`. Stable requires documented API, deterministic stories/fixtures, keyboard and screen-reader path, measured contrast/target/overflow, themes, responsive states, tests, provenance, owners, and at least one successful consumer fixture. Experimental APIs live under an explicit namespace and cannot be promoted silently.

## Agent contributions

An agent may prepare source, tests, documentation, diffs and release evidence within a configured repository binding. Its UI shows proposal → preview → execute → result → verify → evidence. Bound capabilities are allowed by default; central policy can disable a connection or capability. The agent cannot self-approve its protected-branch review or claim success without readback evidence.
